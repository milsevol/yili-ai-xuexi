# 04 DAG 与调度

## DAG 是什么

**Directed Acyclic Graph（有向无环图）**：任务是点，依赖是边；不能有环（A→B→A）。

调度引擎从 **入度为 0** 的节点开始，节点成功后「解锁」后继，直到没有后继。

```
extract_ods ──► transform_dwd ──► aggregate_dws ──► publish_ads
                      │
                      └──► quality_check
```

上例中 `extract_ods` 先跑；`transform_dwd` 成功后，`aggregate_dws` 与 `quality_check` 可并行。

## 设计 DAG 的实用原则

1. **一个节点一件事**：便于失败重试与定位
2. **依赖显式化**：别靠「睡 10 分钟等上游」这种隐式约定
3. **控制宽度与深度**：过宽打爆并发；过深拉长关键路径
4. **大流程拆子工作流**：主题域拆分，主流程只编排子流程
5. **幂等**：同一业务日期重跑结果一致（补数/重试才安全）

## 依赖的两种层次

### 1. DAG 内前后继

连线即依赖：前驱成功（或按策略）后，后继才就绪。

### 2. Dependent 依赖节点

跨工作流/跨周期依赖，例如：「等昨天的用户域 DWD 成功，才跑今天的报表」。

这是数仓里非常常见的能力，也是相对 crontab 的大优势。

## 定时调度（cron + Quartz）

- 到点不一定「立刻跑完」，而是产生启动命令 / 实例
- 若上一次还在跑，要注意 **并行实例** 策略（是否允许叠加）
- cron 示例：

| 需求 | cron 示意 |
| --- | --- |
| 每天 02:00 | `0 0 2 * * ?` |
| 每小时 | `0 0 * * * ?` |
| 工作日 8 点 | `0 0 8 ? * MON-FRI` |

具体 cron 方言以海豚内置 Quartz 为准（字段位数、`?` 用法与 Linux crontab 略有差别）。

## 补数（Backfill）

补历史数据时指定时间区间，系统为每个业务时间生成实例。

常见模式：

- **串行补数**：一天跑完再下一天，资源稳、耗时长
- **并行补数**：多天同时跑，快，但要盯资源与下游压力

补数前务必确认任务 **幂等** 且分区/路径带业务日期。

## 失败策略（并行任务时）

当 DAG 中有并行分支时，某一分支失败：

| 策略 | 行为 |
| --- | --- |
| **继续** | 其他并行任务继续跑完，最终流程仍失败 |
| **结束** | 尽快结束流程，并杀掉仍在跑的并行任务 |

选「结束」可省资源；选「继续」便于一次暴露多个失败点。按业务容忍度选。

## 优先级

- 流程实例优先级、任务实例优先级
- 资源紧张时，高优先级先被调度
- 不设置则近似 FIFO

把「早上必须出的报表」和「可延迟的回刷」分开优先级，比盲目加机器更有效。

## 超时、告警与空跑

- **超时**：任务/流程跑太久触发告警或失败策略
- **告警**：失败、超时、容错等走 Alert
- **空跑 / 跳过**：某些场景只推进依赖不真正执行（视版本与配置）

## 一张「调度脑图」

```
触发：手动 | cron | API | 补数 | 依赖满足
   ↓
创建流程实例
   ↓
就绪任务队列（入度 0 / 前驱完成）
   ↓
分发到 Worker 组
   ↓
成功 → 解锁后继；失败 → 重试 / 策略 / 告警
   ↓
无剩余任务 → 流程成功或失败收尾
```
