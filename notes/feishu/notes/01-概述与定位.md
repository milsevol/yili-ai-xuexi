# 01 概述与定位

## 一句话

**飞书（Lark）**：字节跳动面向企业的**一体化协作平台**，把即时通讯、文档、多维表格、日历、会议、审批、OKR 整合到一个入口，并通过开放平台 API 让企业自建应用嵌入这些能力。不只是「聊天工具」，更是企业数字化的**统一工作入口**。

## 为什么需要飞书

企业内部 IT 的普遍痛点：沟通在 IM、文档在网盘、数据在 Excel、审批在 OA、会议要另装软件 —— 数据割裂、入口分散、上下文切换成本高。飞书的核心解法是**把协作的几件事原生打通在一个产品里**：

| 现实问题 | 传统做法 | 飞书的做法 |
| --- | --- | --- |
| 文档和聊天割裂，发个文件要传来传去 | 微信/邮件传文件，版本混乱 | 飞书文档可直接在群里 @、评论、协同编辑，链接即内容 |
| 项目管理靠 Excel 表格，难协作难汇总 | 每人维护一份 Excel，合并靠人工 | 多维表格 Bitable：多人实时编辑、视图切换、自动化触发 |
| 审批流要装单独 OA，和业务系统脱节 | 审批在 OA，数据在 ERP，两头同步 | 审批 API + 多维表格，审批结果自动写回业务表 |
| 会议要提前约、纪要靠人手记 | 约会议室、记纪要、跟进行动项各一套 | 飞书会议 + 妙记自动转写，会议纪要一键生成待办 |
| 内部系统移动端体验差 | 写原生 App 成本高、H5 能力弱 | 飞书小程序 / 网页应用 + JSAPI，一次开发多端通 |
| 新员工入职配置一堆权限 | 挨个系统开账号 | 通讯录组织架构 + 应用可见范围，入职即开通 |

## 飞书 vs 企业微信 vs 钉钉

| 维度 | 飞书 | 企业微信 | 钉钉 |
| --- | --- | --- | --- |
| **定位** | 一体化协作平台（文档/表格/IM 原生打通） | 企业 IM + 对外客户连接（与微信互通） | 阿里系企业 IM + OA 平台 |
| **身份体系** | App ID + open_id / user_id / union_id | CorpID + UserID（企业成员） | 企业 ID + staffId |
| **差异化能力** | 多维表格 Bitable、云文档协同、妙记（AI 纪要） | 客户联系（SCRM）、与微信互通、侧边栏 | 考勤/审批/组织架构强、阿里生态 |
| **事件订阅** | ✅ HTTP 回调 + WebSocket 长连接（无需公网 IP） | ✅ HTTP 回调（需公网） | ✅ HTTP 回调（需公网） |
| **应用类型** | 自建应用、商店应用（ISV）、小程序 | 自建应用、代开发、第三方应用、小程序 | H5 应用、微应用、小程序 |
| **API 风格** | RESTful，`Bearer token`，版本化 v1/v2 | RESTful，参数拼接，cgi-bin 风格 | RESTful |
| **消息卡片** | ✅ 交互式卡片（JSON 搭建，可回调） | ✅ 模板卡片 / 图文卡片 | ✅ 工作通知卡片 |
| **文档开放** | ✅ 云文档 Block 级 API、多维表格 API | 微盘 API（文档能力较弱） | 文档 API |
| **适合场景** | 知识协同、数据表格驱动、文档密集型团队 | 已有微信生态、需同时服务内部和外部客户 | 阿里生态深度集成、重 OA 审批 |

## 飞书开放平台架构

```
  开发者
    │
    ▼
┌──────────────┐   tenant_access_token   ┌─────────────────┐
│  自建应用后端 │ ──────────────────────▶ │  飞书开放平台     │
│  (你的服务)   │ ◀────────────────────── │ open.feishu.cn   │
│              │   事件回调 / WSS 推送    │ (API Gateway)    │
└──────┬───────┘                         └────────┬────────┘
       │                                          │
       │ 小程序 / H5 前端                          │ 消息下发 / 卡片推送
       ▼                                          ▼
┌──────────────┐                         ┌─────────────────┐
│  飞书客户端   │ ◀── tt.config JSAPI ──  │  IM / 文档 / 表格  │
│ (桌面/移动)   │                         │ (业务数据落点)     │
└──────────────┘                         └─────────────────┘
```

**核心概念**：

| 概念 | 说明 | 在哪获取 |
| --- | --- | --- |
| **App ID** | 应用唯一标识，类似应用身份证 | 开发者后台 → 凭证与基础信息 |
| **App Secret** | 应用密钥，换取 token 用，绝不能泄露 | 开发者后台 → 凭证与基础信息 |
| **tenant_access_token** | 代表「企业 + 应用」身份的 token，绝大多数服务端 API 用它 | 用 App ID + Secret 换取 |
| **open_id** | 用户在某个应用下的唯一 ID（应用隔离） | 通讯录 API / OAuth 登录返回 |
| **user_id** | 用户在企业内的唯一 ID（企业内统一） | 通讯录 API 返回，需申请权限 |
| **union_id** | 同一开发商下多个应用共享的用户 ID | 用户身份接口返回 |

## 开发链路总览

```
① 注册飞书企业 → 进入开放平台 (open.feishu.cn)
② 创建「企业自建应用」→ 获取 App ID + App Secret
③ 配置权限（scopes）→ 勾选要用的 API 权限
④ 配置事件订阅 → 选 HTTP 回调（需公网）或 WebSocket 长连接（推荐）
⑤ 后端获取 tenant_access_token → 调用服务端 API
⑥ 开发前端（小程序 / H5 网页应用）→ JSAPI 鉴权调原生能力
⑦ 发布版本 → 配置可见范围 → 成员在工作台使用
⑧ 线上监控 → 看错误码 / 频控 / 调用日志
```

## 发展简史

- **2017** 字节跳动内部「 Lark」诞生，解决跨时区协作
- **2019** 飞书对外发布，主打「文档 + IM + 日历」一体化
- **2021** 推出多维表格 Bitable，开放平台能力大幅扩展
- **2022** 飞书会议、妙记（AI 转写纪要）上线，深化 AI 协作
- **2023** 开放平台推出 WebSocket 长连接事件订阅，免去公网 IP 门槛
- **2024+** 飞书智能伙伴（AI）、自动化流程、多维表格更深的开放能力
