# 08 性能调优实战

## 一句话

**调优 = 用 UI 证据定位瓶颈（倾斜/Shuffle/资源/GC），再用最小改动消除它**：不猜、先测、改一处、再测。

## 调优方法论：先证据，后改动

```
任务慢 → Spark UI 找最长 Stage → 看 Task 耗时分布
   ├── 少数 Task 特别长  → 数据倾斜（本章 §2）
   ├── 全部 Task 都长、Shuffle 量大 → Shuffle 优化（第 6 章）
   ├── Task 不长但数量少 → 并行度不足（本章 §3）
   ├── GC 时间占比高     → 内存/序列化（本章 §4）
   └── 某 Task 反复失败重跑 → 数据异常 / 资源不足
```

**铁律**：每次只改一个变量，跑对比。同时改三处就不知道是哪处生效的。

## 数据倾斜：离线任务的「头号杀手」

**症状**：Stage 里 99% 的 Task 几分钟完成，剩 1~3 个 Task 跑几小时，且单 Task Shuffle Read 远超均值（UI Tasks 页可见）。

### 成因

- key 分布天然不均：`groupBy("city")` 里「北京」占 50%
- Join 时一侧有热点 key（如默认账号 `0`、空值 `null`、爬虫 IP）
- `repartition(1)` / `coalesce(1)` 人为造成单分区

### 处理方案决策表

| 场景 | 方案 | 代码/参数 |
| --- | --- | --- |
| **小表 join 大表** | 广播小表，消灭 Shuffle | `df.join(F.broadcast(small), "k")` |
| **Join 热点 key 可识别** | 热点拆出来单独处理 | 过滤热点 → 单独 join → union 回主流程 |
| **聚合倾斜（groupBy）** | 加盐两阶段聚合 | 见下代码 |
| **Join 倾斜且不可广播** | 加盐打散 Join 键 | 大表 key+随机后缀，小表 key 膨胀 N 份 |
| **AQE 能解决的** | 开 AQE 倾斜自动拆分 | `spark.sql.adaptive.skewJoin.enabled=true` |
| **少量 null/无效 key** | 过滤掉或随机赋唯一值 | `filter(F.col("k").isNotNull())` 或 `coalesce(k, uuid())` |

### 方案一：两阶段聚合（聚合倾斜首选）

```python
from pyspark.sql import functions as F

# 原写法（北京的数据全压到一个 Task）：
# df.groupBy("city").agg(F.sum("pv"))

# 加盐打散：key → key_随机数
salted = df.withColumn("salted_city", F.concat(F.col("city"), F.lit("_"), (F.rand()*10).cast("int")))

# 第一阶段：按加盐 key 局部聚合
stage1 = salted.groupBy("salted_city").agg(F.sum("pv").alias("part_pv"))

# 第二阶段：去掉盐，全局聚合
result = (stage1.withColumn("city", F.split("salted_city", "_").getItem(0))
                .groupBy("city").agg(F.sum("part_pv").alias("total_pv")))
```

### 方案二：热点 key 单独处理（Join 倾斜首选）

```python
hot_keys = ["0", "-1", "unknown"]          # 已知的热点（占比如 80%）

big_hot  = big.filter(F.col("k").isin(hot_keys))
big_norm = big.filter(~F.col("k").isin(hot_keys))

# 非热点：正常 join（此时无倾斜）
normal_joined = big_norm.join(small, "k")

# 热点：单独广播 join 或特殊逻辑（如热点本身就是无效数据，直接处理）
hot_joined = big_hot.join(F.broadcast(small), "k")

result = normal_joined.unionByName(hot_joined)
```

### 方案三：AQE 自动处理（3.x 默认开）

```python
spark.conf.set("spark.sql.adaptive.enabled", True)
spark.conf.set("spark.sql.adaptive.skewJoin.enabled", True)
spark.conf.set("spark.sql.adaptive.skewJoin.skewedPartitionFactor", 5)   # 中位数 5 倍视为倾斜
spark.conf.set("spark.sql.adaptive.skewJoin.skewedPartitionThresholdInBytes", "256MB")
```

**注意**：AQE 只处理 Join 倾斜，且要求倾斜 key 的数据量能被「拆开后并行」。单 key 上亿行且无法拆分（如全量 distinct 该 key）仍需人工。

## 并行度：让集群「吃饱」

| 层面 | 参数 | 建议 |
| --- | --- | --- |
| 集群总并发 | `num-executors × executor-cores` | 总 Task 线程数 ≥ 集群总核数 |
| Shuffle 后分区 | `spark.sql.shuffle.partitions` | 单 Task 处理 100~200MB 为目标 |
| 输入分区 | `spark.sql.files.maxPartitionBytes` | 默认 128MB，对应 HDFS block |
| 写出小文件 | `repartition` / `coalesce` / AQE 合并 | 见下「小文件治理」 |

**判断并行度不足**：UI 里 Active Tasks 长期远小于总核数；或 Stage 的 Task 总数只有几十个而集群有几百核。

## 内存与 GC 调优

**症状**：UI Executors 页 GC 时间占总运行时间 >10%；日志频繁 Full GC。

| 手段 | 说明 |
| --- | --- |
| **升 executor-memory** | 最直接，但注意 >32G 后 GC 收益递减 |
| **Kryo 序列化** | `spark.serializer=org.apache.spark.serializer.KryoSerializer`，RDD cache 与 Shuffle 都受益 |
| **减少对象创建** | 避免在 map 里 new 大对象；用内置函数替代 UDF |
| **调 unified memory** | `spark.memory.fraction` 默认 0.6，cache 多可调高 storage 占比 |
| **堆外内存** | `spark.memory.offHeap.enabled=true` + `spark.memory.offHeap.size`，减少 GC 压力（Tungsten 直接用） |
| **G1GC** | `spark.executor.extraJavaOptions=-XX:+UseG1GC`，大堆（>8G）默认推荐 |

## 小文件治理（Hive/数仓场景的顽疾）

**症状**：写出目录下几千个几 KB 的文件；下游 Hive 查询慢、NameNode 压力大。

成因：分区数过多（每个 Task 写一个文件）+ 每个文件记录少。

| 方案 | 代码/参数 | 适用 |
| --- | --- | --- |
| **写出前 coalesce/repartition** | `df.repartition(10).write...` | 最直接；注意 repartition 有 Shuffle |
| **按分区列重分区** | `df.repartition("dt").write.partitionBy("dt")` | 每个 dt 分区一个 Task，减少文件 |
| **AQE 合并小分区** | 开 AQE 的 `coalescePartitions` | 自动，省心 |
| **写入层合并** | Delta/Iceberg 的 `OPTIMIZE` | 湖仓格式用户 |

经验：**写出前永远想好分区数**。一个 10GB 的日分区，200 个 Task → 200 个文件（每个 50MB，健康）；2000 个 Task → 2000 个 5MB 文件（灾难）。

## 缓存策略：用对时机

| 该 cache | 不该 cache |
| --- | --- |
| 同一 DF 被 ≥2 个 Action/Join 使用 | 只算一次的流水线 |
| 迭代算法（ML）反复扫同一份数据 | 数据量太大、cache 不下且重算便宜 |
| 计算成本高的中间结果（多轮 join 后） | 简单 filter 后的结果 |

```python
df.persist(StorageLevel.MEMORY_AND_DISK)   # 推荐兜底级别
df.count()                                  # 强制物化，避免 cache 懒触发
# ... 多次使用 ...
df.unpersist()                              # 用完释放
```

**坑**：`cache()` 不立即物化，是**懒标记**。第一个 Action 才真正缓存。有时你 cache 完马上看 UI Storage 是空的，别慌。

## 序列化与 Python 开销

| 场景 | 优化 |
| --- | --- |
| RDD cache / Shuffle | Kryo 序列化器 |
| PySpark UDF | **能用内置函数就不用 UDF**；必须自定义用 `pandas_udf` |
| DataFrame ↔ Pandas | 开 Arrow：`spark.sql.execution.arrow.pyspark.enabled=true` |
| Python worker 内存 | `spark.executor.pyspark.memory` 限制 + `memoryOverhead` 调大 |

## 常见反模式清单（Code Review 用）

| 反模式 | 问题 | 正确做法 |
| --- | --- | --- |
| `df.count()` 后接着 `df.write` | count 触发一次全量计算，write 又触发一次 | 只 write；或先 cache 再 count |
| `collect()` 后 Python 里 for 循环处理 | Driver OOM + 失去分布式意义 | 用 DataFrame 操作或 `foreachPartition` |
| 循环里 `df = df.withColumn(...)` 几百次 | Catalyst 计划爆炸，解析超时 | 用 `select` 列表推导一次完成 |
| `groupByKey` 后 `mapValues(sum)` | 全量 Shuffle，无预聚合 | `reduceByKey` / `groupBy().agg()` |
| 大表 join 大表不广播 | SortMergeJoin 双 Shuffle | 确认能否广播一侧 |
| `repartition(1)` 为了「一个文件」 | 单 Task 瓶颈 | 接受多文件，或下游再合并 |
| 默认 200 分区跑百 GB 级 | 单 Task 处理数 GB | 调大 `shuffle.partitions` 或开 AQE |

## 调优参数速查表（按场景）

| 场景 | 参数组合 |
| --- | --- |
| **通用 3.x 基线** | `adaptive.enabled=true` + `serializer=KryoSerializer` + `shuffle.partitions=按数据量` |
| **数据倾斜** | 上述基线 + `adaptive.skewJoin.enabled=true` + 人工加盐/热点拆分 |
| **小文件多** | `adaptive.coalescePartitions.enabled=true` + 写出前 `repartition(N)` |
| **PySpark UDF 慢** | 换 `pandas_udf` + 开 Arrow + 调大 `memoryOverhead` |
| **GC 严重** | `UseG1GC` + 升内存 + Kryo + 减对象创建 |
| **Join 慢** | 更新表统计信息 `ANALYZE TABLE` + 手动 `broadcast()` + 检查倾斜 |
