# 02 架构与运行原理

## 一句话

**Spark 架构 = Driver（大脑）+ Cluster Manager（资源官）+ Executor（干活的）**：Driver 把你的代码翻译成 DAG 并切成一批 Task，Cluster Manager 分配容器，Executor 并行执行 Task 并把状态汇报回 Driver。

## 三大角色

| 角色 | 职责 | 关键点 |
| --- | --- | --- |
| **Driver**（驱动程序） | 运行 `main()`、创建 SparkSession、构建 DAG、切分 Stage、调度 Task、收集结果 | 每个应用一个；挂了整个应用就挂 |
| **Cluster Manager**（集群管理器） | 分配/回收资源（CPU、内存容器） | Standalone / YARN / K8s，可插拔 |
| **Executor**（执行器） | 在 Worker 节点上常驻的 JVM 进程，真正跑 Task、存 cache 数据 | 一个应用可有许多个；多线程跑 Task |

```
                 ┌────────────────────────────┐
                 │  Driver (你的 main 程序)     │
                 │  SparkSession / DAGScheduler│
                 └───────┬───────────▲────────┘
            申请资源/汇报  │           │  状态心跳
                 ┌───────▼───────────┴────────┐
                 │      Cluster Manager        │
                 │   (YARN RM / K8s / Master)  │
                 └───┬─────────┬─────────┬────┘
              启动容器 │         │         │
              ┌──────▼─┐ ┌─────▼──┐ ┌────▼───┐
              │Executor│ │Executor│ │Executor│   ← 各 Worker 节点
              │ Task×n │ │ Task×n │ │ Task×n │
              │ cache  │ │ cache  │ │ cache  │
              └────────┘ └────────┘ └────────┘
```

## Driver 的两种部署位置：client vs cluster

| 模式 | Driver 在哪 | 适用 | 特点 |
| --- | --- | --- | --- |
| **client** | 你提交命令的那台机器 | 开发调试、交互式（pyspark shell、notebook） |  Driver 日志直接打在本地；提交机宕机 = 应用死 |
| **cluster** | 集群内部某台 Worker | 生产定时任务 | 提交完本地进程即可退出，Driver 由集群托管 |

```bash
spark-submit --master yarn --deploy-mode client  my_job.py   # 调试
spark-submit --master yarn --deploy-mode cluster my_job.py   # 生产
```

## 一次提交的完整生命周期（重点）

以 `df.groupBy("city").count().write.save(...)` 为例：

```
① 用户代码 ──② 逻辑计划 ──③ 逻辑优化(Catalyst) ──④ 物理计划 ──⑤ DAG 切 Stage ──⑥ Task 调度 ──⑦ Executor 执行 ──⑧ 结果
```

1. **提交**：`spark-submit` 启动 Driver，创建 SparkSession。
2. **惰性构建**：遇到 Action（如 `write`、`collect`）前，所有转换只是被记录。
3. **逻辑计划 → 优化**：SQL/DataFrame 先过 Catalyst 优化器（谓词下推、列裁剪等）。
4. **DAG 生成**：DAGScheduler 把作业翻译成 RDD 级别的有向无环图。
5. **切分 Stage**：遇到「宽依赖（Shuffle）」就切一刀，一个 Action 产生 1 个 Job，一个 Job 含多个 Stage。
6. **Task 调度**：TaskScheduler 把每个 Stage 拆成 N 个 Task（N = 该 Stage 的分区数），分发到 Executor。
7. **执行**：Executor 多线程跑 Task，结果写回 Driver（collect）或写存储（save）。
8. **收尾**：状态汇总到 Driver，Spark UI 可查；应用结束释放资源。

## 四个层级的名词别搞混（高频面试题）

| 名词 | 粒度 | 由谁产生 | 数量关系 |
| --- | --- | --- | --- |
| **Application** | 一个 spark-submit | 用户 | 1 个应用 |
| **Job** | 一个 Action | DAGScheduler | 1 应用 = N Job（几个 Action 几个 Job） |
| **Stage** | Job 内按 Shuffle 切分 | DAGScheduler | 1 Job = M Stage（几次 Shuffle 几段） |
| **Task** | 每个分区一个 | TaskScheduler | 1 Stage = K Task（K = 分区数），最小执行单元 |

记忆口诀：**Action 生 Job，Shuffle 切 Stage，Partition 定 Task。**

## 集群管理器对比

| | Standalone | YARN | Kubernetes |
| --- | --- | --- | --- |
| 是什么 | Spark 自带的简易 CM | Hadoop 生态资源管理器 | 容器编排平台 |
| 优点 | 零依赖、开箱即用 | 与 HDFS/Hive 同栈、队列隔离成熟 | 弹性好、混部、镜像化 |
| 缺点 | 功能简单、少有人用于生产 | 依赖 Hadoop 全家桶 | 运维门槛高 |
| 现状 | 测试/学习 | 国内大数据团队主流 | 增长最快，新平台首选 |

## Spark UI：排障第一入口

Driver 默认在 **4040 端口**提供 Web UI（local 模式直接 `http://localhost:4040`）：

| Tab | 看什么 |
| --- | --- |
| Jobs / Stages | 每个 Job 耗时、各 Stage 的 Task 分布、Shuffle 读写量 |
| Tasks | 单 Task 耗时分布——**判断数据倾斜**的核心证据 |
| Storage | cache 了哪些 RDD/DF、占用内存/磁盘 |
| Environment | 全部 Spark 配置，排查「参数没生效」 |
| Executors | 每个 Executor 的资源、GC 时间、失败原因 |
| SQL | DataFrame/SQL 的物理执行计划图（DAG Visualization） |

经验：**先记住 UI 的存在**。第 8 章调优时，大部分结论都要靠 UI 数据支撑，而不是拍脑袋。

## 本地跑起来看架构

```python
from pyspark.sql import SparkSession

spark = (SparkSession.builder
         .master("local[4]")          # 本地 4 线程模拟 4 个 Executor 线程
         .appName("ch02")
         .getOrCreate())

df = spark.range(0, 100000).repartition(8)   # 人为切成 8 个分区
result = df.groupByExpr("id % 10 as k").count().collect()
print(result)
# 此时浏览器打开 http://localhost:4040 可看到 Jobs/Stages/Tasks
input("回车前保持 UI 可访问……")
```
