# 05 混合检索与调优

## 一句话

**纯向量检索不是万能的**：它懂语义但不精关键词（型号、人名、编号召回差）；**BM25 关键词检索精关键词但不懂语义**。生产级搜索的标准做法是**混合检索（Hybrid Search）**：向量 + BM25 各跑一路，用 **RRF（倒数排名融合）**合并结果，再叠加标量过滤和参数调优，才能同时满足「准」和「快」。

## 为什么需要混合检索

| Query 类型 | 向量检索 | BM25 关键词 | 说明 |
| --- | --- | --- | --- |
| 「怎么退货」（语义） | ★★★★★ | ★★☆ | 向量懂「退货≈退款」 |
| 「iPhone 15 Pro Max 256G」（型号） | ★★☆ | ★★★★★ | 精确词项必须命中 |
| 「错误码 E2001」（编号） | ★☆ | ★★★★★ | 向量对无意义编号失效 |
| 「苹果多少钱」（歧义） | ★★★★☆ | ★★★☆ | 需结合上下文 |

**结论**：两路互补，融合后显著优于任何单路。RAG 场景召回质量直接决定 LLM 回答质量，这一步值得投入。

## BM25 快速回顾

BM25 是 ES/Lucene 的默认打分：词频（TF 饱和）× 逆文档频率（IDF）× 文档长度归一化。

```python
# 极简 BM25（rank_bm25 库）
from rank_bm25 import BM25Okapi

corpus = ["退货 流程 申请", "运费 计算 规则", "退款 到账 时间"]
tokenized = [doc.split() for doc in corpus]
bm25 = BM25Okapi(tokenized)

scores = bm25.get_scores("退款 多久 到账".split())
print(scores)   # 第 3 篇得分最高
```

## RRF：倒数排名融合

两路结果各有分数但**量纲不同**（向量 0~1 余弦分，BM25 无上限），不能直接加权。**RRF 不看分数只看排名**：

```
RRF_score(d) = Σ 1 / (k + rankᵢ(d))      k 通常取 60
```

文档在任一路排名越靠前，贡献越大；两路都命中的文档自然浮到最前。

```python
def rrf_fusion(vector_hits, bm25_hits, k=60, top_n=10):
    """vector_hits / bm25_hits: [(doc_id, score), ...] 按分数降序"""
    rrf = {}
    for rank, (doc_id, _) in enumerate(vector_hits, start=1):
        rrf[doc_id] = rrf.get(doc_id, 0) + 1 / (k + rank)
    for rank, (doc_id, _) in enumerate(bm25_hits, start=1):
        rrf[doc_id] = rrf.get(doc_id, 0) + 1 / (k + rank)
    return sorted(rrf.items(), key=lambda x: -x[1])[:top_n]
```

### 替代方案：加权融合

分数先各自 min-max 归一化，再加权：`score = α·vec + (1-α)·bm25`，α 常取 0.5~0.7。比 RRF 多一个可调旋钮，但要处理分数分布差异，RRF 更稳健无参数。**默认选 RRF**。

```python
def weighted_fusion(vector_hits, bm25_hits, alpha=0.6, top_n=10):
    def norm(hits):
        if not hits: return {}
        vals = [s for _, s in hits]
        lo, hi = min(vals), max(vals)
        span = (hi - lo) or 1.0
        return {d: (s - lo) / span for d, s in hits}
    v, b = norm(vector_hits), norm(bm25_hits)
    fused = {d: alpha * v.get(d, 0) + (1 - alpha) * b.get(d, 0)
             for d in set(v) | set(b)}
    return sorted(fused.items(), key=lambda x: -x[1])[:top_n]
```

## 标量过滤（Metadata Filter）

向量检索往往要带业务条件：「只在售后类目下搜」「只看 2026 年的文档」。两种过滤时机：

| 策略 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| **Pre-filter（先过滤）** | 先按标量筛出候选集，再在其中跑 ANN | 结果准确 | 过滤太狠（如只剩 0.1%）时图索引失效退化为暴力 |
| **Post-filter（后过滤）** | 先 ANN 取 Top-N（N≫K），再按标量筛到 K | 快 | 可能筛完不足 K 条 |
| **In-search（遍历中过滤，主流）** | HNSW 图遍历时跳过不满足条件的节点 | 准且快 | 引擎实现复杂 |

Milvus/Qdrant 默认采用 In-search：

```python
# Milvus：布尔表达式随 ANN 遍历生效
client.search("docs", data=[qvec], limit=10,
              filter='category == "refund" and year >= 2026')
```

**标量字段也要建索引**：Milvus 的 scalar index（倒排/Bitmap）、Qdrant 的 payload index——否则过滤本身成为瓶颈。

## 索引参数调优

### HNSW 三参数（最重要）

| 参数 | 作用时机 | 典型值 | 调优方向 |
| --- | --- | --- | --- |
| M | 建库 | 16 / 32 / 48 | 内存够 → 32；召回不够且建库慢可接受 → 48 |
| efConstruction | 建库 | 200 | 建库时间预算内越大越好（≥100 后收益递减） |
| **efSearch（ef）** | **查询** | 64 | **唯一运行时旋钮**：延迟预算内调到召回达标 |

```python
# 调优闭环：固定建库参数，扫 efSearch 画 召回-延迟曲线
for ef in [16, 32, 64, 128, 256]:
    index.hnsw.efSearch = ef
    t0 = time.perf_counter()
    _, ids = index.search(queries, 10)
    lat = (time.perf_counter() - t0) / len(queries) * 1000
    rec = recall_at_k(ids, truth_ids)
    print(f"ef={ef:4d}  召回@10={rec:.3f}  延迟={lat:.1f}ms")
```

### IVF 两参数

- `nlist ≈ 4×√N`：建库时定死，100 万 → 1024~4096
- `nprobe`：查询时旋钮，从 8 起步加倍，直到 Recall@10 ≥ 目标（通常 95%）

### 调优顺序（别乱调）

```
1. 先用 Flat 暴力拿真值 → 2. 选索引（HNSW）默认参数 → 3. 只调运行时参数（ef/nprobe）
→ 4. 召回不达标再回调建库参数（M/efConstruction）→ 5. 还不够考虑 IVF_PQ + 重排
```

## 分片与副本（生产扩展）

### 分片（Sharding）：扛数据量

- **按 ID 哈希分片**：均匀，查询广播到所有分片再合并（Milvus 默认）
- **按业务键分片**（如 tenant_id）：同租户数据同分片，查询只路由单分片——多租户 SaaS 推荐
- 分片数 ≈ 数据总量 / 单分片舒适容量（通常单分片千万级、内存几十 GB）

### 副本（Replica）：扛并发

```
                ┌─ Shard1-Replica1 ─┐
查询 QPS ──> LB ┼─ Shard1-Replica2 ─┤   同分片多副本轮询 → 线性提升 QPS
                └─ Shard2-Replica1 ─┘
```

- 副本是**只读扩容**：写入只进主，副本异步同步（秒级延迟）
- 经验：QPS 翻倍 → 副本翻倍；P99 延迟不变
- 副本 ≠ 高可用的全部：还要有跨机房部署 + 定期快照备份

### 内存估算公式

```
HNSW 内存 ≈ N × (D×4 字节原向量 + M×2×8 字节图边) × 1.1 余量
例：1亿 × (1024×4 + 32×2×8) ≈ 1亿 × 4608B ≈ 460GB → 至少 8 分片 × 64GB 机型
```

内存不够三选一：加分片、换 IVF_PQ（1/32 内存）、降维/量化。

## 常见问题

**Q：RRF 里的 k=60 怎么来的？能调吗？**
A：来自原论文的经验值，对排名靠前结果给足够区分度又不过度倾斜。一般不用调；调小（如 20）头部权重更大，调大（如 100）更平滑。业务上 k 的敏感度远低于「要不要混合检索」本身。

**Q：混合检索两路各取多少条进融合？**
A：通常各取 Top-50~100 进 RRF，最终输出 Top-10。取太少（如各 10）融合收益小；太多增加无效计算。后面如果接重排模型（Rerank），候选集可以给到 100~200。

**Q：标量过滤条件非常苛刻（命中 < 1%）时查询变慢怎么办？**
A：① 给该标量字段建索引；② 改 Pre-filter 显式先过滤；③ 业务层拆分：把苛刻条件做成独立 collection/分区（如按租户分 collection）。

**Q：副本同步期间查询会读到旧数据吗？**
A：会，最终一致。一致性级别通常可选（Milvus 支持 Strong/Bounded/Eventually）。RAG 场景 Eventually 足够；金融类强一致场景用 Strong（牺牲延迟）。
