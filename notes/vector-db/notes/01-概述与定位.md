# 01 概述与定位

## 一句话

**向量数据库是专门存「向量」并做「相似度检索」的数据库**：把文本/图片/音频用 Embedding 模型编码成高维浮点数组（如 768/1024/3072 维），入库后支持「给我一个向量，返回最相似的 Top-K」。它是 RAG、语义搜索、推荐系统的基础设施，解决的是传统数据库「只能精确匹配、不懂语义」的问题。

## 为什么需要向量数据库

传统数据库的查询是**精确匹配**：

```sql
-- 关系库：只能匹配包含关键词的行
SELECT * FROM docs WHERE content LIKE '%退货流程%';
-- 查不到「怎么把买的东西退掉」——虽然语义一样，但字面不同
```

而人类的真实需求是**语义匹配**：

| 用户输入 | 字面匹配结果 | 语义匹配结果 |
| --- | --- | --- |
| 「怎么退货」 | 含「退货」的文档 | 退货流程、退款政策、售后申请（都对） |
| 「苹果手机怎么样」 | 含「苹果」的文档 | iPhone 评测（对） vs 水果苹果种植（错） |
| 「happy」 | 含 "happy" 的文档 | joyful / delighted / 开心（跨语言） |

向量数据库的做法：**把每段文本编码成一个向量，语义相近的文本向量距离也相近**。查询时把问题也编码成向量，找距离最近的 Top-K 即可。

```python
import numpy as np

# 伪代码：Embedding 模型把文本变成向量
q = embed("怎么退货")        # shape (768,)
d1 = embed("退货流程说明")    # 与 q 语义近
d2 = embed("今日天气预报")    # 与 q 语义远

def cosine(a, b):
    return a @ b / (np.linalg.norm(a) * np.linalg.norm(b))

cosine(q, d1)  # ≈ 0.87  语义相近
cosine(q, d2)  # ≈ 0.12  语义无关
```

## 与 ES / 关系库 / Redis 的差异

| 维度 | 向量数据库（Milvus/Qdrant） | Elasticsearch | 关系库（PostgreSQL） | Redis |
| --- | --- | --- | --- | --- |
| 核心能力 | **向量相似度检索** | 全文检索（BM25） | 结构化精确查询 | KV 缓存 |
| 匹配方式 | 语义（距离最近） | 字面（词项匹配） | 精确（=/LIKE） | 精确（key） |
| 索引 | HNSW / IVF / PQ | 倒排索引 | B+Tree | Hash |
| 典型查询 | Top-K 最近邻 | match / term | WHERE / JOIN | GET |
| 向量支持 | 原生一等公民 | 8.x+ dense_vector | pgvector 插件 | RediSearch 模块 |
| 扩展性 | 为海量向量设计 | 中等 | 单表千万级向量吃力 | 内存级、容量小 |

**关键结论**：向量数据库不是替代谁，而是补齐「语义检索」这块拼图。生产上常见组合是 **ES（关键词）+ 向量库（语义）混合检索**，见第 05 章。

## 核心应用场景

### 1. 语义搜索
用户用自然语言搜文档/商品/工单，不按关键词匹配。电商搜索「送妈妈的生日礼物」直接命中相关商品，而不是要求标题含这几个字。

### 2. RAG（检索增强生成）
大模型幻觉问题的主流解法：**先检索、后生成**。用户提问 → 向量库检索相关知识片段 → 塞进 Prompt → LLM 基于检索结果回答。企业知识库问答、客服机器人的标配架构。

```
用户问题 → Embedding → 向量库 Top-K → 拼接上下文 → LLM → 带引用的回答
```

### 3. 推荐与去重
- 「看了又看」：商品向量找近邻做相关推荐
- 内容去重：新闻/短视频向量距离 < 阈值判定为重复
- 以图搜图：图片 Embedding 检索同款

### 4. 风控与异常检测
正常行为聚成簇，离群向量（距离所有簇都远）判定为异常交易/异常日志。

## 一个最小可用示例（纯 numpy，无需任何服务）

```python
import numpy as np

# 1. 假设有 5 个文档向量（实际由 Embedding 模型产出，这里随机模拟）
rng = np.random.default_rng(42)
docs = rng.normal(size=(5, 128)).astype(np.float32)
docs /= np.linalg.norm(docs, axis=1, keepdims=True)  # 归一化

# 2. 查询向量
q = rng.normal(size=(128,)).astype(np.float32)
q /= np.linalg.norm(q)

# 3. 暴力检索：余弦相似度 = 归一化后的点积
scores = docs @ q
topk = np.argsort(-scores)[:3]
print("Top-3:", topk, "得分:", scores[topk])
```

这个例子在小数据量（< 1 万）时完全够用。数据量上到百万级，暴力扫描太慢，就需要 ANN 索引（第 03 章）和专业向量数据库（第 04 章）。

## 主流产品一览

| 产品 | 类型 | 语言/协议 | 特点 | 适合 |
| --- | --- | --- | --- | --- |
| **FAISS** | 库（非服务） | C++/Python | Meta 开源，索引算法最全，单机 | 算法研究、嵌入式检索 |
| **Milvus** | 分布式服务 | Go，gRPC/REST | 云原生、存算分离、生态全 | 生产级大规模（亿级+） |
| **Qdrant** | 服务 | Rust，REST/gRPC | 轻量、过滤强、Rust 性能 | 中小规模生产 |
| **Chroma** | 嵌入式/服务 | Python | 极简 API，AI 应用首选原型 | 快速验证、小项目 |
| **Weaviate** | 服务 | Go，GraphQL | 模块化、内置向量化 | 需要 GraphQL 的团队 |
| **pgvector** | PG 插件 | SQL | 复用 PostgreSQL 生态 | 已有 PG、向量量 < 千万 |
| **Elasticsearch** | 搜索引擎 | REST | dense_vector + HNSW | 已有 ES 栈做混合检索 |
| **Redis Stack** | 内存库 | Redis 协议 | 毫秒延迟，容量受内存限 | 低延迟小数据量 |

**选型速记**：
- 学习/原型 → **FAISS / Chroma**（pip 安装即用）
- 生产亿级 → **Milvus**
- 生产千万级、要简单 → **Qdrant**
- 已有 PostgreSQL → **pgvector** 先顶上

## 常见问题

**Q：向量数据库和传统数据库是竞争关系吗？**
A：不是。向量库只擅长一件事——相似度检索；事务、JOIN、精确过滤还是关系库强。生产上通常并存：业务数据在 MySQL/PG，向量副本在向量库，通过 ID 关联。

**Q：能不能直接用 Redis 数组或 PostgreSQL 存向量，numpy 算距离？**
A：小数据量（万级以下）完全可以，第 03 章会证明暴力检索的瓶颈在哪。数据量大了之后，没有 ANN 索引的暴力扫描延迟无法接受（百万级 768 维单次查询约几百毫秒），这时才需要专业方案。

**Q：向量数据库的「数据库」体现在哪？**
A：除了向量检索，还包含：元数据存储与过滤（标量字段）、持久化、增删改、副本/分片、权限。FAISS 只是算法库没有这些，所以叫「库」不叫「数据库」。
