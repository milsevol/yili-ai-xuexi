# 01 概述与定位

## 一句话

**Apache Kafka**：一个把消息按主题分区、多副本持久化存储的分布式发布订阅系统。它既是消息队列（解耦上下游），也是数据总线（实时链路缓冲），还是分布式提交日志（Streams/Connect 的底层）。

## 为什么需要 Kafka

2011 年 LinkedIn 面对的问题是：用户行为日志每天 TB 级增长，传统做法是每个系统各自拉日志 → 到处是重复采集、无处不写脚本、链路一挂就爆炸。Kafka 的解决方案是**把「数据管道」统一成一个中间层**：Producer 只管往里写，Consumer 按需拉取，Broker 集群保证不丢不重。

| 现实问题 | 传统做法 | Kafka 的做法 |
| --- | --- | --- |
| 日志到处散，每个系统各写一份 | Flume 进 HDFS、Logstash 进 ES、还有一堆自研 | 统一写 Kafka，下游各自消费 |
| 业务耦死：上游一改下游就崩 | 同步调用 + MQ 但量一上去 MQ 扛不住 | Producer 只管发，Consumer 挂了不影响上游 |
| 实时数据处理需要稳定入口 | 直接拉数据库 binlog / 读 API，下游变更就挂 | Kafka Connect 做 CDC，中间 Kafka 缓冲 |
| 做流处理需要有状态能力 | 每个 Flink/Spark 作业自己存状态 | Kafka Streams 直接把 Topic 当状态存储 |
| 审计/回放需要完整日志 | 很难，消息队列一般消费完就删 | Kafka 默认 7 天保留，可配永久，随时回放 |

## 消息队列三大流派

| 流派 | 代表 | 模型 | 典型产品 |
| --- | --- | --- | --- |
| **点对点（Queue）** | RabbitMQ | 一条消息只能被一个 Consumer 拿到 | RabbitMQ / ActiveMQ |
| **发布订阅（Topic）** | Kafka | 一条消息可被多个 Consumer Group 独立消费 | Kafka / RocketMQ / Pulsar |
| **分布式提交日志（Log）** | Kafka/Pulsar | 消息是不可变、有 Offset 的日志，消费后不删除 | Kafka / Pulsar |

Kafka 之所以能脱颖而出，是因为它**同时满足了发布订阅 + 分布式提交日志 + 极致吞吐**这三点：

| 维度 | RabbitMQ | RocketMQ | Kafka |
| --- | --- | --- | --- |
| 模型 | AMQP Queue/Exchange | Topic + Queue | Topic → Partition（日志分片） |
| 吞吐 | ~万级/s | ~十万级/s | ~百万级/s（顺序写磁盘 + 零拷贝） |
| 延迟 | ~微秒级 | ~毫秒级 | ~毫秒级（批量后） |
| 消息保留 | 消费完删除 | 消费完可保留 | 默认 7 天，可配 forever |
| 事务 | 支持 | 支持（半消息） | 支持（幂等 Producer + 事务） |
| 顺序性 | 单 Queue 有序 | 单 Queue 有序 | 单 Partition 有序 |
| 适用场景 | 业务解耦、小量高可靠 | 业务消息 + 大数据链路 | 大数据实时链路、日志、CDC |

## Kafka 的独特之处

1. **分布式提交日志**：消息写进追加日志（Append-Only Log），读就是从 Offset 拉一段出来。这使得 Kafka 同时能做「消息队列」「事件溯源」「流处理状态存储」「数据总线」。
2. **磁盘顺序写 + 零拷贝**：Producer 批量写 Broker 的磁盘文件（Segment），Consumer 读的时候用 `sendfile` 把数据直接从内核缓冲进网卡，不进应用进程。
3. **分区并行**：Topic 拆成多个 Partition，每个 Partition 有独立 Offset，Consumer Group 内每个 Partition 只能被一个 Consumer 消费——这是 Kafka 天然的并行与顺序保证。
4. **解耦：Consumer 自己管进度**：Producer 只管发，Consumer 自己决定什么时候 commit offset。Consumer 挂了重启，从上次 commit 的地方续，不丢不重（取决于提交策略）。

## 发展简史

- **2011** LinkedIn 内部开源 Kafka，Scala 写的，初衷就是统一 LinkedIn 的活动日志管道。
- **2014** 成为 Apache 顶级项目，Java 重写开始。
- **2017** 发布 Streams API；**2019** Connect API 成熟。
- **2022** KRaft（去掉 ZooKeeper）GA，成为生产可用。
- **2023** 3.6 发布；**2024** 3.7/3.8 陆续发布，KRaft 正式推荐新项目使用。
- **2025+** ZooKeeper 模式在 3.8 开始 deprecated，4.0 计划完全移除 ZK 依赖。

## Kafka vs RocketMQ vs RabbitMQ：选型速判

| 场景 | 推荐 | 理由 |
| --- | --- | --- |
| 实时大数据链路（日志、CDC、埋点） | **Kafka** | 吞吐高、生态完善、Flink/Spark 原生支持 |
| 电商交易、业务解耦（小量高可靠） | **RabbitMQ** | 低延迟、AMQP 协议丰富、管理界面友好 |
| 业务消息 + 大数据都要 | **RocketMQ** | 阿里出品，事务消息好、支持延迟消息 |
| 多集群/跨地域复制 + 流存储 | **Pulsar** | BookKeeper 存数据，Broker 无状态 |

## Kafka 在大数据链路中的位置

```
数据源（埋点、日志、DB binlog）
        ↓
   Kafka（缓冲 + 解耦 + 多订阅）
        ↓
  ┌─────┼─────┐
  ↓     ↓     ↓
Flink  Spark  Connect → HDFS/HBase/ES/...
```

Kafka 是「高速公路」：上游只管往里灌，下游（Flink 实时算、Spark 离线批、Connect 同步到各种存储）各自从 Kafka 拉取，互不影响。

## 动手体验：Docker 快速跑起来

```bash
docker run -d --name kafka ^
  -p 9092:9092 -p 9093:9093 ^
  -e KAFKA_NODE_ID=1 \
  -e KAFKA_PROCESS_ROLES=broker,controller \
  -e KAFKA_CONTROLLER_QUORUM_VOTERS=1@localhost:9093 \
  -e KAFKA_LISTENERS=PLAINTEXT://:9092,CONTROLLER://:9093 \
  -e KAFKA_ADVERTISED_LISTENERS=PLAINTEXT://localhost:9092 \
  bitnami/kafka:3.8

# 创建主题
docker exec -it kafka /opt/bitnami/kafka/bin/kafka-topics.sh \
  --bootstrap-server localhost:9092 \
  --create --topic demo --partitions 3 --replication-factor 1

# 生产（控制台输入任意消息回车发送）
docker exec -it kafka /opt/bitnami/kafka/bin/kafka-console-producer.sh \
  --bootstrap-server localhost:9092 --topic demo

# 消费（另一个终端）
docker exec -it kafka /opt/bitnami/kafka/bin/kafka-console-consumer.sh \
  --bootstrap-server localhost:9092 --topic demo --from-beginning
```
