# 02 架构与核心概念

## 一句话

Kafka 集群由一组 **Broker** 组成，数据按 **Topic** 组织，每个 Topic 拆成多个 **Partition**，每个 Partition 有多个 **Replica** 跨 Broker 存放，其中一个 Leader 负责读写、Follower 只同步日志，**ISR**（In-Sync Replicas）是当前与 Leader 保持同步的副本集合。

## 核心实体

```
Kafka Cluster
  ├─ Broker 1 (Broker Id)
  │   ├─ Topic A / Partition 0 / Replica (Leader)
  │   ├─ Topic A / Partition 1 / Replica (Follower)
  │   └─ Topic B / Partition 0 / Replica (Leader)
  ├─ Broker 2
  │   ├─ Topic A / Partition 0 / Replica (Follower)
  │   ├─ Topic A / Partition 1 / Replica (Leader)
  │   └─ Topic B / Partition 0 / Replica (Follower)
  └─ Broker 3 (Controller)
      ├─ Topic A / Partition 0 / Replica (Follower)
      ├─ Topic A / Partition 1 / Replica (Follower)
      └─ Topic B / Partition 0 / Replica (Follower)
```

| 实体 | 一句话 | 关键属性 |
| --- | --- | --- |
| **Broker** | 集群中的一台 Kafka 服务器 | broker.id、listeners、num.partitions 默认分区数 |
| **Topic** | 消息的逻辑分类 | replication-factor、num-partitions |
| **Partition** | Topic 的物理分片，每个分区是一个有序追加日志 | partition.id、offset、leader、isr |
| **Replica** | Partition 在某个 Broker 上的一份拷贝 | replica.id（= broker.id）、ISR 状态 |
| **Leader** | 负责该 Partition 读写的那个 Replica | 唯一；Producer 只写 Leader，Consumer 只读 Leader |
| **Follower** | 只同步 Leader 日志、不对外服务的 Replica | 从 Leader 拉取日志，追上后才能进 ISR |
| **ISR** | 与 Leader 保持同步的副本集合 | 含 Leader + 同步延迟在 threshold 内的 Follower |
| **OSR** | Out-of-Sync Replicas，不在 ISR 里的副本 | 落后太多，不会作为 ack=all 的对象 |
| **Consumer Group** | 一组协同消费的 Consumer | 组内每个 Partition 只能被一个 Consumer 消费 |

## Producer → Partition 的路由

Producer 发送一条消息到某个 Topic 时，目标 Partition 选择规则：

| 场景 | 规则 |
| --- | --- |
| 指定了 partition | 直接用 |
| 未指定 partition，但有 key | `hash(key) % numPartitions`（默认 Murmur2） |
| 都没指定 | Round-Robin 轮询（默认 Sticky Partitioner，3.4+ 起） |

**Sticky Partitioner**：3.4 起默认。不是简单 RR，而是把一批消息粘到一个 Partition，直到该 Partition 的 batch 满或linger 超时才换 Partition。效果是更少的 batch、更高的吞吐，但会改变「无 key 消息均匀分布」的直觉——所以如果你需要严格均匀分布，要么显式传不同的 key，要么禁用 sticky。

## ISR 与副本同步

Follower 通过主动 Fetch 从 Leader 拉取日志。Leader 为每个 Follower 维护一个 `lastCaughtUpTimeMs`，如果 `replica.lag.time.max.ms`（默认 30000ms）内没追上，就把它踢出 ISR；追上后重新加回。

```
ack=1:    Leader 写成功就返回（不关心 ISR）
ack=all:  Leader 写成功 + ISR 里所有副本都 sync 到这条消息才返回
```

**注意**：`acks=all` 的安全边界是「ISR 大小 ≥ min.insync.replicas」。如果 ISR 里只剩 Leader 一个，即使 acks=all 也只写 Leader（等于 acks=1）。生产务必配 `min.insync.replicas >= 2`。

## KRaft vs ZooKeeper

| 维度 | ZooKeeper 模式（老） | KRaft 模式（新） |
| --- | --- | --- |
| 元数据存储 | 外部 ZooKeeper 集群 | Broker 内部的 Metadata Log（Raft） |
| Controller | 独立角色（一个 Active + 备用） | Controller Quorum（可合并到 Broker 进程） |
| 进程数 | N Broker + N ZK | 全在 Kafka 进程里 |
| 部署复杂度 | 要先布 ZK | 直接起 Kafka |
| Broker 启动时间 | 需等 ZK 连接 | 自身 Raft 选主，更快 |
| 生产可用 | ✅ 成熟 | ✅ 3.6+ GA；3.7 起生产推荐 |
| 官方支持 | deprecated（3.8） | 4.0 将移除 ZK 模式 |

KRaft 的本质是把元数据从外部依赖变成了 Kafka 自己用 Raft 协议维护的日志。好处：
1. **少一个外部组件**，运维成本减半。
2. **更快的 Controller 切换**，因为 Raft 比 ZK Watch 更适合 Kafka 的元数据模型。
3. **支持更大的集群规模**，ZooKeeper 在 Topic/Partition 数上有限制（约 20–30K），KRaft 可以到百万级。

## Controller 角色

Controller 是集群大脑，负责：

1. **Partition Leader 选举**：某个 Broker 挂了 → Controller 从 ISR 里挑一个 Follower 当新 Leader。
2. **Topic/Partition 管理**：create/delete topic、动态加分区、分区重分配。
3. **Broker 上下线监听**：ZK 模式靠 Watch 节点，KRaft 靠 Raft log 里的 Broker 注册信息。
4. **元数据广播**：把变更推给所有 Broker 和客户端。

KRaft 模式下 Controller 可以和 Broker 合并部署，也可以独立成 3+ 节点的 Controller Quorum（Raft 选主）。

## Broker 配置关键项（KRaft 最小集）

```properties
# Broker 身份
broker.id=1
node.id=1                              # KRaft: node.id = broker.id
process.roles=broker,controller        # KRaft: 角色
controller.quorum.voters=1@host1:9093,2@host2:9093,3@host3:9093

# 监听
listeners=PLAINTEXT://:9092,CONTROLLER://:9093
advertised.listeners=PLAINTEXT://kafka1:9092

# 存储
log.dirs=/data/kafka-logs

# 主题默认
num.partitions=3
default.replication.factor=3
min.insync.replicas=2                  # acks=all 的安全底线

# 网络
num.network.threads=3
num.io.threads=8
socket.send.buffer.bytes=102400
socket.receive.buffer.bytes=102400
socket.request.max.bytes=104857600

# 日志
log.retention.hours=168                # 7 天
log.segment.bytes=1073741824           # 1GB
log.retention.check.interval.ms=300000
```

## 常见问题

**Q: 为什么 Topic 分区数只能增不能减？**
A: 分区是 Topic 的并行度和顺序性的基本单位。如果允许减分区，就要重新分布数据、打破原有的 key→partition 映射，对下游 Consumer Group 影响巨大。Kafka 目前不支持。

**Q: 一个 Consumer Group 里的 Consumer 数 > Partition 数会怎样？**
A: 多出来的 Consumer 会**闲置**，不消费任何 Partition。这是合理的：Consumer 数 = Partition 数是最佳平衡点。

**Q: 一个 Partition 可以有多少个 ISR？**
A: 最多是 `replication.factor`（包含 Leader）。生产建议 `replication.factor=3`，ISR 常态 3，最差 1（只剩 Leader，此时 acks=all 退化）。
