# 08 运维监控与故障排查

## 一句话

生产运维要盯**三类指标**：Broker 端（UnderReplicatedPartitions、OfflinePartitionsCount）、Consumer 端（ConsumerLag）、Producer 端（request-latency-avg）。排障按「**症状 → 指标 → 日志 → 根因 → 修复**」五步走。

## 核心指标清单

### Broker 端（KRaft 模式）

| 指标 | 含义 | 异常阈值 | 紧急级别 |
| --- | --- | --- | --- |
| `UnderReplicatedPartitions` | ISR < replication.factor 的 Partition 数 | > 0 | 🔴 紧急 |
| `OfflinePartitionsCount` | 没有 Leader 的 Partition 数 | > 0 | 🔴 紧急 |
| `ActiveControllerCount` | 集群里有几个 Active Controller | ≠ 1 | 🟡 脑裂风险 |
| `PartitionCount` | 每 Broker 上 Partition 数 | > 2000 | 🟡 高 |
| `MessageInRate` | Producer 写入速率 | 突变 > 3 倍 | 🟡 可能洪峰 |
| `RequestHandlerIdleRatio` | Broker 处理线程空闲率 | 持续 < 10% | 🟡 瓶颈 |
| `LogFlushRateAndTimeMs` | 刷盘延迟 | P99 > 1000ms | 🟡 磁盘慢 |
| `GC-PauseMs` | GC 停顿 | P99 > 1000ms | 🟡 Consumer 可能 Rebalance |
| `NetworkProcessorIdleRatio` | 网络线程空闲率 | 持续 < 10% | 🟡 网卡/CPU 瓶颈 |

### Consumer 端

| 指标 | 含义 | 异常阈值 |
| --- | --- | --- |
| `ConsumerLag` | Partition Log-End-Offset - Consumer Committed Offset | 持续增长不收敛 |
| `Consumer Rebalance Rate` | 每秒 Rebalance 次数 | > 0（不该有） |
| `CommitLatency` | commitSync 耗时 | P99 > 5000ms |
| `PollIdleRatio` | poll() 平均间隔 / max.poll.interval.ms | 接近 1 |

### Producer 端

| 指标 | 含义 | 异常阈值 |
| --- | --- | --- |
| `request-latency-avg` | Producer 请求平均耗时 | > 100ms |
| `record-error-rate` | 每秒错误率 | > 0 |
| `record-retry-rate` | 每秒重试次数 | 持续偏高 |
| `record-send-rate` | 发送速率 | 突变 > 3 倍 |

## 排障决策树

### 症状：UnderReplicatedPartitions > 0

```
UnderReplicatedPartitions > 0
  ├─ 查 Broker 列表：哪些 Broker 挂了？（kafka-broker-api-versions.sh --bootstrap-server）
  │   ├─ Broker 挂了 → 重启（kill + start，检查日志 OOM / 磁盘满 / GC 停顿）
  │   └─ Broker 活着但 ISR 落后 → 单 Broker 慢
  │       ├─ 网络：iperf3 测带宽（Follower 拉 Leader 走这条）
  │       ├─ 磁盘：df -h 看满了没；iostat 看 %util
  │       ├─ GC：jstat -gcutil <pid> 1000 10 看停顿
  │       └─ 线程：jstack <pid> 看 request-handler 是不是卡了
  └─ 如果长期不恢复
      ├─ 可能 Follower 追不上（`replica.lag.time.max.ms` 太小）
      └─ 手动从 ISR 踢出、换 Broker 重分配
```

### 症状：Controller 切换频繁 / 脑裂

```
ActiveControllerCount ≠ 1
  ├─ KRaft quorum 节点心跳互相收不到？
  │   ├─ 网络连通性：telnet ctrl:9093 通吗？
  │   ├─ GC 停顿：Controller 进程是不是卡了 > election.timeout.ms（默认 1s？实际看配置）
  │   └─ 进程数：是不是有多进程抢 node.id？
  └─ 紧急：把多余的 Controller 进程 kill，检查配置
```

### 症状：Broker 宕机恢复

```
Broker 挂了 → 自动恢复流程
  1. Controller 检测到 Broker 下线 → 该 Broker 上所有 Partition 的 Leader/Follower 重新选举
  2. Leader 从剩余 ISR 里选新 Leader
  3. Follower 从新 Leader 继续同步
  4. 原 Broker 重启后：
     ├─ 先检查本地 log 是否完整（可能有 Leader 切换期间丢的 segment？不会，因为 ISR 保证）
     ├─ 向新 Leader 发 Fetch → 追平 → 重新加入 ISR
     └─ Controller 可能触发 PreferReplicaLeaderElection 把原 Leader 选举回来（3.4+ 自动）
```

### 症状：Rebalance 卡住 / 长时间未完成

```
Rebalance 卡住
  ├─ 某个 Consumer 心跳断了但还在 Group？
  │   ├─ 看 Coordinator 日志：MemberExpire 超时了吗？
  │   └─ 检查 Consumer 端心跳线程状态
  ├─ 重分配 Partition 太多？
  │   ├─ kafka-reassign-partitions.sh --verify 看进度
  │   └─ 如果是，分批重分配，不要一次性搞几百个 Partition
  └─ Controller 元数据广播慢？
      ├─ Controller 是不是负载高（PartitionCount 太多、GC 长停顿）
      └─ 考虑独立 Controller 集群
```

### 症状：Producer 端 RecordTooLargeException

```
RecordTooLargeException
  ├─ 根因：单条消息 > max.message.bytes（Broker 默认 1MB）
  ├─ 解 1：Producer 调 max.request.size；Broker 调 max.message.bytes
  └─ 解 2（推荐）：把大内容存对象存储，Kafka 只发路径引用
```

### 症状：Consumer 端 Rebalance 频繁

```
Rebalance 频繁（每隔几秒/几分钟一次）
  ├─ 业务处理太慢 > max.poll.interval.ms → Consumer 被 Coordinator 踢
  │   └─ 调大 max.poll.interval.ms，或优化业务逻辑 / 减小 max.poll.records
  ├─ GC 停顿 > session.timeout.ms → 心跳没发出去
  │   └─ 调大 heartbeat.interval.ms / session.timeout.ms，或优化 GC
  ├─ 网络抖动 → 心跳 RPC 超时
  │   └─ ping / traceroute 查，或调大 session.timeout.ms
  └─ 有新 Consumer 不断进出（扩容/重启） → 正常但会有 Rebalance
```

### 症状：ISR 频繁抖动

```
ISR 频繁抖动（进进出出）
  ├─ Follower 同步跟不上
  │   ├─ replica.lag.time.max.ms 太小（默认 30000ms）→ 调大到 60000
  │   ├─ Follower 网络带宽不够 → iperf3 测
  │   └─ Follower 磁盘太慢 → iostat 看 %util
  └─ Leader 写入洪峰 → Follower 追不上
      ├─ 调 leader.replication.throttled.replicas + follower.replication.throttled.replicas（限流）
      └─ 或把写入分散到更多 Partition
```

### 症状：ConsumerLag 持续增长

```
ConsumerLag 持续增长
  ├─ 下游业务处理太慢 → 优化
  ├─ Consumer 实例数不够 → 扩容（注意 Rebalance）
  ├─ Partition 数不够 → 加分区（Producer 没 key 的消息可以继续 RR）
  └─ 网络瓶颈（Consumer → Broker）→ 网卡 / 跨机房延迟
```

## 常用运维命令

```bash
# 集群状态
kafka-metadata-quorum.sh --bootstrap-server kafka1:9093 describe --status

# Broker 列表
kafka-broker-api-versions.sh --bootstrap-server kafka1:9092 --broker-list all

# Topic / Partition 状态
kafka-topics.sh --bootstrap-server kafka1:9092 --describe --topic demo
# 看 ISR 分布
kafka-topics.sh --bootstrap-server kafka1:9092 --describe --topic demo | grep Isr

# Consumer Group 状态
kafka-consumer-groups.sh --bootstrap-server kafka1:9092 \
  --describe --group demo-group --members --verbose
# 重置 Offset
kafka-consumer-groups.sh --bootstrap-server kafka1:9092 \
  --reset-offsets --group demo-group --topic demo:0-5 --to-offset 12345 --execute

# Partition 重分配
kafka-reassign-partitions.sh --bootstrap-server kafka1:9092 \
  --generate --topics-to-move-json-file topics.json --broker-list 4,5,6

# 主题压测（内置）
kafka-producer-perf-test.sh --topic demo --num-records 100000 \
  --record-size 1024 --throughput -1 --producer-props bootstrap.servers=kafka1:9092
kafka-consumer-perf-test.sh --bootstrap-server kafka1:9092 \
  --topic demo --messages 100000
```

## 监控：推荐 Prometheus + Grafana

Kafka 自带 JMX Exporter，把 `KAFKA_JMX_OPTS` 配上后 Prometheus 直接 scrape：

```bash
export KAFKA_JMX_OPTS="-Dcom.sun.management.jmxremote \
  -Dcom.sun.management.jmxremote.port=9999 \
  -Dcom.sun.management.jmxremote.authenticate=false \
  -Dcom.sun.management.jmxremote.ssl=false \
  -javaagent:/opt/prometheus/jmx_prometheus_javaagent.jar=8080:/etc/kafka/jmx_exporter.yml"
```

Grafana 社区有现成的 Kafka 监控 Dashboard（ID 721、9963）。
