# 05 存储与分区原理

## 一句话

Kafka 的极致吞吐来自**把追加日志写到磁盘文件上 + 读的时候用零拷贝（sendfile）**。每个 Partition 是一个追加日志，按 Segment（段）滚动，每个 Segment 是一堆消息（message set）+ 一个稀疏索引（Sparse Index）帮助快速定位 offset。

## Partition = Log

每个 Partition 在 Broker 的磁盘上对应一个目录：

```
log.dirs=/data/kafka-logs/
├── test-topic-0/           ← Topic 名称 + Partition 编号
│   ├── 00000000000000000000.log       ← Segment 日志文件（追加写入）
│   ├── 00000000000000000000.index     ← 稀疏索引：offset → 文件位置
│   ├── 00000000000000000000.timeindex ← 时间索引：时间戳 → offset
│   ├── 00000000000000000102.log
│   ├── 00000000000000000102.index
│   └── ...
```

### Segment 滚动条件（满足其一）

1. `log.segment.bytes` 到了（默认 1GB，log segment 满了就滚动）
2. `log.roll.ms`（默认 168h = 7 天，时间到也滚动）
3. Broker 启动时：上一个 Segment 大于 `log.roll.jitter.ms`（默认 0）且当前时间与 segment 滚动时间差超过阈值 → 滚动
4. 新 Segment 第一个 offset 作为文件名前缀，比如 `00000000000000000102.log` 表示从 offset 102 开始

### Log 文件内部

每个 Segment 内部是一个或多个 RecordBatch（批量写入单元）：

```
RecordBatch:
  ├─ Offset        (8 bytes)  ← 内部相对 offset（Segment 内从 0 开始）
  ├─ BatchLength   (4 bytes)
  ├─ PartitionLeaderEpoch (4 bytes)
  ├─ Magic         (1 byte，版本号，v2 是 Kafka 3.x 标准)
  ├─ CRC           (4 bytes)
  ├─ Attributes    (2 bytes，压缩类型、事务标志)
  ├─ LastOffsetDelta (4 bytes)
  ├─ BaseTimestamp / MaxTimestamp (8 bytes each)
  ├─ ProducerId / Epoch / BaseSeq (事务/幂等 Producer 用)
  ├─ RecordsCount  (4 bytes)
  └─ Records[]     ← 每条 Record：length + offset + timestamp + key + value + headers
```

## 零拷贝（Zero-Copy / sendfile）

传统读磁盘文件的路径：

```
磁盘 → 内核 PageCache → 用户进程 Buffer → Socket Buffer → 网卡   ← 4 次拷贝，2 次系统调用
```

Kafka 用零拷贝：

```
磁盘 → 内核 PageCache ──→ 网卡                                   ← 2 次拷贝，1 次系统调用（sendfile）
                         ↑
                   DMA 直接从 PageCache 进网卡
```

Producer 写 Broker 时也走 PageCache（写磁盘其实是写 OS PageCache，由 OS 异步 flush 到磁盘）。所以 Kafka 对磁盘顺序写 + OS PageCache + 零拷贝的组合拳，才是吞吐百万级/s 的根本。

**⚠️ 注意**：零拷贝是 Broker → Consumer 的优势。Producer → Broker 还是走常规网络 IO。此外，开启压缩时（Producer 端），Broker 需要解压 → 检查 → 可能再压缩，这部分不走零拷贝。

## 稀疏索引

`00000000000000000000.index` 是一个稀疏索引（默认每 4KB record batch 建一个索引项），存储 `RelativeOffset → PhysicalPosition`（相对于 Segment 起点的文件偏移）。Consumer 从某个 offset 开始拉数据时：

1. 在 index 文件里二分查找目标 offset 附近的位置
2. 拿到物理文件位置 → 从 log 文件该位置开始顺序扫描（+ CRC 校验）
3. 找到精确 offset → 开始返回记录

稀疏索引之所以叫「稀疏」，是因为它不记录每个 offset 而只每隔一段记一个。好处：**占空间小**（约每 1GB log 文件只占约 1MB index 文件）；坏处：定位时要在 log 里顺序扫描一段。

## 磁盘顺序写优势

磁盘（特别是 HDD）顺序写比随机写快一个数量级：

| 操作 | HDD 延迟 | SSD 延迟 |
| --- | --- | --- |
| 随机写 | ~5-10ms | ~100-200µs |
| 顺序写 | ~100-200µs | ~100-200µs |

Kafka 的追加日志模型天然就是顺序写。Broker 把同一个 Partition 的生产请求追加到同一个 Segment 文件尾部，OS PageCache 把这些写合并、异步 flush，磁盘只看到连续的写流。

## 分区并行度与吞吐

Kafka 的吞吐几乎完全取决于**Partition 数**：

| 维度 | 规则 |
| --- | --- |
| Producer 并行度 | 可同时向 N 个 Partition 生产，互不影响 |
| Consumer 并行度 | Group 内最多 N 个 Consumer 各吃一个 Partition |
| Broker 并行读写 | 一个 Broker 可管几百上千个 Partition，每个都独立 Segment |
| ISR 同步 | Follower 从 Leader 拉 Partition 是并行的 |

**经验公式**：
- 写入吞吐 ≈ Broker 数量 × 每 Broker 磁盘顺序写能力（单盘 ~200MB/s）× 网络带宽
- 读取吞吐 ≈ Consumer Group 里 Consumer 数 × 每 Consumer 网卡带宽
- Partition 数 = Consumer Group 总吞吐量需求 / 单 Consumer 吞吐量

**⚠️ 陷阱**：
1. **Partition 不是越多越好**：每个 Partition 都有自己的 index/timeindex、Metadata、ISR 同步开销。一个 Broker 上 Partition 超过 2000 要小心。
2. **Partition 只能增不能减**：规划时就要算好。
3. **单 Partition 的顺序保证**：一个 Partition 内有序，跨 Partition 没有全局顺序。

## 副本同步机制

```
Leader 写 log 文件（追加到尾部）
    │
    ├─ Follower1 Fetch(offset=100) → 收到新消息 → 写自己的 Segment → 上报 lastOffset
    ├─ Follower2 Fetch(offset=101) → 收到新消息 → 写自己的 Segment → 上报 lastOffset
    └─ ISR 检查（Leader 定期）
        ├─ Follower1 lastCaughtUpTimeMs 还新鲜 → 留在 ISR
        └─ Follower2 落后太久 → 踢出 ISR（变 OSR）
```

`replica.lag.time.max.ms`（默认 30000）：Follower 在这个时间窗口内没追上 Leader 的最新 offset → 踢出 ISR。追上后自动加回。

### ack=all 的真实含义

```
Producer 发送 → Leader 落盘 → 等 ISR 所有副本（除 Leader？No，包括 Leader）都 sync 到这条 → 返回
                                                                 ↑
                                                              min.insync.replicas
```

如果 ISR 当前大小 < min.insync.replicas，**ack=all 直接返回 NOT_ENOUGH_REPLICAS 错误**——不让写。这是 Kafka 的安全底线。

## 压缩

Kafka 支持 Producer 端压缩、Broker 端原样存：

| 算法 | 压缩率 | 压缩速度 | decompress 速度 | 推荐场景 |
| --- | --- | --- | --- | --- |
| gzip | 好 | 慢 | 中 | CPU 充足，空间优先 |
| snappy | 中 | 快 | 极快 | 平衡，低延迟 |
| lz4 | 中 | 极快 | 极快 | 吞吐优先，推荐 |
| zstd | 极好 | 中 | 快 | 空间-时间综合最优，3.x 推荐 |

压缩粒度是 **RecordBatch**，Producer 端把一个批次压缩进一个 wrapper 再发；Broker 端原样存。Consumer 端拉到后解压，对业务透明。

## 关键 Broker 配置

| 配置 | 默认 | 含义 |
| --- | --- | --- |
| `log.dirs` | — | 日志目录（可多个，Broker 会把 Partition 均匀分到各目录） |
| `log.segment.bytes` | 1073741824 | Segment 大小（1GB） |
| `log.roll.ms` | 604800000 | 按时间滚动（7 天） |
| `log.retention.hours` | 168 | 保留时长（7 天），老 Segment 自动删 |
| `log.retention.bytes` | -1 | 按总大小保留上限，超了删最老 |
| `log.index.interval.bytes` | 4096 | 稀疏索引间隔 |
| `replica.lag.time.max.ms` | 30000 | ISR 踢出阈值 |
| `max.message.bytes` | 1048576 | 单条消息上限（1MB） |
| `compression.type` | producer | 压缩类型（默认 Producer 端决定） |
