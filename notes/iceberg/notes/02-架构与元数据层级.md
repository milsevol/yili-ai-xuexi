# 02 架构与元数据层级

## 一句话

Iceberg 的全部魔法都在**元数据层级**里：Catalog 只存一个指针 → 指向 `metadata.json` → 里面有 Snapshot 列表 → 每个 Snapshot 指向一个 **Manifest List** → Manifest List 指向若干 **Manifest File** → Manifest 里记录每个 **Data File** 的路径、分区和统计信息。查询时逐层裁剪，最终只 open 真正需要的文件。

## 为什么要设计这么多层

如果把「表里有哪些文件」写成一个 JSON：表有 1000 万文件时这个 JSON 会有几个 GB，每次查询都要全量读，每次写入都要重写，无法并行。

Iceberg 的解法是**分层 + 不可变 + 分片**：

| 层级 | 单元 | 作用 | 规模 |
| --- | --- | --- | --- |
| 0 | Catalog 指针 | `db.tbl → metadata/v3.metadata.json` | 1 条 |
| 1 | Metadata File | Schema、分区 spec、快照列表、表属性 | KB 级 |
| 2 | Manifest List | 本次快照的 Manifest 清单 + 分区摘要 | 几十 KB ~ MB |
| 3 | Manifest File | 一批 Data File 的路径、分区、列统计 | 每个几 MB |
| 4 | Data File | 真正的数据 | 128MB 左右 |

上层只存「下一层的清单」，所以每层都很小；读取按需下钻，天然可并行。

## 五层结构详解

### 第 0 层：Catalog

Catalog 的职责只有一个：**维护「表名 → 当前 metadata.json 路径」的映射，并提供原子替换（CAS）**。

```
hive_metastore: default.orders
  └── table_params['metadata_location'] = s3://wh/db/orders/metadata/00003-xxx.metadata.json
```

Catalog **不存** Schema、不存文件列表，只存指针。这是 Iceberg 能同时支持 Hive Metastore / REST / Glue / Nessie 的关键。

### 第 1 层：Metadata File（`metadata.json`）

一份 JSON，是「表在某一时刻的完整定义」：

```json
{
  "format-version": 2,
  "location": "s3://wh/db/orders",
  "last-column-id": 8,
  "schemas": [ { "schema-id": 1, "fields": [ ... ] } ],
  "current-schema-id": 1,
  "partition-specs": [ { "spec-id": 0, "fields": [ { "name": "ts_day", "transform": "day", "source-id": 4 } ] } ],
  "default-spec-id": 0,
  "current-snapshot-id": 3051729675574597004,
  "snapshots": [
    { "snapshot-id": 3051729675574597004, "sequence-number": 12,
      "timestamp-ms": 1730000000000, "manifest-list": ".../snap-30517-1-xxx.avro",
      "summary": { "operation": "append", "added-data-files": "2" } }
  ],
  "snapshot-log": [ { "timestamp-ms": 1730000000000, "snapshot-id": 3051729675574597004 } ],
  "metadata-log": [ { "timestamp-ms": 1729999999000, "metadata-file": ".../00002-xxx.metadata.json" } ]
}
```

| 字段 | 含义 | 为什么重要 |
| --- | --- | --- |
| `format-version` | 1 / 2 / 3 | 决定是否支持行级删除 |
| `schemas` + `current-schema-id` | 所有历史 Schema | Schema 演进靠它保留列 ID |
| `partition-specs` + `default-spec-id` | 所有历史分区 spec | 分区演进靠它，每个 spec 独立存在 |
| `current-snapshot-id` | 当前快照 | 查询入口 |
| `snapshots` | 快照列表 | Time Travel 基础 |
| `snapshot-log` | 快照提交时间线 | `TIMESTAMP AS OF` 用它定位 |
| `metadata-log` | 历史 metadata 文件 | 元数据自身可回溯 |

**每次提交都写一份新的 metadata.json**（文件名带递增版本号），旧文件不删，保证任何时刻读到一致视图。

### 第 2 层：Manifest List（`snap-*.avro`）

一个 Avro 文件，每个 Snapshot 一份，内容是「这个快照包含哪些 Manifest，以及每个 Manifest 的分区范围摘要」。

```
Manifest List (snap-30517-1-xxx.avro)
┌─────────────────────────────────────────────────────────┐
│ manifest_path             added_snapshot_id  partition  │
│ .../m0.avro               30517...           ts_day=... │
│ .../m1.avro               30517...           ts_day=... │
└─────────────────────────────────────────────────────────┘
```

意义是**第一层裁剪**：查询 `WHERE ts >= '2026-11-01'` 时先读它，根据分区摘要直接跳过不相关的 Manifest。它还区分 `added`/`existing`/`deleted`，用于增量读取。

### 第 3 层：Manifest File（`*-m0.avro`）

一个 Avro 文件，记录**一批 Data File 的元信息**：

```
Manifest File (xxx-m0.avro)
┌──────────────────────────────────────────────────────────────────────────┐
│ status │ file_path                        │ partition          │ records │
│ ADDED  │ data/ts_day=2026-11-01/f1.parquet│ {day: 2026-11-01}  │ 120000  │
│ ADDED  │ data/ts_day=2026-11-01/f2.parquet│ {day: 2026-11-01}  │  98000  │
│ DELETED│ data/.../f0.parquet              │ {day: 2026-10-31}  │  50000  │
└──────────────────────────────────────────────────────────────────────────┘
```

每个 entry 包含：

- `status`：0=EXISTING，1=ADDED，2=DELETED
- `data_file`：路径、格式、大小、记录数、分区值、所属 snapshot
- `lower_bounds` / `upper_bounds`：**每列的 min/max（序列化后的字节）**
- `null_value_counts` / `value_counts`：null 数量与总数量

这就是**第二层裁剪**：即使 Manifest 被选中，也能根据 Data File 的 min/max 再跳过一批文件。

### 第 4 层：Data File

真正的列式文件（Parquet / ORC / Avro），路径形如 `data/ts_day=2026-11-01/00000-0-xxx.parquet`。

## Snapshot 快照

**Snapshot = 一次提交产生的「表状态」**，只读，包含：唯一 `snapshot-id`、单调递增的 `sequence-number`、`timestamp-ms`、`manifest-list` 路径、`summary`（operation + 增删文件数）。

```
Snapshot 1 (append 2 files) → Snapshot 2 (delete 1 file) → Snapshot 3 (append 5 files)
      │                            │                            │
   m0.avro                      m0.avro                      m0.avro
   m1.avro                      m1.avro (旧)                 m1.avro (旧)
                                m2.avro (新)                 m2.avro (旧)
                                                             m3.avro (新)
```

**Snapshot 之间共享未被修改的 Manifest**：Snapshot 3 复用 m0/m1/m2，只新增 m3。这就是 Iceberg 提交快、存储省的原因。

## 表版本与元数据演进

| 层面 | 载体 | 变化频率 |
| --- | --- | --- |
| 表定义版本 | `metadata.json` 文件名递增 | 每次 Schema / Spec / 属性变更 |
| 数据版本 | Snapshot（snapshot-id） | 每次写入 / 删除 |

一次写入的完整提交流程：

```
1. 写新的 Data File（Parquet）到 data/ 目录
2. 写新的 Manifest File（记录这些 Data File）
3. 写新的 Manifest List（引用新 Manifest + 旧 Manifest）
4. 写新的 metadata.json（current-snapshot-id 指向新 Snapshot）
5. Catalog CAS：把表指针从 v2.metadata.json 换成 v3.metadata.json  ← 原子提交点
```

第 5 步是唯一的「提交点」：成功才可见，失败则前面文件都是垃圾（后续 GC）。这就是原子性来源。

## Catalog 类型对比

| Catalog | 实现 | 优点 | 缺点 | 适用 |
| --- | --- | --- | --- | --- |
| **Hive Metastore** | `type=hive` | 已有设施、多引擎支持、稳 | 依赖 HMS；不支持多表原子提交 | 传统 Hadoop 体系 |
| **REST** | `type=rest` | 标准化、解耦、支持 OAuth | 需部署服务 | 云原生、多租户 |
| **JDBC** | `type=jdbc` | 简单，元数据存 MySQL/PG | 单点、性能一般 | 测试 / 小规模 |
| **Nessie** | `type=nessie` | Git 式分支/合并、跨表事务 | 额外组件 | 数据版本化 |
| **AWS Glue** | `type=glue` | AWS 原生、Serverless | 绑定 AWS | AWS 数据湖 |
| **Hadoop** | `type=hadoop` | 零依赖 | 无并发控制（单写者） | 本地开发 |

```properties
# Hive Metastore
spark.sql.catalog.ice=org.apache.iceberg.spark.SparkCatalog
spark.sql.catalog.ice.type=hive
spark.sql.catalog.ice.uri=thrift://hms1:9083
spark.sql.catalog.ice.warehouse=s3://bucket/warehouse
spark.sql.extensions=org.apache.iceberg.spark.extensions.IcebergSparkSessionExtensions

# REST Catalog
spark.sql.catalog.ice.type=rest
spark.sql.catalog.ice.uri=https://catalog.example.com
spark.sql.catalog.ice.credential=client-id:client-secret
```

## 关键配置

```properties
# ============ 元数据文件管理 ============
write.metadata.delete-after-commit.enabled=true    # 提交后删旧 metadata
write.metadata.previous-versions-max=100           # 保留 100 个历史 metadata

# ============ Manifest 大小 ============
commit.manifest.target-size-bytes=8388608          # 单个 manifest 目标 8MB
commit.manifest-merge.enabled=true                 # 提交时自动合并小 manifest

# ============ 快照管理 ============
history.expire.max-snapshot-age-ms=604800000       # 7 天
```

## 常见问题

**Q：查一张表要读这么多文件，不会很慢吗？**
A：每层都很小且带裁剪信息。查 1 天数据可能只读 1 个 metadata.json（几 KB）+ 1 个 manifest list（几十 KB）+ 1~2 个 manifest（几 MB），跳过 99% 文件。

**Q：metadata.json 会不会无限增长？**
A：`snapshots` 和 `metadata-log` 会累积。靠 `expire_snapshots` 清理快照、`delete-after-commit` + `previous-versions-max` 清理旧 metadata。

**Q：Manifest 和 Manifest List 的区别？**
A：Manifest List 是「Manifest 的清单」（一层索引），Manifest 是「Data File 的清单」（二层索引）。

**Q：Catalog 挂了还能查表吗？**
A：已拿到 `metadata_location` 的查询可继续，但新查询必须经过 Catalog，所以它是可用性依赖，生产要 HA。

**Q：能绕过 Catalog 直接查 metadata.json 吗？**
A：可以，用于排障：`spark.read.format("iceberg").load("s3://.../metadata/v3.metadata.json")`。
