# 03 表格式与文件组织

## 一句话

Iceberg 只规定「表怎么组织」，不规定「文件怎么存」——数据文件可以是 **Parquet / ORC / Avro**，加上 **Manifest（文件级元数据）** 与 **Delete File（行级删除）** 共同构成一张表；文件级的 `min/max/null_count` 统计信息是查询裁剪的核心武器。

## 为什么要把「数据文件」和「元数据文件」分开

Hive 表把「分区 = 目录」当作唯一索引，除了目录名没有任何文件级信息。查询时只能列出分区目录、打开每个文件读 footer、自己判断要不要读。

Iceberg 把「需要打开文件才能知道的信息」提前写进 Manifest：

| 信息 | Hive 需要 | Iceberg 需要 |
| --- | --- | --- |
| 文件路径 | list 目录 | 读 Manifest（一次顺序读） |
| 记录数 | open 文件读 footer | Manifest 里直接有 |
| 列 min/max | open 文件读 footer | Manifest 里直接有 |
| null 数量 | open 文件读 footer | Manifest 里直接有 |
| 所属分区 | 靠目录名 | Manifest 里显式记录 |
| 列类型 | 靠表 Schema | Manifest 里记录字段 ID |

**结论**：Iceberg 把「打开 10000 个文件」变成「读 1 个 Manifest」，这是数量级的差异。

## 三种数据文件格式

### Parquet（默认，最常用）

结构：`Row Group → Column Chunk`，Footer 记录 Schema 与每列每 RG 的统计信息。

- 列式、压缩率高（zstd/snappy），每个 Row Group 有列统计
- Spark / Flink / Trino / Hive 全都原生支持
- **Iceberg 默认格式，90% 生产表都用它**

### ORC（Hive 生态友好）

- 结构类似（Stripe 代替 Row Group），Hive 原生优化好
- 内置 Bloom Filter、索引更丰富
- 纯 Hive 环境迁移方便，但其他引擎的 ORC 读写路径测试较少

### Avro（行式，特殊场景）

- 行式存储，写入快、全表扫描慢
- 适合小文件、元数据文件（Manifest 本身是 Avro）、流式暂存
- 不适合分析型大表

```sql
CREATE TABLE t (...) USING iceberg
TBLPROPERTIES ('write.format.default' = 'parquet');   -- 可选 orc / avro
```

## Manifest 文件结构

Manifest 是 Avro 文件，**每一行是一个 Data File 的条目**：

```
$ java -jar avro-tools.jar tojson metadata/xxx-m0.avro
{
  "status": 1,                                  // 1=ADDED, 0=EXISTING, 2=DELETED
  "data_file": {
    "content": 0,                               // 0=DATA, 1=POS, 2=EQUALITY DELETE
    "file_path": "s3://wh/db/orders/data/ts_day=2026-11-01/00000-0-xxx.parquet",
    "partition": { "ts_day": 20028 },           // day 转换后的天数
    "record_count": 120000,
    "file_size_in_bytes": 134217728,
    "value_counts": { "1": 120000, "2": 120000 },
    "null_value_counts": { "1": 0, "2": 15 },
    "lower_bounds": { "1": "0000000000000001", "2": "9a9999999999b93f" },
    "upper_bounds": { "1": "000000000000270f", "2": "3d0ad7a370fd9f40" }
  }
}
```

容易忽略的点：

- `lower_bounds` / `upper_bounds` 是**序列化后的字节**，不是可读字符串
- `partition` 是转换后的值（`day` → 从 1970-01-01 起的天数）

## 列级统计信息如何加速查询

假设 1000 个 Data File：

```sql
SELECT SUM(amount) FROM orders
WHERE ts >= TIMESTAMP '2026-11-01 00:00:00'
  AND order_id BETWEEN 1000 AND 2000;
```

```
第 1 步：Manifest List 裁剪
  每个 Manifest 记录分区范围 → 跳过 ts_day < 2026-11-01 的
  100 个 Manifest 只剩 3 个

第 2 步：Manifest 内 Data File 裁剪
  对每个文件检查 partition、lower/upper_bounds(ts)、lower/upper_bounds(order_id)
  → 1000 个文件只剩 30 个

第 3 步：文件内 Row Group 裁剪
  Parquet 每个 Row Group 也有 min/max → 只读少量 Row Group
```

从「读 1000 × 128MB = 128GB」变成「约 1GB」，两个数量级。

### 统计信息的边界

| 场景 | 效果 |
| --- | --- |
| 数值 / 日期 / 时间戳 | ✅ min/max 精确 |
| 短字符串 | ✅ 按字典序比较，效果尚可 |
| 超长字符串 | ⚠️ 默认截断 16 字节，可能误判 |
| 高基数列（UUID） | ⚠️ 范围查询有用，等值查询帮助有限 |
| 未收集统计的列 | ⚠️ 无法裁剪 |

```properties
write.metadata.metrics.default=truncate(16)      # 默认：数值 full，字符串截断 16
write.metadata.metrics.column.order_id=full      # 指定列全量统计
write.metadata.metrics.column.trace_id=none      # 高基数列不收集
```

## Data File 与 Delete File

Iceberg v2 引入两种文件：

```
content = 0   DATA FILE       真正的数据（Parquet/ORC/Avro）
content = 1   POSITION DELETE 按「文件路径 + 行号」删除
content = 2   EQUALITY DELETE 按「列值」删除（如 id=1001）
```

`DELETE FROM t WHERE id = 1001` 在不可变文件上有两种实现：

| 模式 | 做法 | 写 | 读 | 适用 |
| --- | --- | --- | --- | --- |
| **COW** | 重写受影响的整个 Data File | 慢（写放大） | 快 | 读多写少、批量修正 |
| **MOR** | 写 delete file，查询时合并 | 快 | 慢（要 merge） | 高频 CDC、流式 Upsert |

```sql
ALTER TABLE orders SET TBLPROPERTIES ('write.delete.mode' = 'merge-on-read');
ALTER TABLE orders SET TBLPROPERTIES ('write.update.mode' = 'merge-on-read');
ALTER TABLE orders SET TBLPROPERTIES ('write.merge.mode' = 'merge-on-read');
```

MOR 的代价是 delete file 累积，需要定期 compaction（第 09 章）。

## 元数据文件大小与规划

| 文件 | 典型大小 | 数量级 | 规划建议 |
| --- | --- | --- | --- |
| metadata.json | 几 KB ~ 几十 KB | 每次提交 +1 | 开 `delete-after-commit` |
| manifest list | 几十 KB ~ 几 MB | 每快照 1 个 | 快照多了会累积 |
| manifest | 1 ~ 10 MB | 每 ~1000 文件 1 个 | 控制 `target-size-bytes` |
| data file | 128 MB（默认） | 表大小 / 128MB | `write.target-file-size-bytes` |

经验值：

- **100 万文件**：约 1000 个 Manifest，元数据读取开销可接受
- **1000 万文件**：必须 `rewrite_manifests`，否则元数据成为瓶颈

## 表目录长什么样

```
s3://bucket/warehouse/db/orders/
├── data/ts_day=2026-11-01/00000-0-9f1c...-00001.parquet
└── metadata/
    ├── 00002-7d4a....metadata.json   ← 当前版本（指针指向它）
    ├── snap-30517-1-9f1c....avro     ← manifest list
    └── 9f1c...-m0.avro               ← manifest
```

> `version-hint.text` 只在 Hadoop Catalog 下存在，只是「最新版本号提示」，**不是**原子提交机制。

## 关键配置

```properties
# ============ 数据文件格式与大小 ============
write.format.default=parquet
write.parquet.compression-codec=zstd
write.target-file-size-bytes=134217728

# ============ 统计信息 ============
write.metadata.metrics.default=truncate(16)
write.metadata.metrics.column.order_id=full

# ============ Delete 模式 ============
write.delete.mode=copy-on-write
write.update.mode=copy-on-write
write.merge.mode=copy-on-write

commit.manifest.target-size-bytes=8388608
```

## 常见问题

**Q：Manifest 里的统计信息会不会让元数据变得很大？**
A：会，但可控。每列约 40~60 字节，1000 文件 × 20 列 ≈ 1MB。列特别多或字符串很长时，按列配置 `none`。

**Q：为什么查询没有命中 min/max 裁剪？**
A：① 查询列没收集统计；② 字符串截断导致边界放宽；③ 表达式非单调（`substr`、`lower`）；④ 分区层已筛掉。

**Q：Delete File 会不会一直累积？**
A：会。MOR 下每次 DELETE/UPDATE 都产生新 delete file，需要 `rewrite_data_files` 合并。

**Q：Data File 一定要 128MB 吗？**
A：不是。点查偏多可调小，批量 ETL 可调到 256~512MB。关键是避免 < 32MB。
