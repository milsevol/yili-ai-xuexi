# 01 概述与湖仓一体

## 一句话

Apache Iceberg 是**构建在数据湖存储之上的开放表格式**——它不存数据、不跑计算，只用一层「元数据树 + 快照」让对象存储上的 Parquet/ORC 文件拥有数据库语义：**ACID、Schema 演进、隐藏分区、Time Travel、多引擎并发读**，是「湖仓一体」的事实标准之一。

## 为什么需要「湖仓一体」

企业数据平台长期被两套系统撕裂：

| | 数据仓库 | 数据湖 |
| --- | --- | --- |
| 存储 | 专有格式 | 开放文件（Parquet/ORC/CSV） |
| Schema | Schema-on-Write | Schema-on-Read |
| 事务 | 完整 ACID | 几乎没有 |
| 成本 | 高 | 低（对象存储） |
| 数据质量 | 高 | 低（小文件、重复数据） |

于是出现「两套数据、两份 ETL、两套口径」：湖里放一份给算法，仓里放一份给 BI，中间靠 T+1 同步搬运。

**湖仓一体（Lakehouse）** 想在廉价对象存储上直接实现数仓能力，技术拼图是三块：

```
湖仓一体 = 开放文件格式（Parquet/ORC）
         + 开放表格式（Iceberg / Hudi / Delta / Paimon）   ← 本文主题
         + 多引擎计算（Spark / Flink / Trino / StarRocks ...）
```

「开放表格式」是关键一层：它把「一堆文件」升级成「一张有事务、有版本、可演进的表」。

## 三代架构对比

| 维度 | 数据湖（Hive 表） | 数据仓库 | 湖仓一体（Iceberg） |
| --- | --- | --- | --- |
| 存储成本 | 低 | 高 | 低 |
| 存算分离 | ✅ | ❌（耦合） | ✅ |
| ACID | ❌（Hive ACID 限制多） | ✅ | ✅（快照隔离） |
| 行级 UPDATE/DELETE | ❌ | ✅ | ✅（MOR） |
| Schema 演进 | 有限 | 有限 | ✅（列 ID） |
| 分区演进 | ❌（要重写） | 有限 | ✅（隐藏分区） |
| Time Travel | ❌ | 部分 | ✅ |
| 多引擎 | 有限 | ❌ | ✅（Spark/Flink/Trino/Hive） |
| 开放程度 | 高（裸文件） | 低（专有格式） | 高（规范公开） |

一句话：**湖仓一体 = 数据湖的成本 + 数据仓库的体验**。

## Hive 表的四大痛点

### 痛点一：没有 ACID，不能行级改数据

Hive 表本质是「目录 + 文件」，HDFS 只追加不能原地改。所以：

- `UPDATE`/`DELETE` 只能 `INSERT OVERWRITE` 整分区重写
- 并发写没有隔离，两个任务写同一分区，文件混在一起，数据重复或丢失
- 任务失败留下半成品文件，下游读到脏数据
- 查询被覆盖时，可能读到「部分旧 + 部分新」的撕裂结果

Hive 3.x 的 ACID 表是补丁：必须 ORC、必须分桶、只能单分区操作，生态兼容差。

### 痛点二：分区演进难，改分区要重写全表

Hive 分区是**物理目录**（`dt=2026-11-01/hour=10/`），带来三个硬伤：

- **改分区粒度 = 重写数据**：从按天改按小时，历史数据要全部重读重写
- **分区字段是数据列**：查询必须写 `WHERE dt='...'`，SQL 与物理布局强耦合
- **分区过多炸元数据**：`dt × hour × province` 笛卡尔积，几百万分区，`SHOW PARTITIONS` 都卡死

### 痛点三：小文件问题

流式写入或高频微批会产出海量小文件，一天几十万个 3KB 文件。Hive 没有内建合并机制，NameNode 压力大、查询 open 开销大，只能离线 `INSERT OVERWRITE` 重写。

### 痛点四：没有 Time Travel

Hive 表只有「当前状态」，覆盖写之后永远回不去。复盘写坏数据、对比今昨版本、审计谁改了什么，全都做不到，只能每天全量备份。

## Iceberg 是什么

**Iceberg 不是数据库，不是计算引擎，而是一份「表格式规范」+ 多语言实现。**

```
一张 Iceberg 表 = 数据文件（Parquet/ORC/Avro）
              + 元数据文件（metadata.json）
              + 清单列表（manifest list）
              + 清单文件（manifest）
              + Catalog 中的指针（指向当前 metadata.json）
```

它定义「文件怎么组织、元数据怎么写、快照怎么切、并发怎么控」。只要按规范写表，任何实现规范的引擎都能正确读写——这就是「开放」。

```sql
CREATE TABLE local.db.orders (
  order_id BIGINT,
  user_id  BIGINT,
  amount   DECIMAL(12,2),
  ts       TIMESTAMP
) USING iceberg
PARTITIONED BY (days(ts))          -- 隐藏分区：按天，但表里没有 dt 列
TBLPROPERTIES ('format-version' = '2');
```

注意 `PARTITIONED BY (days(ts))`：分区由转换函数派生，业务表只有 `ts`，没有 `dt`。

## Iceberg vs Hudi vs Delta Lake

| 维度 | Iceberg | Hudi | Delta Lake |
| --- | --- | --- | --- |
| 起源 | Netflix 2018 → Apache | Uber 2016 → Apache | Databricks 2019 |
| 元数据 | 元数据树 + Manifest | Timeline（instant 序列） | `_delta_log` JSON |
| 写入模式 | COW + MOR（v2 delete file） | COW + MOR（最成熟） | 主要 COW（Deletion Vector 补 MOR） |
| 索引 | 分区 + 列统计 + 可选 sort/Z-order | 布隆、HFile、Record 索引 | 分区 + 列统计 + Z-Order |
| 流式写入 | Flink 支持好（1.5+） | 最强（Upsert 原生） | Spark Structured Streaming 好 |
| 多引擎 | 最广 | 较广 | Spark 最好 |
| 隐藏分区 | ✅ | ❌ | ❌ |
| 分区演进 | ✅ 不重写 | 有限 | 有限 |
| Schema 演进 | ✅ 列 ID | ✅ | ✅（column mapping） |
| 最擅长 | 通用开放 + 多引擎 | CDC Upsert + 增量拉取 | Databricks/Spark 一体 |

## 为什么 Iceberg 成为事实标准

### 1. 开放：规范公开，实现众多

表格式规范写在官网，任何人可实现。已有 Java、Python（PyIceberg）、Rust、Go、C++ 多套实现。对比 Delta 早期把核心能力锁在 Databricks Runtime，Iceberg 的开放性是云厂商广泛接纳的根本原因。

### 2. 引擎无关：一份数据，所有引擎都认

同一张表可以：Spark 批量 ETL、Flink 实时写入、Trino 交互查询、Hive 4 只读、StarRocks/Doris 做 OLAP、Snowflake/BigQuery 外部表读取。元数据在共享 Catalog，各引擎自己实现读取逻辑。

### 3. 隐藏分区：SQL 不再关心物理布局

```sql
-- Iceberg：业务列 ts，自动按天裁剪
SELECT * FROM orders WHERE ts >= TIMESTAMP '2026-11-01 00:00:00';

-- Hive：必须显式写分区列
SELECT * FROM orders WHERE dt = '2026-11-01';
```

分区策略可随时改（按天→按小时/bucket），历史数据不用重写。

### 4. 元数据树设计，天然支持大规模

不用中心事务日志，而是**不可变元数据树 + 原子指针切换**：支撑千万级文件、PB 级表、秒级提交、并发写乐观锁。

## 典型落地架构

```
   Spark（批 ETL）  Flink（实时 CDC）  Trino（交互查询）  StarRocks（OLAP）
              └──────────────┬──────────────┘
                   Iceberg 表格式（元数据 + 快照）
              ┌──────────────┴──────────────┐
   Hive Metastore / REST / Glue / Nessie    对象存储（S3/OSS/HDFS）
              （Catalog，只存指针）          （Parquet/ORC 数据文件）
```

## 关键配置

```properties
# ============ 表级别（TBLPROPERTIES） ============
format-version=2                       # 1=基础，2=行级删除，3=新类型（1.6+ 实验）
write.parquet.compression-codec=zstd
write.target-file-size-bytes=134217728 # 目标 128MB
write.metadata.delete-after-commit.enabled=true
write.metadata.previous-versions-max=100

# ============ Catalog（Spark 示例） ============
spark.sql.catalog.local=org.apache.iceberg.spark.SparkCatalog
spark.sql.catalog.local.type=hive
spark.sql.catalog.local.uri=thrift://hms:9083
spark.sql.catalog.local.warehouse=s3://bucket/warehouse

# ============ 快照保留 ============
history.expire.max-snapshot-age-ms=604800000   # 7 天
```

## 常见问题

**Q：Iceberg 是数据库吗？需要单独部署服务吗？**
A：不是数据库，是表格式规范 + 库。没有「Iceberg Server」，运行时是各引擎的一个 jar；Catalog 可复用 Hive Metastore，也可独立部署 REST Catalog。

**Q：用了 Iceberg 还需要 Hive Metastore 吗？**
A：不一定，但常见。Hive Metastore 只是 Catalog 的一种实现（`type=hive`），也可以选 REST / JDBC / Nessie / Glue / Hadoop。

**Q：Iceberg 会替换 Parquet 吗？**
A：不会。Iceberg 是**表格式**，Parquet 是**文件格式**。Iceberg 表的数据文件默认就是 Parquet。

**Q：Hive 表能直接转 Iceberg 吗？**
A：可以，`CALL local.system.migrate('db.tbl')` 原地把 Hive 表元数据切换成 Iceberg 格式，数据文件不动。

**Q：Iceberg 表的数据存在哪里？**
A：`warehouse/库名/表名/` 下，包含 `data/`（数据文件）和 `metadata/`（元数据、manifest、快照）。
