# 09 性能优化与实践

## 一句话

Iceberg 的性能优化可以浓缩成两句话：**写入端控制文件大小与布局（避免小文件、选对分区），读取端榨干统计信息（分区裁剪 + 文件裁剪 + 列裁剪）**；再配一套定期的表维护（compaction / rewrite_manifests / expire_snapshots），让表长期保持健康。

## 写入端：文件大小是第一优先级

### 小文件的代价

```
128MB 目标文件 vs 128 个 1MB 小文件：
  读取：128 次 open + footer 解析 + 网络 RTT
  元数据：128 个 Manifest entry vs 1 个
  任务：128 个 task 启动
```

| 文件大小 | 评价 |
| --- | --- |
| < 32MB | ❌ 小文件，必须合并 |
| **128 ~ 256MB** | ✅ 推荐区间 |
| > 512MB | ⚠️ 太大，任务并行度不足 |

```properties
# 目标文件大小（默认 128MB）
write.target-file-size-bytes=134217728
write.parquet.row-group-size-bytes=134217728
write.parquet.page-size-bytes=1048576

# 写入分发模式：按分区键 shuffle，避免单 task 写爆
write.distribution-mode=hash
```

### Compaction：rewrite_data_files

```sql
CALL ice.system.rewrite_data_files(
  table => 'db.orders',
  strategy => 'binpack',
  options => map(
    'target-file-size-bytes', '134217728',
    'min-input-files', '5',
    'max-concurrent-file-group-rewrites', '5'
  )
);

-- 只合并指定分区（避免全表扫描）
CALL ice.system.rewrite_data_files(
  table => 'db.orders',
  where => "ts_day >= '2026-10-01'"
);
```

| 策略 | 做什么 | 代价 | 适用 |
| --- | --- | --- | --- |
| `binpack` | 按大小装箱合并 | 中 | 通用小文件治理 |
| `sort` | 合并 + 按列排序 | 高 | 范围查询多、需要聚簇 |
| `zorder` | 合并 + 多维 Z-Order | 高 | 多列组合查询 |

**频率**：实时表每天一次；离线表每周一次；小表按需。

## 元数据端：避免 Manifest 膨胀

```
查询变慢但数据量没变？
  → SELECT count(*) FROM db.orders.manifests;  超过 1 万就要 rewrite_manifests
```

```sql
-- 合并碎片化的小 Manifest、清理已删除 entry
CALL ice.system.rewrite_manifests(table => 'db.orders', use_caching => true);

-- 快照过期（保留 7 天 / 至少 10 个）
CALL ice.system.expire_snapshots(
  table => 'db.orders',
  older_than => TIMESTAMP '2026-10-28 00:00:00',
  retain_last => 10
);

-- 孤儿文件清理（写入失败留下的垃圾）
CALL ice.system.remove_orphan_files(
  table => 'db.orders',
  older_than => TIMESTAMP '2026-10-25 00:00:00'
);
```

## 分区策略选择

```
分区数 ≈ 时间分区数 × 业务维度基数
例：3 年按天 1095 × province 34 = 37230 个分区  ⚠️ 偏多
```

| 原则 | 说明 |
| --- | --- |
| 单分区 1~10GB | 太小 → 文件碎；太大 → 裁剪粗 |
| 分区总数 < 10 万 | 否则元数据开销明显 |
| 优先时间分区 | 绝大多数分析都有时间条件 |
| 高基数用 bucket | 不要用 `identity(user_id)` |
| 避免多级时间 | `days × hours` 通常没必要 |
| 小表不分区 | < 10GB 的表分区反而添乱 |

决策树：<10GB 不分区；10GB~1TB 用 `days(ts)`（按业务维度再加 truncate/bucket）；>1TB 按单日数据量选 `days(ts)` / `hours(ts)`，单日 >100GB 再叠 bucket。

## 排序与 Z-Order

分区只能按分区列裁剪；分区内部的列顺序决定 Parquet Row Group 的 min/max 是否有区分度。

```
未排序：Row Group 0~2 的 id 都是 [1, 9999] → 无法跳过
按 id 排序后：RG0 [1,1000]、RG1 [1001,3000] → 查 id=500 只读 RG0
```

```sql
-- 单列排序（适合范围查询）
CALL ice.system.rewrite_data_files(table => 'db.orders', strategy => 'sort',
  sort_order => 'amount DESC NULLS LAST');

-- Z-Order（多列组合查询）
CALL ice.system.rewrite_data_files(table => 'db.orders', strategy => 'zorder',
  zorder_columns => 'user_id, amount, ts');

ALTER TABLE db.orders WRITE ORDERED BY (user_id, ts);   -- 1.4+ 写入自动聚簇
```

注意：

- Z-Order 写入成本高，适合「读多写少」与多列组合查询
- Z-Order 列不宜超过 3~4 个（维度越多，局部性越差）

## 读取端优化

| 层级 | 依赖 | 关键动作 |
| --- | --- | --- |
| 分区裁剪 | partition spec + Manifest List | 查询写业务列、用范围条件 |
| 文件裁剪 | Manifest 里的 min/max/null_count | 保证统计信息收集 |
| 行组裁剪 | Parquet Row Group 统计 | 文件内排序 / Z-Order |

```properties
# 默认：数值 full，字符串截断 16 字节
write.metadata.metrics.default=truncate(16)
write.metadata.metrics.column.order_id=full     # 关键过滤列全量统计
write.metadata.metrics.column.trace_id=none     # 高基数列不收集
```

```sql
-- ❌ SELECT * 会读所有列；函数包裹会破坏裁剪
SELECT * FROM db.orders WHERE DATE_FORMAT(ts, 'yyyy-MM-dd') = '2026-11-01';

-- ✅ 只读需要的列 + 直接用列做范围条件
SELECT order_id, amount FROM db.orders
WHERE ts >= TIMESTAMP '2026-11-01 00:00:00' AND ts < TIMESTAMP '2026-11-02 00:00:00';
```

## 表维护最佳实践

| 任务 | 频率 | 作用 |
| --- | --- | --- |
| `rewrite_data_files`（binpack） | 每天 / 每周 | 合并小文件、清理 delete file |
| `rewrite_data_files`（sort/zorder） | 每周 / 每月 | 优化聚簇 |
| `rewrite_manifests` | 每周 | 合并 manifest、清理 entry |
| `expire_snapshots` | 每天 | 清理旧快照，释放元数据 |
| `remove_orphan_files` | 每周 | 清理垃圾文件 |

**顺序不能反**：

```
rewrite_data_files → rewrite_manifests → expire_snapshots → remove_orphan_files
```

先过期快照再合并，可能把 compaction 还需要读的文件删掉。

### 监控指标

健康值：平均文件 > 64MB、Manifest < 1 万、快照 < 100、delete file 占比 < 10%。用 `db.orders.files / manifests / snapshots` 元数据表定期检查。

## 一个完整的调优案例

Flink 实时写入导致 12000 个 2MB 小文件、8600 个快照、15000 个 manifest。优化：checkpoint 30s→120s、`distribution-mode=hash`、每天 compaction、每天 expire、每周 rewrite_manifests。结果：文件 180 个 / 平均 128MB，查询 P99 45s→3s。

## 关键配置

```properties
# ============ 写入与统计 ============
write.target-file-size-bytes=134217728
write.distribution-mode=hash
write.parquet.compression-codec=zstd
write.metadata.metrics.default=truncate(16)

commit.manifest.target-size-bytes=8388608
write.metadata.delete-after-commit.enabled=true
write.metadata.previous-versions-max=100
history.expire.max-snapshot-age-ms=259200000    # 3 天
history.expire.min-snapshots-to-keep=10
```

## 常见问题

**Q：compaction 会不会影响正在跑的查询？**
A：不会。compaction 写新文件、提交新快照，旧快照仍然可读。但会消耗 IO/CPU，建议低峰期跑。

**Q：Z-Order 和普通 sort 怎么选？**
A：单列范围查询用 `sort`；多列组合（如 `user_id + ts`）用 `zorder`；不确定就先 `binpack`，再根据慢查询分析。
