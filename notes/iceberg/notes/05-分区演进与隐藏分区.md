# 05 分区演进与隐藏分区

## 一句话

Iceberg 的**隐藏分区（Hidden Partitioning）**把分区从「用户必须写的物理列」变成「引擎按转换函数自动计算的物理布局」：表里只有业务列 `ts`，分区由 `days(ts)` 派生；**分区 spec 可以随时演进（新增/删除/重命名/换转换函数），历史数据不用重写**，查询仍能自动裁剪。

## Hive 分区 vs Iceberg 隐藏分区

### Hive：分区 = 物理目录 + 显式列

```sql
CREATE TABLE orders (order_id BIGINT, amount DECIMAL(12,2))
PARTITIONED BY (dt STRING);       -- dt 是表的一列，也是目录名

INSERT INTO orders PARTITION (dt='2026-11-01') SELECT ...;
SELECT * FROM orders WHERE dt = '2026-11-01';
```

问题：

- `dt` 是**数据的一部分**，浪费存储，还要保证写入正确
- 改分区粒度（天→小时）→ 目录结构变了，历史数据得全部重写
- 分区字段与业务语义耦合，SQL 不可移植

### Iceberg：分区 = 派生值 + 元数据

```sql
CREATE TABLE orders (
  order_id BIGINT,
  amount   DECIMAL(12,2),
  ts       TIMESTAMP
) USING iceberg
PARTITIONED BY (days(ts));        -- 没有 dt 列！分区是 ts 的派生

INSERT INTO orders VALUES (1, 99.00, TIMESTAMP '2026-11-01 10:23:00');
SELECT * FROM orders WHERE ts >= TIMESTAMP '2026-11-01 00:00:00';
```

Iceberg 在 Manifest 里记录 `partition = { ts_day: 20028 }`（day 转换后的天数），**表数据里没有 `ts_day` 列**。这就是「隐藏」。

| 维度 | Hive 分区 | Iceberg 隐藏分区 |
| --- | --- | --- |
| 分区字段 | 表结构中的真实列 | 派生值，不存储 |
| 写入 | 必须指定分区值 | 自动计算 |
| 查询 | 必须写分区列 | 写业务列即可 |
| 改分区策略 | 重写数据 | ✅ 只改 spec，不重写 |
| 分区类型 | 只能目录（string/int） | transform 派生（day/hour/bucket/truncate） |
| 分区数量 | Metastore 显式记录，易爆 | 元数据里轻量记录 |

## 分区转换函数（Transform）

| Transform | 作用 | 示例 | 输出类型 |
| --- | --- | --- | --- |
| `identity` | 原值（等值分区） | `identity(country)` | 原类型 |
| `bucket[N]` | 哈希取模 N 桶 | `bucket(16, user_id)` | int |
| `truncate[W]` | 数值按宽度 / 字符串按长度截断 | `truncate(10, id)` | 原类型 |
| `year/month/day/hour` | 时间粒度 | `day(ts)`、`month(created_at)` | int |
| `void` | 丢弃分区（演进时删除分区字段用） | `void(old_col)` | — |

```sql
-- 按天 / 按小时 / 按月
PARTITIONED BY (days(ts))
PARTITIONED BY (hours(ts))
PARTITIONED BY (months(ts))

-- 组合：先按天、再按业务维度
PARTITIONED BY (days(ts), bucket(16, user_id))
```

注意：`days(ts)` 是 `day(ts)` 的语法糖；底层存储「从 1970-01-01 起的天数」（int）。

## 分区 spec 演进

这是 Iceberg 相对 Hive 的杀手锏：**同一张表可以有多个 partition spec，每个 spec 有自己的 id，历史数据保留原 spec，新数据用新 spec**。

### 演进操作

```sql
-- 1) 新增分区字段（不重写历史）
ALTER TABLE db.orders ADD PARTITION FIELD hours(ts);

-- 2) 删除分区字段（用 void 保留 spec 兼容性）
ALTER TABLE db.orders DROP PARTITION FIELD days(ts);

-- 3) 重命名分区字段
ALTER TABLE db.orders RENAME PARTITION FIELD ts_day TO event_day;

-- 4) 替换分区字段
ALTER TABLE db.orders REPLACE PARTITION FIELD days(ts) WITH hours(ts);
```

### 演进时到底发生了什么

```
演进前：
  spec 0: day(ts)
  历史数据 → data/ts_day=2026-11-01/xxx.parquet  （Manifest 里 spec_id=0）

执行 REPLACE PARTITION FIELD days(ts) WITH hours(ts)：

演进后：
  spec 0: day(ts)      （仍然存在，历史数据继续用它）
  spec 1: hour(ts)     （新写入用这个）

  旧数据：spec_id=0，目录 ts_day=...  ✅ 不重写
  新数据：spec_id=1，目录 ts_hour=... ✅ 新布局
```

关键：**每个 Manifest 记录自己的 `partition_spec_id`**，查询可以混合裁剪不同 spec 的数据。整个过程**没有一次全表重写**。

## 分区裁剪如何生效

```sql
SELECT * FROM orders
WHERE ts >= TIMESTAMP '2026-11-01 00:00:00'
  AND ts <  TIMESTAMP '2026-11-02 00:00:00';
```

1. **解析**：把 `ts` 条件按当前 spec 转换成 `ts_day = 20028`
2. **Manifest List 裁剪**：只保留分区范围覆盖 20028 的 Manifest
3. **Manifest 裁剪**：只保留 `partition.ts_day = 20028` 的 Data File
4. **文件内裁剪**：Parquet Row Group 的 min/max 再筛一遍

### 为什么必须用「业务列」

```sql
-- ✅ 能裁剪（Iceberg 自动做 day 转换）
WHERE ts >= TIMESTAMP '2026-11-01 00:00:00'

-- ❌ 不能裁剪（表达式不可逆/非单调）
WHERE DATE_FORMAT(ts, 'yyyy-MM-dd') = '2026-11-01'
WHERE substr(cast(ts as string), 1, 10) = '2026-11-01'

-- ⚠️ 可能部分裁剪（取决于引擎）
WHERE year(ts) = 2026
```

**规则**：条件里的列必须是**分区源列**，且表达式能被识别为对分区转换的映射（等值、范围、IN）。函数包裹会破坏裁剪。

### 用 EXPLAIN 验证

```sql
EXPLAIN EXTENDED
SELECT count(*) FROM orders WHERE ts >= TIMESTAMP '2026-11-01 00:00:00';
```

看输出里是否有 `PartitionFilters: [isnotnull(ts), (ts >= 2026-11-01 00:00:00)]`，以及 `IcebergScan: ... (files=3, partitions=1)`。

## 分区策略怎么选

| 数据特征 | 推荐策略 | 理由 |
| --- | --- | --- |
| 日志/埋点，按时间查 | `days(ts)` 或 `hours(ts)` | 时间范围查询命中 |
| 实时流，单日数据量大 | `hours(ts)` + `bucket(N, user_id)` | 时间 + 打散 |
| IoT/设备数据 | `days(ts)` + `bucket(32, device_id)` | 时间 + 高基数 |
| 维表/全量快照 | 不分区（`PARTITIONED BY ()`） | 表小，分区反而添乱 |
| 高基数 ID 点查 | `bucket(64, id)` | 均匀打散 |
| 行政区划/品类 | `truncate(4, code)` | 有业务含义的前缀 |

经验法则：

- **单分区数据量 1GB ~ 10GB 最佳**：太小 → 分区爆炸；太大 → 裁剪粒度粗
- **分区数控制在 10 万以内**：再多元数据开销明显
- **避免笛卡尔积**：`days(ts) × province × category` 会产生巨量分区
- **优先时间 + bucket，不要多级时间**：`days × hours` 一般没必要（用 `hours` 即可）

## 常见问题

**Q：Iceberg 分区字段会出现在 `SELECT *` 结果里吗？**
A：不会。分区是隐藏的，`SELECT *` 只返回表定义的列。这是与 Hive 最大的体验差异。

**Q：演进分区后，旧数据的查询会变慢吗？**
A：不会明显变慢。旧数据仍按旧 spec 的 manifest 组织，裁剪按 spec_id 分别处理。

**Q：能删除分区字段吗？会不会报错？**
A：可以。`DROP PARTITION FIELD` 实际是把 spec 里的字段替换成 `void`，保证新旧 manifest 的 spec 兼容。

**Q：为什么我的查询没有分区裁剪？**
A：① 条件没用业务列；② 函数包裹；③ `EXPLAIN` 里 `PartitionFilters` 为空；④ 老 spec 数据未统一。

**Q：Iceberg 支持多级分区吗？**
A：支持。`PARTITIONED BY (days(ts), bucket(16, user_id))` 会生成复合分区，但注意分区数 = 天数 × 16。

**Q：Hive 表迁移到 Iceberg 后分区怎么处理？**
A：`migrate` 把 Hive 分区列映射成 `identity` spec。想改隐藏分区需 `REPLACE PARTITION FIELD` 并重写历史数据（或保留旧 spec）。
