# 01 概述与定位

## 一句话

**Apache Hive**：把 HDFS 上杂乱无章的文件，通过一份元数据（Metastore）映射成一张张有名字、有列、有类型的「表」，然后用类 SQL（HiveQL）来查询和建模。今天的 Hive 本质上是 **Metastore + SQL 兼容层**，真正跑 SQL 的是 Tez、Spark 或 Flink。

## 它解决什么问题

HDFS 解决了「海量数据存下来」，但直接操作文件太痛苦：业务方不会写 Java MapReduce，也不想关心 block 和副本。Hive 的思路是：**既然你会 SQL，那我把文件装成表，让你用 SQL 查**。

| 痛点 | 没 Hive 时 | 有 Hive 后 |
| --- | --- | --- |
| 业务同学要查数据 | 学 Java、写 MapReduce、打包提交 | Beeline 里写 `SELECT * FROM t` |
| 数据怎么组织 | 文件目录是业务方随手建的 | 数仓分层（ODS/DWD/DWS/ADS）统一规范 |
| 同一套文件被多团队用 | 各写各的脚本，字段含义不一致 | Metastore 统一元数据，一个表一个真相 |
| 慢查询 | 只能优化 MapReduce 参数 | 分区、分桶、ORC、CBO 等 Hive 层面优化 |

## 核心架构（从 3.x 到 4.x 的变化）

```
Hive 3.x 之前
  Client → HiveServer2 → Driver → Compiler → Tez/Spark/MR → HDFS
                           ↕
                      Metastore（内嵌 Derby / 本地 MySQL / 远程 Thrift）

Hive 4.x
  Client → HiveServer2 → Compiler（独立为 Metacat）→ Tez/Spark/Flink → HDFS
                                     ↕
                              Metastore（可被 Spark/Flink/Trino 直接访问）
```

4.x 的关键变化：**Metastore 从 Hive 内部拆出来，成为共享的元数据中心**。Spark、Flink、Trino 都可以直接连 Hive Metastore 读表结构、列信息、分区，不再需要经过 HiveServer2。

## Hive vs Spark SQL vs Trino：什么时候选谁

| 维度 | Hive (on Tez/Spark) | Spark SQL | Trino (Presto 分支) |
| --- | --- | --- | --- |
| **延迟** | 分钟级（Tez/MR），秒级（Spark） | 秒级（内存计算 + Catalyst） | 亚秒级~秒级（纯内存列式） |
| **场景** | 离线 ETL、数仓建模、每日批量 | 批+流+图+ML，多模态 | 交互式 ad-hoc 查询、联邦查询 |
| **事务** | 4.x ACID（仅 ORC，Bucket 表） | Delta Lake / Iceberg 支持好 | Iceberg / Hudi / Delta 支持好 |
| **计算模型** | DAG（Tez）/ MR / Spark | RDD + DataFrame + Catalyst | Pipeline（每一步都是内存算子） |
| **优势** | 成熟稳定、数仓生态完善 | 多模态、迭代计算快 | 低延迟、多数据源联邦 |
| **劣势** | 依赖 YARN、启动慢、实时弱 | 资源占用大 | 不擅长长 ETL、UDF 生态弱 |

**选型建议**：

- 已有 Hadoop 集群、数仓体系成熟 → **Hive on Tez** 性价比最高
- 既要离线又要实时、还要 ML / 图计算 → **Spark**
- 业务方要秒级交互式查询、多数据源打通 → **Trino**
- 混合场景：**Hive（ETL）+ Spark（实时/ML）+ Trino（报表/查询）** 是常见组合

## 为什么不用 HBase / ClickHouse 代替

| 组件 | 能做数仓吗 | 适合什么 | 不适合什么 |
| --- | --- | --- | --- |
| **HBase** | 不行。列存 KV，无 SQL 引擎 | 点查、高并发写、在线业务库 | 聚合分析、JOIN、数仓分层 |
| **ClickHouse** | 可以做 ADS 层 | 列存压缩好、单表聚合极快 | 复杂 JOIN、长链路 ETL、事务 |
| **Hive** | 可以。元数据中心 + SQL 层 | 全链路数仓（ODS → ADS） | 亚秒级交互、实时流处理 |

ClickHouse 经常被用来**替换 Hive 的 ADS 报表层**，但前面的 ODS/DWD/DWS 清洗链路还是要靠 Hive/Spark 来跑。

## 4.x 现状与社区动态

| 版本 | 发布时间 | 关键特性 |
| --- | --- | --- |
| 3.1.x | 2019–2023 | 最后一个 MR 主版本，ACID 表支持较好 |
| 4.0 | 2024 | Metacat 独立、Iceberg Catalog 支持、MR 弃用、Tez 默认引擎 |
| 4.1 | 2024 年底 | SQL 标准兼容增强、性能优化 |
| 4.2 | 2025 | 进一步与 Iceberg / Delta Lake 湖仓整合 |

**社区趋势**：

- Hive 不再强调自己是独立的执行引擎，而是往 **Metastore + SQL 兼容层** 演进
- 湖仓一体（Iceberg / Hudi / Delta）成为 Hive 的默认表格式选项
- Spark SQL 和 Trino 在查询层面比 Hive 快，但它们大多还是用 Hive Metastore

## 一句话记住 Hive 的边界

> **Hive 是「文件变表」的那层胶水**：元数据管文件结构，SQL 管怎么查文件。它不存数据（数据在 HDFS/对象存储）、不直接算（计算交给 Tez/Spark），它只做「翻译」和「管理」。

## 常见问题

**Q：学了 Hive SQL，Spark SQL 能用吗？**
A：大部分能。Spark SQL 兼容 Hive 表和 Metastore，但 Spark SQL 的函数、CTE 语法、性能优化更现代。

**Q：Hive 3.x 还能用吗？**
A：生产还有大量存量。但新项目建议 4.0+，MR 已在 4.0 中标记 deprecated。

**Q：HiveServer2 和 Metastore 可以部署在同一台机器吗？**
A：开发可以，生产建议分开。Metastore 是高可用服务，HS2 是入口网关，资源诉求不同。
