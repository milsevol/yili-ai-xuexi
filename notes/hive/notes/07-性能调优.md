# 07 性能调优

## 一句话

Hive 性能瓶颈 90% 出在 **「扫描了不该扫的分区」「Shuffle 次数太多」「Join 策略选得笨」** 这三件事上。调优优先级：**分区裁剪 → 谓词下推 → MapJoin 广播 → 数据倾斜处理 → CBO 基于代价优化 → 矢量化执行**。

## 调优全景图

```
SQL 提交 → 编译器（Parse + Semantic + Optimize）→ 物理计划 → 引擎执行

调优可以发生在四个阶段：
① SQL 写法层面（分区键、JOIN 顺序、WHERE 位置）
② 表设计层面（分区、分桶、存储格式、压缩）
③ 编译器优化（CBO、谓词下推、MapJoin 自动转换）
④ 执行引擎层面（并行度、容器内存、小文件合并）
```

## 第一优先级：分区裁剪

这是**收益最大、成本最低**的调优。WHERE 条件里必须让 Hive 能静态判断分区键：

```sql
-- ✅ 能裁剪
WHERE dt = '2026-11-03'
WHERE dt IN ('2026-11-01','2026-11-02')
WHERE dt BETWEEN '2026-10-01' AND '2026-10-31'

-- ❌ 不能裁剪（函数包裹 / 隐式类型转换）
WHERE substr(dt,1,7) = '2026-11'
WHERE concat('2026','-','11','-','03') = dt
WHERE dt IN (SELECT max(dt) FROM ods_order)   -- 子查询不能做静态裁剪

-- ✅ 改写后可以裁剪
WHERE dt LIKE '2026-11-%'  -- 4.x 优化器能识别 pattern 前缀
WHERE dt = from_unixtime(unix_timestamp()-86400, 'yyyy-MM-dd')  -- 4.x 会常量折叠
```

**EXPLAIN 验证**：

```sql
EXPLAIN SELECT * FROM dwd_order_detail WHERE dt='2026-11-03';
-- Partition Specs: [(dt='2026-11-03')]  ← 只扫一个分区，裁剪生效

EXPLAIN SELECT * FROM dwd_order_detail WHERE substr(dt,1,7)='2026-11';
-- Partition Specs: [(dt='*')]  ← 全分区扫描，分区裁剪失效
```

## 第二优先级：谓词下推

**谓词下推 = 把 WHERE 条件提前到读取文件时过滤**，减少 Map 端中间数据量。

```
没有谓词下推：
  Map 读整个文件 → 全部 emit → Shuffle → Reduce 过滤 WHERE
  （无效数据也参与 Shuffle）

谓词下推生效：
  Map 读文件时只取匹配 WHERE 的行 → emit → Shuffle → Reduce
  （无效数据在 Map 端就被丢弃）
```

| 存储格式 | 谓词下推支持 | 说明 |
| --- | --- | --- |
| TextFile | 只靠 Map 端 Reader | 没有列裁剪，仍读整行 |
| **ORC** | ✅ 强（Stripe 级 + Bloom Filter） | 列裁剪 + Stripe 级跳过 + Bloom Filter 跳过行 |
| **Parquet** | ✅ 强（Row Group 级） | 列裁剪 + Row Group 级跳过 |
| Avro | 基础 | Schema 演进友好，但谓词下推能力弱 |

```sql
-- ORC + Bloom Filter 示例
CREATE TABLE t_order_bf (...)
STORED AS ORC
TBLPROPERTIES (
  'orc.bloom.filter.columns' = 'user_id,product_id'
);
-- WHERE user_id=123456 时，ORC Reader 会用 Bloom Filter 快速判断 Stripe 里有没有，
-- 直接跳过没有的 Stripe，不用读文件
```

**开启谓词下推**（默认开启）：

```properties
hive.optimize.ppd=true          # 谓词下推
hive.optimize.ppd.storage=true  # 存储层谓词下推（ORC/Parquet）
hive.io.file.readcolumn.ids.enable=true  # ORC 列裁剪
```

## 第三优先级：Join 策略

### MapJoin vs ReduceJoin

| 策略 | 做法 | 什么时候用 | 限制 |
| --- | --- | --- | --- |
| **MapJoin** | 把小表广播到所有 Map 端，本地 JOIN，**无 Shuffle** | 小表 ≤ 25–50MB | 只有等值 JOIN（=）能用 |
| **ReduceJoin（Shuffle Join）** | 两边按 JOIN key 做 Shuffle，Reduce 端合并 | 大表 × 大表，无小表可广播 | 有一次 Shuffle，瓶颈在 Reduce |
| **Bucket MapJoin** | 两表同分桶 key + 同桶数，Map 端直接对齐 | 预建好的分桶表 | 建表时固定 |

### 自动 MapJoin（强烈建议开启）

```properties
hive.auto.convert.join=true
hive.auto.convert.join.noconditionaltask.size=25000000   # 小表 ≤ 25MB 自动广播
hive.auto.convert.join.bucketizedtask.mapjoinhint=true   # 分桶表提示 MapJoin
```

```sql
-- 自动广播
EXPLAIN FORMATTED SELECT /*+ MAPJOIN(dwd_user) */ *
FROM dwd_order_detail o
JOIN dwd_user u ON o.user_id = u.user_id
WHERE o.dt='2026-11-03';
-- 输出会显示: BLOB BROADCAST(dwd_user)，没有 Shuffle！
```

### JOIN 顺序规则

**小表放 JOIN 右边**（Hive 会把最右边的表作为广播候选）：

```sql
-- ✅ 推荐（dwd_user 小，放右边）
SELECT ... FROM dwd_order o JOIN dwd_user u ON o.user_id = u.user_id;

-- ❌ 不推荐（小表在左边）
SELECT ... FROM dwd_user u JOIN dwd_order o ON u.user_id = o.user_id;
-- 这种情况下 Hive 不会自动广播 dwd_user
```

**多表 JOIN**：如果有多个小表，Hive 会自动选最右的 1–2 个广播。也可以显式指定：

```sql
SELECT /*+ MAPJOIN(dwd_user, dwd_product) */ ...
FROM dwd_order_detail o
JOIN dwd_user u ON o.user_id = u.user_id
JOIN dwd_product p ON o.product_id = p.product_id;
```

### JOIN 失败常见原因

| 现象 | 原因 | 解决 |
| --- | --- | --- |
| MapJoin 没触发 | 小表超过 hive.auto.convert.join.noconditionaltask.size | 调大阈值或加 MAPJOIN hint |
| 笛卡尔积错误 | 少写 ON 条件或 ON 条件太宽 | 检查 WHERE 里是否漏了关联条件 |
| LEFT JOIN 后 WHERE 过滤右表数据变 INNER JOIN | LEFT JOIN 的右表条件放 WHERE 会先过滤 | 右表条件放 ON 里 |

```sql
-- ❌ 错误：LEFT JOIN 后 WHERE 过滤右表，等于 INNER JOIN
SELECT * FROM dwd_order o
LEFT JOIN dwd_user u ON o.user_id = u.user_id
WHERE u.level = 'V3';

-- ✅ 正确：右表条件放 ON 里
SELECT * FROM dwd_order o
LEFT JOIN dwd_user u ON o.user_id = u.user_id AND u.level = 'V3';
```

## 第四优先级：数据倾斜处理

**什么是倾斜？** 同一个 JOIN key 或 GROUP BY key 的数据量远大于其他 key。比如 `user_id=123` 有 100 万条记录，其他 user_id 平均 1000 条。

### 倾斜识别

```sql
-- 1) 看 EXPLAIN 输出
EXPLAIN SELECT ... GROUP BY user_id;

-- 2) 跑的时候注意
--   Reduce 任务绝大多数秒完成，唯独 1 个跑了 30 分钟还在 Shuffle
--   90% 的资源都在等这一个 Reduce 结束
```

### 倾斜解法

| 解法 | 做法 | 适用 |
| --- | --- | --- |
| **开启倾斜优化** | `hive.groupby.skewindata=true`（聚合倾斜）/ `hive.optimize.skewjoin=true`（JOIN 倾斜） | 通用兜底 |
| **拆分成两段** | 先聚合热点 key，再聚合非热点 key，最后 UNION ALL | JOIN key 可枚举时 |
| **加盐随机 key** | 热点 key 加随机后缀（如 `user_id=123_0` ~ `user_id=123_15`），分 16 份并行处理，最后合并 | 热点 key 无法枚举 |
| **MapJoin 绕过** | 如果其中一张表足够小，直接广播绕过 Shuffle | 小表场景 |

### SQL 显式处理倾斜示例

```sql
-- 场景：user_id=123 是超级大 V，有 100 万订单
-- 把 user_id 拆成 16 份处理

-- 写法 1：GROUP BY 倾斜
SELECT user_id, SUM(amount)
FROM (
  -- 第一阶段：按 user_id + 随机后缀 聚合（Map 端并行）
  SELECT CASE WHEN user_id = 123
              THEN CONCAT(user_id, '_', FLOOR(RAND()*16))
              ELSE CAST(user_id AS STRING) END AS temp_key,
         user_id, amount
  FROM dwd_order_detail
  WHERE dt='2026-11-03'
) t
GROUP BY user_id;

-- 写法 2：直接开启 Hive 倾斜优化
SET hive.groupby.skewindata=true;
SET hive.groupby.mapaggr.checkinterval=100000;  -- 超过这个值认为是倾斜
```

## CBO：基于代价的优化

Hive 4.x 默认开启 CBO（Cost Based Optimization）。CBO 会**根据表统计信息**（行数、数据量、列分布）自动选最优 JOIN 顺序和 JOIN 策略。

```properties
hive.cbo.enable=true                   # 默认 true 4.x
hive.compute.query.using.stats=true
hive.stats.fetch.column.stats=true
hive.stats.fetch.partition.stats=true
```

**收集统计信息（关键！CBO 没有统计就是瞎跑）：**

```sql
-- 建表时自动统计
CREATE TABLE dwd_order_detail (...)
PARTITIONED BY (dt STRING)
STORED AS ORC
TBLPROPERTIES ('hive.stats.autogather'='true');

-- 手动刷新统计
ANALYZE TABLE dwd_order_detail COMPUTE STATISTICS;
ANALYZE TABLE dwd_order_detail PARTITION (dt='2026-11-03') COMPUTE STATISTICS FOR COLUMNS;

-- 查看统计
DESCRIBE FORMATTED dwd_order_detail;
-- Basic Statistics: numFiles=10, numRows=15000000, rawDataSize=...
```

**为什么统计这么重要？** CBO 要判断「dwd_user 有多少行？是不是小于 25MB？要不要广播？」没有统计就只能靠规则猜，猜错了反而比手动指定 MAPJOIN 还慢。

## 矢量化执行（Vectorization）

矢量化 = 一次处理 1024 行的列式批次，而不是逐行处理。ORC + Tez/Spark 默认支持：

```properties
hive.vectorized.execution.enabled=true            # 默认 true 4.x
hive.vectorized.execution.reduce.enabled=true
hive.vectorized.groupby.checkinterval=1024
hive.vectorized.groupby.maxentries=1024
```

ORC 存储格式 + 矢量化执行，聚合查询速度可以提升 **2–3x**。

## 小文件治理

INSERT OVERWRITE 后可能产生成千上万的小文件（每个 Map/Reduce 输出一个文件）：

```properties
# 自动合并小文件（INSERT OVERWRITE 后）
hive.merge.mapfiles=true
hive.merge.mapredfiles=true
hive.merge.size.per.task=268435456        # 合并后每个文件 ~256MB
hive.merge.smallfiles.avgsize=134217728  # 平均 < 128MB 触发合并

# Tez 专用
hive.tez.merge.mapfiles=true
```

## 常见问题

**Q：EXPLAIN 里 Partition Specs 显示 `(dt='*')`，但我明明写了 WHERE dt='2026-11-03'？**
A：检查分区键的字段类型——可能是 `STRING` vs `DATE` 的隐式转换问题。确保 WHERE 里的分区键类型和建表定义一致。

**Q：MapJoin 总是触发不了？**
A：先 `DESCRIBE FORMATTED dwd_user;` 看 `Data Size`，如果统计不准就 `ANALYZE TABLE dwd_user COMPUTE STATISTICS`。统计是 CBO 和自动 MapJoin 的基础。

**Q：倾斜怎么快速定位？**
A：跑 `hive.groupby.skewindata=true` 先让 Hive 自动拆两阶段跑通，再慢 SQL 里找热点 key（可以用 `GROUP BY user_id COUNT(*) ORDER BY COUNT(*) DESC LIMIT 10` 看谁是热点）。

**Q：分区键越多越好吗？**
A：分区键不是越多越好。分区数 ≥ 10 万会拖慢 Metastore（HMS 查询分区列表变慢）。通常一天一个分区，单表分区数 ≤ 10 万。
