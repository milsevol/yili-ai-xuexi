# 05 数仓分层设计

## 一句话

**数仓分层是把原始数据按「脏 → 清 → 汇总 → 应用」四层递进的方法论**：ODS（贴源）→ DWD（明细清洗）→ DWS（公共汇总）→ ADS（应用明细），配合拉链表、增量表、快照表覆盖历史回溯与实时增量，最终用维度建模（星形模型 / 雪花模型）让业务方一眼看懂。

## 为什么要分层

如果不分层，一个复杂报表的 SQL 会把「取原始日志 → 清洗脏数据 → 关联多表 → 聚合计算 → 输出指标」全部写在一个查询里。缺点：

| 痛点 | 不分层 | 分层后 |
| --- | --- | --- |
| 一个 SQL 几百行，谁也看不懂 | 业务方直接写 ODS JOIN 清洗 | ODS 不动，DWD 统一清洗，业务只写 ADS |
| 指标口径不一致 | 各业务方各算各的 GMV | DWS 统一定义 GMV、UV、留存 |
| 上游改了字段 | 所有下游报表同时崩 | DWD 层统一适配，下游不用改 |
| 重算成本高 | 每天全链路重跑 | DWD 存历史快照，增量跑 DWS/ADS |

## 四层分层详解

### ODS 贴源层（Operational Data Store）

> 原始数据几乎不变，只做最轻量的格式统一。

| 属性 | 说明 |
| --- | --- |
| 数据来源 | MySQL 业务库（CDC / Sqoop）、日志文件（Flume）、Kafka（Flink）、外部 API |
| 典型表类型 | 增量表（每日全量 / 变更数据）、日志明细行 |
| 表类型选择 | 外部表（EXTERNAL），因为数据由上游 Flink/DataX 写入 |
| 存储格式 | ORC / Parquet 均可（Flink CDC 落的可能是 Parquet） |
| 分区键 | 通常 dt（日期），有时加上 hour |

```sql
-- ODS 订单表（Flink CDC 写入，外部表，按 dt 分区）
CREATE EXTERNAL TABLE IF NOT EXISTS ods_order_inc (
  order_id    BIGINT        COMMENT '订单ID',
  user_id     BIGINT        COMMENT '用户ID',
  product_id  BIGINT        COMMENT '商品ID',
  amount      DECIMAL(12,2) COMMENT '金额',
  pay_status  TINYINT       COMMENT '支付状态 0待支付 1已支付 2已退款',
  pay_time    TIMESTAMP     COMMENT '支付时间',
  create_time TIMESTAMP     COMMENT '创建时间',
  update_time TIMESTAMP     COMMENT '更新时间'
)
PARTITIONED BY (dt STRING)
STORED AS ORC
TBLPROPERTIES ('orc.compress'='SNAPPY');
```

**ODS 层铁律**：**不做业务清洗**，只做格式统一。字段名、类型尽量和上游一致。上游改了字段，先在 ODS 层体现，DWD 再做适配。

### DWD 明细层（Data Warehouse Detail）

> ODS 清洗后的「事实明细」，一条业务事件一行。

| 属性 | 说明 |
| --- | --- |
| 主要工作 | 脏数据清洗（空值、异常值）、维度退化（关联后的宽化）、事实表统一主键 |
| 典型表类型 | 拉链表（历史回溯）、增量表（当天新数据）、快照表（每日全量） |
| 表类型 | 通常内部表（MANAGED），DWD 由 Hive INSERT OVERWRITE 写入 |
| 分区键 | dt |

```sql
-- DWD 订单明细表（清洗 ODS，去掉未支付/已退款）
CREATE TABLE IF NOT EXISTS dwd_order_detail (
  order_id    BIGINT        COMMENT '订单主键',
  user_id     BIGINT        COMMENT '用户ID',
  product_id  BIGINT        COMMENT '商品ID',
  amount      DECIMAL(12,2) COMMENT '实付金额',
  pay_status  TINYINT       COMMENT '1已支付',
  city_code   INT           COMMENT '用户所在城市（维度退化）',
  create_date DATE          COMMENT '下单日期',
  pay_date    DATE          COMMENT '支付日期'
)
PARTITIONED BY (dt STRING)
CLUSTERED BY (user_id) INTO 16 BUCKETS
STORED AS ORC
TBLPROPERTIES ('orc.compress'='SNAPPY');

-- 每日凌晨跑：从 ODS 取前一天已支付订单
INSERT OVERWRITE TABLE dwd_order_detail PARTITION (dt='2026-11-03')
SELECT o.order_id, o.user_id, o.product_id, o.amount, o.pay_status,
       u.city_code,
       DATE(o.create_time), DATE(o.pay_time)
FROM ods_order_inc o
LEFT JOIN ods_user_snapshot u ON o.user_id = u.user_id AND u.dt = '2026-11-03'
WHERE o.dt = '2026-11-03' AND o.pay_status = 1;
```

### DWS 汇总层（Data Warehouse Summary）

> 公共指标按常用维度预聚合，避免 ADS 重复计算。

| 属性 | 说明 |
| --- | --- |
| 主要工作 | 按日/周/月 × 业务线/渠道/地区 聚合 GMV、UV、订单数、客单价等 |
| 表类型 | 汇总表（多维度聚合）、公共指标表 |
| 分区键 | dt |

```sql
-- DWS 每日城市渠道汇总
CREATE TABLE IF NOT EXISTS dws_city_channel_day (
  city_code      INT           COMMENT '城市',
  channel        STRING        COMMENT '渠道',
  gmv            DECIMAL(14,2) COMMENT 'GMV',
  order_cnt      BIGINT        COMMENT '订单数',
  pay_user_cnt   BIGINT        COMMENT '支付UV',
  avg_amount     DECIMAL(10,2) COMMENT '客单价'
)
PARTITIONED BY (dt STRING)
STORED AS ORC
TBLPROPERTIES ('orc.compress'='SNAPPY');

INSERT OVERWRITE TABLE dws_city_channel_day PARTITION (dt='2026-11-03')
SELECT city_code, channel,
       SUM(amount) AS gmv,
       COUNT(DISTINCT order_id) AS order_cnt,
       COUNT(DISTINCT user_id) AS pay_user_cnt,
       ROUND(SUM(amount) / NULLIF(COUNT(DISTINCT user_id), 0), 2) AS avg_amount
FROM dwd_order_detail
WHERE dt='2026-11-03'
GROUP BY city_code, channel;
```

### ADS 应用层（Application Data Store）

> 面向具体应用/报表/接口，字段名贴近业务方语言。

```sql
-- ADS：交易大盘报表（直接给 BI 工具）
CREATE TABLE IF NOT EXISTS ads_trade_dashboard (
  dt                    DATE          COMMENT '日期',
  total_gmv             DECIMAL(14,2) COMMENT '全站GMV',
  new_user_gmv          DECIMAL(14,2) COMMENT '新客GMV',
  old_user_gmv          DECIMAL(14,2) COMMENT '老客GMV',
  new_user_order_cnt    BIGINT        COMMENT '新客订单数',
  old_user_order_cnt    BIGINT        COMMENT '老客订单数',
  new_user_rate         DECIMAL(5,4)  COMMENT '新客占比'
)
STORED AS ORC
TBLPROPERTIES ('orc.compress'='SNAPPY');
```

## 三种事实表类型

| 类型 | 写入方式 | 适用场景 | 优缺点 |
| --- | --- | --- | --- |
| **每日快照表** | 每天全量重算覆盖 | 用户画像、商品库存、店铺状态 | 简单但冗余大 |
| **增量表（Change Table）** | 只追加当天变更行 | 订单流水、支付流水、日志 | 省空间但要自己 merge 最新状态 |
| **拉链表（SCD Type 2）** | 历史全量 + start_date + end_date | 有**状态变迁**需要回溯的维度表 | 可以查任意一天的历史状态，实现略复杂 |

### 拉链表实战

典型需求：商品价格会变，想查询「2026-10-01 当天订单对应商品的历史价格」。

```sql
-- 商品拉链表：记录每个商品的历史价格区间
CREATE TABLE IF NOT EXISTS dwd_product_zipper (
  product_id   BIGINT        COMMENT '商品ID',
  sku_id       BIGINT        COMMENT 'SKU',
  price        DECIMAL(10,2) COMMENT '价格',
  start_date   DATE          COMMENT '生效日期',
  end_date     DATE          COMMENT '失效日期（9999-12-31 表示当前有效）'
)
STORED AS ORC;

-- 查询 2026-10-01 订单对应的历史价格
SELECT o.order_id, p.price
FROM dwd_order_detail o
JOIN dwd_product_zipper p
  ON o.product_id = p.product_id
  AND o.dt >= p.start_date
  AND o.dt <= p.end_date   -- 落在历史有效期内
WHERE o.dt = '2026-10-01';
```

拉链表每日更新：关闭上一条 end_date = 今天-1，插入新一条 start_date = 今天、end_date = 9999-12-31。

## 维度建模：事实表 + 维度表

这是 Kimball 经典方法论，数仓分层之上再叠一层建模方式。

### 星形模型

> 一个大事实表在中间，周围挂多个小维度表（城市、商品、用户、日期）。

```
                 [dim_city]
                    ↑
[dim_user] ← fact_order → [dim_product]
                    ↓
                 [dim_date]
```

**事实表**：度量数据（GMV、订单数、用户数），外键指向维度表。
**维度表**：描述性数据（城市名、商品名、用户名、日期属性），一列主键 + 多列属性。

### 雪花模型

> 维度表再拆一层子维度（如商品分类 → 大分类 → 小分类）。规范化程度高但 JOIN 多，性能差。**数仓优先用星形模型**。

### SCD（缓慢变化维度）处理

| 类型 | 做法 | 适用 |
| --- | --- | --- |
| **SCD Type 1** | 直接覆盖（只保留最新值） | 用户昵称、商品名这类不影响历史统计的小改 |
| **SCD Type 2** | 加行（保留所有历史，用 start/end date 标记） | **最常用**：价格、城市、等级会回溯影响历史统计 |
| **SCD Type 3** | 加列（只保留「上一个」和「当前」两个值） | 变化很少但需要对比的维度 |

```sql
-- SCD Type 1：覆盖更新用户昵称
INSERT OVERWRITE TABLE dwd_user_snapshot PARTITION (dt='2026-11-03')
SELECT user_id, IF(u.nickname <> o.nickname, u.nickname, o.nickname) AS nickname
FROM ods_user_snapshot u
LEFT JOIN dwd_user_snapshot o ON u.user_id = o.user_id AND o.dt = '2026-11-02';

-- SCD Type 2：拉链表更新（见上文）
```

## 宽表 vs 宽表拆分

**宽表**：在 DWD/DWS 层就把所有维度 JOIN 进来，一行包含用户、商品、订单、城市所有字段。优点是下游 ADS 不用 JOIN；缺点是字段多、更新成本高。

**拆分原则**：
- 超过 50 列的宽表，考虑按业务主题拆成 2–3 张子表
- 高频查询字段（金额、状态、时间）和低频字段（扩展属性、标签）分开
- 拉链表相关的历史字段单独放

```sql
-- 主表（高频查询）
CREATE TABLE dwd_order_detail (...主字段...) PARTITIONED BY (dt) STORED AS ORC;

-- 扩展表（低频查询）
CREATE TABLE dwd_order_ext (...扩展字段...) STORED AS ORC;

-- ADS 按需 JOIN
SELECT o.*, e.tag_ids FROM dwd_order_detail o
LEFT JOIN dwd_order_ext e ON o.order_id = e.order_id
WHERE o.dt='2026-11-03';
```

## 实战：完整链路示例

```
[MySQL / Kafka 实时]
         ↓ Flink CDC
[ODS 贴源表]  dt='2026-11-03' / dt='2026-11-02' ...
         ↓ Hive ETL INSERT OVERWRITE
[DWD 明细 + 拉链表]  清洗 + 维度退化 + 历史版本
         ↓ Hive INSERT OVERWRITE
[DWS 日度汇总]  GMV、订单数、UV、客单价
         ↓ Hive INSERT OVERWRITE
[ADS 报表接口]  BI 大盘 / 接口 JSON
```

## 关键配置

```properties
# —— DWD 拉链表常见 ——
hive.exec.dynamic.partition=true
hive.exec.dynamic.partition.mode=nonstrict

# —— 大表 JOIN 自动 MapJoin ——
hive.auto.convert.join=true
hive.auto.convert.join.noconditionaltask.size=25000000   # ≤25MB 自动广播

# —— 分桶表同桶 JOIN ——
hive.optimize.bucketmapjoin=true
hive.optimize.bucketmapjoin.sortedmerge=true

# —— 数仓分层规范 ——
# 数据库命名：ods_xxx / dwd_xxx / dws_xxx / ads_xxx
# 表命名：层_主题_粒度（如 dwd_order_detail、dws_city_day、ads_trade_dashboard）
# 分区键统一 dt，格式 yyyy-MM-dd
```

## 常见问题

**Q：ODS 层做了清洗还算 ODS 吗？**
A：**不算**。ODS 铁律是只做格式统一，不做业务逻辑。清洗放 DWD 层。

**Q：什么时候用拉链表，什么时候用增量表？**
A：需要回溯历史状态（「上个月的价格是多少」）→ 拉链表；只关心发生了什么事件（「今天有多少新订单」）→ 增量表。

**Q：分层后性能会不会变差？**
A：不会。反而更好——ODS 只被 DWD 扫描，DWS/ADS 只扫 DWD 或 DWS，下游不用碰原始大表。分区裁剪 + 预聚合减少了总体扫描量。

**Q：分区键 dt 用 string 还是 date？**
A：String。Hive 分区键不支持 date 类型，统一用 `dt STRING` 存 `yyyy-MM-dd` 格式。
