# 02 架构与核心组件

## 一句话

ClickHouse 架构极简：**Server 进程**（一个二进制）同时承载 HTTP API、Native 协议、查询引擎、存储引擎。数据写入后以 **Part（列分片）** 形式落到磁盘，后台 **Merge 线程** 异步把同一分区的多个 Part 合并成一个有序大 Part。分布式靠 **Distributed 引擎** 跨节点路由，副本靠 **ReplicatedMergeTree + Keeper** 保证一致性。

## 节点角色

ClickHouse 没有 Master/Worker 区分——每个 Server 节点都可以接收查询、存储数据、执行计算。集群模式下通常的角色划分是**人为约定**：

| 角色 | 职责 | 对应引擎 |
| --- | --- | --- |
| **Server 节点** | 接收查询、存储数据、执行计算 | MergeTree（本地）、Distributed（分布式路由） |
| **Coordinator（可选）** | 纯路由节点，不存数据，只做 Distributed 引擎的查询分发 | 只有 Distributed 引擎，无 MergeTree 表 |
| **ClickHouse Keeper** | 分布式协调（ZooKeeper 协议兼容），管理副本同步、选举 | 独立进程，9181 端口 |
| **外部系统** | MySQL / Kafka / S3 / HDFS 引擎做数据桥接 | MySQL / Kafka / S3 / HDFS 引擎 |

## 存储结构：Part / Marks / Data Part

这是理解 MergeTree 的核心：

```
一张 MergeTree 表在磁盘上的结构：

data_demo.db/
├── orders/
│   ├── 20261103_0_0_0/          ← 一个 Part（Partition + MinBlock + MaxBlock + Level）
│   │   ├── id.bin               ← 列文件：UInt32 二进制压缩存储
│   │   ├── id.marks             ← 稀疏索引（Marks 文件）
│   │   ├── user_id.bin
│   │   ├── user_id.marks
│   │   ├── amount.bin
│   │   ├── amount.marks
│   │   ├── dt.bin
│   │   ├── dt.marks
│   │   ├── _part_metadata.json  ← Part 元数据（总行数、边界值、分区键）
│   │   └── minmax_dt.idx        ← 跳数索引（minmax 类型，可选）
│   ├── 20261103_100_150_0/      ← 另一个 Part
│   ...
```

| 概念 | 含义 | 大小/粒度 |
| --- | --- | --- |
| **Part** | 一次写入（INSERT）产生的数据分片，包含一个分区下的数据 | 通常 100MB–1GB |
| **Marks** | Part 内的稀疏索引，每 8192 行（index_granularity）一个 mark | 每个 Part 每个列都有一个 marks 文件 |
| **Data Part** | Part 的正式名称，包含 `.bin` 列文件 + `.marks` 索引文件 + 元数据 | 同上 |

**Part 命名规则**：`{PartitionID}_{MinBlock}__{MaxBlock}__{Level}`
- PartitionID：分区键的哈希或值（如 `20261103` 对应 `toYYYYMMDD(dt)` 分区）
- MinBlock / MaxBlock：这个 Part 包含的块范围（按 ORDER BY 排序键）
- Level：Merge 次数，Level 越高 Part 越大、越有序

## Marks 稀疏索引原理

```
Part 内每 8192 行一个 mark（index_granularity = 8192）：

行号:     0       8192    16384   24576   ...
Marks:    [m0]    [m1]    [m2]    [m3]    ...

查询时：
  WHERE amount > 500
  
  主索引（ORDER BY amount）:
    查 marks 文件，定位 amount > 500 从哪个 mark 开始
    → 假设 amount 有序，m2 之后才满足
    → 跳过 m0, m1（16384 行），只扫 m2, m3...
  
  跳数索引（minmax amount）:
    每个 Part 记录 amount 的 MIN/MAX
    WHERE amount > 500 时，Part 的 MAX < 500 整个跳过
  
  二级索引（bloom_filter user_id）:
    每个 Part 生成 user_id 的 Bloom Filter
    WHERE user_id = 123 时，如果 Part 的 BF 中没有 123 直接跳过
```

## 写入流程

```
① 客户端 INSERT
   INSERT INTO orders VALUES (1, 101, 99.0, '2026-11-03'), ...
   （ClickHouse 接收后先放内存缓冲 Buffer）

② Buffer 满（max_insert_block_size）或定时
   把 Buffer 数据按 PARTITION BY 拆分区
   每个分区内按 ORDER BY 排序
   压缩每一列，写成 .bin + .marks
   生成一个新的 Part（如 20261103_0_0_0）

③ Part 写入完成
   通知后台 Merge 线程：「我写完一个 Part 了」

④ 后台 Merge 线程（异步）
   扫描所有未合并 Part → 挑出同分区的 Part 组
   按 ORDER BY 做归并排序 → 合并成一个大 Part
   删除旧 Part → 更新元数据

⑤ 查询直接读 Part
   SELECT ... FROM orders WHERE dt = '2026-11-03'
   引擎直接扫描 dt=20261103 分区下的所有 Part（已合并 + 未合并）
```

## 后台线程

ClickHouse 有多个后台线程，核心是 Merge 线程：

| 线程 | 职责 | 可配置 |
| --- | --- | --- |
| **Merge 线程** | 合并同分区的多个 Part 成一个大有序 Part | `max_merges_in_queue`、`max_merge_select_sleep_ms` |
| **Mutation 线程** | 处理 ALTER UPDATE / ALTER DELETE（异步重写 Part） | `max_mutations_in_queue_size` |
| **TTL 清理线程** | 执行表 TTL（自动过期删除 / 移动分区） | `ttl_move_batch_size` |
| **Part 清理线程** | 删除已合并的旧 Part、过期 Part | `max_parts_to_merge_at_once` |
| **Replication 线程** | ReplicatedMergeTree 同步副本（复制日志拉取） | `max_replication_delay` |
| **Distributed 写入线程** | 跨节点 Distributed 引擎的异步写入 | `distributed_insert_async_batch_max_bytes` |

## Distributed 引擎

Distributed 引擎是一个**代理层**，它不存数据，而是把查询路由到远端节点的本地表：

```
Distributed(
  'cluster_name',        -- 集群名（config.xml 定义）
  'db_name',             -- 远端数据库名
  'table_name',          -- 远端本地表名
  sharding_key           -- 分片键（可选）
)
```

| 模式 | 写法 | 说明 |
| --- | --- | --- |
| **只读路由** | `ENGINE = Distributed('my_cluster', 'default', 'orders')` | 查询自动分发到集群所有节点 |
| **写入带分片** | `ENGINE = Distributed('my_cluster', 'default', 'orders', city_hash64(user_id))` | 写入按 user_id 哈希路由到对应分片 |
| **写入直连本地表** | `INSERT INTO orders_local ...` | 推荐！Distributed 引擎写入慢，生产通常业务层自己路由 |

**关键原则**：ClickHouse 集群写入通常**业务层直接写本地表**，由业务方决定写到哪个节点；Distributed 引擎主要用于**查询聚合**。

## 常见问题

**Q：Part 太多会怎么样？**
A：查询性能下降 + 拒绝写入。每个 Part 都要读元数据、跳过检查。ClickHouse 限制单表总 Part 数默认 10 万，超过就拒绝新 INSERT。解决办法：后台 Merge 加速 + 业务写入批量更大。

**Q：Merge 阻塞写入吗？**
A：不阻塞。写入产生新 Part 和后台 Merge 是并行的。但 Merge 占用磁盘 IO 和 CPU，可能让查询变慢。

**Q：本地表 vs Distributed 表怎么选？**
A：写入直接写本地表，查询可以查 Distributed 表让它自动路由。Distributed 引擎写入会多一次网络跳转。

**Q：ClickHouse 需要 Master 节点吗？**
A：不需要！每个节点对等。Keeper 是协调服务（类似 ZooKeeper），不是计算 Master。这是 ClickHouse 和 Spark/Flink 架构最大的区别。
