# 05-分区排序与索引

## 一句话

ClickHouse 查询性能的 80% 取决于**分区策略**（PARTITION BY）和**排序键**（ORDER BY），剩下 20% 靠**跳数索引**和 **Projections**。分区决定「哪些磁盘目录可以跳过」，排序键决定「同一分区内的数据顺序和主索引精度」，跳数索引给特定列加速过滤，Projections 预存常用查询。

## PARTITION BY 分区策略

分区是 ClickHouse 的**第一道过滤关卡**——查询时如果能用分区键裁剪，直接跳过整个磁盘目录的扫描。

### 常用分区方案

| 分区方式 | 表达式 | 分区 ID | 适用场景 | 优缺点 |
| --- | --- | --- | --- | --- |
| **按天分区** | `toYYYYMMDD(dt)` | `20261103` | 绝大多数 OLAP（用户行为、日志、监控） | ✅ 常用范围查询能裁剪；⚠️ 日期粒度太粗时分区太多 |
| **按月分区** | `toYYYYMM(dt)` | `202611` | 历史数据、冷数据 | ✅ 分区少；⚠️ 月内范围查询裁剪不了 |
| **按周分区** | `toMonday(dt)` 或 `toStartOfWeek(dt)` | 周一日期 | 周度报表 | — |
| **按小时分区** | `toStartOfHour(dt)` | 小时起始 | 高吞吐实时场景（>100w 行/秒） | ⚠️ 分区极多，管理成本高 |
| **按业务字段** | `city` / `channel` | 城市名 | 地理/渠道固定枚举 | ✅ 分区少；❌ 业务字段变化时分区无上限 |
| **无分区** | `tuple()` | 空分区 | 小表/维表 | — |

### 分区的坑

| 坑 | 说明 | 解决方案 |
| --- | --- | --- |
| **分区键函数要确定性** | `toYYYYMMDD(dt)` 确定性；`rand()` 每次随机 | 只用纯时间函数或枚举值 |
| **单分区数据量要大** | 单分区至少 100MB+，推荐 1GB+ | 分区粒度不要太细（别按小时分区除非高吞吐） |
| **分区数爆炸** | 分区数 > 10000 元数据开销大 | 按月/周而非按天；业务字段分区要控制枚举值 |
| **ALTER 删分区是异步的** | `DROP PARTITION` 标记为 inactive 后由后台清理 | 大分区用 `FREEZE PARTITION` 先备份 |

### 分区裁剪

查询中的 WHERE 条件**必须等值比较分区键或分区键的函数**才能触发裁剪：

```sql
-- ✅ 触发分区裁剪
SELECT * FROM orders WHERE toYYYYMMDD(dt) = 20261103;
SELECT * FROM orders WHERE dt = '2026-11-03';
SELECT * FROM orders WHERE dt BETWEEN '2026-11-01' AND '2026-11-07';

-- ❌ 不触发分区裁剪
SELECT * FROM orders WHERE toYYYYMMDD(dt) + 1 = 20261103;  -- 分区键被函数包裹
SELECT * FROM orders WHERE formatDateTime(dt, '%Y%m%d') = '20261103';
```

**EXPLAIN 验证**：
```sql
EXPLAIN SELECT * FROM orders WHERE dt = '2026-11-03';
-- 输出中能看到 READ 列的 partition pruned 信息
```

## ORDER BY 排序键

ORDER BY 是 MergeTree **必填**的，决定：
1. 数据的物理存储顺序
2. 主索引（稀疏索引）的精度
3. 后台 Merge 的归并顺序

### 排序键设计原则

```sql
-- ❌ 糟糕的排序键
ORDER BY rand()           -- 每次写入随机，Merge 后还是乱序
ORDER BY (id)             -- 只有单列，其他列查询全表扫描

-- ✅ 好的排序键示例
-- 用户行为表：按 user_id 查、按 dt 过滤
ORDER BY (user_id, dt)

-- 时序日志表：按 dt 范围查询为主
ORDER BY (dt, log_level)

-- 业务维度表：按 city + product 聚合
ORDER BY (city, product_id, id)
```

**设计口诀**：**最常用的查询过滤条件放前面**。ORDER BY 前几个列越常被 `WHERE ... = ...` 用，主索引命中率越高。

### index_granularity

```sql
CREATE TABLE orders (...)
ENGINE = MergeTree()
ORDER BY (user_id, id)
SETTINGS index_granularity = 8192;   -- 默认 8192
```

| 值 | 含义 | 权衡 |
| --- | --- | --- |
| 8192（默认） | 每 8192 行一个 mark | 主索引精确到 8K 行，折中 IO 和内存 |
| 4096 | 每 4K 行一个 mark | 更精确但 marks 文件大 |
| 16384 | 每 16K 行一个 mark | marks 更小但定位不精确 |

## PRIMARY KEY 主键

ClickHouse 的 PRIMARY KEY 和 ORDER BY **可以不同**：

```sql
CREATE TABLE orders (
  id UInt64,
  user_id UInt64,
  amount Float64
) ENGINE = MergeTree()
ORDER BY (user_id, id)          -- 排序键决定物理顺序
PRIMARY KEY (id);               -- 主键只建主键索引，不改变存储顺序
```

| 区别 | ORDER BY | PRIMARY KEY |
| --- | --- | --- |
| 是否必填 | ✅ 必填 | ❌ 可选（默认等于 ORDER BY） |
| 决定存储顺序 | ✅ | ❌ |
| 用于跳数索引 | ✅ | ❌ |
| 用于 FINAL 去重判断 | ✅ | ❌ |

## 跳数索引（Data Skipping Index）

跳数索引是 MergeTree 的**二级索引**，让查询能**跳过整个 Part**（比 Marks 稀疏索引更粗粒度）。

### 四种跳数索引类型

| 类型 | 说明 | 适合 | 语法 |
| --- | --- | --- | --- |
| **minmax** | 每个 Part 存列的 MIN/MAX | 范围查询过滤条件 | `INDEX idx amount amount TYPE minmax GRANULARITY 4` |
| **set(N)** | 每个 Part 存列的 N 个不同值集合 | 等值查询、IN 条件 | `INDEX idx user_id user_id TYPE set(100) GRANULARITY 4` |
| **bloom_filter** | 每个 Part 存 Bloom Filter | 字符串、低基数字段等值查询 | `INDEX idx city city TYPE bloom_filter GRANULARITY 4` |
| **ngrambf_v1** | N-Gram Bloom Filter | 模糊查询 LIKE '%xxx%' | `INDEX idx_name name TYPE ngrambf_v1(3, 0.02, 0.01) GRANULARITY 4` |

### 创建跳数索引

```sql
-- 建表时指定
CREATE TABLE orders (
  id UInt64,
  user_id UInt64,
  amount Float64,
  city String,
  dt Date
) ENGINE = MergeTree()
PARTITION BY toYYYYMMDD(dt)
ORDER BY (user_id, id)
INDEX idx_amount amount TYPE minmax GRANULARITY 4
INDEX idx_city city TYPE bloom_filter GRANULARITY 4
INDEX idx_user_id user_id TYPE set(100) GRANULARITY 4;

-- ALTER 加索引（后台异步生效）
ALTER TABLE orders ADD INDEX idx_status status TYPE set(5) GRANULARITY 4;

-- 查看索引
SHOW CREATE TABLE orders;
```

### GRANULARITY 参数

跳数索引检查的粒度，默认 4：表示每 **4 个 mark**（4 × index_granularity = 32768 行）检查一次。

| GRANULARITY | 含义 | 权衡 |
| --- | --- | --- |
| 1 | 每 8192 行检查 | 最精确，但索引文件大 |
| 4（默认） | 每 32768 行检查 | 折中 |
| 8 | 每 65536 行检查 | 索引小但跳过不精确 |

### 生效条件

跳数索引生效需要两个条件：
1. 查询条件能**直接**关联到索引列（不被函数包裹）
2. 索引类型匹配查询条件类型

```sql
-- ✅ bloom_filter city 索引生效
SELECT * FROM orders WHERE city = '北京';

-- ❌ bloom_filter 不生效（索引是 city，查询是 formatDateTime 包裹）
SELECT * FROM orders WHERE upper(city) = '北京';

-- ✅ minmax amount 索引生效（amount BETWEEN）
SELECT * FROM orders WHERE amount BETWEEN 100 AND 500;
```

## Projections 投影加速

Projections 是 **MergeTree 22.x+** 的特性，让一张表可以**预存多个 ORDER BY 排列的副本**：

```sql
CREATE TABLE orders_proj (
  id UInt64,
  user_id UInt64,
  city String,
  amount Float64,
  dt Date
) ENGINE = MergeTree()
PARTITION BY toYYYYMMDD(dt)
ORDER BY (user_id, id)    -- 主排序键

-- 投影 1：按 city + dt 排列（适合城市维度查询）
PROJECTION proj_city
(
  SELECT city, dt, amount
  ORDER BY (city, dt)
)

-- 投影 2：按 dt + amount 排列（适合时间维度查询）
PROJECTION proj_time
(
  SELECT dt, sum(amount)
  GROUP BY dt
);
```

**引擎自动选择最优 Projection**：查询 `WHERE city = '北京'` 时自动用 `proj_city` 副本，比按主 ORDER BY 扫描快很多。

| 特性 | 说明 |
| --- | --- |
| 写入同步 | INSERT 时自动写 Projection（阻塞写入但读快） |
| Merge 自动同步 | Merge 后自动更新 Projection 数据 |
| 存储开销 | 每个 Projection = 多存一份数据 |
| 适用场景 | 多维度查询、JOIN 前预聚合、常用 group by |

## 完整建表最佳实践

```sql
CREATE TABLE orders_best_practice (
  id UInt64,
  user_id UInt64,
  city String,
  channel Enum('app' = 1, 'web' = 2, 'mini' = 3),
  amount Float64,
  status UInt8 DEFAULT 0,
  dt Date DEFAULT today(),
  created DateTime DEFAULT now()
) ENGINE = MergeTree()

-- ① 分区：按天，单分区数据量 ≥ 1GB
PARTITION BY toYYYYMMDD(dt)

-- ② 排序键：最常用查询过滤条件优先
ORDER BY (user_id, dt, id)

-- ③ TTL：180 天后自动删除
TTL dt + INTERVAL 180 DAY

-- ④ 主索引粒度
SETTINGS index_granularity = 8192,

-- ⑤ 跳数索引：加速常用过滤
INDEX idx_amount amount TYPE minmax GRANULARITY 4,
INDEX idx_city city TYPE bloom_filter GRANULARITY 4,
INDEX idx_status status TYPE set(10) GRANULARITY 4,
INDEX idx_user_id user_id TYPE set(1000) GRANULARITY 4;
```

## 常见问题

**Q：为什么分区键不用 ORDER BY 列？**
A：PARTITION BY 是一级目录切分，ORDER BY 是目录内排序。通常分区用时间字段（方便范围裁剪 + TTL 过期），ORDER BY 用业务查询常用字段（user_id、city 等）。两者可以相同但不推荐——分区内再按同字段排序没收益。

**Q：跳数索引和 ORDER BY 主索引是什么关系？**
A：主索引（Marks）是**有序列的稀疏索引**，跳数索引是**任意列的粗粒度跳过**。ORDER BY 列天然有主索引，其他列靠跳数索引补性能。

**Q：Projections 和物化视图有什么区别？**
A：物化视图是**独立的另一张表**；Projection 是**同一张表的预存排列**，引擎自动选最好的那个。Projections 更透明但也占存储。

**Q：`ORDER BY` 能改吗？**
A：23.x 起支持 `ALTER TABLE ... MODIFY ORDER BY`，但这会**同步重写所有 Part**，大表极慢。建议建表时想清楚排序键。
