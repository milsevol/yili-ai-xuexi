# 06-向量化执行与查询原理

## 一句话

ClickHouse 查询快的根因是**列式存储 + SIMD 向量化执行**——列式存储让 IO 只读需要的列，SIMD 让 CPU 一次处理 64–256 行数据而非逐行处理。配合 Pipeline 模式避免中间结果落盘、主/次级索引裁剪扫描范围、Projections 预存排序副本，查询路径被压缩到极致。

## 列式存储 + SIMD = 高吞吐

### 列式存储 vs 行式存储

```
行式存储（CSV / MySQL / HBase）:
  物理文件: id, user_id, amount, status, dt, ..., id, user_id, amount, ...
  读 SELECT id, amount → 得读所有列，磁盘 IO 大

列式存储（ClickHouse MergeTree）:
  id.bin:       [1, 2, 3, ...]
  user_id.bin:  [101, 102, 103, ...]
  amount.bin:   [99.0, 199.0, 49.0, ...]
  dt.bin:       ['2026-11-03', '2026-11-03', '2026-11-04', ...]
  读 SELECT id, amount → 只读 id.bin 和 amount.bin，跳过其他列
```

| 维度 | 行式 | 列式 | 列式优势 |
| --- | --- | --- | --- |
| 读部分列 | 读全部列 | 只读需要的列 | IO 减少 50–90% |
| 压缩率 | 低（各值类型混杂） | 高（同类型连续） | 10–20x 压缩比 |
| 更新单行 | 快（定位一行） | 难（要重写列文件） | — |
| 聚合扫描 | 每行随机访问 | 连续扫描 + SIMD | 运算快 5–10x |
| 适合场景 | OLTP | OLAP 聚合 | ClickHouse 场景 |

### SIMD 指令的原理

SIMD（Single Instruction Multiple Data）是 CPU 的**向量指令集**（x86: AVX-512，ARM: NEON/SVE）。

```
传统标量计算（逐行）:
  for row in rows:          # 每轮处理 1 行
    sum += row.amount       # 一次读一个值 + 一次加法

SIMD 向量化（批量）:
  vector = load_64_rows()   # 一次加载 64 个 amount 值到 CPU 向量寄存器
  sum = vector_sum(vector)  # 一个指令加 64 个值
```

| CPU 指令集 | 向量宽度 | 单次处理行数（Float64） |
| --- | --- | --- |
| SSE | 128 bit | 2 个 Float64 |
| AVX | 256 bit | 4 个 Float64 |
| AVX-512 | 512 bit | **8 个 Float64** |
| ARM NEON | 128 bit | 2 个 Float64 |
| ARM SVE | 1024 bit | **16 个 Float64** |

**ClickHouse 自动检测 CPU 指令集**，编译时开启对应 SIMD 优化，用户不用配。

### 结合起来看

```
查询: SELECT count(), sum(amount) FROM orders WHERE dt = '2026-11-03'

ClickHouse 执行路径:
① 分区裁剪          ← 只扫 dt=20261103 那一个分区目录
② 跳数索引          ← 检查每个 Part 的 bloom_filter dt，跳过不含该日期的
③ 主索引 Marks      ← 跳过 Part 内无关的 mark 区间
④ 列裁剪            ← 只读 amount.bin 和 dt.bin（ORDER BY 列自动读）
⑤ SIMD 向量化       ← count() 和 sum() 用 SIMD 批量算
⑥ Pipeline          ← 结果不落盘，直接传给下一个算子
```

## 向量化 vs 行式执行

| 对比项 | 行式执行（MySQL / Spark 旧版） | 向量化执行（ClickHouse / Dremel） |
| --- | --- | --- |
| 数据加载 | 每次一行 | 一次 64–256 行 |
| CPU 指令 | 标量，每值一次指令 | SIMD，每 64+ 值一次指令 |
| 函数调用 | 每行调一次 strlen/toString | 每批调一次（批处理） |
| 分支判断 | 每行做 if/else | 批量 mask 运算 |
| 内存访问 | 随机访问行结构 | 顺序访问列文件（CPU L3 缓存友好） |
| 适用场景 | OLTP 单行读写 | OLAP 大规模聚合 |

**基准数据**：同样 `SELECT count(), sum(amount) FROM 10亿行表`
- MySQL（行式）：~120 秒
- Spark（列式但非向量化旧版）：~30 秒
- ClickHouse（向量化 + 列存）：**~0.5–2 秒**

## Pipeline 模式 vs 非 Pipeline

Pipeline 模式是 ClickHouse 21.x+ 默认的**执行计划优化**——算子之间通过内存管道传递数据，不写中间结果到磁盘。

```
非 Pipeline（传统 OLAP）:
  [Source] → 写临时文件 → [Filter] → 写临时文件 → [Aggregate] → 写临时文件 → [Sink]
  每个算子都落盘，IO 爆炸

Pipeline（ClickHouse）:
  [Source] ─内存管道→ [Filter] ─内存管道→ [Aggregate] ─内存管道→ [Sink]
  数据在内存中以 Block（64K 行）流动，算子流水线并行执行
```

| 模式 | 中间落盘 | 延迟 | 适用 |
| --- | --- | --- | --- |
| Pipeline | ❌ 不落盘 | 低 | 绝大多数查询（默认） |
| 非 Pipeline | ✅ 落盘 | 高 | 大 Shuffle JOIN、内存不够时自动降级 |

Pipeline 模式的前提是**算子输出 ≤ 可用内存**。如果大表 GROUP BY 内存溢出，ClickHouse 会自动降级为非 Pipeline 模式（spill to disk）。

```sql
-- 手动控制
SET enable_pipeline_execution = 1;    -- 默认 1（开启）
SET max_memory_usage = 10000000000;   -- 控制是否触发 spill
```

## EXPLAIN 查询计划分析

ClickHouse 的 EXPLAIN 能看到完整的执行链路：

```sql
EXPLAIN PIPELINE SELECT
  city,
  count() AS uv,
  sum(amount) AS gmv
FROM orders
WHERE dt BETWEEN '2026-11-01' AND '2026-11-07'
GROUP BY city
ORDER BY gmv DESC
LIMIT 10;
```

```
PIPELINE (6 steps)
├── (1) ReadFromMergeTree
│   └── MergeTreeReadPool: Reading 3 parts, 3 granularities
│       ↓ Partition pruning: dt in [20261101, 20261107]
│       ↓ Skipping index: idx_amount minmax (not used - no filter)
│       ↓ Skipping index: idx_city bloom_filter (not used - no filter)
│       Result columns: [city, amount]   ← 列裁剪只读需要的
│       Marks read: 12/20  ← 主索引跳过了 8 个 mark
│
├── (2) Filter
│   └── Expression: dt BETWEEN ...       ← 谓词下推（分区裁剪已做，剩下的再过滤一次）
│
├── (3) GroupBy
│   └── Aggregate: count() = uniqExact(), sum(amount)
│   └── Keys: [city]
│
├── (4) Sorting
│   └── sort(gmv DESC)
│
├── (5) Limit
│   └── limit 10
│
└── (6) OutputPort
    └── Output: [city, uv, gmv]
```

**关键信息解读**：
- `Partition pruning`：分区裁剪命中了多少分区
- `Skipping index`：哪些跳数索引被用上/没用上
- `Marks read: 12/20`：主索引跳过的比例（越大越好）
- `Result columns`：列裁剪后实际读了哪些列

```sql
-- 其他 EXPLAIN 类型
EXPLAIN SELECT ...;                  -- 基础执行计划
EXPLAIN PIPELINE SELECT ...;         -- Pipeline 详情
EXPLAIN PLAN SELECT ...;             -- 计划树
EXPLAIN PLAN indexes SELECT ...;     -- 索引使用情况
```

## 优化器

ClickHouse 有一套自带的**基于规则的优化器（RBO）**，不是基于代价的（CBO）：

| 优化规则 | 说明 |
| --- | --- |
| **分区裁剪** | WHERE 中的分区键条件 → 只扫相关分区目录 |
| **跳数索引裁剪** | WHERE 中条件匹配跳数索引列 → 跳过不匹配的 Part |
| **主索引 Marks 裁剪** | WHERE 中 ORDER BY 列的条件 → 跳过 Part 内 mark 区间 |
| **谓词下推** | 把过滤条件尽量推到离数据源近的地方 |
| **列裁剪** | 只读 SELECT、WHERE、GROUP BY、ORDER BY 涉及的列 |
| **投影裁剪** | 选择最合适的 Projection 副本（如果有） |
| **广播 JOIN** | 小表（< broadcast_join_threshold）自动广播到每个节点 |
| **GROUP BY 去重** | 提前做预聚合减少数据量 |
| **Distinct 优化** | DISTINCT 自动用 uniq 近似或 group by 替代 |

### 优化器无法决定的事

ClickHouse 优化器**没有统计信息驱动**——它不扫描表来收集列的基数、分布等信息。很多性能决策需要**手动配置**：

```sql
-- Broadcast JOIN 阈值（默认 100MB）
SET max_rows_in_distinct = 10000000;
SET broadcast_join_threshold = 100000000;  -- 100MB

-- 并行度
SET max_threads = 8;

-- 分布式查询策略
SET prefer_localhost_replica = 1;   -- 本地有副本优先读本地
```

## 查询性能 Checklist

```sql
-- ✅ 好查询示例
SELECT
  city,
  count() AS uv,
  sum(amount) AS gmv
FROM orders                          -- ① 分区裁剪：WHERE dt BETWEEN
WHERE dt BETWEEN '2026-11-01' AND '2026-11-07'
  AND amount > 100                   -- ② 跳数索引 minmax amount 生效
  AND city IN ('北京', '上海')        -- ③ 跳数索引 bloom_filter city 生效
GROUP BY city                         -- ④ GROUP BY 列在 ORDER BY 里（主索引加速）
ORDER BY gmv DESC
LIMIT 20;                             -- ⑤ 最后 LIMIT 减少返回数据
```

| 优化手段 | 期望效果 | 验证方式 |
| --- | --- | --- |
| 分区裁剪 | 只扫 7/365 分区 | `EXPLAIN PIPELINE` 看 partition pruning |
| 跳数索引 | 跳过 N 个 Part | `EXPLAIN PIPELINE` 看 skipping index |
| 主索引 | Marks 跳过 | `EXPLAIN PIPELINE` 看 marks read 比例 |
| 列裁剪 | 只读 5/20 列 | `EXPLAIN PIPELINE` 看 result columns |
| SIMD | count()/sum() 极快 | `SELECT count()` 10 亿行 < 2 秒 |

## 常见问题

**Q：为什么 ClickHouse 没有 CBO（基于代价优化）？**
A：ClickHouse 是列式存储 + 向量化执行引擎，执行路径的成本变化不像传统行存 DBMS 那样大（列式 + SIMD 对大多数查询都极快）。RBO 已经覆盖了 90% 的优化场景。

**Q：大表 JOIN 为什么慢？**
A：ClickHouse 的 JOIN 是 Hash Join，大表（>100GB）没有 Broadcast 优势时需要 Shuffle，而 ClickHouse Shuffle 是分布式的（跨节点网络传输）。建议：① 小表广播；② 大表 JOIN 业务层预路由；③ 复杂 JOIN 交给 Spark。

**Q：Pipeline 模式什么时候降级到非 Pipeline？**
A：超过 `max_memory_usage` 时自动降级（spill to disk）。可以在 EXPLAIN PIPELINE 里看 Spill 节点。

**Q：`SET max_threads = 8` 是不是越大越好？**
A：不是。CPU 核数决定了真正并行的上限，超过物理核数后更多线程反而增加上下文切换开销。建议和 CPU 核数一致。
