# 07-分布式与集群

## 一句话

ClickHouse 分布式架构极简：**每个节点对等**（无 Master/Worker 区分），靠 **Distributed 引擎** 做查询路由、**ReplicatedMergeTree + ClickHouse Keeper** 做副本同步。写入通常**业务层直接写本地表**，查询通过 Distributed 引擎自动跨节点聚合。集群规模从几个节点到上百节点都能优雅扩展。

## 集群基础概念

| 概念 | 含义 | 说明 |
| --- | --- | --- |
| **节点 Node** | 一台运行 ClickHouse Server 的机器 | 每个节点都能接收查询、存数据、执行计算 |
| **分片 Shard** | 集群中的一个数据分片组 | 一个 Shard 里可以有多个副本 |
| **副本 Replica** | 同一个数据分片在不同节点上的备份 | ReplicatedMergeTree 引擎自动同步 |
| **集群 Cluster** | 多个 Shard 组成的逻辑单元 | Distributed 引擎用集群名路由查询 |
| **Coordinator 节点** | 只做路由不存数据的节点 | 部署在 K8s 等场景方便水平扩展 |

```
典型集群拓扑:

  Cluster: production
  ├── Shard 1（分片 1）
  │   ├── Replica 1 → ck-node1:9000
  │   └── Replica 2 → ck-node2:9000
  ├── Shard 2（分片 2）
  │   ├── Replica 1 → ck-node3:9000
  │   └── Replica 2 → ck-node4:9000
  └── Shard 3（分片 3）
      ├── Replica 1 → ck-node5:9000
      └── Replica 2 → ck-node6:9000

  + ClickHouse Keeper 集群（独立进程，3 节点）
    keeper1:9181, keeper2:9181, keeper3:9181
```

## Distributed 引擎 — 查询路由

Distributed 引擎是**只读（或路由写入）的代理层**，不存数据：

```sql
-- 在任何节点上创建 Distributed 表
CREATE TABLE orders_distributed AS orders_local
ENGINE = Distributed(
  'production',                    -- 集群名（config.xml 定义）
  'default',                       -- 远端数据库
  'orders_local',                  -- 远端本地表名
  cityHash64(user_id)              -- 分片键（用于写入路由）
);

-- 查询 Distributed 表 → 自动并发查询所有分片并聚合
SELECT city, count()
FROM orders_distributed
WHERE dt = '2026-11-03'
GROUP BY city;
-- ClickHouse 自动把查询下发到 3 个 Shard 各跑一次，结果在 Coordinator 节点聚合
```

### Distributed 查询路由流程

```
用户查询 → ck-node1（任意节点）
  │
  ├─ 解析 Distributed 引擎 → 知道要查 production 集群
  │
  ├─ 并发下发到 3 个 Shard 的本地表：
  │   ↓ ck-node1 的 orders_local（Shard 1, Replica 1）
  │   ↓ ck-node3 的 orders_local（Shard 2, Replica 1）  ← 每个 Shard 选一个 Replica
  │   ↓ ck-node5 的 orders_local（Shard 3, Replica 1）
  │
  ├─ 3 个节点各自本地执行 PARTITION BY + ORDER BY + SIMD
  │
  ├─ 结果返回 ck-node1 → 聚合（MergeTree 的聚合逻辑再跑一遍）
  │
  └─ 返回最终结果给用户
```

### Distributed 引擎参数

```sql
Distributed(
  cluster,          -- 集群名
  database,         -- 远端数据库
  table,            -- 远端本地表
  sharding_key,     -- 分片键（可选，用于写入路由）
  replica_key       -- 副本选择键（可选，同一数据读本地副本）
)
```

### 副本选择策略

| 策略 | 配置 | 说明 |
| --- | --- | --- |
| **随机** | 默认 | 每个查询随机选一个副本 |
| **本地优先** | `SET prefer_localhost_replica = 1` | 同节点有本地副本时读本地，减少网络 |
| **副本感知** | replica_key 参数 | 同一 replica_key 的查询路由到同一副本 |
| **按延迟** | `SET read_from_replicas = 1` | 优先选最近（网络延迟最低）的副本 |

### Distributed 查询优化参数

```sql
-- 分布式查询并发数
SET max_distributed_connections = 1024;

-- 集群并行度（同时发往多少个分片）
SET distributed_product_mode = 'local';
SET remote_cluster_choose_random_host = 1;

-- 分布式写入超时
SET distributed_insert_timeout = 300;

-- 写 Distribute 表时同步/异步
SET distributed_insert_async = 1;
SET distributed_insert_async_batch_max_bytes = 10485760;
SET distributed_insert_async_interval_ms = 500;
```

## Distributed 引擎写入 vs 直连本地表

**生产推荐：业务层直接路由到本地表写入**，而非 Distributed 引擎：

```sql
-- ❌ 不推荐：Distributed 引擎写入
INSERT INTO orders_distributed VALUES (...);
-- 问题：① 多一层网络跳转 ② 一个节点写失败影响其他分片 ③ 数据量大时成为瓶颈

-- ✅ 推荐：业务层直连本地表
-- 业务代码里根据 user_id 哈希选分片
shard = hash(user_id) % shard_count;
ck_node = shards[shard][0];  -- 选该分片的一个副本

-- 直接写入目标节点的本地表
INSERT INTO orders_local ON ck_node VALUES (...);
```

| 对比 | Distributed 引擎写入 | 业务层直连本地表 |
| --- | --- | --- |
| 网络跳转 | 多一跳 | 直接 |
| 吞吐 | 受限于 Distributed 节点 | 所有节点均衡承载 |
| 失败处理 | 一处失败影响全局 | 某节点挂了只影响该分片 |
| 复杂度 | 简单 | 业务层要做路由 |
| 生产推荐 | ❌ | ✅ |

## ReplicatedMergeTree + Keeper 副本

副本靠 **ReplicatedMergeTree** 引擎 + **ClickHouse Keeper**（或 ZooKeeper）实现：

```sql
-- 在每个节点创建 ReplicatedMergeTree 表（路径相同）
-- ck-node1
CREATE TABLE orders_local (
  id UInt64, user_id UInt64, amount Float64, dt Date
) ENGINE = ReplicatedMergeTree(
  '/clickhouse/tables/{shard}/default/orders_local',   -- Keeper 路径（含 shard 编号）
  '{replica}'                                           -- 副本标识（hostname 或 IP）
)
PARTITION BY toYYYYMMDD(dt)
ORDER BY (user_id, id);

-- ck-node3（另一个 Shard）
CREATE TABLE orders_local (...)
ENGINE = ReplicatedMergeTree(
  '/clickhouse/tables/{shard}/default/orders_local',   -- shard 值不同
  '{replica}'
)
...;
```

### Keeper 路径约定

```
Keeper ZNode 结构:

/clickhouse/
  └── tables/
      └── 1/                        ← Shard 1 路径
          └── default/
              └── orders_local/
                  ├── ...
      └── 2/                        ← Shard 2 路径
          └── default/
              └── orders_local/
```

| 模板 | 含义 | 示例值 |
| --- | --- | --- |
| `{shard}` | 分片编号（从 config.xml 读取） | `1`, `2`, `3` |
| `{replica}` | 副本标识（hostname 或 IP） | `ck-node1`, `ck-node2` |

### 副本同步原理

```
① ck-node1 (Shard 1, Replica 1) 写入 Part
   INSERT INTO orders_local VALUES (...);
   生成 Part: 20261103_0_0_0

② ck-node1 把 Part 元数据注册到 Keeper
   /clickhouse/tables/1/default/orders_local/partitions/...

③ ck-node2 (Shard 1, Replica 2) 的 ReplicatedMergeTree 后台线程
   从 Keeper 发现新 Part → 从 ck-node1 拉取 Part 数据

④ ck-node2 本地创建相同 Part → 查询时本地就能读到
```

**特性**：
- 副本是**异步**同步的，延迟通常 < 10 秒
- 读任意副本都能查到数据（最终一致）
- 写入只需写一个副本（推荐写本地或优先副本）
- Keeper 协调 Part 的全局唯一编号（避免冲突）

### Keeper vs ZooKeeper

ClickHouse Keeper 是官方兼容 ZooKeeper 协议的替代方案：

| 对比 | ClickHouse Keeper | ZooKeeper |
| --- | --- | --- |
| 协议 | 兼容 ZooKeeper | ZAB 协议 |
| 部署 | ClickHouse 同仓库编译，单二进制 | 需要单独装 ZooKeeper |
| 性能 | 更高（更精简的协议栈） | 成熟稳定 |
| 运维 | 可以直接从 ZooKeeper 迁移 | 存量系统 |
| 推荐 | ✅ ClickHouse 官方推荐 | 已有 ZooKeeper 集群时可以复用 |

## 分片 Shard 策略

分片键决定**数据怎么散落到各 Shard**：

| 策略 | 表达式 | 特点 | 适用 |
| --- | --- | --- | --- |
| **哈希分片** | `cityHash64(user_id) % 3` | 均匀分布，查询带分片键能路由到单 Shard | 绝大多数场景 |
| **范围分片** | 按 dt 或 ID 范围 | 数据集中，范围查询只扫对应 Shard | 时间序列、ID 递增表 |
| **枚举分片** | 按 city / channel 等 | 固定枚举值映射到固定 Shard | 业务维度固定的场景 |
| **无分片（单 Shard）** | 只有一个 Shard | 所有数据都在一个集群 | 小数据量或单节点先跑 |

### Distributed 引擎分片键示例

```sql
-- 哈希分片（按 user_id 哈希）
CREATE TABLE orders_distributed ...
ENGINE = Distributed('production', 'default', 'orders_local', cityHash64(user_id));

-- 范围分片（按 dt 范围硬编码）
-- 方案：多 Distributed 表 + 业务层路由
```

## 集群 Cluster 配置

在每个节点的 `config.xml` 里定义集群：

```xml
<!-- 所有节点的 config.xml 要一致 -->
<remote_servers>
  <production>
    <shard>
      <internal_replication>true</internal_replication>  <!-- 副本间自动复制 -->
      <replica>
        <host>ck-node1</host>
        <port>9000</port>
        <replica_priority>1</replica_priority>
      </replica>
      <replica>
        <host>ck-node2</host>
        <port>9000</port>
        <replica_priority>2</replica_priority>
      </replica>
    </shard>
    <shard>
      <internal_replication>true</internal_replication>
      <replica>
        <host>ck-node3</host>
        <port>9000</port>
      </replica>
      <replica>
        <host>ck-node4</host>
        <port>9000</port>
      </replica>
    </shard>
  </production>
</remote_servers>

<!-- Keeper 配置 -->
<zookeeper>
  <node>
    <host>keeper1</host>
    <port>9181</port>
  </node>
  <node>
    <host>keeper2</host>
    <port>9181</port>
  </node>
  <node>
    <host>keeper3</host>
    <port>9181</port>
  </node>
</zookeeper>

<!-- Shard 编号（每个节点不同） -->
<macros>
  <shard>1</shard>            <!-- Shard 1 节点填 1，Shard 2 填 2 -->
  <replica>ck-node1</replica> <!-- 填 hostname 或唯一标识 -->
</macros>
```

### 检查集群状态

```sql
-- 查看集群所有节点
SELECT * FROM system.clusters WHERE cluster = 'production';

-- 查看本地表和 Replicated 表
SELECT database, table, engine FROM system.tables WHERE engine LIKE '%Replicated%';

-- 查看 Keeper 连接状态
SELECT * FROM system.zookeeper WHERE path = '/clickhouse';

-- 分片健康度
SELECT shard_num, is_local, hostname, port, status
FROM system.clusters
WHERE cluster = 'production'
ORDER BY shard_num, is_local DESC;
```

## 查询路由：分布式 vs 本地查询

```sql
-- 分布式查询（查所有分片）
SELECT count() FROM orders_distributed WHERE dt = '2026-11-03';

-- 本地查询（只查当前节点的分片）
SELECT count() FROM orders_local WHERE dt = '2026-11-03';

-- 带分片键条件的分布式查询 → ClickHouse 自动只下发到相关 Shard
SELECT count() FROM orders_distributed
WHERE cityHash64(user_id) % 3 = 0    -- 只路由到 Shard 0
  AND dt = '2026-11-03';
```

## 跨机房部署

| 模式 | 说明 | 推荐场景 |
| --- | --- | --- |
| **单机房多节点** | Shard 内副本都在同机房 | 绝大多数生产 |
| **同城双活** | 每个 Shard 的 Replica 分布到两个机房 | 金融、核心业务 |
| **跨地域灾备** | Keeper 选法定居一地，副本异步同步 | 极端容灾 |

跨机房时配置 `<internal_replication>true</internal_replication>` 让 ReplicatedMergeTree 自动在跨机房副本间复制 Part。

## 常见问题

**Q：为什么分布式查询不走 ORDER BY？**
A：Distributed 引擎会自动在 Coordinator 节点做最终聚合。如果 GROUP BY 在远端做了预聚合，Coordinator 再做一次聚合就能得到正确结果。但 ORDER BY 需要全量数据，会把所有分片结果拉回 Coordinator，可能爆内存。解决办法：加 LIMIT 让 Coordinator 只排前 N 条。

**Q：节点挂了怎么办？**
A：如果挂的是某个 Replica → 没关系，Keeper 会自动让其他 Replica 继续服务。如果挂的是整个 Shard（所有 Replica 都挂）→ 数据暂时不可读，恢复后自动。分布式写入时如果目标节点不可用，Distributed 引擎会重试或丢数据（看超时配置）。

**Q：ReplicatedMergeTree 和 Distributed 是什么关系？**
A：完全独立！ReplicatedMergeTree 是**本地表的副本机制**，Distributed 是**跨节点查询路由**。通常一起用：本地表用 ReplicatedMergeTree 存数据，Distributed 表作为查询入口。

**Q：集群规模上限？**
A：ClickHouse 官方测试过 200+ 节点的集群。但超过 50 节点后 Distributed 查询的 Coordinator 节点可能成为瓶颈，需要按业务做路由拆分或用多个 Coordinator。
