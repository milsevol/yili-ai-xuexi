# 01 概述与定位

## 一句话

**ClickHouse**：一个列式存储 + 向量化执行的 OLAP（在线分析处理）数据库，核心是 MergeTree 引擎家族。它把「海量数据聚合查询」这件事做到极致快——同量级数据下，单表聚合通常比 Hive / Spark SQL / Trino 快 5–100 倍。

## 它解决什么问题

Hive / Spark SQL 的问题：数仓链路太长（ETL→落 HDFS→执行引擎跑 MR/Tez/Spark），即使 Spark 也得 Shuffle 落盘；Trino 虽然快但依赖外部存储（HDFS/S3）的随机 IO，列式能力有限。ClickHouse 的思路是：**数据直接在本地 SSD 上、按列存、向量化算、有序合并**，查询路径最短、IO 最少、SIMD 打满。

| 痛点 | 用 Hive/Spark 时 | 用 ClickHouse 后 |
| --- | --- | --- |
| 实时看板延迟 | 小时级（等 ETL）或分钟级（Spark Streaming） | 秒级（数据写了就查） |
| 用户行为分析 | 写 DWD/DWS/ADS 分层、跑 Spark 作业 | 一张表直接 `SELECT count(*), ... GROUP BY ...` |
| 日志检索分析 | Elasticsearch（贵）或 Hive（慢） | MergeTree 列式压缩好 + Bloom Filter |
| 指标系统 | Redis（存不下全量）或 ClickHouse | 实时聚合写入 + SummingMergeTree 预聚合 |

## ClickHouse vs Hive vs Spark SQL vs Trino vs Doris

| 维度 | ClickHouse | Hive (on Tez) | Spark SQL | Trino | Doris |
| --- | --- | --- | --- | --- | --- |
| **存储** | 本地 MergeTree（SSD/HDD） | HDFS / 对象存储 | 外部存储（HDFS/S3） | 外部存储（HDFS/S3） | 本地列存（SSD） |
| **查询延迟** | 毫秒~秒级 | 分钟级 | 秒级~分钟级 | 亚秒级~秒级 | 毫秒级~秒级 |
| **写入模型** | 批量/微批量 + Merge 后台合并 | 批式 INSERT OVERWRITE | 批式 + 微批（Structured Streaming） | 只读（查询外部表） | 实时/批式导入 + Compaction |
| **分布式** | 原生 Distributed + ReplicatedMergeTree | 依赖 YARN + Tez/Spark | 原生集群 | 原生 Coordinator/Worker | 原生 FE/BE 两节点 |
| **事务** | ❌ 无 ACID（MergeTree 最终一致） | 4.x ACID（仅 ORC） | Delta/Iceberg 支持 | Iceberg/Hudi/Delta 支持 | ✅ 部分事务 |
| **复杂 JOIN** | ⚠️ 较弱（BroadcastHashJoin 有限） | ✅ 成熟 | ✅ Catalyst 优化好 | ✅ 强（多数据源） | ✅ 强 |
| **点查（PK）** | ❌ 不适合（但有 primary key 索引） | ❌ | ❌ | ❌ | ✅ 支持 |
| **优势** | 单表聚合极快、列存压缩好、向量化 | 数仓建模成熟、元数据中心 | 多模态、迭代、ML | 多数据源联邦交互 | 兼容 MySQL 协议、冷热分离 |

## 为什么 ClickHouse 那么快

四个原因环环相扣：

| 机制 | 原理 | 性能提升 |
| --- | --- | --- |
| **列式存储 + 压缩** | 同一列数据类型相同，压缩率可达 10–20x；查询只读需要的列 | IO 减少 90%+ |
| **SIMD 向量化执行** | 一次处理 64–256 行数据（CPU 寄存器批处理），而非逐行 | 运算吞吐 5–10x |
| **有序合并 MergeTree** | 数据按 ORDER BY 写入、后台异步合并成有序 Part，查询天然有序 | 减少排序 + 索引精准定位 |
| **无锁异步 IO** | 写入 append-only 无锁；Merge 后台线程异步；查询无全局锁 | 高并发下不阻塞 |

```
CPU 视角的向量化
  传统行式:  1 行 1 行算 → 每次计算一个值
  向量化:    64 行打包 → 一个 SIMD 指令算 64 个值

磁盘视角的列存
  行存 (CSV/JSON): SELECT col1 → 读整行所有列
  列存 (MergeTree): SELECT col1 → 只读 col1 这一列的文件
```

## 适用场景 vs 不适合场景

| 适用场景 | 为什么 | 示例 |
| --- | --- | --- |
| 实时看板 / BI 报表 | 秒级响应、聚合快、可直接供 Grafana/Metabase | 电商大盘、广告投放监控 |
| 用户行为分析 | 点击流、埋点日志，一张表 TB 级 | UV/PV、漏斗转化、留存分析 |
| 日志分析 | 列式压缩节省空间、Bloom Filter 加速检索 | ClickHouse Keeper / ZK 集群监控 |
| 指标系统 | SummingMergeTree / AggregatingMergeTree 预聚合 | 游戏服务器指标、APM 系统 |
| 时序数据分析 | Date/DateTime 分区 + 列存 | IoT 传感器、金融行情 |

| 不适合场景 | 为什么 | 替代方案 |
| --- | --- | --- |
| OLTP 在线业务库 | 无事务、不支持 DELETE/UPDATE 即时生效 | MySQL / PostgreSQL / TiDB |
| 高频点查（PK 定位一行） | MergeTree 按范围扫描，不是 KV 引擎 | HBase / Redis / TiDB Primary Key |
| 复杂多表 JOIN | BroadcastHashJoin 有限，大表 JOIN 性能差 | Spark SQL / Doris / StarRocks |
| 长链路 ETL | 不支持事务、Compaction/Merge 会影响查询 | Hive on Spark / Flink |

## 一句话记住 ClickHouse 的边界

> **ClickHouse 是「写入→合并→聚合查询」的那台大机器**：列存让它 IO 少，向量化让它算得快，MergeTree 让它天然有序。它不做事务、不做点查、不做复杂 JOIN——这些交给 MySQL / HBase / Spark，ClickHouse 专注「大规模聚合查询」。

## 常见问题

**Q：ClickHouse 能替代 Hive 吗？**
A：不能全替代。Hive 做 ETL（长链路、事务、多表 JOIN），ClickHouse 做 ADS 层（报表查询、实时看板）。常见组合是 Hive/Spark 把清洗后的数据写到 ClickHouse 供查询。

**Q：ClickHouse 能写入 MySQL 数据吗？**
A：可以通过 MySQL 引擎 `CREATE TABLE ... ENGINE = MySQL(...)` 查询 MySQL 表，但不推荐长期写入——ClickHouse 真正擅长的是 append-only 的批量写入。CDC 场景推荐 Flink CDC + Kafka + Materialized View 入 ClickHouse。

**Q：ClickHouse 和 Doris / StarRocks 怎么选？**
A：都做 OLAP 但路径不同。ClickHouse 偏极简、列式极致快、无事务；Doris 兼容 MySQL 协议、有事务、冷热分离好。选型看团队熟悉度和场景（复杂 ETL+OLAP→Doris；纯实时看板→ClickHouse）。
