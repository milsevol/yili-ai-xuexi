# 09-性能调优与实践

## 一句话

ClickHouse 调优分四类：**写入调优**（批量、异步、max_insert_block_size）、**查询调优**（分区裁剪、跳数索引、投影、IN 代替 JOIN）、**后台 Merge 调优**（控制 Part 数量、Merge 并发、阻塞排查）、**Mutation 调优**（避免频繁 ALTER UPDATE/DELETE，用 ReplacingMergeTree 替代）。80% 的问题来自 Part 太多——从根源上解决比调参数有效。

## 写入优化

写入是 ClickHouse **最容易踩坑的环节**——每次 INSERT 产生一个 Part，Part 太多 = 查询变慢 + Merge 堆积。

### 写入模式选择

| 模式 | 方法 | Part 产生 | 适用 |
| --- | --- | --- | --- |
| **批量 VALUES** | 单次 INSERT 5000+ 行 | 1 个 Part / 批次 | ✅ 推荐，绝大多数场景 |
| **微批量 Buffer** | 100–1000 行/次，BatchWriter 缓冲 | 1 个 Part / 刷盘 | 实时场景（写入频率高） |
| **异步写入** | AsyncInsert（21.x+） | 1 个 Part / flush 周期 | 极高并发写入 |
| **kafka 引擎** | Kafka → MV 入仓 | 1 个 Part / 消费批次 | CDC 场景 |
| **单行多次 INSERT** | ❌ 禁止 | N 个 Part！ | 会产生 Part 爆炸 |

### 批量写入参数

```sql
-- 单次 INSERT 多少行算一个 block（默认 1M 行）
SET max_insert_block_size = 1048576;    -- 1M 行 / Part（默认）

-- 单次 INSERT 最大消息体（字节）
SET max_insert_size = 1073741824;       -- 1GB / INSERT

-- INSERT 目标表 Part 过多警告阈值
SET max_parts_in_total = 100000;        -- 超过拒绝写入
SET max_parts_per_queue = 50000;        -- Merge 队列中 Part 上限

-- 一个插入批次最少多少 Part 才触发 Merge
SET min_merge_bytes_to_use_direct_io = 104857600;  -- 100MB 以上用 Direct IO
```

### 异步写入 AsyncInsert

21.x+ 新特性，适合高并发微批量写入：

```sql
-- 服务器级开启（config.xml）
<async_insert>1</async_insert>
<async_insert_max_data_size>10485760</async_insert_max_data_size>  -- 10MB 刷盘
<async_insert_busy_timeout_ms>200</async_insert_busy_timeout_ms>   -- 最多等 200ms
<wait_for_async_insert>1</wait_for_async_insert>                   -- 同步等待刷盘完成
```

```sql
-- 或者 SQL 级控制单次 INSERT 异步
SET async_insert = 1;
INSERT INTO orders VALUES (...);   -- 自动进入 Buffer，批量刷盘
```

**优点**：多个小 INSERT 自动合并成一个 Part。**注意**：客户端要开启 `wait_for_async_insert = 1` 确保写入成功反馈。

### Python 写入示例

```python
from clickhouse_driver import Client

client = Client('localhost', port=9000)

# ✅ 批量写入（推荐）
rows = [(i, 101, 99.0, '2026-11-03') for i in range(100000)]
client.execute('INSERT INTO orders VALUES', rows)   # 一次 10 万行

# ❌ 不要：循环单行 INSERT
for row in rows:
    client.execute('INSERT INTO orders VALUES', [row])  # 产生 10 万 Part！
```

## 查询优化

### 查询 Checklist（从高到低优先级）

| 优先级 | 优化项 | 验证 |
| --- | --- | --- |
| ⭐⭐⭐ | **分区裁剪**：WHERE 用等值或范围分区键 | EXPLAIN PIPELINE 看 partition pruning |
| ⭐⭐⭐ | **跳数索引**：WHERE 列有 bloom_filter / minmax / set 索引 | EXPLAIN 看 Skipping index |
| ⭐⭐⭐ | **主索引**：WHERE 列在 ORDER BY 前面 | EXPLAIN 看 Marks read 比例 |
| ⭐⭐ | **列裁剪**：只 SELECT 需要的列 | EXPLAIN 看 Result columns |
| ⭐⭐ | **投影 Projections**：常用查询预存副本 | 自动选择 |
| ⭐⭐ | **IN 代替 JOIN**：小表值用 IN 过滤 | 避免 JOIN 开销 |
| ⭐ | **DISTINCT → GROUP BY** | DISTINCT 底层转 GROUP BY，手动写更可控 |
| ⭐ | **FINAL 慎用** | FINAL 强制合并 Part，极慢！ |

### IN 代替 JOIN

```sql
-- ❌ 慢（大表 JOIN）
SELECT o.* FROM orders o
INNER JOIN (SELECT user_id FROM vips WHERE level >= 3) v
ON o.user_id = v.user_id;

-- ✅ 快（小表值直接 IN）
SELECT * FROM orders
WHERE user_id IN (101, 102, 103, ..., 9999);   -- vips 表先查出再拼 IN
```

### GROUP BY 优化

```sql
-- GROUP BY 列有 ORDER BY 前缀 → 主索引加速
SELECT city, count() FROM orders GROUP BY city;
-- 如果 ORDER BY (city, user_id, dt) → GROUP BY city 能走主索引

-- 如果 GROUP BY 列不在 ORDER BY 里 → 用 External Dictionary
```

### External Dictionary 字典表

把维表预加载到内存，查询时像函数一样查：

```xml
<!-- config.xml 定义字典 -->
<dictionaries>
  <dictionary>
    <name>user_dict</name>
    <source>
      <mysql>
        <host>mysql-host</host>
        <port>3306</port>
        <db>shop</db>
        <table>users</table>
        <user>root</user>
        <password>root</password>
      </mysql>
    </source>
    <structure>
      <id>user_id</id>
      <attribute name="level" type="UInt8" />
      <attribute name="city" type="String" />
    </structure>
    <layout><flat /></layout>   <!-- 内存全量加载 -->
    <lifetime><min>300</min><max>3600</max></lifetime>
  </dictionary>
</dictionaries>
```

```sql
-- 查询时像函数一样用
SELECT
  user_id,
  dictGet('user_dict', 'level', user_id) AS level,
  dictGet('user_dict', 'city', user_id) AS city
FROM orders
WHERE dt = '2026-11-03';
-- 等价于 JOIN，但字典查询是内存操作，极快
```

### EXPLAIN PIPELINE 验证

```sql
EXPLAIN PIPELINE SELECT ...;

-- 重点看：
-- 1. Partition pruning: dt in [...]     ← 分区裁剪
-- 2. Skipping index: idx_xxx used       ← 跳数索引
-- 3. Marks read: 5/20                   ← 主索引跳过比例（越大越好）
-- 4. Result columns: [city, amount]     ← 列裁剪
-- 5. Spill: yes                          ← 是否溢出到磁盘
```

## Merge 阻塞排查

### Part 太多是第一杀手

```sql
-- 查看某表的 Part 数量
SELECT count() FROM system.parts WHERE table = 'orders' AND active;

-- 查看单表 Part 数和数据量
SELECT
  table,
  count() AS parts,
  sum(rows) AS rows,
  sum(bytes_on_disk) / 1024 / 1024 AS size_mb
FROM system.parts
WHERE active AND database = 'default'
GROUP BY table
ORDER BY parts DESC;
```

**Part 数警戒线**：
| 单表 Part 数 | 风险 | 处理 |
| --- | --- | --- |
| < 100 | 正常 | — |
| 100–1000 | 关注 | 检查写入批量大小 |
| 1000–10000 | 警告 | 加速 Merge 或优化写入 |
| > 10000 | 危险 | **可能即将拒绝写入** |

### Merge 堆积诊断

```sql
-- 查看 Merge 任务队列
SELECT
  table,
  count() AS queued_merges,
  sum(rows) AS rows_merged,
  sum(merge_progress) AS progress
FROM system.merges
GROUP BY table;

-- 查看 Merge 延迟（多久没合并了）
SELECT
  table,
  name,
  rows,
  bytes_on_disk / 1024 / 1024 AS size_mb,
  now() - modification_time AS age_sec
FROM system.parts
WHERE active
ORDER BY modification_time
LIMIT 20;
```

### Merge 调优参数

```sql
-- 服务器级 config.xml
<max_merge_select_sleep_ms>50</max_merge_select_sleep_ms>      <!-- 两次 Merge 选择间隔 -->
<max_parts_to_merge_at_once>100</max_parts_to_merge_at_once>   <!-- 单次 Merge 最多合并多少 Part -->
<merge_with_ttl_timeout>86400</merge_with_ttl_timeout>          <!-- TTL 分区 Merge 等待时间 -->

-- SQL 级临时调优
SET max_merges_in_queue = 16;            <!-- 同时执行的 Merge 数 -->
SET max_merge_bytes = 104857600000;      <!-- 单次 Merge 最大 100GB -->
SET use_minimalistic_part_header_in_zookeeper = 1;  <!-- 减少 Part 元数据大小 -->

-- 手动紧急触发 Merge（慎用！会占用大量资源）
SYSTEM START MERGES orders;
OPTIMIZE TABLE orders FINAL;   -- 强制所有 Part 合成一个
```

### Merge 慢的常见原因

| 原因 | 诊断 | 解决 |
| --- | --- | --- |
| **Part 产生太快** | 每秒写入产生 > 10 个 Part | 加大 INSERT 批量；开 AsyncInsert |
| **磁盘 IO 不够** | Merge 时磁盘使用率 100% | 换 SSD 或加节点分散负载 |
| **单表 Merge 被其他表抢了** | 系统有其他大表 Merge 排队 | 提高该表 Merge 优先级 `merge_with_ttl_timeout` |
| **TTL 分区卡住** | 有 TTL 过期分区但没 Merge | 手动 `SYSTEM FLUSH TTL` |

## Mutation 慢处理

Mutation 是 ClickHouse 的「UPDATE / DELETE」——实际上是后台**重写所有 Part**：

```sql
-- ❌ 很慢！Mutation = 重写所有 Part
ALTER TABLE orders UPDATE status = 2 WHERE id IN (1, 2, 3);
ALTER TABLE orders DELETE WHERE dt < '2025-01-01';

-- 替代方案 1：ReplacingMergeTree 代替 UPDATE
-- 写入新数据让后台 Merge 去重

-- 替代方案 2：Partition DROP 代替 DELETE
ALTER TABLE orders DROP PARTITION '20241231';

-- 替代方案 3：TTL 自动过期
ALTER TABLE orders MODIFY TTL dt + INTERVAL 90 DAY;
```

| 操作 | 推荐方式 | 不推荐方式 |
| --- | --- | --- |
| 单行/少量行更新 | ReplacingMergeTree + 写入新数据 | ALTER UPDATE |
| 批量更新 | 业务层重新写整表 | ALTER UPDATE |
| 删除过期数据 | TTL 自动过期 / DROP PARTITION | ALTER DELETE |
| 单行删除 | ReplacingMergeTree + 写入新行替代 | ALTER DELETE |

### Mutation 进度检查

```sql
SELECT
  table,
  mutation_id,
  command,
  create_time,
  latest_fail_reason,
  parts_to_do,
  is_done
FROM system.mutations
WHERE NOT is_done
ORDER BY create_time;
```

## TTL 后台调度

```sql
-- config.xml TTL 调度参数
<merge_with_ttl_timeout>86400</merge_with_ttl_timeout>    <!-- 24h 检查一次 TTL -->
<merge_reduce_tightness>4</merge_reduce_tightness>         <!-- Merge 紧急度 -->
<max_threads_ttl_move>4</max_threads_ttl_move>             <!-- TTL Move 线程数 -->

-- 强制立即执行 TTL
SYSTEM FLUSH TTL orders;

-- TTL Delete vs Move
-- 直接删除：TTL dt + INTERVAL 180 DAY DELETE
-- 移动到冷盘：TTL dt + INTERVAL 180 DAY TO DISK 'cold'
-- 先移动后删除：TTL dt + INTERVAL 180 DAY TO DISK 'cold', dt + INTERVAL 365 DAY DELETE;
```

## 常见报错速查

| 报错信息 | 原因 | 解决方案 |
| --- | --- | --- |
| `Too many parts` | 单表 Part 数超限（默认 10w） | ① 优化写入；② 手动触发 Merge；③ 临时提高 max_parts_in_total |
| `Timeout exceeded` | 分布式查询超时 | ① 加 SET distributed_insert_timeout；② 检查网络/Keeper |
| `Memory limit (total)` | 查询内存超限 | ① 调大 max_memory_usage；② 加 LIMIT；③ 拆查询；④ 检查大 JOIN |
| `Cannot insert null` | 写入 Nullable 列但列没标 Nullable | 检查 DDL 是否有 Nullable 声明 |
| `Cannot parse date` | 日期格式不对 | 用 toDate('2026-11-03') 或正确格式 |
| `Keeper connection timeout` | Keeper 连不上 | ① 检查 Keeper 集群；② 检查 DNS；③ 看 Keeper 日志 |
| `Cannot read from replica` | 副本同步卡住 | ① 手动 SYSTEM SYNC REPLICA；② 重建副本 |
| `TTL not applied` | TTL 没生效 | ① 检查 TTL 语法；② 强制 SYSTEM FLUSH TTL |
| `No such sharding key` | Distributed 引擎分片键不对 | 检查 Distributed 表的 sharding_key 参数 |
| `Mutations queue is full` | ALTER UPDATE/DELETE 堆积 | ① 清理 mutations；② 用 ReplacingMergeTree 代替；③ 提高 max_mutations_in_queue_size |

## 性能调优 Checklist

```
✅ 写入侧
  [ ] 批量 INSERT（≥ 5000 行/批）
  [ ] 避免高频单行 INSERT
  [ ] AsyncInsert 开启（高并发场景）
  [ ] ReplacingMergeTree / SummingMergeTree 用于去重/预聚合

✅ 存储侧
  [ ] PARTITION BY 用时间字段（toYYYYMMDD）
  [ ] ORDER BY 按最常用查询过滤条件排序
  [ ] index_granularity = 8192（默认）
  [ ] 跳数索引 bloom_filter city / minmax amount / set user_id

✅ 查询侧
  [ ] WHERE 分区键等值/范围 → 分区裁剪
  [ ] WHERE ORDER BY 前缀 → 主索引命中
  [ ] 只用需要的列 → 列裁剪
  [ ] IN 代替小表 JOIN
  [ ] DISTINCT → GROUP BY 手动写

✅ 后台维护
  [ ] 定期检查 Part 数（< 1000）
  [ ] 定期检查 Merge 队列
  [ ] TTL 自动清理历史数据
  [ ] 避免 Mutations（ALTER UPDATE/DELETE）
```

## 常见问题

**Q：分布式查询慢，怎么加并发？**
A：先看每个 Shard 的本地查询是否快。本地查询没问题但分布式慢 → 检查 `SET max_distributed_connections` 和 Coordinator 节点内存。本地查询也慢 → 回到查询侧 checklist。

**Q：大表 DROP PARTITION 卡住？**
A：DROP PARTITION 是异步的，标记 inactive 后由后台线程删除。可以用 `SYSTEM FREEZE PARTITION` 先备份，等后台清理完再确认。

**Q：ReplacingMergeTree 的 FINAL 查询太慢？**
A：FINAL 强制查询时合并所有 Part。如果必须临时去重且数据不大可以用，但数据量大（>10GB）时完全不可接受。建议业务层用 ReplacingMergeTree 的 Merge 天然去重逻辑，不用 FINAL。
