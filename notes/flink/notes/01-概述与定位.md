# 01 概述与定位

## 一句话

**Apache Flink**：一个真正的**流计算引擎**——它假设数据是连续不断地到来的（无限流），在这个前提下把**状态 State、精确一次 Exactly-Once、事件时间 Event-Time、检查点 Checkpoint** 四件事做到了开箱即用，同时也能把有限数据集当作流来跑，实现**流批一体**。

## 为什么世界需要 Flink

2014 年以前，流处理有三个流派：

| 流派 | 代表 | 核心思路 | 问题 |
| --- | --- | --- | --- |
| **微批** | Spark Streaming (DStream) | 把无限流切成小批次（如 1s），每批走 Spark 批处理引擎 | 延迟 ≈ 批间隔，语义是「逐批一次」不是「单条一次」；状态靠外部存储 |
| **原生流** | Storm / Heron | 每条消息立即处理 | 状态管理简陋；容错只能靠 ACK/Tuple Tree；Exactly-Once 很难；窗口和时间需要自己造 |
| **Lambda 架构** | Netflix 提出 | 热路径 Storm 实时、冷路径 Hadoop 批处理；两套代码合并 | 两套系统维护成本大；结果合并不一致 |

Flink 的核心洞察：**数据本质上是流**。批数据只是「有限流」。所以它从一开始就以流为原语，在流引擎上复用了算子链、状态、时间语义。

## Flink vs Spark Streaming vs Storm

| 维度 | Flink | Spark Structured Streaming | Storm |
| --- | --- | --- | --- |
| 处理模型 | 逐条/微批（底层流） | 微批（默认 100ms+，也可连续） | 逐条（原生流） |
| 延迟 | ms ~ s 级 | ms ~ s 级（取决于微批） | ms 级 |
| Exactly-Once | Checkpoint + Barrier，原生支持 | Checkpoint + WAL，支持 | 靠 ACK + 重放，应用层自己保证 |
| 状态管理 | KeyedState / OperatorState / RocksDB | Offset + StateStore (RocksDB) | 几乎无，靠外部 |
| 事件时间 | Watermark 原生 | Watermark 支持（2.3+） | 无原生支持 |
| 窗口 | 滚动/滑动/会话/自定义 | 滚动/滑动/会话（SQL Window） | 要自己实现 |
| 吞吐 | 高（异步 IO、算子链） | 高（批处理引擎复用） | 中（纯逐条） |
| API | DataStream / ProcessFunction / SQL | DataFrame / Dataset / SQL | Topology / Spout / Bolt |

## Flink 在大数据链路中的位置

```
┌─────────┐     ┌─────────┐     ┌──────────────┐     ┌──────────┐
│  Kafka  │────▶│  Flink  │────▶│ HBase / Doris │────▶│ 查询引擎  │
│ (数据入湖)│     │  (ETL)   │     │ / Iceberg     │     │ Trino    │
└─────────┘     └─────────┘     └──────────────┘     └──────────┘
                    │
                    ▼
            Flink SQL CDC
                    │
                    ▼
            MySQL/PG Binlog → 湖仓表（Iceberg/Hudi）
```

- **上游**：Kafka（实时消息总线）、MySQL/PG Binlog（CDC）、文件（HDFS/S3）
- **中游**：Flink 做 ETL / 规则引擎 / 实时聚合 / CDC 入湖
- **下游**：HBase / Doris / ClickHouse（在线点查/OLAP），Iceberg/Hudi/Delta（湖仓表），Kafka（写回）

## 发展简史

- **2014** StratoSphere（柏林工业大学 + 阿里）项目进入 Apache，改名 Flink
- **2016** 成为 Apache 顶级项目；同年 1.1 发布，DataStream API 初版
- **2018** 阿里巴巴 Blink 分支合入社区，Table API / SQL 引擎重大升级
- **2020** 1.11 发布 SQL CDC Source；国内团队大规模上生产
- **2022** 1.15 引入 Watermark 新机制；1.17 引入 Dynamic Table Changes
- **2024** 1.18 / 1.19 稳定版；1.20 引入 Async State 与 Flink SQL Gateway

## 真正的流 vs 微批

这是理解 Flink 的第一道坎：

| | 真正的流（Flink） | 微批（Spark Streaming 旧版） |
| --- | --- | --- |
| 数据怎么进来 | 逐条触发算子 | 积累到批间隔再一起处理 |
| 状态更新 | 每条更新，可即时触发 Timer | 批内聚合，批结束写状态 |
| Checkpoint | Barrier 对齐，每条都能包含 | 批结束后统一 Checkpoint |
| 窗口触发 | 时间到达 + Watermark 触发 | 批边界触发 |
| 反压 | 原生（Mailbox、Credit-Based） | 靠 Receiver 限流 |

Spark Structured Streaming 在 2.3 之后引入了 Continuous Processing 模式和 Watermark，向 Flink 靠拢，但底层仍然是批处理引擎的 DAG 执行。

## Flink 的四个核心概念

1. **State（状态）**：Flink 算子在处理过程中持有的中间数据，如窗口缓存、会话、计数器。Keyed State 自动按 Key 分片。
2. **Checkpoint（检查点）**：Flink 定期把所有算子的状态快照持久化，失败后从最近一次 Checkpoint 恢复，保证 Exactly-Once。
3. **Watermark（水位线）**：衡量「事件时间至少到哪了」的机制。单调递增，允许一定乱序容忍。用来触发窗口、判断迟到。
4. **Exactly-Once（精确一次）**：每条数据只被处理一次。靠 Barrier 对齐 + Checkpoint + Sink 事务/幂等配合。

## 关键配置

```properties
# 启用 Checkpoint（这是生产必须的）
execution.checkpointing.enabled: true
execution.checkpointing.interval: 60000   # 60s 一次
execution.checkpointing.mode: EXACTLY_ONCE
execution.checkpointing.timeout: 600000
execution.checkpointing.min-pause: 10000

# State Backend（生产推荐 RocksDB）
state.backend: rocksdb
state.checkpoints.dir: hdfs:///flink/checkpoints
state.savepoints.dir: hdfs:///flink/savepoints

# 重启策略
restart-strategy: fixed-delay
restart-strategy.fixed-delay.attempts: 5
restart-strategy.fixed-delay.delay: 10s

# 并行度（全局默认）
parallelism.default: 4
```

## 常见问题

- **Flink 和 Spark 谁更好？** → 实时性（< 1s）选 Flink，批处理/T+1/SQL 生态选 Spark；新项目两者互补。
- **Flink 能跑批吗？** → 能，把有限数据集读入当作流处理即可；Flink SQL 支持 Batch 执行器。
- **Exactly-Once 就一定完全一致吗？** → 不一定。Sink 必须是事务型或幂等的（Kafka 0.11+ Producer、HBase put 带版本）。如果 Sink 做不到，只能 At-Least-Once。
- **Storm 还有人用吗？** → 逐渐萎缩，新项目基本不选；Heron（Twitter 贡献）也趋于停滞。
