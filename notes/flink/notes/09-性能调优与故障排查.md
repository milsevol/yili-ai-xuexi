# 09 性能调优与故障排查

## 一句话

Flink 生产排障遵循「**反压 → 倾斜 → Checkpoint → State → GC**」的路径：先用 Flink UI 找到哪个算子是反压源头，再看数据倾斜、State 大小、Checkpoint 时长、GC 日志。性能优化从「让算子链跑满」（并行度匹配、Operator Chain、异步 IO）到「让状态可控」（RocksDB、增量 Checkpoint、TTL），最后到「让 GC 不卡」（G1 参数、Heap 大小）。

## 排障总览决策树

```
作业出问题了
│
├─ 【现象 1】吞吐低 / 延迟高
│   │
│   ├─ Flink UI 看反压（Backpressure）
│   │   ├─ HIGH → 该算子被下游堵住了
│   │   │   ├─ 下游是 Sink → Sink 慢（Kafka Broker/HBase/HDFS）
│   │   │   ├─ 下游是 Window → 窗口聚合慢（并行度不够？倾斜？）
│   │   │   └─ 下游是 keyBy → keyBy 之后倾斜（看各 Subtask 处理量）
│   │   ├─ OK → 继续查
│   │
│   ├─ 数据倾斜（Skewed Data）
│   │   └─ 见「数据倾斜」节
│   │
│   └─ GC 问题
│       └─ 见「GC 问题」节
│
├─ 【现象 2】Checkpoint 慢 / 超时
│   ├─ 见第 06 章 Checkpoint 慢排查
│   └─ State 太大 → 见 State 节
│
├─ 【现象 3】作业反复重启
│   ├─ State 过大 OOM → 换 RocksDB + 加 TTL
│   ├─ Checkpoint 对齐超时 → 反压或 Source 卡顿
│   └─ 外部依赖挂（Kafka/HBase）→ 下游 Sink 阻塞
│
└─ 【现象 4】算子 Subtask 异常
    ├─ NullPointerException → 业务代码
    ├─ ClassCastException → 类型转换问题
    └─ OutOfMemoryError
        ├─ Java heap space → Heap 不够
        └─ Direct buffer memory → Network Buffer 不够
```

## 反压 Backpressure

### 原理

Flink 用**Credit-Based 流控**（1.5+）：

```
上游 OP1 ──── 下游 OP2
   │ 有 Credit（允许发送多少数据量/字节） │
   └──────────────────────────────────┘
```

下游消费慢 → Credit 少 → 上游收到的 Credit 不够 → 反压。

### 定位方法

**Flink UI → Job → 某个 Operator → SubTask → BackPressure 列**：

| 状态 | 含义 |
| --- | --- |
| **OK** | 无反压 |
| **LOW** | 轻微反压，通常可接受 |
| **HIGH** | 严重反压，需要处理 |

### 常见原因与解决

| 反压源头 | 原因 | 解法 |
| --- | --- | --- |
| **Sink** | Kafka Broker 慢、HBase RegionServer 满、HDFS 写慢 | 查外部系统指标；加 Sink 并行度；异步 IO；本地先攒批 |
| **Window** | 窗口内数据太多（倾斜）、WindowFunction 计算慢 | 查各 Subtask 窗口大小；Window Function 里用增量 AggregateFunction |
| **KeyBy 之后** | 数据倾斜 → 某个 Subtask 数据量远大于其他 | 见「数据倾斜」节 |
| **Source** | Source 并行度不够 / 下游算子太慢 | Source 并行度 = Kafka Partition；下游并行度跟上 |
| **Checkpoint 期间** | Barrier 对齐时产生反压 | 正常现象；反压严重说明算子状态大或下游反压 |

## 数据倾斜

### 怎么识别

Flink UI → Job → Operator → Subtasks Tab → **Records In/Out** 列：

- **正常**：各 Subtask 记录数在 ±30% 范围内
- **倾斜**：某个 Subtask 远大于其他（比如 10x）

### 常见倾斜场景与解法

| 场景 | 解法 |
| --- | --- |
| **空值 Key**（null） | 单独处理 null Key（随机分到不同 Subtask）；或过滤掉 |
| **大 Key**（如热门商品、热门用户） | 拆分大 Key：Key → Key + 随机后缀；最后再聚合回来 |
| **动态 Key 数量暴增** | 加过滤；限制 Key 集合；用 TTL 清理过期 Keyed State |
| **keyBy 之前没先过滤** | keyBy 之前加 filter 减少数据量 |
| **Session Window 倾斜** | 加随机前缀拆大会话 |

### 大 Key 拆分示例

```java
// 原代码：user_id 倾斜严重
dataStream.keyBy(o -> o.getUserId())
          .window(...).aggregate(...);

// 解法：先随机分桶聚合，再二次 keyBy 合并
dataStream
    .map(o -> new Tuple3<>(o.getUserId(), o, ThreadLocalRandom.current().nextInt(10)))
    .keyBy(t -> t.f0 + "_" + t.f2)    // 加随机桶
    .window(...).aggregate(partial)
    .keyBy(t -> t.f0)                 // 再按原 Key
    .sum("amount");                    // 二次聚合
```

## State 过大 OOM

### 识别

- TM 日志出现 `java.lang.OutOfMemoryError: Java heap space`
- 或 Flink UI 显示 `State Size` 持续增长

### 解法阶梯

1. **换 RocksDBStateBackend**（必须的第一步）
2. **加 State TTL**（过期 Keyed State 自动清理）
3. **加窗口 allowedLateness** 但别太大（否则窗口状态堆）
4. **检查 ListState / MapState 是否无限增长**（业务 Bug）
5. **增加 TM Managed Memory** + 加 TM 节点
6. **检查并行度**：是不是某些 Key Group 分布不均（罕见）

### State TTL

```java
// 在 KeyedProcessFunction 里创建 StateDescriptor 时加 TTL
ValueStateDescriptor<Long> desc = new ValueStateDescriptor<>("counter", Long.class);
StateTtlConfig ttl = StateTtlConfig
    .newBuilder(Time.hours(24))
    .setUpdateType(StateTtlConfig.UpdateType.OnCreateAndWrite)
    .setStateVisibility(StateTtlConfig.StateVisibility.NeverReturnExpired)
    .build();
desc.enableTimeToLive(ttl);
this.counter = getRuntimeContext().getState(desc);
```

TTL 工作方式：

- 每次写入 State 时刷新过期时间
- 24 小时没写入 → 该 State 过期
- 过期 State **不是立刻物理删除**，Flink 在访问时跳过 / 清理，或 Checkpoint 时跳过

## Checkpoint 慢

详见第 06 章的 Checkpoint 慢排查图。补充几个关键点：

### RocksDB 本地磁盘

```bash
# 在 TM 节点上看磁盘 IO
iostat -x 1
# %util 接近 100% → 磁盘瓶颈，换 SSD / 加盘 / 调小 State
```

### 增量 Checkpoint

```properties
state.backend.incremental: true
state.backend.rocksdb.compaction-task-threads: 4
```

### Checkpoint 间隔

```
间隔 ≥ max(快照时间 × 3, 60s)
```

间隔太小 → Checkpoint 叠在一起，更慢；间隔太大 → 恢复时重放太多数据。

## GC 问题

### 怎么识别

- Flink UI 上 TM 的 **JVM CPU Usage** 长期 > 50%
- TM 日志里 Full GC 频率高、停顿时间长
- GC 日志：`-Xlog:gc*:file=gc.log:time,uptime,level,tags`

### 调优步骤

1. **确认用 G1GC**（JDK 11 默认，但要加参数优化）
2. **Heap 大小**：Flink TM 堆 = (Total Memory - Managed - Network) / 2 左右，别太小也别太大
3. **GC 目标停顿时间**：`-XX:MaxGCPauseMillis=200`（默认 200ms，通常够用）
4. **确认 RocksDB 用 Off-Heap**：如果 RocksDB State Backend 的 state 居然在 Heap 上，那就是大问题

### 常见 GC 坑

| 坑 | 表现 | 解法 |
| --- | --- | --- |
| State Backend 选错 | RocksDB 的 State 进了 Heap | 确认 `state.backend: rocksdb`，用 Managed Memory |
| ListState 无限增长 | Heap 里一堆 List 元素 | 加 TTL；检查业务逻辑 |
| Window allowedLateness 太大 | 窗口状态留太久 | 设合理的 lateness |
| Operator Chain 太短 | 多个中间对象创建 | 尽量算子链；避免不必要的中间 map |
| JDK 版本 | JDK 8 的 GC 不如 11 | 用 JDK 11 |

## 常见报错速查

| 报错 | 原因 | 解法 |
| --- | --- | --- |
| `Job was suspended (NoResourceAvailableException)` | Slot 不够 | 加 TM / 加 Slot / 降并行度 |
| `OutOfMemoryError: Direct buffer memory` | Network Buffer 不够 | 加 `taskmanager.memory.network.size` |
| `OutOfMemoryError: Java heap space` | Heap 不够 / State 泄漏 | 加 Heap；换 RocksDB；加 TTL |
| `Checkpoint expired before completing` | Checkpoint 太慢或对齐超时 | 增 checkpoint timeout；查反压 |
| `Task failed` + `RecordTooLongException` | 单条数据 > Network Buffer 默认 32KB | 调 `taskmanager.network.memory.buffers-per-channel` |
| `ClassCastException` / `NullPointerException` | 业务代码 | 查异常堆栈 |
| `Could not find checkpoint Coordinator` | JM 挂了 + HA 配置错 | 查 HA 配置；JM 日志 |
| `RocksDB state backend not found` | 没引 RocksDB 依赖 | 加 `flink-statebackend-rocksdb` 依赖 |

## 关键调优清单

```properties
# === 算子链（减少序列化） ===
# 默认就链，除非显式 disable

# === 网络 ===
taskmanager.network.memory.buffers-per-channel: 16
taskmanager.network.memory.floating-buffers-per-gate: 16
# 数据倾斜严重时增加

# === RocksDB ===
state.backend.incremental: true
state.backend.rocksdb.compaction-task-threads: 4
state.backend.rocksdb.localdir: /data1,/data2,/data3

# === GC ===
env.java.opts.taskmanager: "-XX:+UseG1GC -XX:MaxGCPauseMillis=200 -XX:+ParallelRefProcEnabled"

# === State TTL（代码里设） ===

# === Checkpoint ===
execution.checkpointing.interval: 60000
execution.checkpointing.timeout: 600000
execution.checkpointing.min-pause: 10000
```
