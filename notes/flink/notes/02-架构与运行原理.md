# 02 架构与运行原理

## 一句话

**Flink 运行时**由 **JobManager（集群管理者）** 和 **TaskManager（工作节点）** 两类进程组成；用户提交的流作业会经历 **StreamGraph → JobGraph → ExecutionGraph** 三次变换，最终被拆成若干可并行的 **Task** 部署到 TaskManager 的 **Slot** 上运行，相同 Key 的操作链可以合并成 **Operator Chain** 减少序列化开销。

## 总体架构

```
                     Client（提交作业）
                        │
                        ▼
   ┌───────────────────────────────┐
   │     JobManager (JM)            │
   │  ┌───────────┐ ┌───────────┐  │
   │  │ JobMaster  │ │ Resource   │  │
   │  │(每个作业一个)│ │ Manager    │  │
   │  └───────────┘ └───────────┘  │
   │  ┌───────────┐ ┌───────────┐  │
   │  │ Checkpoint │ │ Dispatcher │  │
   │  │ Coordinator│ │ (REST 提交) │  │
   │  └───────────┘ └───────────┘  │
   └──────────┬────────────────────┘
              │ RPC / HTTP (Actor 通信)
              ▼
   ┌───────────────────────────────┐
   │  TaskManager (TM)              │
   │  ┌─────┐ ┌─────┐ ┌─────┐      │
   │  │Slot 0│ │Slot 1│ │Slot 2│     │
   │  │Task A│ │Task B│ │Task A│     │
   │  │Task C│ │      │ │Task D│     │
   │  └─────┘ └─────┘ └─────┘      │
   │  [网络栈 / IO / RocksDB]        │
   └───────────────────────────────┘
```

## 各角色职责

| 角色 | 职责 | 是一个还是多个 |
| --- | --- | --- |
| **Client** | 编译 JobGraph，提交给集群；只在提交时存在 | 每个作业一个（进程退出后清理） |
| **Dispatcher** | REST 入口，接收作业提交，拉起 JobMaster | JM 内一个 |
| **ResourceManager** | 管理 Slot 资源：向 TM 要 Slot、分配、心跳 | JM 内一个 |
| **JobMaster** | 每个作业一个；把 ExecutionGraph 的 Task 部署到 Slot；监听状态；触发 Checkpoint | 每个作业一个（JM 内） |
| **TaskManager** | 真正跑 Task 的进程；提供 Slot；上报心跳和指标 | 通常集群中多个（至少一个） |

## 数据流图的三次变换

用户写的 DataStream API 代码不会直接执行，会经过三次编译变换：

| 阶段 | 产物 | 做什么 | 代码位置 |
| --- | --- | --- | --- |
| 1. 逻辑图 | **StreamGraph** | 把 API 调用串起来，每个算子都展开；包含 Side Output、Async IO 等 | `StreamGraphGenerator` |
| 2. 优化图 | **JobGraph** | 做 **Operator Chain**（能合并的算子链合成一个 Chain，减少序列化）；设置 slot sharing group | `StreamGraphHasherV2` / `OperatorChainer` |
| 3. 物理图 | **ExecutionGraph** | 每个 JobVertex 按并行度展开成 `p` 个 **ExecutionJobVertex**；建立上下游边；分配 Slot 共享 | `ExecutionGraphBuilder` |

```
StreamGraph（逻辑，一并发一节点）
    │  Operator Chain
    ▼
JobGraph（优化，能链的链在一起）
    │  并行度展开
    ▼
ExecutionGraph（物理，有并行度 × 任务数）
    │  部署
    ▼
ExecutionVertex（Slot 上实际跑的 Task）
```

## Slot 概念

**Slot 是 TaskManager 的资源分片**：

- 一个 TM 默认 CPU 核数 = Slot 数（可配 `taskmanager.numberOfTaskSlots`）
- 一个 Slot 可以跑多个 Task（来自同一个 SlotSharingGroup）
- 同一个 Job 的并行度 × SlotSharingGroup 数 = 至少需要的 Slot 数
- 默认所有算子属于同一个 SlotSharingGroup → 可以把一个作业塞进一台 TM 的所有 Slot

```
TM (3 Slot):
┌─────┐ ┌─────┐ ┌─────┐
│Slot 0│ │Slot 1│ │Slot 2│
│map   │ │map   │ │map   │   ← 4 并行度的 map 算子，这里只画了 3
│keyBy │ │keyBy │ │      │   ← 相同 keyBy 并行度
│window│ │window│ │window│
└─────┘ └─────┘ └─────┘
```

**Slot 不等于 CPU**：Slot 是逻辑资源配额，JVM 线程调度时可能多个 Slot 抢同一核。CPU 密集型作业可以把 Slot 数设为 ≈ CPU 核数；IO 密集型可以多开。

## Operator Chain（算子链）

**能合并的算子就合并**——链成一个 Task，省掉上下游之间的序列化 / 网络传输：

| 可以链的条件 | 说明 |
| --- | --- |
| 上下游并行度相同 | 并行度不同必须 shuffle，链不了 |
| 上下游之间没有 shuffle 边界 | keyBy / rebalance / rescale / custom partition 都打断链 |
| 没有显式 `disableChaining()` | 程序员可以手动打断 |
| 没有 SlotSharingGroup 变化 | 不同 group 不链 |

```java
// 默认：map → filter → keyBy → sum 会自动链成两段
//   第一段: map + filter（可以链，同并行度，无 shuffle）
//   第二段: keyBy → sum（keyBy 是 shuffle，打断链，sum 是窗口前的聚合）
DataStream<Integer> s = source
  .map(x -> x + 1)
  .filter(x -> x > 0)    // ← 和 map 同链
  .keyBy(x -> x)         // ← shuffle 边界，打断
  .sum(0);
```

## 并发度 vs 并行度

**同一个概念，不同层面的叫法**：

- **并行度（Parallelism）**：算子层面。`map(x).setParallelism(8)` → map 有 8 个并行实例
- **并发度**：ExecutionGraph 层面。同一个 Job 所有 Task 的并行度之和 = 总并发度
- 默认全局并行度：`parallelism.default` 配置项 / 提交时 `-p` 参数 / 代码里 `env.setParallelism()`

> 实战建议：先给算子分别设并行度，不要依赖全局默认。Sink 的并行度通常和 Source 对齐。

## Subtask 与 Key Group

- 每个并行实例叫一个 **Subtask**（从 0 到 parallelism-1 编号）
- Flink 把 Key 空间 hash 到 **128 个 Key Group**（`MAX_PARALLELISM`）
- 每个 Subtask 负责 `ceil(128 / parallelism)` 个 Key Group
- **为什么用 Key Group？** 方便动态扩缩容：扩容时只需要重分配 Key Group 而不是重 hash 所有 Key

## 通信模型（Task 之间怎么传数据）

| 连接类型 | 场景 | 方式 |
| --- | --- | --- |
| **Forward** | 上下游并行度 1:1，同 SlotSharingGroup | 同线程方法调用（最快） |
| **Rebalance** | 无状态重平衡，轮询 | 同 TM 内 netty 或跨 TM 网络 |
| **Rescale** | 上下游并行度是整数倍 | 同 Rebalance，但每个上游只发 `target/upstream` 个下游 |
| **KeyBy** | 按 Key hash | `hash(key) % downstream_parallelism` |
| **Broadcast** | 广播状态 | 发到所有下游 Subtask |

## 常见问题

- **JM 挂了怎么办？** → Standalone 模式默认单点。生产用 HA（ZooKeeper / K8s Leader Election），JM 元数据持久化，备 JM 接管后从最近 Savepoint 或 Checkpoint 恢复作业。
- **一个作业至少要多少 Slot？** → 至少 `max(所有算子的并行度)`；有 SlotSharingGroup 时还要 × group 数。
- **为什么同一个作业的所有 Task 可以放进一个 TM？** → 默认同一个作业的所有算子属于同一个 SlotSharingGroup。`new SlotSharingGroup("g1")` 可以隔离。
- **Slot Sharing Group 什么时候要设？** → 大算子（如复杂 ProcessFunction）可以单独占一组，免得被轻算子抢资源。
