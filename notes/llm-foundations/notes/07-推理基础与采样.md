# 07 推理基础与采样

## 一句话

**推理就是「一次只生成一个 token，然后把新 token 接回输入再算下一次」的自回归循环**；采样策略决定「怎么从概率分布里挑下一个词」，KV Cache 决定「为什么第二次比第一次快」。理解了这三件事，你就能解释所有「为什么输出不稳定 / 为什么长文本变慢 / 为什么改 temperature 效果会变」的问题。

## 自回归生成流程

```
prompt: "今天天气真"
   ↓ 前向一次
分布 P(next | prompt) → 采样得到 "好"
   ↓ 拼接
"今天天气真好" → 前向 → 采样 "，"
   ↓
"今天天气真好，" → 前向 → 采样 "适合"
   ...
直到生成 <EOS> 或达到 max_new_tokens
```

```python
import torch

@torch.no_grad()
def greedy_decode(model, input_ids, max_new_tokens=32, eos_id=2):
    """最朴素的贪婪解码：每步取概率最大的 token"""
    for _ in range(max_new_tokens):
        logits = model(input_ids).logits[:, -1, :]      # 只要最后一个位置
        next_id = logits.argmax(dim=-1, keepdim=True)
        input_ids = torch.cat([input_ids, next_id], dim=-1)
        if next_id.item() == eos_id:
            break
    return input_ids
```

**关键点**：每生成一个 token 都要做一次完整前向——这是推理慢的根本原因，也是 KV Cache 存在的理由。

## 采样策略

### 从概率到选择

模型输出的是词表上的一整个概率分布。怎么挑？

| 策略 | 做法 | 特点 | 适用 |
| --- | --- | --- | --- |
| **贪婪 Greedy** | 取 argmax | 确定、易重复、无聊 | 抽取、代码补全 |
| **Beam Search** | 保留 k 条最优路径 | 更可能找到高概率整体序列 | 翻译（传统）、摘要 |
| **Temperature** | 用 T 缩放 logits 后再采样 | T<1 更确定，T>1 更发散 | 通用调节旋钮 |
| **Top-k** | 只在概率最高的 k 个里采样 | 砍掉长尾，简单有效 | 通用 |
| **Top-p（核采样）** | 取累积概率达到 p 的最小集合 | 自适应候选集大小 | **默认首选** |

### Temperature 的数学

```python
def apply_temperature(logits, temperature):
    """T → 0 趋近贪婪；T = 1 保持原分布；T > 1 更平坦"""
    return logits / max(temperature, 1e-5)

def top_p_filter(logits, p=0.9):
    """按概率降序累积，保留到累积概率 >= p 的最小集合"""
    sorted_logits, sorted_idx = torch.sort(logits, descending=True)
    probs = torch.softmax(sorted_logits, dim=-1)
    cumulative = torch.cumsum(probs, dim=-1)
    # 累积概率超过 p 的位置之后全部屏蔽
    mask = cumulative - probs > p
    sorted_logits[mask] = -float("inf")
    filtered = torch.full_like(logits, -float("inf"))
    filtered[sorted_idx] = sorted_logits
    return filtered
```

| temperature | 效果 | 场景 |
| --- | --- | --- |
| 0.0 ~ 0.2 | 几乎确定，重复风险高 | 数据抽取、SQL 生成 |
| 0.7 | 稳定但不呆板 | 客服、问答（**推荐默认**） |
| 1.0 | 原始分布 | 创意写作 |
| 1.3+ | 发散、易跑题 | 头脑风暴（需配合 top-p） |

> 经验配置：`temperature=0.7, top_p=0.9` 是通用起点；结构化输出用 `temperature=0`。

## KV Cache：推理加速的核心

### 为什么需要

计算第 t 个 token 的 Attention 时，需要所有历史 token 的 K、V。如果不缓存，每步都要重算全部历史——复杂度 O(L²) 重复计算。

```
无 Cache：第 t 步要重算 1..t 的 K/V
有 Cache：只算第 t 个 token 的 K/V，历史从缓存读
```

### 显存代价

```
KV Cache 显存 ≈ 2 × 层数 × 头数 × head_dim × 序列长度 × batch × 精度字节
```

以 7B 模型（32 层、32 头、head_dim=128、BF16）为例：

| 序列长度 | 单条请求 KV Cache |
| --- | --- |
| 2K | ~0.5 GB |
| 8K | ~2 GB |
| 32K | ~8 GB |

**这解释了三个现象**：
1. 长上下文为什么贵——KV Cache 随长度线性增长；
2. 为什么并发上不去——每条请求都要独立缓存；
3. 为什么有 PagedAttention / GQA / KV 量化——都是在压这块显存。

> 优化方向：MQA/GQA 减少 KV 头数、KV Cache 量化（INT8/FP8）、PagedAttention 消除碎片、前缀缓存（prefix caching）复用 system prompt。

## 常见推理参数

| 参数 | 含义 | 建议 |
| --- | --- | --- |
| `max_new_tokens` | 最多生成多少 token | 按任务设，别用默认无限 |
| `temperature` | 随机性 | 抽取 0，问答 0.7 |
| `top_p` | 核采样阈值 | 0.9 |
| `top_k` | 候选数上限 | 一般不设，交给 top_p |
| `repetition_penalty` | 重复惩罚 | 1.05~1.2，过大伤流畅度 |
| `stop` / `stop_ids` | 停止词 | 结构化输出必设 |
| `seed` | 随机种子 | 需要可复现时设 |

## 一个典型问题：输出不稳定

| 现象 | 排查顺序 |
| --- | --- |
| 同样输入结果差异大 | temperature 是否过高？是否未设 seed？ |
| 输出中途跑题 | top_p 太宽 / 上下文太长导致注意力稀释 |
| 重复同一句话 | temperature 过低 + repetition_penalty 未开 |
| 长文本越写越慢 | KV Cache 增长，检查并发与 max_new_tokens |
| 结构化输出偶尔坏格式 | temperature 不为 0；缺 stop 词；未做 schema 校验 |

## FAQ

**Q：temperature=0 就一定可复现吗？**
A：接近，但浮点非确定性、批处理顺序、kernel 实现差异仍可能造成微小差别；严格可复现需要固定 seed + 确定性算子。

**Q：top_p 和 top_k 要一起用吗？**
A：通常二选一。两者同时开相当于取交集，容易过度收窄候选集。

**Q：为什么流式输出第一个 token 很慢？**
A：prefill 阶段要处理整个 prompt，长 prompt 的 prefill 时间是主要延迟来源（TTFT）。

**Q：KV Cache 能跨请求共享吗？**
A：可以——前缀缓存（prefix caching）对相同 system prompt 生效，这是 vLLM/SGLang 的重要优化项。

**Q：为什么长上下文模型仍然会「忘」中间内容？**
A：注意力在超长序列上会被稀释（lost in the middle）。工程上应把关键信息放在开头或结尾，或做检索式截断。
