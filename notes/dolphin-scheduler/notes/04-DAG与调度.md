# 04 DAG 与调度

## DAG 是什么

**Directed Acyclic Graph（有向无环图）**：任务是点，依赖是边，不允许环（A→B→A 会被保存校验拦下）。

调度引擎的执行模型：

1. 找入度为 0 的节点 → 进入就绪队列
2. 节点成功 → 其后继入度 -1，减到 0 即解锁
3. 直到没有可运行节点 → 汇总出流程最终状态

```
extract_ods ──► transform_dwd ──► aggregate_dws ──► publish_ads
                      │
                      └──► quality_check
```

上例中 `extract_ods` 先跑；`transform_dwd` 成功后，`aggregate_dws` 与 `quality_check` **并行**。

## 设计 DAG 的实用原则

1. **一个节点一件事**：失败重试 / 恢复粒度才够细
2. **依赖显式化**：禁止用「sleep 30 分钟等上游」这种隐式约定
3. **控制宽度与深度**：过宽打爆 Worker 并发；过深拉长关键路径
4. **大流程拆子工作流**：按主题域拆分，主流程只编排 SubWorkflow 节点
5. **幂等**：同一业务日期重跑结果一致——这是补数和重试安全的前提
6. **失败要快**：数据质量检查尽量前置，早失败、早告警，别等污染下游

## 依赖的两个层次

### 1. DAG 内连线（同流程前后继）

连线即依赖：默认前驱**成功**才解锁后继；配合 Conditions / Switch 节点可实现「失败走另一分支」等逻辑。

### 2. Dependent 依赖节点（跨流程 / 跨周期）

表达「等待另一个流程的某个结果」。典型场景：

- 等**昨天的**「用户域 DWD 日批」成功，才跑今天的报表流程
- 等上游 ODS 同步流程的**本周**实例成功

Dependent 节点可配置：依赖哪个项目 / 流程 / 任务、哪个周期（日 / 周 / 月）、取最近一次还是全部。它把「流程间协同」产品化——这是相对 crontab 的核心优势之一。

## 定时调度（cron + Quartz）

海豚内嵌 Quartz，cron 是 **6~7 位、秒开头**，与 Linux crontab（5 位、分开头）不同：

| 需求 | Quartz cron（海豚） | Linux crontab |
| --- | --- | --- |
| 每天 02:00 | `0 0 2 * * ?` | `0 2 * * *` |
| 每小时整 | `0 0 * * * ?` | `0 * * * *` |
| 每 5 分钟 | `0 0/5 * * * ?` | `*/5 * * * *` |
| 工作日 08:00 | `0 0 8 ? * MON-FRI` | `0 8 * * 1-5` |
| 每月 1 号 06:00 | `0 0 6 1 * ?` | `0 6 1 * *` |

要点：

- UI 里可可视化生成 cron，别手写
- 到点 ≠ 立刻执行完：到点只是**生成实例**，执行时长取决于任务与资源
- 上一次实例没跑完、下一次又到点：默认会**并行生成新实例**；不希望叠加就调大间隔，或让任务幂等抗并发
- 注意时区：Server 端时区决定触发时刻，跨国业务要确认全链路时区一致

## 补数（Backfill）

对「已上线的工作流」选一段时间区间，系统为区间内每个业务日期生成一个实例。

操作要点（UI：工作流定义 → 补数）：

1. 选时间区间（如 2026-10-01 ~ 2026-10-31）
2. 选执行方式：
   - **串行**：一天跑成功再跑下一天——稳、慢、对下游压力小
   - **并行**：多天同时跑——快，但要盯 Worker 负载与下游（Hive/DB）压力
3. 并行模式下可指定并行度

补数前检查清单：

- [ ] 任务**幂等**：同一 bizdate 重跑结果一致（分区覆盖写 `INSERT OVERWRITE`，而非追加）
- [ ] 所有路径 / SQL 都由**业务日期参数**驱动（`$[yyyy-MM-dd-1]`），而不是 `date -d yesterday` 这类「相对今天」的写法——补数时「今天」是错的
- [ ] 评估资源：天数 × 单实例资源消耗，必要时串行
- [ ] 下游能否承受批量并发写入

## 失败策略（流程级，并行分支时生效）

当 DAG 中有并行分支，某一分支失败：

| 策略 | 行为 | 适用 |
| --- | --- | --- |
| **继续（Continue）** | 其他并行分支继续跑完，流程最终标记失败 | 想一次暴露多个失败点；分支间互不影响 |
| **结束（End）** | 尽快结束流程：杀掉仍在跑的并行任务，不再派发新任务 | 省资源；强串行语义的链路 |

配置位置：工作流保存时的「失败策略」。数仓日批常用「继续」（早上能一次看到所有失败域），核心链路用「结束」。

## 优先级

两级：

- **流程实例优先级**（启动 / 补数时指定）：Master 处理实例的顺序
- **任务实例优先级**：同一实例内，就绪任务被派发的顺序

资源紧张时高优先级先跑。实战：「早上 9 点前必须出的报表」设高优先级，「可随时回刷的历史任务」设低优先级——比盲目加机器更有效。

## 超时、告警与空跑

- **任务超时**：可配「超时告警」（继续跑但发告警）或「超时失败」（杀掉任务记失败）
- **流程告警**：成功 / 失败 / 超时通知到告警组
- **空跑 / 跳过**：联调或只推进依赖的场景可用（以所用版本支持为准）

## 调度全景脑图

```
触发源：手动 | cron | OpenAPI | 补数 | 容错
   ↓ 生成命令（t_ds_command）
Master 认领命令 → 创建流程实例
   ↓ 拓扑解析
就绪队列（入度为 0，按优先级排序）
   ↓ 按 Worker 组 / 负载派发
Worker 执行 → 回报状态
   ├─ 成功 → 解锁后继
   ├─ 失败 → 任务级重试 → 仍失败 → 流程级失败策略（继续/结束）→ 告警
   └─ 超时 → 告警 / 杀任务
   ↓
无剩余任务 → 流程实例收尾（成功/失败）→ 通知
```
