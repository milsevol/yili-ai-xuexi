# 03 核心概念

学海豚调度，先把名词对齐，否则 UI 和文档会绕晕。

## 概念地图

```
租户 Tenant（≈ Worker 机器上的 Linux 用户）
  └── 用户 User（绑定一个租户；登录/操作的人）
        └── 项目 Project（授权与协作单位）
              └── 工作流定义 Workflow Definition（DAG 模板，有版本）
                    ├── 任务定义 Task Definition（节点）
                    ├── 定时 Schedule（cron）
                    └── 触发 → 工作流实例 Workflow Instance
                                  └── 任务实例 Task Instance
```

## 租户（Tenant）

- 对应 **Worker 机器上的 Linux 系统用户**：任务进程以租户身份 fork 执行
- 作用：资源与权限隔离——HDFS 目录、Yarn 队列、文件属主都跟着 Linux 用户走
- 在「安全中心 → 租户管理」创建；**Worker 机器上必须真实存在同名用户**，否则任务起不来
- 创建用户时绑定租户；一个用户对应一个租户，一个租户可被多用户共用

> 实战：生产规划租户时与大数据平台账号体系统一（如 `dw_ods`、`dw_ads`）；测试环境可用一个公共租户。

## 用户与权限

- 用户：登录 UI / 调 OpenAPI 的账号
- 两类角色：**管理员**（管租户、用户、Worker 组、环境等全局资源）与 **普通用户**（在被授权的项目内操作）
- 授权粒度：项目、数据源、资源、环境、告警组都可单独授权
- 建议：按团队建用户、按域建项目，避免所有人共用 admin

## 项目（Project）

一组相关工作流的容器，也是授权边界。常见划分方式：按数据域（`user_domain`、`trade_domain`）或按团队。

## 工作流定义（Workflow / Process Definition）

- DAG 模板：任务节点 + 连线 + 全局参数 + 失败策略 + 通知策略
- **有版本**：每次保存生成新版本；**只有「上线」状态的定义才会被调度 / 手动启动**
- 编辑后未上线 → 定时仍按旧版本跑；上线即切换
- **下线**后定时不再触发，但不影响已创建的运行中实例（实例用的是创建时的快照）

## 任务定义（Task Definition）

DAG 上的一个节点。两大类：

- **业务节点**：Shell、SQL、Python、Spark、Flink、HTTP、DataX……
- **逻辑 / 控制节点**：子工作流（SubWorkflow）、依赖（Dependent）、条件（Conditions）、开关（Switch）

每个任务的通用配置：

| 配置 | 说明 |
| --- | --- |
| 失败重试次数 / 间隔 | 任务级自动重试 |
| 超时告警 / 超时失败 | 防止挂死 |
| Worker 组 | 指定跑在哪些机器 |
| 环境 | 预置的环境变量组合（3.x 环境管理，见第 07 章） |
| 资源文件 | 执行前从资源中心拉到 Worker 本地 |
| 本地参数 / 出参 | 见第 06 章 |
| 任务优先级 | 实例内就绪任务的派发顺序 |

## 工作流实例 / 任务实例

| | 定义 Definition | 实例 Instance |
| --- | --- | --- |
| 是什么 | 模板 | 某一次具体运行 |
| 何时产生 | 保存（版本 +1） | 手动启动 / 定时 / 补数 / API / 容错 |
| 数量 | 一个工作流一份定义（多版本） | 每次触发一份 |
| 状态 | 上线 / 下线 | 见下方状态机 |

**流程实例状态**（常见）：提交成功 → 运行中 → 成功 / 失败 / 停止 / 暂停 / 准备暂停 / 容错中……

**任务实例状态**：提交成功 → 运行中 → 成功 / 失败 / 停止 / 需要容错 / 延时执行……

排障第一眼就看这两个状态 + 时间线。

## 调度（Schedule）

- 绑定在「已上线的工作流」上，UI 可视化生成 cron
- **调度本身也有上线/下线开关**——工作流上线 ≠ 调度上线，两个开关都开才会定时触发
- 常见坑：时区不一致、cron 写错（Quartz 方言见第 04 章）、只上线了工作流忘了开调度

## 参数（详见第 06 章）

分层理解即可：全局参数（工作流级）→ 本地参数（任务级）→ 上游出参 → 系统内置时间变量（如 `$[yyyy-MM-dd]`）。数仓场景几乎总要**业务日期（bizdate）**驱动分区路径与 SQL where。

## 命令类型（Command）——理解一切运维操作的钥匙

Master 消费 `t_ds_command` 里的命令。UI 操作与命令的对应关系：

| 用户操作 | 命令类型 | 效果 |
| --- | --- | --- |
| 启动 / 定时触发 | START_PROCESS | 从起始节点正常跑 |
| 重跑 | REPEAT_RUNNING | 整个实例从头再跑一遍 |
| 从失败节点恢复 | RECOVER_TOLERANCE_FAULT_PROCESS | 只重跑失败任务及其后继 |
| 从当前节点执行 | START_CURRENT_TASK_PROCESS | 指定节点起跑，后继按依赖推进 |
| 补数 | COMPLEMENT_DATA | 按时间区间批量生成实例 |
| 暂停 | PAUSE | 不再派发新任务，运行中的继续 |
| 停止 | STOP | 杀掉运行中任务，实例终止 |
| 容错恢复 | 系统内部产生 | Master/Worker 故障后系统接管 |

三个易混概念：

1. **任务失败重试**：任务级、自动、按配置次数——抖动脉冲型问题靠它
2. **从失败节点恢复**：流程级、通常人工触发——修完问题后接着跑
3. **重跑**：流程级、从头再来——口径变了 / 整体重算时用

## 自测

1. 「改了 DAG 但没按新逻辑跑」，最可能漏了哪一步？
2. 租户和项目分别隔离什么？为什么租户要对应 Linux 用户？
3. 「任务重试 3 次」和「从失败节点恢复」谁自动、谁偏人工？
4. 工作流上线了但定时没跑，列出至少 3 个排查点。
