# 02 架构与组件

## 总览

3.x 的核心进程与外部依赖：

```
            ┌─────────┐
            │   UI    │  前端页面
            └────┬────┘
                 │ HTTP/REST
            ┌────▼────┐        ┌──────────────┐
            │   API   │────────│   元数据库    │
            │ Server  │        │ MySQL/PG/... │
            └────┬────┘        └──────▲───────┘
                 │ 写命令/查状态        │
        ┌────────┴─────────┐          │
        │      Netty       │          │
   ┌────▼────┐        ┌────▼────┐     │
   │ Master  │◄──────►│ Worker  │─────┘（2.x 起 Worker 不直连 DB）
   │ Server  │        │ Server  │
   └────┬────┘        └────┬────┘
        │                  │
        └────────┬─────────┘
                 │ 注册 / 心跳 / 协调
          ┌──────▼───────┐
          │   注册中心     │  ZooKeeper / Etcd / JDBC
          └──────────────┘

          ┌──────────────┐
          │ Alert Server │  告警插件：邮件/钉钉/企业微信/Slack…
          └──────────────┘
```

> 记忆法：**API 管「人怎么操作」，Master 管「什么时候跑、怎么拆」，Worker 管「真正干活」，注册中心管「谁活着」，Alert 管「出事了喊人」，元数据库管「记账」。**

## API Server

对外唯一的 HTTP 入口，无状态、可水平扩展（前面挂 Nginx / SLB）。

职责：

- 工作流定义 / 任务定义的增删改查、上线、下线
- 手动启动、重跑、补数、暂停、停止 → 转化为写入 DB 的 **Command**
- 项目、租户、用户、数据源、资源文件、告警组等元数据管理
- 状态查询：实例列表、任务日志（向 Worker 实时拉取）等

**注意**：API Server 不执行任务，只写命令和查状态。即便 Master 全部短暂不可用，UI 仍能登录查数据，只是不会有新任务被调度。

## Master Server

去中心化、多活。每个 Master 主要干四件事：

1. **扫描 Command 表**：轮询 `t_ds_command`，认领「启动 / 重跑 / 补数 / 容错恢复」等命令（多 Master 通过 DB 锁避免重复认领）。
2. **DAG 切分与推进**：为命令创建工作流实例，做拓扑排序，把入度为 0 的就绪任务通过 Netty 派发给 Worker；收到任务结果后解锁后继。
3. **定时触发**：内嵌 **Quartz**（基于 DB 的分布式调度），到点为「已上线且开了调度」的工作流生成启动命令。
4. **容错（failover）**：监听注册中心，发现其他 Master / Worker 宕机后接管：为「运行中但宿主失联」的实例生成容错命令，重新调度。

补充：

- Master 不跑业务任务本身，调度压力主要来自「实例数 × 任务数」。
- 关键配置：`master.exec-threads`（并发处理实例的线程数）等。

## Worker Server

去中心化、多活。职责：

1. **执行任务**：接收 Master 派发的任务，fork 子进程执行（Shell / SQL / spark-submit…），按任务配置处理重试、超时。
2. **回报状态**：通过 Netty 把任务结果（成功/失败/出参）回传 Master。
3. **提供日志**：任务日志写在 Worker 本地磁盘，UI 查看时由 API 向对应 Worker 拉取。
4. **心跳与负载上报**：向注册中心上报心跳与负载（CPU / 内存 / 线程池水位），Master 派发时参考。

关键设计（2.x 起）：**Worker 不再直连数据库**，状态全部经由 Master 中转——Worker 可以大规模横向扩容而不压垮 DB。

Worker 侧常调参数：

| 配置 | 含义 |
| --- | --- |
| `worker.exec-threads` | 单机并发任务数（按机器规格调） |
| `worker.max-cpu-load-avg` | 负载阈值，超过则不再接新任务 |
| `worker.reserved-memory` | 保留内存，低于此值拒绝新任务 |
| `worker.groups` | 本机所属 Worker 组 |

## 注册中心（Registry）

作用：

- **服务发现**：Master / Worker 启动时注册自己的地址
- **健康感知**：心跳超时即判定宕机，触发容错
- **分布式协调**：互斥锁、成员变更通知（3.x Master 无主，注册中心主要用于故障检测与互斥）

演进：

| 版本 | 注册中心 |
| --- | --- |
| 1.x | 强依赖 ZooKeeper（连任务队列都放 ZK，ZK 压力大） |
| 2.x | ZooKeeper（只用于注册与协调） |
| 3.2+ | 可插拔：**ZooKeeper（默认）/ Etcd / JDBC** |

小规模部署可用 JDBC 注册中心少维护一套 ZK；生产大集群仍推荐 ZK 或 Etcd。

## Alert Server

- 消费「需要告警」的事件：流程失败/成功、任务失败、超时、容错等
- **插件化**通道：邮件、钉钉、企业微信、Slack、飞书、HTTP 回调、自定义脚本……
- 3.x 支持 Alert Server 高可用（多实例 + 告警落库防丢）
- 接收人通过**告警组**管理；工作流上绑定告警组与通知策略（失败才发 / 成功失败都发）

## 元数据库

存一切「定义」与「运行态」。几张高频打交道的表（名字有个印象，排障时会查）：

| 表 | 内容 |
| --- | --- |
| `t_ds_process_definition` | 工作流定义（含版本） |
| `t_ds_process_instance` | 工作流实例 |
| `t_ds_task_instance` | 任务实例 |
| `t_ds_command` | 待消费命令 |
| `t_ds_schedules` | 定时配置 |
| `t_ds_user` / `t_ds_tenant` | 用户与租户 |

支持 MySQL（5.7+/8）、PostgreSQL 等。生产必须做主从与定时备份，并定期清理历史实例表（见第 09 章）。

## 一次调度的完整链路（串起所有组件）

以「每天 02:00 的日批工作流」为例：

1. 用户在 UI 把工作流 **上线** 并配置 cron（落到 `t_ds_schedules`）
2. Master 内嵌 Quartz 到点 → 向 `t_ds_command` 写入一条 `START_PROCESS` 命令
3. 某个 Master 扫到并认领该命令 → 创建 **工作流实例**（`t_ds_process_instance`）
4. Master 解析 DAG，找出入度为 0 的任务，按 **Worker 组 + 负载 + 优先级** 派发给合适 Worker
5. Worker 收到任务 → 拉取资源文件 → fork 进程执行 → 回报状态
6. 任务成功 → Master 解锁后继，重复 4–5；任务失败 → 按任务配置自动重试，仍失败则按流程级「失败策略」处理（继续 / 结束）
7. 全部任务结束 → 流程实例收尾；按配置触发 Alert 通知
8. 用户在 UI 查看实例时间线与任务日志

手动启动、补数、重跑、从失败节点恢复，区别只在第 2 步写入的**命令类型**不同，后续链路一致。

## 去中心化在说什么

不是「没有 Master」，而是：

- 多 Master / 多 Worker **地位对等、无单点**，可水平扩展
- 通过注册中心感知成员上下线
- 某台 Master 宕机：其他 Master 通过容错命令接管其「运行中」实例
- 某台 Worker 宕机：其上运行中任务被标记失败 / 杀掉，由任务重试或人工恢复兜底（前提：任务幂等）

## Worker 分组（实战常考点）

生产把 Worker 按「能力」分组，任务指定跑在哪个组：

| 组 | 机器特点 | 跑什么 |
| --- | --- | --- |
| `default` | 常规配置 | Shell / SQL / HTTP |
| `spark` | 装有 Spark 客户端、Yarn 权限 | spark-submit |
| `hive` | 装有 Hive 客户端 | Hive CLI |
| `gpu` | 有 GPU / 驱动 / 科学计算栈 | 训练任务 |

避免「任务被派到没装客户端的机器上莫名失败」。
