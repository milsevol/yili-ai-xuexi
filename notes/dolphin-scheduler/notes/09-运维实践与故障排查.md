# 09 运维实践与故障排查

## 容错机制详解

### 任务级

- **自动重试**：任务配置的「失败重试次数 + 间隔」，适合网络抖动、锁冲突等瞬时问题
- **超时处理**：超时告警 / 超时失败，防挂死

### 流程级

| 操作 | 场景 |
| --- | --- |
| 从失败节点恢复 | 修完脚本 / 数据问题后接着跑（最常用） |
| 重跑 | 口径变了整体重算 |
| 从当前节点执行 | 跳过前面已确认无问题的环节 |
| 暂停 / 停止 | 止血 |

### 平台级（failover）

- **Master 宕机**：注册中心感知 → 其他 Master 接管其「运行中」实例（生成容错命令，重新推进）
- **Worker 宕机**：其上运行中任务被标记失败（或需容错）→ 靠任务重试 / 人工恢复；前提还是那句话：**任务幂等**

## 日志与排障顺序

标准动线：

1. **UI 工作流实例**：哪条实例失败、停在哪个节点
2. **任务实例日志**：UI 直接看（API 向 Worker 实时拉取）——80% 的问题在这一步定位（脚本错误、SQL 报错、数据问题）
3. 区分问题域：
   - **调度问题**：没触发 / 依赖不满足 / 卡在就绪 → 查 Master 日志、调度配置、Dependent 上游状态
   - **执行问题**：脚本 / SQL / 环境 → 查任务日志、Worker 日志、Worker 组环境
4. 仍不明朗：看 Worker Server 日志、Master Server 日志、Alert 日志（各角色安装目录 `logs/`）

注意：**任务日志存在 Worker 本地执行目录**，Worker 下线或日志被清理后 UI 看不到。

## 高频问题清单

### 1. 任务一直「提交成功」不运行

- 没有匹配 Worker 组的在线 Worker（组名打错最常见）
- Worker 负载超阈值（CPU / 内存保护）拒绝接收
- Master 线程池打满：看 `master.exec-threads` 与命令积压

### 2. 调度没触发

- 工作流未上线，或**调度未上线**（两个开关）
- cron 写错（Quartz 方言，秒开头）
- 时区错乱：Server 与预期时区不一致

### 3. 实例表膨胀

`t_ds_process_instance` / `t_ds_task_instance` 会无限增长，拖慢 UI 列表与 Master 扫表。治理：

- 定期归档 / 清理历史实例（按时间删除或转储）
- 监控表大小与慢查询
- 大规模补数后主动检查一轮

### 4. 注册中心抖动

ZK 会话超时 → Master / Worker 互相误判 → 无意义 failover。对策：ZK 独立部署、调大会话超时、网络稳定优先。

### 5. 补数把集群打爆

- 并行补数没限并行度，Worker 全满、正常日批被饿死
- 对策：串行补数、限制并行度、低峰期补、调低补数流程优先级

### 6. UI 看日志失败

- 对应 Worker 已下线 / 日志已清理
- API 到 Worker 网络不通

## 监控告警

- **进程存活**：systemd / supervisor 或 K8s liveness
- **指标**：3.x 暴露 Micrometer / Prometheus 指标，可接 Grafana 看板：实例成功率、任务积压、线程池水位
- **告警通道实测**：接手系统第一件事——故意失败一次，确认告警真的能到人

## 升级注意事项

- 官方提供 schema 升级脚本（`tools/bin/upgrade-schema.sh`），**先备份元数据库**
- 跨大版本（2.x → 3.x）重点看 Release Notes 的 Breaking Changes
- 滚动升级顺序参考：先 API / Alert，再 Master，最后 Worker；灰度一个 Worker 组先验证
