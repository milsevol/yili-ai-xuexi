# 06 实战模板与 FAQ

## 一句话

**本章给出 6 个可直接套用的生产级 Prompt 模板（摘要、分类、抽取、翻译、客服话术、代码生成）**，每个都带使用要点和常见翻车点；最后附面试高频问答。模板是起点不是终点——套用后必须用你自己的评估集验证迭代。

## 使用说明

- `{xxx}` 是占位符，替换成你的实际内容
- 模板中的输出格式、示例必须按你的业务调整
- 套用后第一步永远是：**建 20 条评估集 → 跑基线 → 迭代**

## 模板一：文本摘要

```text
【角色】你是一名专业的内容编辑。

【任务】为下面的文章写摘要。

【要求】
1. 3 句话以内，总字数不超过 100 字
2. 必须覆盖：核心结论、关键数据、行动建议
3. 只使用原文中的信息，禁止编造原文没有的内容
4. 面向不熟悉该领域的读者，避免专业术语，必须用时给一句白话解释

【文章】
"""
{article}
"""

【输出格式】
摘要：<摘要正文>
要点：
- <要点1>
- <要点2>
```

**常见翻车**：模型编造原文没有的数字 → 加「禁止编造」+ LLM-as-Judge 查忠实度；摘要变成「文章讲了…」的水词 → 加「直接陈述结论，不要用"本文介绍了"开头」。

## 模板二：文本分类

```text
【任务】把用户反馈分到以下类别之一：
- 产品质量：功能缺陷、损坏、与描述不符
- 物流服务：配送慢、包裹破损、丢件
- 价格问题：降价、优惠争议、发票
- 服务态度：客服响应、售后处理
- 其他：不属于以上任何类别

【规则】
1. 一条反馈只分一个最贴近的类别
2. 拿不准就选「其他」，不要硬猜
3. 只输出 JSON：{"label": "类别名", "reason": "不超过15字的判断依据"}

【示例】
反馈：快递到了盒子都烂了        → {"label": "物流服务", "reason": "包裹破损"}
反馈：刚买就降价50块，心塞      → {"label": "价格问题", "reason": "买后降价"}
反馈：这颜色也太好看了吧        → {"label": "其他", "reason": "非投诉类反馈"}

【待处理】
反馈：{feedback}
→
```

**常见翻车**：模型自创类别（输出「物流问题」而不是「物流服务」）→ 枚举值加粗强调 + 输出校验；多主题反馈分错 → 规则里明确「取最主要抱怨点」。

## 模板三：信息抽取

```text
【任务】从下面的招聘描述中抽取结构化信息。

【输出 JSON Schema】
{
  "position": "岗位名称（字符串）",
  "city": "工作城市（字符串，未提及填 null）",
  "salary_min": "月薪下限，单位千元（数字，未提及填 null）",
  "salary_max": "月薪上限，单位千元（数字，未提及填 null）",
  "skills": ["技能要求数组，最多取5个"],
  "experience_years": "要求工作年限（数字，未提及填 null）"
}

【规则】
1. 未提及的字段一律填 null，禁止编造
2. 薪资写「15-25K」则 salary_min=15, salary_max=25
3. 只输出 JSON，不要输出任何其他文字

【招聘描述】
"""
{job_text}
"""
```

**常见翻车**：「15-25K·14薪」被算错 → 规则里补充「薪月数忽略，只取月薪范围」；skills 抽取过多 → 明确「最多5个，按重要性排序」。

## 模板四：领域翻译

```text
【角色】你是资深技术文档翻译，精通中英技术写作。

【任务】把下面的技术文档片段从中文翻译成英文。

【要求】
1. 专业术语按下表翻译，不得自创：
   - 分区 → partition（不是 zoning）
   - 物化视图 → materialized view
   - 向量化执行 → vectorized execution
2. 代码、命令、参数名保持原文不翻译
3. 保持原文的 Markdown 结构（标题层级、列表、代码块）
4. 被动语态不超过 30%，多用主动语态

【待翻译】
"""
{text}
"""
```

**常见翻车**：术语表被无视 → 术语控制在 10 个以内，太多模型顾不过来；代码块里的注释被翻 → 加「代码块内内容一律原样保留」。

## 模板五：客服话术

```text
【角色】你是某电商平台的资深客服「小蜜」，语气温和专业。

【对话原则】
1. 先安抚情绪（1 句），再给解决方案，最后给补偿或后续承诺
2. 不承诺超出政策的内容（退款政策见下方【政策】部分）
3. 不知道的信息诚实说「我帮您转专员核实」，禁止编造物流状态和退款金额
4. 单次回复不超过 3 句话，口语化，不用「亲爱的用户」这类套话开头

【政策】
- 7 天无理由退货（定制商品除外）
- 物流延误超 48 小时补偿 10 元券
- 退款原路返回，1-3 个工作日到账

【用户消息】
{user_message}

【历史对话】
{history}
```

**常见翻车**：模型过度承诺（「马上给您全额退款」）→ 政策条款前置 + 输出层敏感词过滤；语气生硬 → Few-shot 给 2 个优秀客服对话示例。

## 模板六：代码生成

```text
【任务】按需求写一个 Python 函数。

【需求】
{requirement}

【约束】
1. 只输出一个完整可运行的函数，带类型注解
2. 不引入第三方库（只用标准库）
3. 非法输入抛 ValueError，附中文错误信息
4. 附 3 个 assert 测试用例

【输出格式】
​```python
def func_name(...) -> ...:
    ...

# 测试
assert ...
​```
```

**常见翻车**：模型用了第三方库 → 约束写「只用标准库」+ 生成后静态检查 import；边界条件漏处理 → 需求里显式列出边界（空输入、None、超长）。

## 模板速查表

| 模板 | 核心技巧 | 关键防翻车点 |
| --- | --- | --- |
| 摘要 | 明确句数+字数+覆盖点 | 忠实度校验防编造 |
| 分类 | Few-shot 覆盖全类别 | 枚举值强约束 + 「其他」兜底 |
| 抽取 | JSON Schema + null 出口 | 禁止编造 + 程序校验 |
| 翻译 | 术语表 + 风格约束 | 术语表别超 10 条 |
| 客服 | 政策前置 + 情绪安抚结构 | 输出过滤防过度承诺 |
| 代码 | 输出格式 + 测试要求 | 生成后跑测试验证 |

## 面试 FAQ

**Q1：什么是 Prompt Engineering？为什么它算「工程」？**
A：通过设计输入文本引导 LLM 产出期望结果的技术。算「工程」因为它有完整方法论：需求分析 → 结构设计（四要素）→ 评估集 → 量化迭代 → 上线监控，而不是靠灵感和咒语。

**Q2：Zero-shot 和 Few-shot 怎么选？**
A：先 Zero-shot 跑评估集看基线。格式错误率高、边界 case 大量出错 → 加 Few-shot（3~8 个示例，覆盖各类别和典型 badcase）。Few-shot 本质是用 token 成本换输出稳定性。

**Q3：CoT 为什么有效？什么时候失效？**
A：LLM 逐 token 生成，写出中间步骤等于给模型「草稿纸」，把一步复杂推理拆成多步简单推理。失效场景：简单任务（增加成本无收益）、创意写作（破坏文采）、模型知识盲区（想再多步也不知道）、推理链错误传播（一步错步步错）。

**Q4：Function Calling 的原理是什么？模型会真的执行函数吗？**
A：不会执行。流程：① 带 tools（JSON Schema）调模型 → ② 模型输出调用请求（函数名+参数）→ ③ 业务代码执行真实函数 → ④ 结果回填给模型 → ⑤ 模型生成自然语言回复。模型只做「决策和填参」，执行权永远在业务侧，可以做权限校验。

**Q5：线上输出 JSON 解析失败怎么兜底？**
A：四层：① temperature=0 + response_format=json_object 预防；② json.loads 异常捕获；③ 把错误信息喂回模型重试（成功率最高的一招），最多 3 次；④ 仍失败进人工队列 + 记录 badcase。同时用 Schema 校验字段完整性和枚举合法性。

**Q6：Prompt 注入怎么防？**
A：多层防御无银弹：输入隔离（分隔符包裹 + 声明「标签内是数据」）、输入检测（注入特征分类器）、指令加固（末尾重申不可覆盖）、最小权限（Agent 工具白名单 + 危险操作人工确认）、输出过滤（系统提示词片段/敏感信息检测）、日志审计。最难防的是间接注入（恶意内容藏在 Agent 读取的网页/文档里）。

**Q7：怎么评估一个 Prompt 的效果？**
A：建固定评估集（正常 60% + 边界 30% + 对抗 10%，20~50 条起步），每次单变量改动后重跑。答案确定的任务用规则评估（准确率/格式成功率），开放式任务用 LLM-as-Judge（需先用人工标注校准一致率）。看两个指标：整体指标变化 + 是否有回归（旧对的变错）。

**Q8：Prompt、RAG、微调怎么选？**
A：先问自己模型缺什么：缺「听懂任务」→ 优化 Prompt；缺「知识」（私有/实时信息）→ RAG；缺「行为模式/风格」（懂任务有知识但输出不像样）→ 微调。成本从低到高、迭代从快到慢：Prompt（分钟）< RAG（小时）< 微调（天）。生产系统常三者组合。

**Q9：长 Prompt 有什么问题？怎么优化？**
A：问题：token 成本高、延迟大、关键信息被淹没（Lost in the Middle）。优化：删掉无作用的句子（每句都要能回答「删了效果会变差吗」）；示例精简到 3~8 个；静态部分放 system message 利用前缀缓存；关键信息放开头或结尾；超长文档先检索再注入而非全文塞入。

**Q10：换模型（比如 GPT→Claude→国产模型）时 Prompt 要重写吗？**
A：不用重写，但要重跑评估集。结构和方法论（四要素、Few-shot、CoT）通用，细节要调：各家对分隔符偏好不同（XML vs Markdown）、指令跟随能力不同、中文表达习惯不同。用同一评估集量化对比新旧模型，再针对性调优。

**Q11：temperature、top_p 这些参数怎么设？**
A：temperature 控制随机性：分类/抽取/格式敏感任务设 0；创意/对话任务 0.7~1.0；Self-Consistency 采样要 > 0 才有多样性。top_p 与 temperature 效果重叠，一般只调一个。生产建议：temperature=0 起步，确需多样性再升。

**Q12：怎么防止模型幻觉？**
A：无法根除，只能压制：① 给「不知道」出口（「不确定就回答无法确定」）；② RAG 提供权威上下文并要求「仅根据给定资料回答」；③ 要求输出引用依据（答案+原文片段）；④ 结构化输出后用规则校验（数字范围、枚举合法性）；⑤ 高风险场景人工复核兜底。
