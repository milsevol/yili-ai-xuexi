# 01 概述与定位

## 一句话

**Prompt Engineering（提示词工程）是在不改模型参数的前提下，通过精心设计输入文本，让大语言模型稳定输出你想要结果的技术**。它是使用 LLM 成本最低、迭代最快的手段，但不是万能的——遇到知识盲区、强一致性要求、风格深度定制时，需要与 RAG、微调分工配合。

## 什么是 Prompt Engineering

一次 LLM 调用 = 一段输入文本（Prompt）+ 模型推理 → 输出文本。Prompt Engineering 研究的就是：

- 怎么写**指令**让模型听懂任务
- 怎么给**上下文**让模型有足够信息
- 怎么给**示例**让模型模仿输出格式
- 怎么约束**输出格式**让程序能解析

```text
┌─────────────────────────────────────┐
│  Prompt（你写的输入）                 │
│  ├─ 角色设定：你是资深数据工程师      │
│  ├─ 任务指令：把下面日志分成三类      │
│  ├─ 上下文：业务背景 + 字段说明      │
│  └─ 输出格式：JSON，含 label 字段    │
└─────────────────────────────────────┘
              ↓ 模型推理
┌─────────────────────────────────────┐
│  输出：{"label": "ERROR", ...}       │
└─────────────────────────────────────┘
```

本质：**模型能力已经存在，Prompt 只是「调用方式」**。同一个模型，Prompt 写得好与差，效果天差地别。

## 为什么重要

| 维度 | 说明 |
| --- | --- |
| 成本最低 | 不需要训练数据、GPU，改几行文本就能验证想法 |
| 迭代最快 | 分钟级改 Prompt → 立刻看效果；微调动辄数小时到数天 |
| 效果上限高 | GPT-4 / Claude 级别的模型，好 Prompt 能解决 80% 的常见任务 |
| 可迁移 | 同一个 Prompt 模板可以套到不同模型上比较效果 |
| 人人可用 | 不需要 ML 背景，产品和运营也能参与调优 |

**经验法则**：任何 LLM 应用，**先把 Prompt 优化到极限**，再考虑 RAG 和微调。跳过 Prompt 直接微调，是新手最常见的过度工程。

## 能力边界：Prompt 不是万能的

Prompt 能做什么、不能做什么，直接决定你的技术选型：

| 场景 | Prompt 能否解决 | 说明 |
| --- | --- | --- |
| 文本分类、情感分析 | ✅ 能 | 给几个示例即可达到生产可用 |
| 摘要、改写、翻译 | ✅ 能 | 指令 + 输出约束即可 |
| 信息抽取（NER、结构化） | ✅ 能 | 配合 JSON Schema 输出 |
| 逻辑推理、数学计算 | ⚠️ 部分 | 需要 CoT 等技巧，复杂推理仍会错 |
| 私有/实时知识问答 | ❌ 不能 | 模型不知道你公司数据 → 需要 RAG |
| 事实幻觉（编造引用、数字） | ⚠️ 缓解 | Prompt 可约束「不知道就说不知道」，但无法根除 |
| 输出风格深度定制 | ⚠️ 部分 | Prompt 能模仿风格，但要 100% 稳定 → 微调 |
| 超长文档全文理解 | ❌ 受限 | 受上下文窗口限制，需切分或 RAG |
| 需要 100% 格式稳定 | ⚠️ 部分 | 配合 Function Calling / 重试校验才行 |

**三条硬边界**（写 Prompt 前必须知道）：

1. **知识截止**：模型训练数据有时间截止点，之后发生的事它不知道，编造是常态。
2. **幻觉**：模型会自信地编造看似合理的内容（人名、法条、API 参数），Prompt 只能降低概率不能消除。
3. **上下文窗口**：超出窗口的内容会被截断或遗忘，「塞得进」≠「记得住」（长文本中间的信息最容易被忽略，即 Lost in the Middle 现象）。

## 与微调、RAG 的分工

三者是互补关系，不是替代关系：

| 维度 | Prompt Engineering | RAG（检索增强生成） | Fine-tuning（微调） |
| --- | --- | --- | --- |
| 解决什么问题 | 任务表达、格式约束、风格引导 | 模型缺少的知识（私有/实时） | 行为模式、领域风格、稳定输出 |
| 成本 | 几乎为零 | 中（向量库 + 检索链路） | 高（数据 + 训练 + 评估） |
| 迭代速度 | 分钟级 | 小时级（更新知识库） | 天级 |
| 需要训练数据 | 不需要（几个示例即可） | 不需要 | 需要几百~几万条标注数据 |
| 知识更新 | 改文本即可 | 更新知识库即可 | 需重新训练 |
| 风险 | 长 Prompt 贵、有注入风险 | 检索质量决定上限 | 过拟合、灾难性遗忘 |

**决策树**：

```text
模型表现不好，先问自己：
│
├─ 是「没听懂任务」吗？（格式乱、答非所问）
│   └─ 先优化 Prompt：加指令、给示例、约束格式
│
├─ 是「缺知识」吗？（不知道私有数据、最新信息）
│   └─ 上 RAG：检索相关文档塞进上下文
│
├─ 是「风格/行为模式不对」吗？（懂任务有知识，但输出不像你司口吻）
│   └─ 考虑微调：准备几百条高质量样例
│
└─ 三者都要？ → 组合使用：RAG 给知识 + Prompt 给指令 + 微调定风格
```

**典型组合实例**（智能客服）：

- 微调：让模型学会公司客服话术风格
- RAG：实时检索产品手册、订单数据
- Prompt：约束「先安抚情绪 → 再给方案 → 结尾引导评价」的对话结构

## Prompt 工程师的日常

1. **明确任务**：把模糊需求翻译成可验证的输出标准（「分类准」→「测试集准确率 ≥ 95%」）
2. **写初版 Prompt**：四要素补齐（详见第 02 章）
3. **建评估集**：20~50 条覆盖正常/边界/对抗的用例
4. **跑评估 → 看 badcase → 改 Prompt**：循环 10~30 轮是常态
5. **上线 + 监控**：记录线上 badcase 回流到评估集

## 常见问题

**Q：Prompt 写得越长越好吗？**
A：不是。长 Prompt 增加 token 成本、延迟，且关键信息容易被淹没。原则是「够用且精确」：每一句都要有作用，删掉一句效果不变就删。

**Q：不同模型的 Prompt 能通用吗？**
A：大体思路通用（指令清晰、给示例、约束格式），但细节要调。比如有的模型对 XML 标签更敏感，有的对 Markdown 更敏感；换模型后要重跑评估集。

**Q：Prompt 能替代模型选型的差距吗？**
A：不能完全替代。Prompt 决定「能否发挥出模型能力」，模型能力决定上限。小模型 + 神 Prompt 通常仍打不过大模型 + 普通 Prompt，但成本可能差 10 倍——按场景选性价比组合。

**Q：学习 Prompt Engineering 需要会编程吗？**
A：入门不需要（能写清楚需求就行），进阶需要。批量评估、A/B 测试、Function Calling、重试校验都要写代码，Python 是主流。

**Q：Prompt 是「工程」还是「玄学」？**
A：玄学部分在变少。早期靠咒语式技巧（"你是最厉害的 AI"），现在主流是**可评估的工程方法**：固定评估集 + 量化指标 + 单变量迭代。靠感觉调 Prompt 的时代已经过去。
