# 02 架构与核心组件

## 一张图看全景

```
应用 / JDBC / MySQL Client / OBClient
                │
                ▼
        ┌───────────────┐
        │    OBProxy    │  无状态，SQL 解析 + 路由 + 故障摘除
        └───────┬───────┘
                │  按分区 leader 路由
   ┌────────────┼─────────────┐
   ▼            ▼             ▼
┌────────┐  ┌────────┐   ┌────────┐
│Zone 1  │  │Zone 2  │   │Zone 3  │   ← 故障域（机房/机架）
│OBServer│  │OBServer│   │OBServer│
│ 副本   │  │ 副本   │   │ 副本   │   ← 每个分区 3 副本组成 Paxos 组
└────────┘  └────────┘   └────────┘
        RootService 内置于某一台 OBServer，负责调度与元数据
```

## 核心组件职责

| 组件 | 部署形态 | 职责 |
| --- | --- | --- |
| **OBServer** | 每台机器一个进程 | SQL 引擎、事务引擎、存储引擎、Paxos 日志、分区副本 |
| **RootService（RS）** | 内置在某台 OBServer | 集群管理：建租户/建表、副本调度、负载均衡、合并调度、故障处理 |
| **OBProxy** | 独立无状态进程 | 接收客户端连接、解析 SQL、按分区 leader 路由、连接池、黑名单 |
| **OCP** | 独立 Web 平台 | 集群/租户/备份/监控/告警/巡检 |
| **OMS** | 独立服务 | 迁移与同步 |
| **OBClient / ODC** | 客户端 | 命令行 / Web SQL 开发 |

> RootService 不是单独进程，而是 OBServer 内的一个服务。它通过 Paxos 选举产生，只有一台 OBServer 上的 RS 是主，其他为备。

## 关键概念

### Region 与 Zone

- **Region**：地理区域，例如「杭州」「上海」。
- **Zone**：Region 内的故障域，通常对应一个机房、机架或可用区。一个 Zone 内可以有多台 OBServer。
- **Locality**：副本分布策略，例如 `FULL{1}@zone1, FULL{1}@zone2, FULL{1}@zone3` 表示三个 Zone 各一份全量副本。

三 Zone 是最常见形态：任意一个 Zone 故障，剩余两个 Zone 仍构成多数派，业务不中断。

### 分区、Tablet 与 Paxos 组

| 概念 | 含义 |
| --- | --- |
| **分区（Partition）** | 表按范围/哈希/列表切分后的逻辑单元 |
| **Tablet** | 分区在某个副本上的物理载体 |
| **副本组** | 同一分区的多个副本组成一个 Paxos 组 |
| **Leader** | 组内主副本，承担读写；由 Paxos 选举产生 |
| **Follower** | 从副本，同步日志，可在弱读场景提供读服务 |

同一个分区的所有写入都走 Leader；Leader 把 redo 日志通过 Paxos 同步给多数派，多数派落盘后才算提交。

### Paxos 与多数派

| 副本数 | 容忍故障 | 说明 |
| --- | --- | --- |
| 3 | 1 | 最常见，三 Zone 各一副本 |
| 5 | 2 | 金融核心、两地三中心常见 |
| 2F + 1A | 1 | 仲裁副本（A）不存数据，降低成本 |

> RPO=0 的前提是「多数派已持久化」。如果只剩少数派，集群会停止写入而不是接受可能丢失的数据。

### 多租户

一个 OceanBase 集群可以创建多个租户，每个租户是一个逻辑实例：

- 独立的 CPU / 内存 / 日志盘配额；
- 独立的数据库、用户、权限；
- 独立的兼容模式（MySQL 或 Oracle）；
- 独立的备份、恢复、扩缩容。

系统租户 `sys` 管理集群元数据；每个用户租户还有一个对应的 Meta 租户，用于存放该租户的元数据。

## 一次写入的完整链路

```
1. 客户端连 OBProxy（默认 2883）
2. OBProxy 解析 SQL，定位目标分区及其 Leader
3. 请求转发到 Leader 所在 OBServer（SQL 端口默认 2881）
4. Leader 写 MemTable + 本地 clog（redo 日志）
5. clog 通过 Paxos 同步到多数派 Follower
6. 多数派持久化成功 → 事务提交 → 返回客户端
7. 后台线程异步把 MemTable 冻结、转储、合并到 SSTable
```

读请求同样先到 Leader（强读）；弱读一致性场景可以路由到 Follower。

| 端口 | 用途 |

## 部署形态怎么选

| 形态 | 副本 | 适用 |
| --- | --- | --- |
| 单机体验 | 1 Zone 1 副本 | 本地学习、POC，无高可用 |
| 三 Zone 三副本 | 3F | 生产标配，容忍单 Zone 故障 |
| 五副本 | 5F | 金融核心、两地三中心 |
| 2F + 1A | 2 全量 + 1 仲裁 | 成本敏感但仍需容灾 |
| 主备租户 | 主租户 + 备租户 | 异地多活、读写分离、灾备 |

## 常见问题

**Q：OBProxy 是必须的吗？**
A：不是。客户端可以直连 2881，但直连需要自己知道分区 leader；OBProxy 负责路由和故障摘除，生产环境通常必配，并用 LVS/F5 做高可用。

**Q：RootService 挂了怎么办？**
A：RS 是 Paxos 选举的，主 RS 所在 OBServer 故障后会自动在其他 OBServer 上选出新主，不影响数据面读写。

**Q：三副本是不是写性能只有单机三分之一？**
A：不是。Paxos 是并行复制，写入延迟取决于多数派中最慢的一个；吞吐可以通过多分区、多 Leader 并行扩展。
