# 03 存储引擎与多副本

## 一句话

OceanBase 的存储引擎是**基于 LSM-Tree 的分布式存储**：写入先进内存 MemTable，日志通过 Paxos 同步到多数派；内存写满后冻结、转储成 SSTable，后台定期合并成新的基线数据。多副本之间靠 clog（redo 日志）保持一致。

## 整体结构

```
                 ┌──────────────────────────────┐
   写入 ────────▶│  MemTable（增量，内存有序）  │
                 └──────────────┬───────────────┘
                                │ 冻结 / 转储
                 ┌──────────────▼───────────────┐
                 │  SSTable（增量，磁盘）        │
                 └──────────────┬───────────────┘
                                │ 合并（Major Compaction）
                 ┌──────────────▼───────────────┐
                 │  Baseline SSTable（基线数据）│
                 └──────────────────────────────┘

   每次写入同时写 clog（redo），Paxos 同步到多数派后才算提交
```

| 层次 | 位置 | 特点 |
| --- | --- | --- |
| **MemTable** | 内存 | 有序结构，支持快速写入与查询；内存写满触发冻结 |
| **增量 SSTable** | 磁盘 | 冻结后的 MemTable 落盘，按版本分层 |
| **基线 SSTable** | 磁盘 | Major Compaction 后的全量有序数据 |
| **clog** | 磁盘 | redo 日志，Paxos 同步，保证多副本一致与崩溃恢复 |

## 写入路径

1. Leader 收到写请求，写 MemTable；
2. 同时写本地 clog；
3. clog 通过 Paxos 复制到多数派；
4. 多数派持久化成功，事务提交；
5. 后台在 MemTable 达到阈值时冻结，异步转储为增量 SSTable；
6. 每日合并窗口把增量 SSTable 与基线合并，生成新基线。

> 写入是追加式的，没有 B+ 树随机写放大；代价是读可能需要合并 MemTable 与多层 SSTable。

## SSTable 内部结构

| 结构 | 作用 |
| --- | --- |
| **Macro Block** | 磁盘 IO 的基本单位，通常 2 MB |
| **Micro Block** | 块内更小的数据单元，通常 16 KB |
| **Block Index** | 记录每个 Micro Block 的偏移与统计信息 |
| **Bloom Filter** | 快速判断某行是否可能存在，减少无效 IO |
| **Encoding** | 字典编码、RLE、位打包等，先编码再压缩 |
| **Compression** | lz4 / zstd 等，按列/块压缩 |

**编码 + 压缩**是高压缩率的来源：同一列数据类型一致、局部有序，字典编码和差值编码效果很好。

## 合并（Major Compaction）

| 概念 | 说明 |
| --- | --- |
| **冻结（Freeze）** | MemTable 写满或达到阈值后转为只读，等待转储 |
| **转储（Dump）** | 把冻结的 MemTable 落成增量 SSTable |
| **合并（Merge）** | 把增量 SSTable 与基线合并，消除重复、回收旧版本 |
| **合并窗口** | 默认在业务低峰（常见凌晨 2 点），可配置 |

相关参数（以实际版本为准）：

```sql
SHOW PARAMETERS LIKE 'major_freeze_duty_time';     -- 每日合并时间
SHOW PARAMETERS LIKE 'freeze_trigger_percentage';  -- 触发冻结的内存阈值
SHOW PARAMETERS LIKE 'memstore_limit_percentage';  -- MemStore 可用内存比例
SHOW PARAMETERS LIKE 'merger_check_interval';      -- 合并进度检查间隔
```

手动触发合并：

```sql
ALTER SYSTEM MAJOR FREEZE;
```

> 合并期间会占用 IO 与 CPU。生产上要把合并窗口放在低峰，并监控合并进度；长期合并失败会导致增量数据膨胀、查询变慢。

## 多副本与日志同步

| 日志 | 作用 |
| --- | --- |
| **clog** | redo 日志，记录数据修改，Paxos 同步 |
| **ilog** | 索引日志 |
| **slog** | 存储层元数据日志 |

副本类型：

| 类型 | 是否存数据 | 是否参与投票 | 用途 |
| --- | --- | --- | --- |
| **FULL** | 是 | 是 | 全量副本，可读可写（Leader） |
| **LOGONLY** | 否（只存日志） | 是 | 低成本容灾 |
| **仲裁副本（A）** | 否 | 是 | 2F+1A，降低存储成本 |

Locality 示例：

```sql
-- 三 Zone 各一份全量副本
ALTER TENANT ob_mysql SET LOCALITY = 'FULL{1}@zone1, FULL{1}@zone2, FULL{1}@zone3';
```

## 事务与一致性

- **快照隔离（Snapshot Isolation）**：读看到事务开始时的快照，避免脏读、不可重复读。
- **全局时间戳服务（GTS）**：为事务分配全局递增时间戳，保证跨节点一致性。
- **单分区事务**：在 Leader 本地完成，延迟低。
- **跨分区事务**：两阶段提交（2PC），由事务协调者驱动，依然保证原子性。
- **多副本**：clog 多数派持久化后才提交，故障切换不丢已提交数据。

## 读路径

```
SQL → 解析/优化 → 定位分区与 Leader
   → 读 MemTable + 各层 SSTable
   → 按版本合并（多版本去重）
   → 过滤、聚合、返回
```

读放大的来源是「MemTable + 多层 SSTable」需要合并。优化的方向：

- 控制合并频率，避免增量层数过多；
- 合理设计主键与索引，减少扫描；
- 使用分区裁剪；
- 大查询走并行执行或列存副本。

## 常见问题排查

| 现象 | 可能原因 | 处理 |
| --- | --- | --- |
| 合并一直不结束 | IO 瓶颈、磁盘空间不足、大租户 | 查看合并进度与磁盘；错峰；扩容 |
| 增量数据越来越大 | 合并失败或长期未合并 | 检查 `DBA_OB_MAJOR_COMPACTION`；手动触发 |
| 查询越来越慢 | 增量层多、统计信息过期 | 合并、收集统计信息、检查执行计划 |
| clog 同步延迟 | 网络抖动、磁盘慢、副本所在机器负载高 | 检查网络与磁盘；确认多数派健康 |
| 磁盘使用率高 | 合并保留旧版本、备份、日志 | 调整保留策略；清理过期备份；扩容 |

## 常见问题

**Q：LSM-Tree 和 B+ 树有什么区别？**
A：B+ 树原地更新，读快写有随机 IO；LSM-Tree 追加写、后台合并，写吞吐高、压缩好，但读要合并多层数据。OceanBase 用 LSM-Tree 换取分布式写入与高压缩。

**Q：合并会不会阻塞业务？**
A：合并是后台任务，正常情况下不阻塞读写，但会消耗 IO/CPU。需要错峰并监控资源。

**Q：三副本写入为什么要等多数派？**
A：为了保证已提交数据在任意单副本故障时不丢失（RPO=0）。等多数派是强一致的代价。
