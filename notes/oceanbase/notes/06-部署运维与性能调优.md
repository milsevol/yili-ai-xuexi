# 06 部署运维与性能调优

## 一句话

OceanBase 的运维围绕四件事：**部署（集群/租户）→ 监控（资源/合并/慢 SQL）→ 备份恢复 → 扩缩容与升级**。性能调优则遵循「先定位瓶颈，再动参数」：大多数问题出在 SQL、索引、分区和统计信息，而不是数据库参数。

## 部署方式怎么选

| 方式 | 适用 | 特点 |
| --- | --- | --- |
| **OBD** | 本地学习、POC、小规模 | 命令行一键部署，简单直接 |
| **OCP** | 生产 | 图形化运维、监控、备份、租户管理 |
| **ob-operator** | Kubernetes | 云原生、声明式管理 |
| **OB Cloud** | 托管 | 免运维，按需使用 |

### 本地最小体验（Docker）

```bash
docker run -d --name ob \
  -p 2881:2881 -p 2883:2883 \
  -e MODE=mini \
  oceanbase/oceanbase-ce:latest

# 查看启动日志，等待初始化完成
docker logs -f ob

# 连接 sys 租户
docker exec -it ob obclient -h127.0.0.1 -P2881 -uroot@sys -p -Doceanbase
```

> 镜像标签与默认密码随版本变化，以官方快速开始文档为准。单机容器仅用于学习，不具备高可用。

### 生产部署要点

| 项 | 建议 |
| --- | --- |
| **Zone 数** | 至少 3 个，分布在不同机架/机房 |
| **副本** | 3F 起步；核心系统 5F 或 2F+1A |
| **磁盘** | 数据盘与日志盘分开；SSD/NVMe |
| **网络** | 节点间万兆、低延迟；Paxos 对网络敏感 |
| **内存** | 给系统预留足够内存，不要把物理内存全分给租户 |
| **时钟** | 配置 NTP，时间偏差会影响事务与日志 |

## 日常巡检看什么

| 维度 | 指标/命令 | 异常信号 |
| --- | --- | --- |
| 集群 | `DBA_OB_SERVERS` | 节点状态非 ACTIVE |
| Zone | `DBA_OB_ZONES` | Zone 非 ACTIVE |
| 租户 | `DBA_OB_TENANTS` | 租户状态异常、副本不足 |
| 合并 | `DBA_OB_MAJOR_COMPACTION` | 合并失败或长时间未完成 |
| 资源 | CPU、内存、磁盘、IOPS | 磁盘超过 80%、内存打满 |
| 慢 SQL | `GV$OB_SQL_AUDIT` | 平均耗时上升、超时增多 |
| 日志 | clog 同步延迟 | 副本落后、写入变慢 |

```sql
-- 合并状态
SELECT * FROM oceanbase.DBA_OB_MAJOR_COMPACTION;

-- 租户资源使用
SELECT TENANT_ID, TENANT_NAME, CPU_WEIGHT, MEMORY_SIZE
FROM oceanbase.DBA_OB_RESOURCE_POOLS;

-- 会话与执行中的 SQL
SELECT SID, USER, COMMAND, TIME, INFO
FROM oceanbase.GV$OB_PROCESSLIST
WHERE COMMAND <> 'Sleep';
```

## 备份与恢复

OceanBase 的物理备份由两部分组成：

1. **数据备份**：基线数据 + 增量数据；
2. **日志归档**：clog 持续归档，支持恢复到任意时间点。

```sql
-- 配置备份目的地（示例：NFS / OSS）
ALTER SYSTEM SET backup_dest = 'oss://bucket/obbackup?host=...';

-- 开启日志归档
ALTER SYSTEM ARCHIVELOG;

-- 发起全量备份
ALTER SYSTEM BACKUP DATABASE;

-- 查看备份进度
SELECT * FROM oceanbase.DBA_OB_BACKUP_JOBS;
```

恢复通常恢复到**新租户**，验证后再切换业务。备份要定期做恢复演练，只备份不恢复等于没备份。

## 合并与日常维护

| 操作 | 说明 |
| --- | --- |
| **每日合并** | 默认低峰执行，和业务高峰错开 |
| **手动合并** | `ALTER SYSTEM MAJOR FREEZE;` 用于异常时补合并 |
| **统计信息** | 大表数据变化后及时收集，避免执行计划走偏 |
| **回收站** | 开启后误删表可恢复，注意保留时间与空间 |
| **升级** | 按官方升级路径逐版本升级，先备灾再操作 |

## 性能调优方法论

```
1. 定位：是 CPU、内存、IO、网络，还是单条 SQL？
2. 缩小：慢 SQL → SQL_ID → 执行计划 → 算子耗时
3. 优化：索引 > 分区裁剪 > SQL 改写 > 并行 > 参数
4. 验证：对比优化前后耗时、扫描行数、IO
5. 固化：加索引、调统计信息、加限流/超时
```

### 常见 SQL 优化手段

| 手段 | 说明 |
| --- | --- |
| **索引** | 覆盖索引、联合索引最左前缀；避免在索引列上做函数运算 |
| **分区裁剪** | 查询条件带分区键，减少扫描分区 |
| **SQL 改写** | 去掉 `SELECT *`、减少子查询嵌套、拆分大 UNION |
| **并行执行** | 大查询用 `/*+ PARALLEL(n) */`，小查询不要开 |
| **计划绑定** | 用 Outline 固定执行计划，防止计划回退 |
| **统计信息** | `ANALYZE TABLE` / `DBMS_STATS` 保持统计信息新鲜 |
| **限流** | 设置 `ob_query_timeout`、大查询阈值，保护在线业务 |

```sql
-- 查看执行计划
EXPLAIN SELECT * FROM t_order WHERE user_id = 1001;

-- 收集统计信息（MySQL 模式）
ANALYZE TABLE t_order;

-- 设置查询超时（会话级）
SET ob_query_timeout = 10000000; -- 单位微秒
```

### 常用参数

| 参数 | 作用 | 注意 |
| --- | --- | --- |
| `memory_limit_percentage` | OBServer 可用内存比例 | 给系统预留余量 |
| `system_memory` | 系统内存 | 过小会导致内部错误 |
| `cpu_count` | 可用 CPU 数 | 与宿主机/容器限制匹配 |
| `ob_query_timeout` | 查询超时 | 防止慢查询拖垮业务 |
| `ob_trx_timeout` | 事务超时 | 长事务要拆批 |
| `large_query_threshold` | 大查询阈值 | 控制大查询资源占用 |
| `enable_sql_audit` | SQL 审计 | 生产建议开启，注意磁盘 |
| `writing_throttling_trigger_percentage` | 写入限流阈值 | 防止内存打满 |

> 参数调整要逐个进行、观察效果，不要一次改一堆。

## 常见故障与处理

| 错误/现象 | 可能原因 | 处理 |
| --- | --- | --- |
| `ERROR 4012 (HY000): Timeout` | 查询/事务超时 | 优化 SQL、调大超时、检查锁等待 |
| `ERROR 4030: Packet too large` | 包超过限制 | 调大 `ob_proxy_max_packet_size` 或拆分请求 |
| `ERROR 4007: memory` | 内存不足 | 优化大查询、扩容、调内存参数 |
| 写入突然变慢 | 合并、磁盘满、clog 延迟 | 查合并状态、磁盘、副本健康 |
| 连接数打满 | 连接泄漏、连接池配置不当 | 查会话、加连接池上限、杀空闲连接 |
| 主备延迟 | 网络、备租户资源不足 | 检查网络与备租户规格 |

## 安全与合规

- 开启 TLS 加密连接；
- 最小权限原则，按业务建用户；
- 开启 SQL 审计，保留关键操作日志；
- 生产环境关闭不必要的公网访问；
- 备份文件加密并异地保存；
- 定期做恢复演练与权限复核。
