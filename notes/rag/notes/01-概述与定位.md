# 01 概述与定位

## 一句话

**RAG（Retrieval-Augmented Generation，检索增强生成）= 给 LLM 外挂一个「开卷资料库」**：回答前先从知识库检索相关片段，拼进 Prompt 再让模型生成。它用「检索」解决 LLM 的两大先天缺陷——**幻觉**（不懂装懂、编造答案）和**知识截止**（训练数据有时间边界，不知道新事物），是企业落地 LLM 的第一选择。

## LLM 的两个根本问题

### 问题 1：幻觉（Hallucination）

LLM 的本质是「下一个 token 概率预测」，它**不知道自己不知道什么**：

```python
# 直接问 LLM（无 RAG）
问: "我们公司 2026 年的年假政策是多少天？"
答: "根据贵公司规定，年假为 15 天……"   # 编造的，语气还非常自信
```

幻觉高发场景：
- 训练语料里稀少的**长尾知识**（公司内部文档、小众领域）
- 需要**精确数字/日期/条款**的问题（模型倾向给一个「看起来合理」的值）
- 要求**引用出处**时（模型会编造不存在的文献和链接）

### 问题 2：知识截止（Knowledge Cutoff）

模型参数在训练完成那一刻就冻结了：

| 知识类型 | LLM 参数里有没有 |
| --- | --- |
| 2024 年前的公开百科知识 | 有 |
| 上周发布的产品价格 | 没有 |
| 你公司的内部 wiki | 没有 |
| 今天的新闻 | 没有 |

**参数化记忆（Parametric Memory）** vs **非参数化记忆（Non-parametric Memory）**：
- 参数化：知识存在模型权重里，更新要重新训练，成本极高
- 非参数化：知识存在外部数据库里，**改一行数据库记录就生效**——这就是 RAG 的核心思想

## RAG 的工作原理（最简版）

```python
# 伪代码：RAG 就是三行核心逻辑
def rag_answer(question: str) -> str:
    docs = vector_db.search(embed(question), top_k=5)   # 1. 检索相关文档
    prompt = f"基于以下资料回答：\n{docs}\n\n问题：{question}"  # 2. 拼装 Prompt
    return llm.generate(prompt)                          # 3. 生成答案
```

关键转变：LLM 从「闭卷考试凭记忆答」变成「**开卷考试查资料答**」。答案被检索到的资料**锚定**（grounding），幻觉大幅降低，且每个答案都能给出引用来源。

## RAG vs 微调（Fine-tuning）的边界

面试和工程选型的高频问题。两者**不互斥**，但职责完全不同：

| 维度 | RAG | 微调（SFT/LoRA） |
| --- | --- | --- |
| 解决什么 | 注入**事实知识**（what） | 塑造**行为风格/格式/领域语感**（how） |
| 知识更新 | 改数据库，秒级生效 | 重新训练，小时~天级 |
| 可溯源性 | 天然支持引用出处 | 不支持（知识揉进权重） |
| 幻觉控制 | 强（答案被检索内容锚定） | 弱（仍可能编造） |
| 数据需求 | 原始文档即可 | 需要构造指令对（成本高的环节） |
| 启动成本 | 低（Embedding + 向量库即可） | 高（GPU + 训练管线 + 评估） |
| 失效模式 | 检索不到就答不好 | 灾难性遗忘、过拟合 |

**决策口诀**：
- 知识过期、需要溯源、知识频繁变 → **RAG**
- 输出格式/语气/术语风格不对、特定任务模式（如 SQL 生成、病历书写） → **微调**
- 既要领域风格又要私有知识 → **微调定风格 + RAG 供知识**（业界主流组合）

**一个经典误区**：试图用微调让模型「记住」公司内部知识库。结果通常是——知识稍微一更新模型就过时，而且模型对没记牢的知识照样幻觉。知识问题请用 RAG 解决。

## RAG 适用场景 vs 不适用场景

**适用**：
- 企业知识库问答（制度、文档、FAQ）
- 客服 Copilot（结合产品手册回答）
- 法律/医疗/金融等强合规领域（必须给出引用条款）
- 代码库问答、技术文档助手
- 新闻/行情等时效性内容问答

**不适用或慎用**：
- 需要**跨全文推理**的问题（"这本书的主线矛盾是什么"——切块后全局信息丢失，GraphRAG/长上下文更合适）
- 精确**统计聚合**（"库里一共有多少条投诉"——这是 SQL 的活，不是检索的活）
- 知识库本身质量极差（垃圾进垃圾出，先治理数据）
- 超低延迟场景（检索+生成链路长，首 token 延迟比纯 LLM 高）

## 完整链路鸟瞰

```
┌─────────────────────── 索引期（离线，文档变更时跑） ───────────────────────┐
│                                                                          │
│  原始文档      解析        切块         向量化          入库               │
│  PDF/Word ──→ 提取文本 ──→ Chunk ──→ Embedding ──→ 向量数据库              │
│  /网页/HTML    清洗         512 token   768/1024 维    + 元数据            │
│                                                                          │
└──────────────────────────────────────────────────────────────────────────┘

┌─────────────────────── 查询期（在线，每个用户问题跑一次） ─────────────────┐
│                                                                          │
│  用户问题     检索         重排        拼装          生成                  │
│  "年假几天" ─→ Top-50 ──→ Top-5 ──→ Prompt ──→ LLM 答案 + 引用           │
│               多路召回     Reranker   上下文        流式输出               │
│                                                                          │
└──────────────────────────────────────────────────────────────────────────┘
```

## 常见问题

**Q：RAG 和直接在 Prompt 里塞文档有什么区别？**
A：上下文窗口装不下整个知识库（百万级文档），且塞得越多越贵、越慢、越容易「迷失在中间」（Lost in the Middle）。RAG 的价值是**精准选出最相关的几段**，只把这些喂给模型。

**Q：有了 100 万 token 的长上下文模型，还需要 RAG 吗？**
A：多数场景仍需要。长上下文成本高（每次请求全量付费）、延迟大、且实验表明模型对长上下文中间部分的利用率显著下降。RAG 是「先海选再精读」，长上下文是「全书通读」，前者性价比通常更高。两者之争详见第 07 章。

**Q：RAG 系统最大的坑一般在哪？**
A：按出问题的概率排序：① 文档解析脏乱（PDF 表格/多栏解析烂了）；② Chunk 切得不合理（上下文截断）；③ 检索召回率低（Embedding 模型不匹配领域）；④ 最后才是 Prompt 和模型选择。**前面三项占了 80% 的问题**。

**Q：RAG 一定要用向量数据库吗？**
A：不是。检索可以用关键词（BM25）、向量（语义）、图（GraphRAG）等多种方式，且生产系统几乎都是**多路混合召回**。向量只是其中一路，见第 04 章。
