# 04 检索优化与多路召回

## 一句话

**检索阶段的核心 KPI 是召回率——答案相关的 Chunk 必须出现在候选集里，否则后面 Rerank 和 LLM 再强也无力回天**。单路向量检索在真实业务中召回率往往不够用，生产标配是：查询改写（把烂问题变好）+ 多路召回（向量 + 关键词互补）+ 元数据过滤（先缩小搜索空间）。

## 为什么单路向量检索不够用

向量检索（语义检索）擅长**语义相似**，但有三类硬伤：

| 失败场景 | 例子 | 原因 |
| --- | --- | --- |
| 专有名词/编号 | "A-7832 报错怎么处理" | Embedding 对陌生 token 编码能力差 |
| 精确关键词 | "《员工手册（2026 修订版）》" | 语义相近但版本词必须精确匹配 |
| 问题与答案表述差异大 | 问"怎么请假"，文档写"休假申请流程" | 语义相关但向量距离偏远 |

**对策就是本章三板斧：改写查询、多路召回、元数据过滤。**

## 查询改写（Query Rewrite / Expansion）

用户的问题常常不是好查询：太短、有歧义、带口语、依赖对话上下文。用 LLM 先改写再检索：

### 1. 改写（Rewrite）——修正表达

```python
REWRITE_PROMPT = """把用户的口语化问题改写成适合检索的规范查询，补全主语，去掉语气词。
原问题：{question}
改写查询（只输出查询本身）："""

# "那个年假怎么休来着？" → "正式员工年假申请流程与天数规定"
```

### 2. 扩写（Expansion / Multi-Query）——一生多

让一个 LLM 生成 3~5 个同义改写，**每个改写各检索一次，结果合并去重**：

```python
def multi_query_retrieve(question: str, n: int = 4) -> list[dict]:
    variants = llm.generate(
        f"给出该问题的 {n} 个不同表述，每行一个：\n{question}"
    ).strip().split("\n")
    all_hits = []
    for q in [question, *variants]:
        all_hits.extend(vector_db.search(embed(q), top_k=20))
    return dedup_by_chunk_id(all_hits)   # 按 chunk_id 去重
```

- 收益：对表述差异大的场景召回率提升明显
- 代价：检索次数 ×n，延迟和成本上升

### 3. 回退一步（Step-back Prompting）

把具体问题抽象成更 general 的问题一起检索。问"Qwen3-8B 在 MMLU 上多少分"，回退一步检索"Qwen3 系列模型评测结果"——背景文档常常一起被召回。

### 4. 对话上下文改写（多轮必备）

多轮对话里「它多少钱」里的「它」必须结合历史补全成「iPhone 17 多少钱」，否则检索完全跑偏：

```python
def contextualize(question: str, history: list[dict]) -> str:
    return llm.generate(
        f"根据对话历史，把最新问题补全为独立完整的问题。\n"
        f"历史：{history}\n最新问题：{question}\n独立问题："
    )
```

## HyDE：假设文档检索

**思路反转**：不直接用问题检索，而是让 LLM 先**编一个假想答案**，用假想答案去向量检索——因为「答案和答案」在向量空间里比「问题和答案」更近：

```python
def hyde_retrieve(question: str, top_k: int = 20) -> list[dict]:
    # 1. 让 LLM 生成一段假设答案（可以是错的，只要风格像文档）
    hypo = llm.generate(f"请写一段可能回答该问题的文档片段（100 字）：\n{question}")
    # 2. 用假设答案的向量去检索真实文档
    return vector_db.search(embed(hypo), top_k=top_k)
```

| 优点 | 缺点 |
| --- | --- |
| 问答表述差异大的场景召回提升明显 | 多一次 LLM 调用，延迟 +0.5~1s |
| 零样本即可用 | 假设答案编得太离谱时反而带偏检索 |

适用：开放域问答、问题与文档文风差异大的场景；不适用：精确关键词查询。

## 多路召回（Hybrid Search）

生产标配：**向量召回 + BM25 关键词召回，两路互补，融合去重**。

```
                  用户问题
                ┌────┴────┐
          向量召回        BM25 召回
        （语义相似）      （关键词精确）
        Top-20            Top-20
                └────┬────┘
                 RRF 融合排序
                     ↓
                融合 Top-30 → 送 Rerank
```

### RRF 融合算法（Reciprocal Rank Fusion）

不需要归一化两路分数，直接用**排名**融合，稳定好用：

```python
def rrf_fuse(result_lists: list[list[dict]], k: int = 60, top_k: int = 30) -> list[dict]:
    """RRF: score(d) = Σ 1 / (k + rank_i(d))，k 通常取 60。"""
    scores: dict[str, float] = {}
    docs: dict[str, dict] = {}
    for results in result_lists:
        for rank, doc in enumerate(results):
            cid = doc["chunk_id"]
            scores[cid] = scores.get(cid, 0.0) + 1.0 / (k + rank + 1)
            docs[cid] = doc
    fused = sorted(scores.items(), key=lambda x: x[1], reverse=True)
    return [docs[cid] for cid, _ in fused[:top_k]]
```

**为什么 RRF 比加权分数融合好**：向量余弦（0~1）和 BM25 分数（0~几十）量纲完全不同，加权系数很难调；RRF 只用排名，天然免疫量纲问题。

### 各路召回的分工

| 路 | 擅长 | 不擅长 |
| --- | --- | --- |
| 向量（稠密） | 语义改写、同义表达、"怎么请假"→"休假流程" | 专有名词、编号、精确匹配 |
| BM25（稀疏关键词） | 编号、术语、人名、版本号精确匹配 | 同义词、语义相关 |
| SPLADE/稀疏向量 | 兼顾关键词与一定语义 | 部署复杂 |

## 元数据过滤（Metadata Filtering）

先过滤再检索，把搜索空间从「全库」缩到「该用户该看的那部分」：

```python
# 向量库原生支持：过滤条件 + 向量相似一起做
vector_db.search(
    query_vector=embed(question),
    top_k=20,
    filter={
        "department": {"$in": user.departments},   # 权限过滤（必须！）
        "doc_type": "policy",                       # 文档类型
        "updated_at": {"$gte": "2025-01-01"},      # 时间范围
    },
)
```

**关键设计**：切块入库时就把元数据（部门、密级、文档类型、时间）存进去——第 02 章说的「只存向量不存元数据」的坑，到这里就会爆雷。

**注意**：过滤条件太狠会把相关文档也滤掉（"该部门没有"≠"全公司没有"），生产上常做**降级策略**：过滤后结果太少时放宽过滤重试一次。

## 子查询分解（Query Decomposition）

复杂问题一个查询检索不全，拆成多个子问题分别检索：

```
原问题："对比 A 产品和 B 产品的售后政策差异"
  ├─ 子查询 1："A 产品售后政策"      → 检索 → 命中 Chunk 组 1
  ├─ 子查询 2："B 产品售后政策"      → 检索 → 命中 Chunk 组 2
  └─ 合并两组 → 拼装 → LLM 对比生成
```

```python
def decompose_retrieve(question: str) -> list[dict]:
    sub_queries = llm.generate(
        f"把复杂问题拆成 2-4 个可独立检索的子问题，每行一个：\n{question}"
    ).strip().split("\n")
    chunks = []
    for sq in sub_queries:
        chunks.extend(retrieve(sq, top_k=10))
    return dedup_by_chunk_id(chunks)
```

适用：对比类、多实体类、多跳推理类问题。代价：多次 LLM + 多次检索，延迟显著增加——通常只在识别到复杂问题时才触发（可以用分类器或 Agent 判断，见 07 章）。

## 检索优化组合拳（推荐默认配置）

```
用户问题
  → 多轮改写（如有历史）
  → 元数据过滤（权限 + 业务域）
  → 向量召回 Top-20 ∥ BM25 召回 Top-20     （必要时 + Multi-Query）
  → RRF 融合 Top-30
  → Rerank 精排 Top-5                       （第 05 章）
```

## 常见问题

**Q：多路召回里向量路和 BM25 路各占多少权重？**
A：用 RRF 就不需要调权重。如果一定要分数加权融合，常见起点是 0.7 向量 + 0.3 BM25，但要用评估集实测——这就是为什么 RRF 更受欢迎。

**Q：HyDE 和 Multi-Query 能一起用吗？**
A：可以但延迟爆炸（每个改写都生成假设文档再检索，N×M 次调用）。一般二选一：追求召回上限选 HyDE，追求稳定选 Multi-Query。

**Q：检索结果一大堆但相关的不多（ precision 低）怎么办？**
A：那是 Rerank 要解决的问题（第 05 章）。检索阶段宁多勿漏，precision 靠精排兜底。

**Q：BM25 一定要上 Elasticsearch 吗？**
A：不一定。原型期 Python 的 `rank_bm25` 库几十行搞定；很多向量库（Qdrant/Milvus 2.5+/PGVector+pg_search）已内置 BM25/全文检索；ES 适合已有 ES 基建的团队。

**Q：查询改写会不会把用户意图改偏？**
A：会，这是它的风险。护栏做法：① 改写 Prompt 里强调「保持原意，不得引入新信息」；② 原查询和改写查询**一起**参与多路召回，改写只增不替。
