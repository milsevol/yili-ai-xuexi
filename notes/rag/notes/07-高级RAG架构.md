# 07 高级RAG架构

## 一句话

**基础 RAG 是「一次检索 + 一次生成」的直线流程，高级 RAG 是把「检索」变成一个可控、可反思、可分支的子系统**：多跳问题拆开查、缺信息时主动再查、跨文档关系用知识图谱串、复杂任务交给 Agent 自己决定何时查。核心都在解决同一件事——**固定 Top-K 检索不够用**。

## 为什么基础 RAG 会撞墙

| 问题类型 | 基础 RAG 的表现 | 原因 |
| --- | --- | --- |
| 多跳问题（A 的子公司 B 的营收） | 只能答一半 | 单次检索拿不到跨两跳的信息 |
| 全局性问题（总结所有合同的风险点） | 答得很浅 | Top-K 只覆盖局部片段 |
| 需要计算/聚合（同比增速） | 容易算错 | 检索片段里没有算好的数 |
| 需要时效性（今天的股价） | 答错或拒答 | 知识库没有实时数据 |
| 模糊问题（帮我分析下这家公司） | 泛泛而谈 | 一次检索无法覆盖多角度 |

## 六种进阶架构

```
① 多路召回 + 融合       —— 向量 + 关键词 + 元数据
② 查询规划（多查询）    —— 一个问题拆成 3~5 个子查询
③ 迭代检索（Self-RAG）  —— 检索→判断够不够→不够再查
④ 分层/父子检索         —— 先找章节，再取细节
⑤ GraphRAG              —— 实体关系图 + 社区摘要
⑥ Agentic RAG           —— Agent 自主决定检索策略与工具
```

### ① 多路召回 + 融合

```
query ─┬─→ 向量检索（语义）   ─┐
       ├─→ BM25（关键词）     ─┼─→ RRF 融合 → Rerank → Top-5
       └─→ 元数据过滤（时间/部门）─┘
```

**收益**：专有名词、编号、法规条款这类「关键词精确匹配」场景，BM25 补向量检索的短板。

### ② 查询规划（Multi-Query / 子问题分解）

```python
# 让模型把复杂问题拆成可独立检索的子查询
DECOMPOSE_PROMPT = """把用户问题拆成最多 4 个可独立检索的子问题。
只输出 JSON 数组，不要解释。

问题：{question}
"""

# 例：
# "对比 2023 和 2024 年公司毛利率变化原因"
# → ["2023 年公司毛利率", "2024 年公司毛利率",
#    "毛利率变化的原因分析"]
```

**注意**：子查询并行检索后要做去重与融合，否则噪声翻倍。

### ③ 迭代检索（Self-RAG / 反思式）

```
检索 → 生成草稿 → 自我检查：
    ├─ 证据够吗？不够 → 改写查询再检索（最多 N 轮）
    ├─ 答案有依据吗？无依据的句子删掉
    └─ 够了 → 输出
```

| 优点 | 风险 |
| --- | --- |
| 显著提升多跳与长尾问题 | 延迟与成本成倍增加 |
| 能主动承认「查不到」 | 轮次不设上限会死循环 |

**工程建议**：最多 2~3 轮，每轮必须有新增证据才继续，否则直接返回「暂无法回答」。

### ④ 分层检索（父子块 / Small-to-Big）

```
一级索引：章节摘要（小块，检索精准）
    ↓ 命中章节后
二级取回：该章节下的完整段落（大块，上下文完整）
```

这解决了「小块检索准但上下文碎、大块上下文全但检索糊」的矛盾。

### ⑤ GraphRAG

```
文档 → 实体/关系抽取 → 知识图谱
                          ↓
              社区检测（Leiden）→ 社区摘要
                          ↓
       查询：局部检索（实体邻域）+ 全局摘要（社区报告）
```

| 适用 | 不适用 |
| --- | --- |
| 多跳关系问答（供应链、股权、人物关系） | 单文档事实问答（成本不划算） |
| 全局总结类问题（"这批文档的主要风险"） | 数据量小、关系稀疏的场景 |

**代价**：建图阶段的 LLM 抽取成本很高（一份 100 页文档可能几十美元级），且图需要持续维护。

### ⑥ Agentic RAG

把「检索」变成 Agent 的一个工具，由模型自己决定：

```
用户问题 → Agent 规划
   ├─ 需要查内部知识库？→ 调 retrieve 工具
   ├─ 需要实时数据？→ 调行情/搜索 API
   ├─ 需要计算？→ 调 code interpreter
   ├─ 需要澄清？→ 反问用户
   └─ 信息够了 → 组织答案并标注来源
```

> 这就是 RAG 与 Agent 的交汇点——详见 [Agent 智能体](/agent/) 主题。

## 架构选型决策树

```
问题里有明确的实体/条款/编号？
  └─ 是 → 多路召回（向量 + BM25）+ Rerank

问题需要跨文档、跨章节串联？
  ├─ 关系型（谁投资谁）→ GraphRAG
  └─ 覆盖型（总结全部）→ 分层检索 + 全局摘要

问题需要多次查询才能回答？
  └─ 是 → 迭代检索（Self-RAG）或 Agentic RAG

问题需要实时数据/计算？
  └─ 是 → Agentic RAG（检索只是工具之一）

只是简单的FAQ/制度查询？
  └─ 基础 RAG + Rerank 就够，别过度设计
```

## 成本与延迟对照

| 架构 | 相对延迟 | 相对成本 | 适用规模 |
| --- | --- | --- | --- |
| 基础 RAG | 1× | 1× | 首选基线 |
| + 多路召回 + Rerank | 1.5~2× | 1.5× | 中等规模，收益最稳 |
| 多查询/分层 | 2~3× | 2~3× | 复杂问题多 |
| 迭代检索 | 3~5× | 3~5× | 高价值任务 |
| GraphRAG | 建图极高 / 查询中等 | 高 | 关系密集型知识 |
| Agentic RAG | 3~10× | 高 | 任务型助手 |

**原则：先在基础 RAG 上做评估，用 badcase 驱动升级，而不是一上来就上最复杂的架构。**

## 长上下文 vs RAG

| 维度 | 长上下文（把文档全塞进去） | RAG |
| --- | --- | --- |
| 成本 | 每轮都按全长计费 | 只算检索片段 |
| 延迟 | 首 token 慢（prefill 长） | 快 |
| 准确率 | 中间内容易被忽略 | 检索准则更聚焦 |
| 数据规模 | 受上下文窗口限制 | 可到亿级 |
| 更新 | 每次重塞 | 增量索引 |

**实践结论**：小规模（< 200 页）且问题需要通读全文时可用长上下文；大规模、多用户、成本敏感场景仍以 RAG 为主，二者可混用（RAG 粗筛 + 长上下文精读）。

## FAQ

**Q：GraphRAG 一定要上吗？**
A：不需要。它解决的是「全局性/关系型问题」，对普通 FAQ 是过度设计，且建图成本高。

**Q：迭代检索会不会越查越偏？**
A：会。必须要求每轮基于「缺失信息」改写查询，并设最大轮次；用评估集验证收益。

**Q：分层检索和 Rerank 冲突吗？**
A：不冲突，常配合使用：小块召回 → 映射回父块 → Rerank → Top-K。

**Q：Agentic RAG 相比固定链路最大好处？**
A：能处理「不知道该查什么」的问题，并且可以调用检索之外的工具（计算、实时 API）。代价是可控性下降、成本上升。

**Q：什么时候该放弃 RAG 改微调？**
A：当问题是「风格/格式/领域表达习惯」而非「事实知识」缺失时。知识与时效问题优先 RAG。
