# 02 RAG核心流程

## 一句话

**RAG 是一条两阶段流水线**：索引期（离线）把文档「解析 → 切块 → 向量化 → 入库」建成可检索的知识底座；查询期（在线）对用户问题「检索 → 重排 → 拼装 → 生成」产出带引用的答案。每个环节都有明确的输入输出，**任何一环质量不达标，最终答案就会崩**——排障时按链路逐段定位。

## 两阶段总览

```
══════════════════════════ 索引期（离线） ══════════════════════════

 原始文档        文档解析         文本切块          向量化          入库
┌────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐   ┌──────────┐
│ PDF    │    │ 提取正文  │    │ Chunk 1  │    │ [0.12,   │   │ 向量库    │
│ Word   │ ─→ │ 去页眉页脚│ ─→ │ Chunk 2  │ ─→ │  -0.33,  │→ │ +倒排索引 │
│ HTML   │    │ 表格转MD  │    │ Chunk 3  │    │  ...]    │   │ +元数据   │
│ MD     │    │ OCR兜底   │    │ ...      │    │ 768/1024维│   │          │
└────────┘    └──────────┘    └──────────┘    └──────────┘   └──────────┘
   输入          纯文本          文本块数组        向量数组        可检索索引

══════════════════════════ 查询期（在线） ══════════════════════════

┌────────┐    ┌──────────┐    ┌──────────┐    ┌──────────┐   ┌──────────┐
│ "年假  │    │ 向量召回  │    │ Cross-   │    │ system   │   │ LLM      │
│  几天?"│ ─→ │ +BM25    │ ─→ │ Encoder  │ ─→ │ + 资料   │ → │ 流式答案 │

               输入: 问题       输入: Top-50    输入: Top-5     输入: Prompt

```

**为什么要分两阶段？**
- 索引期是**重活**（解析、Embedding 推理），文档量级大，但只需在文档变更时跑
- 查询期是**快路**（检索毫秒级 + 一次 LLM 调用），对延迟敏感
- 两阶段解耦后，索引可以异步重建/增量更新，查询链路保持稳定

## 索引期四环节详解

### 环节 1：解析（Parse）

| 项 | 内容 |
| --- | --- |
| 输入 | PDF / Word / HTML / Markdown / 扫描件 |
| 输出 | 结构化纯文本（保留标题层级、表格、段落边界） |
| 关键动作 | 提取正文、去页眉页脚、表格转 Markdown、扫描件 OCR |
| 常见坑 | PDF 多栏顺序错乱、表格被打散成碎行、图片信息丢失 |

### 环节 2：切块（Chunk）

| 项 | 内容 |
| --- | --- |
| 输入 | 解析后的长文本 |
| 输出 | Chunk 数组，每块通常 256~1024 token，块间保留重叠 |
| 关键动作 | 按标题/段落递归切分、控制块大小、保留重叠窗口 |
| 常见坑 | 一刀切断句子/表格；块太大噪声多，块太小语义不完整 |

```python
# 切块的最小示例（递归切分器思想）
def chunk_text(text: str, chunk_size: int = 512, overlap: int = 64) -> list[str]:
    chunks, start = [], 0
    while start < len(text):
        end = start + chunk_size
        # 尽量在句号/换行处断开，避免切断句子
        if end < len(text):
            boundary = max(text.rfind("。", start, end), text.rfind("\n", start, end))
            if boundary > start:
                end = boundary + 1
        chunks.append(text[start:end])
        start = end - overlap          # 回退重叠窗口，保住上下文衔接
    return chunks
```

### 环节 3：向量化（Embed）

| 项 | 内容 |
| --- | --- |
| 输入 | Chunk 文本数组 |
| 输出 | 等长浮点向量数组（如 1024 维） |
| 关键动作 | 调用 Embedding 模型，批量推理；中文场景选 bge-m3 / Qwen3-Embedding 等 |
| 常见坑 | 查询和入库**必须用同一个模型**；模型领域不匹配导致检索质量差 |

### 环节 4：入库（Index）

| 项 | 内容 |
| --- | --- |
| 输入 | (向量, 原文, 元数据) 三元组 |
| 输出 | 可检索的向量索引（HNSW/IVF）+ 关键词倒排 + 元数据存储 |
| 关键动作 | 建 ANN 索引；元数据落库（doc_id、来源、权限、时间戳）供过滤 |
| 常见坑 | 只存向量不存元数据 → 后期无法做权限过滤和增量更新 |

## 查询期四环节详解

### 环节 1：检索（Retrieve）

```python
# 多路召回的最小骨架
def retrieve(question: str, top_k: int = 50) -> list[dict]:
    q_vec = embed(question)                          # 同一个 Embedding 模型！
    vec_hits = vector_db.search(q_vec, top_k=top_k)  # 路 1：语义召回
    bm25_hits = bm25_index.search(question, top_k=top_k)  # 路 2：关键词召回
    return rrf_fuse([vec_hits, bm25_hits], top_k=top_k)   # RRF 融合（见 04 章）
```

- 输入：用户原始问题（或改写后的查询）
- 输出：候选 Chunk 集合（Top-20 ~ Top-100，宁多勿漏）
- 目标：**召回率优先**——这一步漏掉了，后面再强的 Rerank 也救不回来

### 环节 2：重排（Rerank）

- 输入：Top-50 候选
- 输出：精排后的 Top-5
- 原理：Cross-Encoder 把「问题 + Chunk」拼在一起过模型，算相关性分数，比向量余弦精度高一个档次（见 05 章）

### 环节 3：拼装（Prompt Stuffing）

```python
def build_prompt(question: str, chunks: list[dict]) -> str:
    context = "\n\n".join(
        f"[资料{i}]（来源：{c['source']}）\n{c['text']}" for i, c in enumerate(chunks, 1)
    )
    return f"""你是企业知识库助手。仅基于以下资料回答问题，资料中没有就明说"未找到相关信息"，禁止编造。

{context}

问题：{question}
回答（末尾用 [资料N] 标注引用）："""
```

- 关键点：**明确指令模型只用给定资料**（降幻觉的核心手段）
- 给每段资料编号，要求答案带引用标号 → 可溯源

### 环节 4：生成（Generate）

- 输入：拼装好的 Prompt
- 输出：答案 + 引用标注（生产环境用流式输出）
- 参数建议：temperature 调低（0~0.3），知识问答要确定性不要创造性

## 各环节输入输出速查表

| 阶段 | 环节 | 输入 | 输出 | 耗时量级 |
| --- | --- | --- | --- | --- |
| 索引期 | 解析 | 原始文件 | 结构化文本 | 秒/文档 |
| 索引期 | 切块 | 长文本 | Chunk 数组 | 毫秒/文档 |
| 索引期 | 向量化 | Chunk 数组 | 向量数组 | 毫秒~秒/批 |
| 索引期 | 入库 | 向量+元数据 | ANN 索引 | 秒/批 |
| 查询期 | 检索 | 问题 | Top-50 候选 | 10~100 ms |
| 查询期 | 重排 | Top-50 | Top-5 | 50~300 ms |
| 查询期 | 拼装 | Top-5 + 问题 | Prompt | <1 ms |
| 查询期 | 生成 | Prompt | 答案 | 秒级（首 token 0.3~1s） |

## 常见架构变体

- **Naive RAG**：上文描述的基础版，检索一次生成一次
- **Advanced RAG**：加查询改写、多路召回、Rerank、元数据过滤（04/05 章）
- **Modular / Agentic RAG**：检索变成 Agent 可调用的工具，自主决定何时检索、检索几次（07 章）

## 常见问题

**Q：Top-K 取多少合适？**
A：检索阶段取大（20~100，保召回），重排后取小（3~10，保精度）。最终进 Prompt 的 Chunk 数量还要受上下文窗口和成本约束，一般 3~8 段、总长 1000~3000 token 是甜区。

**Q：为什么查询期的向量化必须用和入库相同的模型？**
A：不同 Embedding 模型的向量空间完全不兼容——模型 A 的向量在模型 B 的空间里毫无意义，相似度计算全错。换 Embedding 模型 = 全库重建索引。

**Q：检索和重排都是排序，能不能合并成一步？**
A：不能。检索（Bi-Encoder）是把库中**百万级**候选粗筛到几十个，要求快；重排（Cross-Encoder）是对几十个候选精排，要求准。直接用 Cross-Encoder 扫全库成本不可接受，两者是「海选 → 决赛」的关系。

**Q：生成环节幻觉还是出现了怎么办？**
A：按顺序排查：① 检索结果里有没有答案（没有 → 检索问题，不是生成问题）；② Prompt 里有没有明确「仅基于资料回答」；③ temperature 是否过高；④ 换用指令遵循更强的模型。第 06 章的忠实度指标可以量化这个问题。
