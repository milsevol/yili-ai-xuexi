# 01 概述与定位

## 一句话

**Apache HBase**：运行在 HDFS 之上的分布式列式 KV 数据库，用 **LSM-Tree** 把随机写压到每秒百万级、点查压到毫秒级，把一张大表按 **RowKey** 有序切成无数 **Region** 分布在整个集群——适合「海量记录 + 高并发随机读写 + 宽表」，不适合「多表 Join + 复杂聚合」。

## 为什么要有 HBase

HDFS 能存海量文件，但它是文件系统，不是数据库——它不支持**随机定位到某一行**，也不支持**高并发点查**：

| 场景 | HDFS 能做什么 | 做不到什么 |
| --- | --- | --- |
| 按主键查一条记录 | 把整张表当文件扫一遍（慢） | 毫秒级点查 |
| 每秒写入几十万条 | 走文件追加 + 多文件并行 | 同一文件的高并发随机写 |
| 按时间范围扫一段 | 可以，文件是顺序的 | 按 RowKey 连续区间快速定位 |
| 多表 Join、聚合分析 | 靠 MapReduce/Spark 批处理 | 交互式、秒级 SQL |

而传统关系库（MySQL、Oracle）在单机上能做，但**纵向扩不动**：一台 16 核 128GB 的机器，表到几十亿行就吃紧了。HBase 的答案是：**横向加机器**——一张表可以切成几百上千个 Region，每台 RegionServer 管几个，加机器就加 RegionServer。

| 产品 | 它是什么 | 强项 | 弱项 |
| --- | --- | --- | --- |
| **HDFS** | 分布式文件系统 | 存海量大文件、高吞吐、低成本 | 不是数据库，点查极慢 |
| **Hive** | SQL 数仓（跑在 HDFS 上） | 离线批处理、SQL 交互、低成本 | 延迟分钟级，不支持随机写 |
| **HBase** | 分布式列式 KV | 高并发随机点查/写、毫秒级延迟 | 不支持 Join、多条件查询、二级索引要自建 |
| **Cassandra** | 分布式宽列存储 | 多 DC 复制、无主架构、写吞吐高 | 一致性可调、运维复杂度高 |
| **RocksDB / LevelDB** | 嵌入式 KV | 极致低延迟、LSM 成熟 | 单进程、不分布式 |
| **ClickHouse** | 列式 OLAP | 聚合分析快到飞起 | 不适合高并发点查，写吞吐有限 |

## 设计假设决定架构

HBase 的一切设计都来自这几个假设：

| 假设 | 设计结果 |
| --- | --- |
| 机器永远会坏 | WAL（预写日志）保证写不丢、Region 可在 RS 间迁移 |
| 写多读少 | LSM-Tree 把随机写变成顺序写（MemStore 内存写、Flush 到磁盘） |
| 点查/范围扫描是主要读模式 | RowKey 有序、同一 CF 的数据存在一起、HFile 有序存储 |
| 表可以非常大 | 一张表可切几千个 Region，RowKey 前缀路由到特定 Region |
| 不做 Join，不做复杂 SQL | 每个 Region 独立，无分布式事务，无全局索引 |

## 关键概念速览

- **Table（表）**：逻辑上的一张表，物理上是一个或多个 HDFS 目录。
- **Region**：Table 的一段 RowKey 范围，是**存储和负载均衡的最小单位**。一张表可以有几千个 Region。
- **Column Family（CF）**：列族，创建表时就要定下来（不能后面加新 CF），同一 CF 的所有列一起存储、一起压缩。一个 HBase 表至少一个 CF。
- **Qualifier（列）**：CF 里的具体列，**随时可以加**，不同行可以有不同的列。列式存储的关键。
- **RowKey**：行的唯一主键，**按字典序排序**，是设计性能的核心。
- **Cell**：`RowKey + CF + Qualifier + Version` 定位的一个值；一个 Cell 可以有多个 Version。
- **RegionServer（RS）**：真正干活的进程，管多个 Region，负责读写、Flush、Compaction。
- **HMaster**：管理进程，负责 Region 分配、故障恢复、元数据管理；**不服务客户端读写**。
- **ZooKeeper**：协调服务，记录活跃的 RS、Master 选主、`hbase:meta` 位置。
- **WAL（Write-Ahead Log）**：RegionServer 的预写日志，写之前先追加到 WAL，RS 挂了可以恢复 MemStore 未 Flush 的数据。

## 数据模型长什么样

HBase 是**列式**的——同一行的不同 CF 存在一起，但不同行的同一个 CF 又是连续存储的：

```
RowKey          CF:qualifier   timestamp   value
user001         info:name       1700000000  "Alice"
user001         info:age        1700000000  28
user001         addr:city       1700000000  "Beijing"
user002         info:name       1700000000  "Bob"
user002         addr:city       1700000000  "Shanghai"
```

- RowKey 是**有序字符串**，`user001` 和 `user002` 的数据会挨在一起，同一 Region 管。
- `info` 和 `addr` 是 CF；`name`、`age`、`city` 是 Qualifier。
- 一个 Cell 可以有多个时间戳版本，默认保留 1 个，最多保留 100 个。
- **稀疏**：user002 没有 `info:age` 这列，磁盘上不会存空值。

## 什么时候用 HBase：场景 CheckList

**适合：**

- 海量用户画像 / 设备画像 / 商品画像（一行存几百上千个属性）
- 时序数据（OpenTSDB、监控数据，按 device_id + timestamp 做 RowKey）
- 实时计数（网站 UV/PV、广告点击，用 `Increment`）
- 用户行为日志（用户 ID 做前缀、时间戳做后缀，支持单用户的历史扫描）
- 金融风控（高并发点查用户画像）

**不适合：**

- 需要多表 Join、复杂聚合 → 用 Hive / Spark / ClickHouse
- 需要 ACID 事务 → 用关系库（小数据量）或 TiDB（分布式）
- 需要二级索引、按任意条件查询 → 用 Phoenix / ES / 自建索引
- 数据量小（< 100GB）→ 用 MySQL / PostgreSQL 就行

## 与其他组件的关系

```
                    ┌── RegionServer ──┬── Region ──┬── HFile (HDFS)
                    │                  │            └── MemStore (内存)
                    │                  └── Region
Client(Java/Python)─┤
                    ├── HMaster（不读写数据，只分配 Region）
                    │
                    └── ZooKeeper（选主、hbase:meta 位置、RS 注册）
                              │
                    hbase:meta（特殊表，记录「哪个 RowKey 范围在哪个 RS」）
```

## 易错点清单

1. **HBase ≠ 关系库**：它不做 Join、不做事务、不做复杂 SQL，别拿关系库的期待来用。
2. **HBase 写 HDFS，但不走 YARN**：HMaster、RegionServer 都是独立 JVM 进程，自己管内存和线程。
3. **Region 是数据分片**：一张表可以切几千个 Region，加机器就加 RegionServer。
4. **RowKey 设计是头等大事**：RowKey 决定热点分布、读写路径、Compaction 成本。
