# 08 运维监控与故障排查

## 一句话

HBase 运维的核心是**盯指标、看日志、查 ZooKeeper、懂数据路径**——常见故障无非四类：HMaster 切换、RegionServer 宕机、Compaction 阻塞、GC 问题；排障动线永远是「客户端报错 → RS → HDFS → ZK → HMaster」。

## 核心监控指标

### RegionServer 关键指标

| 指标 | 正常范围 | 超过阈值可能意味着 |
| --- | --- | --- |
| MemStore Size | < RS 堆 × 0.40 | 超了 → 阻塞写入、可能 OOM |
| BlockCache Hit Ratio | > 90% | < 70% → HFile 太多（Compaction 不及时）或内存不足 |
| Number of Regions | 50–200/RS | > 200 → Flush/Compaction 风暴、GC 压力大 |
| Number of Stores | 100–500/RS（= Region × CF 数） | > 500 → HFile 总数量多、读路径长 |
| Number of StoreFiles | < 5/Stores（平均） | > 10 → Compaction 没跟上、读路径爆炸 |
| Flush Latency | < 1s | > 5s → HDFS 慢、磁盘/网络问题 |
| Compaction Queue Size | 0–10 | > 50 → Compaction 策略太松或 IO 瓶颈 |
| Puts/Scan 请求数 | 平稳 | 突增 → RowKey 热点或突发流量 |
| GC Pause Time | < 1s | > 10s → 心跳超时风险 |
| Full GC Count | 0 | > 0 → 紧急！内存泄漏或堆不够 |

### HMaster 关键指标

| 指标 | 说明 |
| --- | --- |
| Balancer Status | 是否在平衡 Region |
| Average Load | 每台 RS 的平均 Region 数 |
| Region in Transition | 正在 Split/Move/Open 的 Region 数 |
| Active Master | 当前 Active 是谁 |
| Num Live RegionServers | 存活 RS 数量 |

### ZooKeeper 关键指标

| 指标 | 说明 |
| --- | --- |
| zk_outstanding_requests | 未完成请求数，持续 > 0 说明 ZK 慢 |
| zk_avg_latency | 请求平均延迟（毫秒） |
| zk_znode_count | ZNode 总数（HBase 有 RS、Region Transition 等） |
| zk_watch_count | Watch 总数 |
| zk_children_count | 每个 ZNode 的子节点数 |

### HDFS 关键指标（跟 HBase 强相关）

| 指标 | 说明 |
| --- | --- |
| DataNode Disk Utilization | > 85% 要警惕 |
| DataNode Failed Volumes | 非 0 → 坏盘 |
| DFSClient Read/Written | RegionServer 的读写速率 |
| Short-Circuit Read Ratio | < 100% → SCR 没开或配置不对 |

## HMaster 切换

### 自动切换流程

```
Active HMaster
  │
  │ 心跳超时（默认 60s，hbase.master.znode.session.timeout）
  ▼
ZooKeeper 删除 /hbase/master 临时节点
  │
  │ Standby HMaster 监听，抢到临时节点
  ▼
Standby → Active
  │
  │ 从 hbase:meta 加载最新 Region 分配
  │ 扫描 /hbase/rs 看哪些 RS 还活着
  │ 对 Region in Transition 的 Region 做最终处理
  │ 对上次 Active 还没处理的 Split/Move 继续处理
  ▼
集群恢复服务
```

### 切换耗时

- 最快几秒，最慢几分钟。
- 影响因素：Standby HMaster 是否"热启动"、Region in Transition 数量、HMaster 堆内存大小。
- **切换期间 RegionServer 不受影响**——客户端直连 RS 读写，读写不中断。只有 Region 的分配/迁移工作暂停。

### 手动切换

```bash
# 查看当前 Active Master
hbase shell
> status 'simple'

# 触发手工故障转移（先停 Active 再让 Standby 顶）
# 或直接杀掉 Active Master 进程
kill <active_master_pid>
# Standby 会在 session timeout（60s）后自动成为 Active
```

### 常见切换问题

| 问题 | 原因 | 排查 |
| --- | --- | --- |
| 切换后 RS 全部重连 | ZK session timeout 期间 RS 误判自己 session 过期，重新注册 | 查 ZK 和 RS 的 timeout 配置是否一致 |
| Region 全部重新 Open | ZK 网络分区导致 RS 误以为挂了，HMaster 重分配所有 Region | 查 ZK 日志的 session expire、客户端断连 |
| 切换耗时过长 | Region in Transition 太多 | HMaster 日志看 RIT 处理情况 |
| Active Master 抢不到锁 | ZK 临时节点还在（老 Active 还活着），需要 fencing | HMaster fencing 配置 |

## RegionServer 宕机

### 检测与恢复流程

```
RegionServer 进程挂了（OOM / 机器故障 / GC 超时）
  │
  │ ZK session timeout（默认 60s，hbase.regionserver.lease.period）
  ▼
ZooKeeper 删除 /hbase/rs/<host>:16020:<startcode> 临时节点
  │
  │ HMaster 监听 RS 列表，发现 RS 不见了
  ▼
HMaster 处理：
  1. 标记该 RS 上所有 Region 为 CLOSED（或 CLOSING）
  2. 在 WAL 中检查哪些 Region 还没 Flush
  3. 选择存活 RS 分配 Region
  4. 新 RS 打开 Region → 从 WAL 回放恢复 MemStore → 读 HFile
  ▼
Region 恢复完毕，接受读写
```

### 恢复耗时

- Region 数量少（< 10）：几十秒。
- Region 数量多（> 100）：几分钟。
- 瓶颈：HMaster 分配 Region、新 RS 重新 Open Region、WAL 回放、BlockIndex 加载。

### 影响范围

- **RegionServer 宕机期间，它上面的所有 Region 不服务**——客户端读/写会收到 `NotServingRegionException`，然后自动重试等 Region 迁移完。
- **不会丢数据**——WAL 保证写已持久化到 HDFS，MemStore 未 Flush 的部分从 WAL 回放。
- **但可能有重复计数**——如果客户端重试 Increment，可能在 Region 迁移后重新执行。

### Region 级复制（2.6+）

2.6 起支持 Region 热副本：每个 Region 有主副本和热副本（在另一台 RS 上），热副本实时同步主副本的写入。主副本挂了，热副本直接接替，**几乎零中断**。

## Compaction 队列阻塞

### 症状

- Compaction Queue 里任务数持续 > 50，清理不掉
- HFile 数量越来越多 → 读路径爆炸
- 读写延迟飙升

### 根因

| 根因 | 排查方向 |
| --- | --- |
| **IO 瓶颈** | HDFS DataNode 磁盘 await、网络带宽、HFile 大小 |
| **Compaction 策略太松** | threshold 太高、max.size 太大，该合并的不合并 |
| **Compaction 资源不够** | 线程数少、RS 堆满、Compaction 优先级被用户请求抢占 |
| **写流量持续高** | MemStore 不断 Flush → 新 HFile 不断产生 → 合并速度跟不上产生速度 |

### 诊断命令

```bash
# 1. 看 Compaction 队列
hbase shell
> compaction_queue 'user'

# 2. 看每个 Region 的 HFile 数量
curl "http://rs-host:16030/regions-table?name=user" | grep storefiles

# 3. RS 日志搜 compaction
grep -i "compaction" hbase-regionserver.log | tail -100

# 4. HDFS DataNode 磁盘
datanode-host$ iostat -x 1
datanode-host$ df -h /data/*

# 5. 手动触发一次 Major（缓解一下）
hbase shell
> major_compact 'user'
```

### 解决

1. **先缓解**：手动 Major Compaction（但会吃满 IO，选业务低谷做）。
2. **根因处理**：调 Compaction 策略（调小 threshold、调小 max.size、换 FIFO/DateTiered）。
3. **IO 扩容**：加 DataNode 磁盘、换 SSD、加网络带宽。
4. **RowKey 优化**：根本上减少 Flush 频率（减少热点、减少 MemStore 阻塞）。

## GC 问题

### 典型症状

- RegionServer 日志里出现 "GC pause > 10s"
- 客户端大量超时
- ZooKeeper session 超时 → RS 被误判挂掉 → Region 重分配 → 集群抖动
- Prometheus 看到 Full GC 计数器非 0

### 诊断

```bash
# 1. 实时看 GC
jstat -gcutil <regionserver_pid> 1000

# 2. 看 GC 日志
tail -f /var/log/hbase/rs-gc.log

# 3. 看 heap dump（OOM 时自动产生）
# MAT 或 jhat 分析，找哪个对象占最多

# 4. 堆内存分配
jmap -heap <pid>
```

### 常见根因

| 根因 | 排查 |
| --- | --- |
| **MemStore / BlockCache 分配太大** | 两者之和不能 > 80% 堆 |
| **Region 太多** | 1 台 RS 上 Region > 200，每个 Region 的 CF MemStore 叠加起来吃掉堆 |
| **HFile 太多导致 BlockCache 不够用** | Compaction 不及时 → BlockCache 命中率低 → 对象在堆里堆积 |
| **Scan 产生大量中间对象** | 客户端 `setCaching` 太大、返回数据没及时释放 |
| **堆太小** | 32GB 堆在大集群上可能不够 → 升到 64GB |

### 预防

- 生产**禁用 Swap**（见第 06 章）。
- 用 G1GC / ZGC。
- BlockCache + MemStore ≤ 70% 堆。
- Region 数上限 200/RS。
- GC 日志 + 监控告警。

## 日志分析

### RegionServer 日志关键关键词

| 关键词 | 含义 |
| --- | --- |
| `Blocked updates` | 全局 MemStore 超了，写入被阻塞 |
| `Compaction: starting` | 开始 Compaction |
| `Compaction: finished` | Compaction 完成，带耗时和输入/输出文件数 |
| `flush: region=X, store=Y` | Flush 触发 |
| `GC pause` / `Full GC` | GC 暂停，看时长 |
| `connection reset` / `java.net.SocketException` | HDFS 或客户端连接问题 |
| `NotServingRegionException` | Region 不在本 RS（迁移中或刚迁移完） |
| `RegionServer abort` | RS 自己 abort 了，通常因为 WAL 恢复失败或致命错误 |
| `outOfMemStore` | MemStore 已满，阻塞写入 |
| `Could not split because...` | Split 被跳过，看原因 |

### HMaster 日志关键关键词

| 关键词 | 含义 |
| --- | --- |
| `Master startup` | HMaster 启动信息 |
| `ZNode /hbase/master acquired` | 抢到锁成为 Active |
| `Region in transition` | 正在处理 Region 状态变更 |
| `Dead servers` | 发现 RS 挂了，开始处理 |
| `Balance` | Balancer 状态 |
| `Split region` | 处理 Split |

### ZooKeeper 日志

```bash
# ZK 日志通常在 zookeeper dataLogDir 下
tail -f /data/zookeeper/log/zookeeper.out

# 搜关键事件
grep -i "session" zookeeper.out | tail -20   # 会话事件
grep -i "leader" zookeeper.out               # Leader 选举
grep -i "error" zookeeper.out                # 错误
```

## 排障决策树

```
客户端报错
  │
  ├─ "NotServingRegionException"
  │   └─ → 正常？Region 迁移/Split 中 → 客户端重试自动解决
  │
  ├─ "SocketTimeoutException"
  │   ├─ RS GC 超时？→ 看 GC 日志
  │   ├─ HDFS 慢？→ 看 DataNode 磁盘
  │   ├─ RowKey 热点？→ 看 RS Web UI 写请求分布
  │   └─ ZK 慢？→ 看 ZK latency
  │
  ├─ "RetriesExhaustedException"
  │   ├─ 网络不通？→ ping / telnet RS 端口
  │   ├─ RS 挂了？→ jps 看进程
  │   ├─ ZK session expire？→ 看 ZK 日志
  │   └─ Region 长时间不服务？→ 查 HMaster RIT
  │
  └─ "OutOfMemoryError"
      ├─ RS 堆不够 → 加堆 / 减 Region / 调 BlockCache
      ├─ GC 后仍不够 → 查泄漏（heap dump）
      └─ WAL 恢复时 OOM → 看 WAL 大小
```

## 易错点清单

1. **Compaction Queue 长期满着不处理**：它不会自动好；会越来越严重，直到 BlockCache 命中率掉穿。
2. **HMaster 切换期间读写也中断**：错——HMaster 不扛读写，读写不中断；只有 Region 分配暂停。
3. **RegionServer 挂了一定丢数据**：错——WAL 保证已 fsync 的写不丢，MemStore 未 Flush 的从 WAL 回放。
4. **NotServingRegionException 必须手动处理**：错——HBase 客户端内部就做了重试，大多数情况自动恢复。

## 自测

1. 客户端报大量 "NotServingRegionException"，但几秒后自动好，最可能的原因是什么？
2. RegionServer 的 GC Pause Time 突然升到 15 秒，你会先查哪些指标？
3. Compaction Queue 满了，Compaction 却迟迟不完成，你怎么一步步诊断根因？
4. 一台 RegionServer 突然被 HMaster 判定为 dead，但你登录机器发现它还在跑——可能的原因？
