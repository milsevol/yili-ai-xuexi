# 02 架构与组件

## 一句话

HBase 的架构是「**HMaster 管分配、RegionServer 扛读写、ZooKeeper 做协调、Region 切片、WAL 保不丢、HFile 存 HDFS**」——每个 RegionServer 管几十上百个 Region，客户端直连 RegionServer，HMaster 只在「Region 搬新家」的时候出场。

## 全局架构图

```
Client (Java/Python)
  │
  │ 1. 查 hbase:meta（走 ZooKeeper 拿位置，缓存到客户端）
  │    meta 表结构: (table, region_start) → RegionServer:port
  │
  ├─────── ZooKeeper ───────────────────────────────────────┐
  │        - /hbase/master → 当前 Active Master             │
  │        - /hbase/rs/  → 所有活跃的 RegionServer 列表     │
  │        - /hbase/meta-region-server → meta 表在哪台 RS    │
  │                                                          │
  │ 2. 读写 ──► RegionServer ──┬── Region A (table=user, [,row5000))
  │                             │   ├── MemStore (内存，按 CF 分)
  │                             │   ├── WAL (HLog，HDFS)
  │                             │   └── StoreFile × N (HFile，HDFS)
  │                             │
  │                             ├── Region B (table=user, [row5000, row10000))
  │                             │
  │                             └── Region C, D, ...
  │
  │ 3. Region 分配/迁移 ──► HMaster
  │                          - 新 RegionServer 注册进来
  │                          - Region 分裂（Split）出新 Region
  │                          - RegionServer 宕机：把它的 Region 重分配
  │
  └──────────────────────────────────────────────────────────┘
```

## 角色分工

| 角色 | 一句话职责 | 关键配置/端口 |
| --- | --- | --- |
| **Client** | 发起读写；先查 meta 缓存、再直连 RegionServer | `hbase.zookeeper.quorum`、`zookeeper.znode.parent=/hbase` |
| **ZooKeeper** | 协调中心：选主、RS 注册、meta 位置 | 至少 3 台（奇数，2F+1），2181 |
| **HMaster** | Region 分配/迁移、元数据管理、Admin API | 16000/RPC、16010/Web UI |
| **RegionServer (RS)** | 管 Region、服务客户端读写、Flush、Compaction | 16020/RPC、16030/Web UI |
| **WAL (HLog)** | RegionServer 级预写日志，先写 WAL 再写 MemStore | 存 HDFS，滚动切割 |
| **MemStore** | Region 内内存写缓冲，满了 Flush 成 HFile | 默认 128MB，按 CF 分 |
| **HFile (StoreFile)** | Flush/Compaction 产物，有序 KV 文件，存 HDFS | 块级索引 + BloomFilter |
| **BlockCache** | RegionServer 级读缓存，缓存 HFile 数据块 | 默认堆外，`hfile.block.cache.size` |

## ZooKeeper 里存了什么

ZooKeeper 是 HBase 的**通讯录**，不是数据库：

| ZNode | 作用 |
| --- | --- |
| `/hbase/master` | 当前 Active HMaster 的地址；多个 Master 谁抢到临时节点谁当 Active |
| `/hbase/backup-masters` | Standby Master 列表（可多台） |
| `/hbase/rs/<hostname>,<port>,<startcode>` | 每个 RegionServer 注册一个临时节点；挂了节点自动消失 |
| `/hbase/meta-region-server` | hbase:meta 表所在的 RegionServer 地址；客户端先查这个 |
| `/hbase/region-in-transition` | Region 正在 Split/Merge/迁移时的状态跟踪 |
| `/hbase/hbaseid` | 集群唯一 ID，防止 RS 误连别的集群 |

> 重要：**ZooKeeper 挂了会导致 RegionServer 无法心跳、Master 无法选主，但不会丢数据**——它只存协调信息，不存业务数据。

## hbase:meta —— 路由表

`hbase:meta` 是一张特殊表，记录「每个 Region 在哪台 RS 上」：

| RowKey | CF:server | CF:startkey | CF:endkey |
| --- | --- | --- | --- |
| `user,,1700000000` | rs1:16020 | (空，表示起点) | row0001 |
| `user,row0001,1700000001` | rs2:16020 | row0001 | row0500 |
| `user,row0500,1700000002` | rs1:16020 | row0500 | (空，表示终点) |

- meta 表本身也放在某个 RegionServer 上（位置写在 ZooKeeper 的 `/hbase/meta-region-server`）。
- 客户端**启动时查一次 meta 位置，然后缓存整个 meta 表**到内存；Region 迁移后，客户端收到 `NotServingRegionException`，再重新查 meta。
- 这是 HBase 读路径的**第一步**，也是为什么 ZooKeeper 访问性能很重要。

## Region 的生命周期

```
Table 创建
  │
  ▼
HMaster 创建 1 个初始 Region（覆盖整个 RowKey 范围）
  │
  ▼
Region 被分配到某台 RegionServer
  │
  ▼
RegionServer 打开 Region → 建立 MemStore、加载 HFile 索引
  │
  ▼
Region 不断写 → MemStore 满 → Flush 成 HFile
  │
  ▼
HFile 越来越多 → Compaction 合并成一个新 HFile
  │
  ▼
Region 大小超过阈值 → Split（分裂）成 2 个 Region，各自管一半 RowKey
  │
  ▼
HMaster 把新 Region 分配到（可能不同的）RegionServer
  │
  ▼
RegionServer 宕机 → 它上面的所有 Region 先关闭（close）
                    → WAL 回放恢复 MemStore
                    → HMaster 把 Region 分配到其他存活的 RS
```

## WAL（Write-Ahead Log）架构

**为什么需要 WAL**：RegionServer 写数据时先写 MemStore（内存），如果写完 MemStore 但还没 Flush 到 HFile、RS 就挂了——这些数据就丢了。WAL 就是为了解决这个问题：

```
客户端 Put 请求
  │
  ├── ① 写 WAL（追加到 HDFS，保证 fsync 落盘）
  │        WAL 是 RegionServer 级共享的，所有 Region 共用一个（2.5 起支持 per-Region WAL）
  │
  ├── ② 写 MemStore（内存追加）
  │
  └── ③ 返回成功给客户端
```

- **WAL 滚动**：一个 WAL 文件写满或到达时间阈值就切新文件（`hbase.regionserver.logroll.period` 默认 3600 秒，`hbase.regionserver.hlog.blocksize` 默认 HDFS 块大小）。
- **WAL 清理**：当该 WAL 中所有 Region 的 MemStore 都已经 Flush 完毕后，这个 WAL 文件才能被删除。
- **WAL 恢复**：RegionServer 重启后，读取未清理的 WAL 文件，回放其中的 Edit 到 MemStore，再 Flush。
- **关闭 WAL**：对日志类、可重放的写入，可以关闭 WAL 换性能（`Put.setDurability(Durability.SKIP_WAL)`），但**风险极高**。

## 写路径完整流程

```
Client                        RegionServer                    HDFS
  │
  │ ① 查 meta（或走缓存），知道 RowKey 属于哪个 Region、在哪台 RS
  │
  │ ② Put → RegionServer RPC ──► WAL 追加（fsync 落盘）
  │                                    │
  │                                    ▼
  │                              MemStore 追加（按 CF 分桶）
  │                                    │
  │                                    ▼
  │                              返回 Ack 给 Client
  │
  │                        MemStore 满（默认 128MB / CF）
  │                                    │
  │                                    ▼
  │                              Flush 触发
  │                                    │
  │                                    ▼
  │                              生成临时 HFile ──► 写入 HDFS
  │                                    │
  │                                    ▼
  │                              重命名为 StoreFile
  │                                    │
  │                                    ▼
  │                              清空对应 CF 的 MemStore
  │                              WAL 标记该 CF 数据可回收
  │
  │                     StoreFile 数超过阈值 → Compaction（见第 04 章）
```

## 读路径完整流程

```
Client Get/Scan → RegionServer
  │
  ├── ① 查 BlockCache（堆外内存，缓存 HFile 数据块）
  │     命中 → 直接返回，最快路径
  │     未命中 → 继续
  │
  ├── ② 查 MemStore（内存中的最新数据，包括未 Flush 的）
  │     命中 → 合并版本后返回
  │     未命中 → 继续
  │
  ├── ③ 查 HFile（按时间戳倒序：新 → 旧）
  │     用 BloomFilter 先快速判断「这个 RowKey 大概率在/不在这个 HFile」
  │     不在 → 跳过这个 HFile
  │     在 → 定位 block index → 读数据块 → 放入 BlockCache
  │
  └── ④ 合并：MemStore 数据 + 所有 HFile 命中的 Cell → 取最新版本 → 返回
```

> **读路径的性能关键**：`BlockCache 命中率` 和 `HFile 数量`。BlockCache 命中率低就要读 HDFS；HFile 数量多就要逐个查 BloomFilter + 定位，Compaction 的意义就在此。

## HMaster HA

HMaster 本身不是数据路径上的单点故障，因为客户端读写不经过它，但它挂了就不能做 Region 分配/迁移/Split 处理了。

```
Active HMaster ──┐
                 ├─ ZooKeeper /hbase/master 选主
Standby HMaster ─┘
```

- 至少部署 2 台 HMaster：一台 Active，其余 Standby。
- 谁抢到 `/hbase/master` 临时节点谁当 Active。
- Active 挂了，ZooKeeper 心跳超时（`hbase.master.znode.session.timeout`），Standby 立刻顶上去。
- 多 RegionServer 同时挂掉的恢复流程：HMaster 从 ZooKeeper 的 RS 列表发现谁不见了 → 把它负责的 Region 分配到其他存活 RS → 新 RS 从 WAL 回放恢复。

## 易错点清单

1. **HMaster 不扛读写**：HMaster 只做管理，客户端直接打 RegionServer；HMaster 挂了读写不受影响，只是不能 Split/迁移。
2. **WAL 是 RegionServer 级**：不是 Region 级（2.5 虽支持 per-Region WAL 但默认仍共享），所以 WAL 是 RS 的性能关键点。
3. **meta 表本身也在某个 RegionServer 上**：ZooKeeper 只存 meta 表的位置，meta 的数据在 HDFS 上。
4. **Region 迁移是 HMaster 管的**：客户端收到 NotServingRegionException 才知道 Region 搬家了。

## 自测

1. 用一句话说清 HMaster、RegionServer、ZooKeeper 三者之间的分工和依赖关系。
2. 客户端读一条数据，最长路径要经过哪些组件？最短路径呢？
3. WAL 为什么要先 fsync 到 HDFS？如果关闭 WAL 会怎样？什么场景下可以关？
4. 一台 RegionServer 宕机后，它上面的 Region 怎么恢复？中间会丢数据吗？
