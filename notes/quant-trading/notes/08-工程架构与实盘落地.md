# 08 工程架构与实盘落地

## 一句话定位

实盘工程的核心不是「把回测代码跑在服务器上」，而是让**研究、信号、交易、风控、监控共享同一份事实**：同一份数据快照、同一份因子代码、同一份配置、同一套订单状态。回测与实盘的差距，八成来自工程不一致，而不是策略逻辑。

## 解决什么问题

- 研究环境用后复权、实盘用不复权，同一因子算出来的值不一样。
- 回测用 `close` 成交，实盘 9:30 发单，成交价和回测差了几个点。
- 断线重连后重复下单，或者不知道哪些订单还挂着。
- 盘中没有 kill switch，策略失控时只能手动一个个撤单。
- 出了亏损无法复盘：日志里没有信号值、订单号、风控判断、行情快照。

## 研究与实践为什么会对不上

| 不一致来源 | 典型表现 | 后果 |
| --- | --- | --- |
| 两份代码 | 研究用 notebook，实盘重写一遍 | 因子计算细节漂移，没人能复现 |
| 两套数据 | 回测读本地 CSV，实盘读行情 API | 复权、停牌、缺失值处理不同 |
| 两种复权 | 回测后复权，实盘前复权/不复权 | 价格、收益率、信号全错位 |
| 两个时点 | 回测用当日收盘，实盘用次日开盘 | 引入了未来信息 |
| 两套参数 | 配置文件各写一份 | 回测和实盘不是同一个策略 |

解决原则只有一句：**核心逻辑只写一份，环境差异全部外置为配置和数据快照。**

```text
research/ ──┐
            ├──> core/（因子、信号、组合、风控规则，纯函数，无 IO）
live/     ──┘         │
                      ├── config/research.yaml（数据源=parquet 快照 v20240601）
                      └── config/live.yaml（数据源=行情 API，交易开关=true）
```

工程上要落地三件事：

1. **同一份因子/信号代码**：`core/` 不读文件、不连数据库、不写日志，只接受 DataFrame，返回 DataFrame。研究、回测、实盘都调它。
2. **同一份配置**：参数、股票池、风控阈值放在版本化配置里，回测与实盘加载同一份，只覆盖「数据源、交易通道」这类环境项。
3. **同一套数据快照**：每天盘后固化一份带版本号（日期 + 文件 hash）的行情/财务快照。回测指向快照，实盘盘前也先落一份快照再算信号，保证「今天实盘用的数据」和「明天回测用的数据」是同一份。

## 系统分层架构

```text
┌──────────────────────────────────────────────────────────────┐
│ 监控层  Prometheus / Grafana / 企业微信告警 / 对账报表        │
├──────────────────────────────────────────────────────────────┤
│ 风控层  事前额度与池子 │ 事中异常与回撤 │ 事后归因与审计      │
├──────────────────────────────────────────────────────────────┤
│ 交易层  OMS（订单/持仓/资金） → EMS（拆单/路由） → 券商通道   │
├──────────────────────────────────────────────────────────────┤
│ 信号层  每日信号 / 盘中信号 / 目标组合 / 订单计划              │
├──────────────────────────────────────────────────────────────┤
│ 研究层  因子计算、回测、参数搜索、归因                         │
├──────────────────────────────────────────────────────────────┤
│ 数据层  采集 → 清洗 → 复权/对齐 → 存储（Parquet/DuckDB/CK）   │
└──────────────────────────────────────────────────────────────┘
```

分层的关键约束是**依赖单向向下**：交易层不回头调用研究层，风控层不依赖策略内部实现，监控层只读不改。这样任何一层都可以单独替换、单独测试。

## 技术栈选型

| 组件 | 推荐 | 角色 | 取舍 |
| --- | --- | --- | --- |
| 计算 | Python + pandas | 因子/回测/信号 | 生态最全，单机到千万行够用 |
| 计算（大规模） | polars | 列式、多核、惰性求值 | API 与 pandas 有差异，团队要统一 |
| 存储（单机） | Parquet + DuckDB | 历史行情、因子快照 | 零运维，适合个人/小团队 |
| 存储（服务） | ClickHouse | 分钟线、逐笔、指标查询 | 运维成本高，个人没必要上来就上 |
| 调度 | Airflow / DolphinScheduler | 盘前数据、盘后任务 | 重；单机 cron + 脚本也能跑很久 |
| 缓存/状态 | Redis | 订单状态、限频、分布式锁 | 要设计持久化，不能当唯一账本 |
| 实时 | Kafka | 行情/回报的流式管道 | 只有低延迟多消费者时才需要 |
| 监控 | Prometheus + Grafana | 指标采集与看板 | 需要埋点规范，否则全是噪声 |
| 告警 | 企业微信/飞书 Webhook | 人工介入入口 | 必须分级，避免告警疲劳 |

选型原则：**先用最少的组件跑通闭环，再按瓶颈加组件**。个人量化用「cron + Parquet + DuckDB + 一个进程 + Webhook 告警」就能覆盖日频策略；分钟级、多账户、多策略再考虑 Redis/Kafka。

## 交易日历与时区

- 所有时间统一存 **Asia/Shanghai**，数据库存 UTC 或带时区时间戳，展示层再转本地。跨市场策略必须显式做时区转换，不能依赖服务器本地时区。
- A 股：9:15–9:25 开盘集合竞价（9:20–9:25 不可撤单），9:25 撮合出开盘价，9:30–11:30、13:00–15:00 连续竞价，14:57–15:00 收盘集合竞价。**14:57 之后进入收盘集合竞价，通常不可撤单**（以交易所最新规则为准），尾盘算法要提前收口。
- 港股有半日市（如圣诞前夕），A 股一般没有常规半日市，但会有临时休市。交易日历必须来自交易所/权威数据源，不能自己用「周一到周五」推算。
- 信号生成时点决定可用数据：用 T 日收盘数据生成信号，最早 T+1 开盘执行；若要在 T 日 14:50 发单，只能用 14:50 之前的分钟数据，且要接受「收盘前最后 10 分钟」的额外不确定性。

## 实盘主循环

```text
盘前（08:00–09:25）
  1. 检查交易日历、账户、通道连通性
  2. 拉取/校验行情与财务数据，落当日快照
  3. 计算因子 → 生成信号 → 目标组合
  4. 与当前持仓比对，生成订单计划
  5. 事前风控：额度、集中度、禁投池、涨跌停、流动性
  6. 人工/自动确认，进入待发状态

盘中（09:30–15:00）
  7. 按计划发单（幂等 client_order_id）
  8. 接收成交回报，更新订单/持仓/资金
  9. 定时查询未完成订单，处理超时、废单、断线
 10. 事中风控：价格异常、撤单率、单票超限、回撤触发降仓
 11. kill switch 随时可中断全部交易

盘后（15:05–17:00）
 12. 拉取柜台成交与资金流水
 13. 订单、成交、持仓、资金四方对账
 14. 计算执行质量（滑点、IS、参与率）与当日归因
 15. 归档日志、快照、配置版本，生成日报
```

## 关键工程问题

| 问题 | 错误做法 | 正确做法 |
| --- | --- | --- |
| 幂等下单 | 超时后直接重试 | `client_order_id` 作为幂等键，重试前先查询 |
| 订单去重 | 用「股票+方向+数量」判重 | 用当日唯一序号 + 哈希，允许同标的合法多笔 |
| 断线重连 | 只续增量回报 | 先全量拉当前委托/成交，按订单号对齐，再开增量 |
| 状态恢复 | 依赖内存变量 | 订单/持仓落盘（SQLite/Redis），重启后重建状态机 |
| 资金校验 | 只看策略算的可用资金 | 以柜台资金为准，下单前冻结估算，成交后以回报校正 |
| 涨跌停/停牌 | 回测不过滤 | 发单前检查涨跌停价、停牌标记、可交易状态 |
| 限频 | 循环里无节制发单 | 令牌桶限速，遵守券商/交易所报单频率 |
| 发布 | 盘中改代码重启 | 盘后发布，版本号 + 回滚包，盘中只切开关 |
| 熔断 | 靠人盯盘 | 策略级、账户级两级 kill switch，一键撤单并禁止新单 |

**幂等的本质**：同一笔业务意图，无论调用多少次，结果只发生一次。实现上要同时做三层：客户端本地记录、券商侧 `ClOrdID` 去重、成交回报按订单号幂等更新。只做其中一层，都会在超时重试时出问题。

## 风控三层

| 层级 | 时机 | 检查内容 | 失败动作 |
| --- | --- | --- | --- |
| 事前 | 发单前 | 总仓位/净敞口、单票集中度、行业集中度、禁投池、杠杆、单笔金额、涨跌停、停牌、流动性（下单量/日均成交量） | 拒单并记录原因 |
| 事中 | 盘中实时 | 价格偏离、报单/撤单频率、单票仓位漂移、当日回撤、数据断流、重复订单 | 暂停策略、撤单、降仓、告警 |
| 事后 | 盘后 | 成交与持仓对账、PnL 归因、滑点/IS、限额突破、审计留痕 | 复盘、调参、追责、修复 |

事中风控要独立于策略进程：策略崩了，风控仍能撤单。最简单的做法是「风控检查函数 + 独立看门狗进程」，高级做法是券商侧预置风控 + 自建风控双保险。

## 合规要点

- **程序化交易报备**：按证监会《证券市场程序化交易管理规定（试行）》及沪深北交易所《程序化交易管理实施细则》，投资者需通过券商报告账户、策略类型、交易频率、软件等信息；高频交易还有额外报告与监控要求。规则会更新，落地前以交易所和券商最新要求为准。
- **异常交易监控**：虚假申报、频繁撤单、拉抬打压、自成交、日内反向交易等会被重点监控。策略设计要避免「大量挂单后秒撤」这类看似套利、实为扰动的行为。
- **交易留痕**：订单、回报、参数、代码版本、风控判断、行情快照都要可追溯，保存期限满足监管要求。日志要能还原「当时为什么下这一单」。
- **数据与密钥安全**：密钥放环境变量或密钥管理服务，禁止硬编码进仓库；账户最小权限；生产与测试隔离；敏感数据脱敏后再进日志。

## 实践：最小实盘主循环骨架

以下代码用内存模拟券商，完整走一遍「盘前信号 → 事前风控 → 幂等下单（含一次模拟超时）→ 盘后对账」。只依赖标准库 + numpy + pandas，可直接运行。

```python
import hashlib
import logging
from dataclasses import dataclass
from datetime import date

import numpy as np
import pandas as pd

logging.basicConfig(
    level=logging.INFO,
    format="%(asctime)s %(levelname)s %(message)s",
    datefmt="%H:%M:%S",
)
log = logging.getLogger("live")

TRADE_DATE = date(2024, 6, 3)
CAPITAL = 1_000_000.0
MAX_SYMBOL_WEIGHT = 0.30
MAX_TOTAL_EXPOSURE = 0.90
FORBIDDEN = {"000002.SZ"}
KILL_SWITCH = False


@dataclass
class Order:
    client_id: str
    symbol: str
    side: str
    qty: int
    price: float
    status: str = "NEW"
    filled: int = 0
    avg_price: float = 0.0


class FakeBroker:
    """内存模拟券商。drop_first=True 时模拟「柜台已受理但网络超时」。"""

    def __init__(self, drop_first=False):
        self.orders = {}
        self.fills = []
        self.drop_next = drop_first

    def place_order(self, client_id, symbol, side, qty, price):
        if client_id in self.orders:
            log.info("[broker] 幂等命中 %s，返回已有订单", client_id)
            return self.orders[client_id]
        order = Order(client_id, symbol, side, qty, price,
                      status="FILLED", filled=qty, avg_price=price)
        self.orders[client_id] = order
        self.fills.append({"client_id": client_id, "symbol": symbol, "side": side,
                           "qty": qty, "price": price})
        if self.drop_next:
            self.drop_next = False
            raise ConnectionError("simulated timeout after accepted")
        log.info("[broker] 成交 %s %s %s %d股 @ %.2f",
                 client_id, symbol, side, qty, price)
        return order

    def query_orders(self):
        return list(self.orders.values())


class OrderClient:
    """客户端幂等层：同一业务意图只生成一个 client_order_id。"""

    def __init__(self, broker):
        self.broker = broker
        self.sent = {}
        self.seq = 0

    def submit(self, symbol, side, qty, price, retry=2):
        self.seq += 1
        raw = f"{TRADE_DATE}|{symbol}|{side}|{self.seq}"
        cid = "ORD-" + hashlib.sha1(raw.encode("utf-8")).hexdigest()[:12].upper()
        if cid in self.sent:
            log.info("[oms] 本地幂等命中 %s", cid)
            return self.sent[cid]
        for attempt in range(1, retry + 1):
            try:
                order = self.broker.place_order(cid, symbol, side, qty, price)
                self.sent[cid] = order
                return order
            except ConnectionError:
                log.warning("[oms] 第 %d 次下单超时，先查询再重试", attempt)
                for o in self.broker.query_orders():
                    if o.client_id == cid:
                        self.sent[cid] = o
                        log.info("[oms] 查询确认订单已受理 %s，不再重发", cid)
                        return o
        raise RuntimeError("下单最终失败: " + cid)


def make_daily_bars():
    """构造确定性的日线数据：带趋势的价格 + 成交量。"""
    rng = np.random.default_rng(20240603)
    dates = pd.bdate_range("2024-04-01", periods=40)
    trend = np.linspace(0, 1, len(dates))
    drifts = {"600000.SH": 0.18, "000001.SZ": 0.10, "300750.SZ": -0.06}
    close, volume = {}, {}
    for sym, drift in drifts.items():
        close[sym] = 20 * (1 + drift * trend) + rng.normal(0, 0.25, len(dates))
        volume[sym] = rng.integers(1_500_000, 3_000_000, len(dates))
    return pd.DataFrame(close, index=dates), pd.DataFrame(volume, index=dates)


def pre_trade_check(symbol, side, qty, price, current_value, total_exposure,
                    prev_close, avg_volume):
    notional = qty * price
    if symbol in FORBIDDEN:
        return False, "在禁投池"
    if qty < 100 or qty % 100 != 0:
        return False, "数量不是100股整数倍"
    if side == "BUY" and current_value + notional > CAPITAL * MAX_SYMBOL_WEIGHT:
        return False, "单票集中度超限"
    if side == "BUY" and total_exposure + notional > CAPITAL * MAX_TOTAL_EXPOSURE:
        return False, "总仓位超限"
    limit_pct = 0.20 if symbol.startswith("300") else 0.10
    if price > prev_close * (1 + limit_pct) * 1.001:
        return False, "价格超出涨停附近"
    if qty > avg_volume * 0.05:
        return False, "下单量超过日均成交量5%"
    return True, "通过"


def main():
    close, volume = make_daily_bars()
    ma5 = close.rolling(5).mean().iloc[-1]
    ma20 = close.rolling(20).mean().iloc[-1]
    last = close.iloc[-1]
    prev_close = close.iloc[-2]
    avg_volume = volume.tail(20).mean()

    log.info("[pre] 交易日 %s，数据快照 rows=%d", TRADE_DATE, len(close))
    targets = {}
    for sym in close.columns:
        if ma5[sym] > ma20[sym] and last[sym] > close[sym].iloc[-20]:
            targets[sym] = 0.25
            log.info("[signal] %s 通过均线+20日动量，目标权重 25%%", sym)
        else:
            log.info("[signal] %s 不满足条件，跳过", sym)

    log.info("[pre] 开始事前风控与订单计划")
    plan = []
    total_exposure = 0.0
    for sym, weight in targets.items():
        price = round(float(last[sym]) * 1.0005, 2)
        qty = int(CAPITAL * weight / price // 100 * 100)
        ok, reason = pre_trade_check(sym, "BUY", qty, price, 0.0,
                                     total_exposure, float(prev_close[sym]),
                                     float(avg_volume[sym]))
        if not ok:
            log.warning("[risk] 拒绝 %s %d股：%s", sym, qty, reason)
            continue
        plan.append((sym, qty, price))
        total_exposure += qty * price
        log.info("[risk] 通过 %s 买 %d股 @ %.2f，预计敞口 %.1f%%",
                 sym, qty, price, 100 * total_exposure / CAPITAL)

    # 额外演示一笔会被风控拒绝的大单
    big_qty = 100_000
    ok, reason = pre_trade_check("600000.SH", "BUY", big_qty, float(last["600000.SH"]),
                                 0.0, total_exposure, float(prev_close["600000.SH"]),
                                 float(avg_volume["600000.SH"]))
    log.info("[risk] 大单检查 %d股 -> %s (%s)", big_qty, "通过" if ok else "拒绝", reason)

    broker = FakeBroker(drop_first=True)
    client = OrderClient(broker)
    log.info("[intraday] 开始执行 %d 笔订单", len(plan))
    for sym, qty, price in plan:
        if KILL_SWITCH:
            log.warning("[kill] 熔断打开，停止后续下单")
            break
        client.submit(sym, "BUY", qty, price)

    log.info("[post] 盘后对账")
    filled = {}
    cash_used = 0.0
    for o in broker.query_orders():
        filled[o.symbol] = filled.get(o.symbol, 0) + o.filled
        cash_used += o.filled * o.avg_price
    all_pass = True
    for sym, qty, _ in plan:
        got = filled.get(sym, 0)
        status = "PASS" if got == qty else "FAIL"
        all_pass &= got == qty
        log.info("[recon] %s 计划 %d / 成交 %d -> %s", sym, qty, got, status)
    ids = [o.client_id for o in broker.query_orders()]
    unique = len(ids) == len(set(ids))
    log.info("[recon] 订单号唯一性 -> %s", "PASS" if unique else "FAIL")
    log.info("[recon] 资金占用 %.2f，剩余 %.2f", cash_used, CAPITAL - cash_used)
    log.info("[recon] 总体对账 -> %s", "PASS" if all_pass and unique else "FAIL")


if __name__ == "__main__":
    main()
```

运行后可以看到几个关键行为：

- 网络超时那笔单没有重复成交：客户端先查询，发现柜台已受理，直接复用。
- 每笔订单都有 `ORD-` 开头的唯一 ID，盘后可以按 ID 对账。
- 大单被「单票集中度」或「日均成交量 5%」拦截，日志给出明确原因。
- `KILL_SWITCH` 在任何一笔下单前检查，打开后停止新单（真实系统还要加「立即撤所有挂单」）。

把 `FakeBroker.place_order` 换成 QMT/Ptrade/CTP 的真实调用，把 `make_daily_bars` 换成行情 API，把内存记录换成 SQLite，这个骨架就能演进成可用的日频实盘系统。

## 常见误区与坑

1. **只看策略不看运维**：回测夏普 2.0，实盘因为数据延迟、订单被拒、进程崩溃，实际收益为负。
2. **没有 kill switch**：出事时手动撤单，越急越乱。必须有「一键停止新单 + 撤销全部挂单」的独立入口。
3. **日志不足**：只记录成交价，不记录信号值、风控判断、行情快照。复盘时无法区分「策略错」还是「执行错」。
4. **盘中改代码**：改完重启，内存状态丢一半，订单状态和柜台不一致。发布只在盘后，盘中只切配置开关。
5. **密钥硬编码**：API key、账户密码写进 Git，仓库一泄露全盘皆输。用环境变量/密钥管理，禁止日志打印。
6. **把 Redis 当唯一账本**：Redis 挂了就不知道持仓。柜台是资金的最终事实，本地状态必须可重建。
7. **不校验数据**：行情缺失、重复、时间戳错乱直接进策略，产生幽灵信号。盘前必须做行数、空值、涨跌幅、时间连续性校验。
8. **忽略 T+1**：A 股当日买入不可卖出，策略里的「日内平仓」在股票上不成立；卖出资金当日可继续买入，但提现要 T+1。

## 常见问题 Q&A

**Q1：回测和实盘对不上，先查什么？**
按「数据 → 时点 → 成交假设 → 费用」顺序查：先对齐同一段日期的行情快照，再确认信号用的是 T 日收盘还是 T+1 开盘，然后看成交价假设和滑点，最后核对佣金、印花税、过户费。80% 的问题在前两步。

**Q2：个人做量化需要微服务/K8s 吗？**
不需要。日频策略一个 Python 进程 + cron + SQLite/Parquet 足够；分钟级多策略再考虑 Redis 和容器。上微服务之前，先把幂等、对账、告警做好，收益远大于架构复杂度。

**Q3：盘中发现 bug 能不能改？**
不能直接改生产代码。正确流程是：kill switch 停止策略 → 撤单 → 记录现场 → 盘后修复 → 回放验证 → 发布新版本。盘中只允许切换预先定义好的开关（如停止某策略、降低仓位上限）。

**Q4：断线重连后怎么恢复订单状态？**
先调用券商的「查询当前委托」和「查询当日成交」，用 `client_order_id` 与本地订单表做全量对齐；对「本地有、柜台无」的订单标记为失败/待确认，对「柜台有、本地无」的订单补录；确认无差异后再恢复增量回报。绝不能只靠内存里的状态继续跑。

**Q5：对账到底对什么？**
四样东西：订单（数量/状态/价格）、成交（数量/均价/费用）、持仓（数量/可用/冻结）、资金（可用/冻结/总资产）。再加上费用明细和分红送转。差异要能定位到具体订单号，否则对账没有意义。

**Q6：程序化交易一定要报备吗？**
按现行监管要求，通过程序化方式交易 A 股的投资者需要经券商向交易所报告相关信息；高频交易有更严格的要求。具体口径和流程随规则更新，落地前让券商合规确认，不要凭经验判断。

## 自测

1. 为什么「回测用后复权、实盘用不复权」会导致信号错误？给出一种工程上的统一方案。
2. 画出你理解的实盘主循环，标出盘前、盘中、盘后各自必须完成的三件事。
3. `client_order_id` 如何设计才能同时满足「幂等」「可读」「不冲突」？超时重试的完整流程是什么？
4. 事中风控为什么不能和策略跑在同一个进程里？如果必须同进程，如何降低风险？
5. 某天对账发现「柜台持仓比本地多 100 股」，列出至少三种可能原因和排查顺序。
6. 设计一个两级 kill switch：策略级和账户级分别应该做什么？触发条件有哪些？

参考要点：1）复权改变历史价格，均线/收益率/阈值全部漂移；统一用同一份带复权因子的事实表，在读取层决定展示复权方式。2）盘前数据/信号/风控；盘中发单/回报/异常；盘后对账/归因/归档。3）`日期+标的+方向+序号` 哈希，加业务前缀；超时先查柜台再决定是否重发。4）策略崩溃会带走风控；独立进程/独立账户权限/券商侧预置风控兜底。5）手工交易、分红送转、成交回报丢失、昨日未对账、多账户混用；先查流水再查持仓。6）策略级停新单并撤该策略挂单；账户级撤全部、禁新单、通知人工；触发条件包括回撤、异常报单、数据断流、人工按钮。
