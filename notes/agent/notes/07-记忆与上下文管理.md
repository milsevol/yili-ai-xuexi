# 07 记忆与上下文管理

## 一句话

**上下文窗口是 Agent 最稀缺的资源**：多轮工具调用几轮就能吃掉几十万 token。记忆管理的本质是**分层**——短期记忆放对话历史（满了就截断/摘要），长期记忆放向量库（用的时候检索注入），工具结果要压缩。谁管好上下文预算，谁的 Agent 就能跑得又长又稳。

## 为什么记忆是生产分水岭

Demo 里的 Agent 只跑 3 轮，生产里的 Agent 跑 30 轮：

```
第 1 轮：system prompt (2K) + 用户问题 (0.1K)
第 5 轮：+ 4 次工具调用结果，每次平均 2K → 累计 ~10K
第 15 轮：+ 14 次工具结果 → 累计 ~30K，开始接近 32K 窗口上限
第 30 轮：直接爆窗 / 成本爆炸 / 模型被噪音淹没，忘记最初目标
```

三个连锁后果：**爆窗报错、成本失控、注意力稀释**（关键指令被海量工具输出淹没，模型「遗忘」目标）。记忆管理就是解决这三件事。

## 短期记忆：对话历史的三种截断策略

### 1. 滑动窗口（Truncation）

只保留最近 N 条消息，最老的直接丢。

```python
def truncate(messages: list, max_tokens: int) -> list:
    system = [m for m in messages if m["role"] == "system"]   # system 永保留
    rest = [m for m in messages if m["role"] != "system"]
    kept, total = [], 0
    for m in reversed(rest):                                   # 从最新往回放
        t = estimate_tokens(m)
        if total + t > max_tokens:
            break
        kept.insert(0, m)
        total += t
    return system + kept
```

- 优点：零成本、实现 10 行
- 缺点：**可能丢掉关键早期信息**（如用户开头说的硬性约束）

### 2. 摘要压缩（Summarization）

老消息交给 LLM 压缩成一段摘要，替换原文：

```python
def summarize_if_needed(messages: list, threshold: int = 8000) -> list:
    if estimate_tokens(messages) < threshold:
        return messages
    old, recent = messages[:-6], messages[-6:]      # 保留最近 3 轮完整对话
    summary = llm.chat([{
        "role": "user",
        "content": f"把以下对话历史压缩成 300 字摘要，保留关键决策、已查到的数据、用户约束：\n{format(old)}"
    }])
    return [messages[0],                              # system
            {"role": "system", "content": f"【前情摘要】{summary}"},
            *recent]
```

- 优点：信息保留好
- 缺点：多一次 LLM 调用；摘要质量依赖模型

### 3. Token 感知截断（生产推荐）

滑动窗口 + 摘要 + 保护清单的组合：

| 消息类型 | 策略 |
| --- | --- |
| System prompt | 永远保留 |
| 用户最初目标 | 永远保留（防目标漂移） |
| 最近 N 轮 | 完整保留 |
| 更早的轮次 | 摘要化 |
| 工具原始返回 | 用「提取后的关键信息」替换 |

## 长期记忆

### 向量库记忆（最常用）

把值得记住的事实存成 Embedding，用的时候按相关性检索注入：

```python
class VectorMemory:
    def __init__(self):
        self.store = []  # 生产用 Qdrant/Milvus/PGVector

    def remember(self, text: str):
        self.store.append((embed(text), text))

    def recall(self, query: str, top_k: int = 3) -> list[str]:
        q = embed(query)
        return sorted(self.store, key=lambda x: -cosine(x[0], q))[:top_k]

# 使用：每轮开始时把相关记忆注入 system
memories = memory.recall(user_question)
system += f"\n关于该用户，我记得：{memories}"
```

**存什么**：
- 用户画像（偏好、身份、历史决策）
- 跨会话的项目上下文（「这个客户上次选了方案 B」）
- 从交互中学到的事实

**不存什么**：一次性中间过程、敏感凭据、可被工具实时查到的信息（股价不用记，现查就行）。

### 知识图谱记忆

实体 + 关系的结构化记忆（如 Mem0 的图谱模式、Zep）。适合关系密集型场景：「A 是 B 的上游供应商，B 的主要客户是 C」。检索时可以沿关系多跳，比纯向量相似度更准。

### 记忆写入时机

| 时机 | 策略 |
| --- | --- |
| 实时写入 | 每轮结束提取事实入库——延迟高，少用 |
| 会话结束写入 | 总结整段会话入库——常用 |
| 显式指令 | 用户说「记住我偏好低风险」时立即写 |

## 上下文窗口预算分配

把窗口当预算来分配（以 128K 为例的生产参考）：

| 区块 | 预算占比 | 说明 |
| --- | --- | --- |
| System prompt + 工具 Schema | 5-10% | 工具别超过 20 个，Schema 本身很吃 token |
| 长期记忆注入 | 5-10% | top_k 控制在 3-5 条 |
| 对话历史（含摘要） | 30-40% | 超阈值触发压缩 |
| 工具结果 | 30-40% | **最大的消耗源**，重点压缩对象 |
| 输出预留 | 10-20% | 别让输出被截断 |

**监控指标**：每次调用记录 `prompt_tokens`，达到窗口 70% 触发压缩，90% 强制截断。

## 工具结果压缩

工具结果是上下文最大的敌人——一次网页搜索可能返回上万 token。四层防御：

### 1. 工具内部裁剪（源头治理）

```python
def search_web(query: str) -> str:
    results = raw_search(query)
    return json.dumps([
        {"title": r["title"], "snippet": r["snippet"][:200]}  # 只留标题+摘要
        for r in results[:5]                                    # 只留 top5
    ], ensure_ascii=False)
```

### 2. 大结果外部化

超长内容存文件/对象存储，上下文里只放引用：

```python
def fetch_report(url: str) -> str:
    content = download(url)                      # 可能有 100K token
    path = save_to_disk(content)
    return json.dumps({"saved_to": path, "size": len(content),
                       "preview": content[:500],
                       "hint": "用 read_file 工具按需读取片段"})
```

### 3. 回灌前提取

工具结果不直接进历史，先让一个小模型提取与当前目标相关的部分。

### 4. 历史消息降级

第 N 轮之后的旧工具结果，用一行摘要替换原文：

```python
# 第 5 轮的工具结果原文（5K token）
# 到第 15 轮时降级为：
{"role": "tool", "content": "[已压缩] 第5轮搜索：找到茅台2024营收1741亿，同比+19%"}
```

## 常见问题

**Q：摘要会不会丢关键信息导致答错？**
A：会，这是摘要的根本风险。缓解：① 摘要 prompt 里明确「保留所有数字、日期、用户约束」；② 关键事实同时写入结构化长期记忆（双保险）；③ 高风险场景保原文、只压工具结果。

**Q：长期记忆会不会把错误信息记住，越用越错？**
A：会。记忆要有**置信度和时效**：给每条记忆打来源和时间戳，召回时过滤过期/低置信条目，定期人工清理。Mem0 等框架内置了记忆的更新/冲突解决机制。

**Q：压缩和模型长窗口（1M token）矛盾吗？**
A：不矛盾。窗口大了，**成本和注意力稀释问题还在**——塞满 1M token 的调用又贵又慢，且研究表明模型对长上下文中部信息的利用率显著下降（Lost in the Middle）。窗口是天花板，不是目标。
