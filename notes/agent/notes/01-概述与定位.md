# 01 概述与定位

## 一句话

**Agent（智能体）= LLM + 规划 + 记忆 + 工具使用**，它能自主地把一个模糊目标拆成步骤、调用工具、观察结果、再决策下一步，直到任务完成。LLM 应用经历了 Prompt → RAG → Agent → 多 Agent 四次演进，Agent 是「让模型动手干活」的范式跃迁，但它有能力边界：幻觉、死循环、成本失控，工程上必须用框架和护栏兜住。

## 什么是 Agent

学术定义：能**感知环境**（Perception）、**自主决策**（Decision）、**执行动作**（Action）以达成目标的实体。放到 LLM 语境里：

```
Agent = LLM（大脑）
      + Planning（把目标拆成步骤）
      + Memory（记住做过什么、学到什么）
      + Tools（手脚：搜索、查库、调 API、执行代码）
```

与普通「调一次 LLM API」的本质区别：

| 维度 | 单次 LLM 调用 | Agent |
| --- | --- | --- |
| 交互轮数 | 1 轮（问→答） | 多轮循环（想→做→看→再想） |
| 状态 | 无状态 | 有状态（记忆、中间结果） |
| 外部世界 | 只靠训练语料 | 可调用工具获取实时信息 |
| 目标 | 回答一个问题 | 完成一个任务 |
| 错误处理 | 错就错了 | 可自我纠错、重试、换路径 |

一句话判断：**如果你的系统里 LLM 的输出会决定下一步调什么工具、并且这个循环会跑多轮，那你做的就是 Agent。**

## LLM 应用的四次演进

### 第一代：Prompt Engineering（提示词工程）

- 形态：一个 System Prompt + 用户输入 → 直接出答案
- 能力上限：模型训练数据里有什么就会什么，知识截止后的事不知道，不能联网、不能查库
- 典型问题：问「今天茅台股价多少」→ 模型只能瞎编或拒答

### 第二代：RAG（检索增强生成）

- 形态：用户问题 → 向量检索相关文档 → 拼进 Prompt → LLM 生成
- 解决了什么：知识时效性、私有知识接入、幻觉降低
- 局限：**检索是一次性的**，检索不到就答错；不能多步推理（「先查 A 公司财报，再和行业均值对比」这种链条做不了）；不能执行动作

```python
# RAG 的典型链路：固定 pipeline，LLM 只在最后出现一次
def rag(question: str) -> str:
    docs = vector_db.search(question, top_k=5)      # 一次性检索
    prompt = f"根据以下资料回答：\n{docs}\n\n问题：{question}"
    return llm.chat(prompt)                          # 一次性生成
```

### 第三代：Agent（单智能体）

- 形态：LLM 在循环里，每轮自己决定「继续想 / 调工具 / 输出最终答案」
- 解决了什么：多步推理、动态检索（查不到就换关键词再查）、执行动作（发邮件、写库、跑代码）
- 代价：延迟高（多轮串行调用）、token 成本高、可能死循环

### 第四代：Multi-Agent（多智能体）

- 形态：多个有角色分工的 Agent 协作（研究员 + 写手 + 审稿人），通过消息或共享状态通信
- 解决了什么：复杂任务分工、上下文隔离（每个 Agent 只看自己需要的上下文）、并行加速
- 代价：协调成本、状态一致性、token 成本翻倍

| 代际 | 关键词 | LLM 调用次数 | 代表技术 |
| --- | --- | --- | --- |
| Prompt | 提示词模板 | 1 | Prompt Template、Few-shot |
| RAG | 检索增强 | 1（检索是外挂） | Embedding、向量库、重排序 |
| Agent | 工具使用 + 循环 | N（动态） | ReAct、Function Calling、LangGraph |
| Multi-Agent | 分工协作 | N × M | AutoGen、CrewAI、Swarm |

**注意**：演进不是替代关系。90% 的生产系统仍是「RAG + 少量工具调用」的混合体，纯自主 Agent 只在明确需要多步决策的场景才值得引入。

## Agent 的典型应用场景

| 场景 | 为什么需要 Agent | 例子 |
| --- | --- | --- |
| 深度研究 | 需要多轮检索、交叉验证、综合 | Deep Research、投研报告生成 |
| 编程助手 | 需要读代码→改代码→跑测试→看报错→再改 | Claude Code、Cursor Agent |
| 数据分析 | 需要写 SQL→执行→看结果→修正 | ChatBI、Text2SQL Agent |
| 客服/工单 | 需要查订单→判断政策→执行退款 | 电商售后 Agent |
| 运维巡检 | 需要查监控→定位异常→执行预案 | AIOps Agent |

判断标准：**任务步骤在写代码时无法穷举、必须运行时动态决定**，才需要 Agent。步骤固定的任务用普通 pipeline 更稳更快。

## Agent 的能力边界

Agent 不是万能的，清楚边界才能不上当：

**能做好的**：
- 目标明确、工具接口清晰的多步任务（「查 A 股今天涨幅前 10 的股票并生成表格」）
- 有明确反馈信号的迭代任务（代码报错→修复→再跑）
- 基于工具的实时信息整合

**做不好的**：
- 开放式创意（「帮我写个爆款文案」——没有客观反馈，循环再多轮也不一定更好）
- 高精度计算与事实（模型会算错数、记错事实，必须靠计算器/检索工具兜底）
- 超长程任务（100+ 步的任务，错误会累积，需要人为分段）

## 风险与工程护栏

| 风险 | 表现 | 护栏 |
| --- | --- | --- |
| 死循环 | Agent 反复调同一个工具不收敛 | max_iterations 硬上限、循环检测（相同 Action 出现 3 次即终止） |
| 幻觉工具调用 | 编造不存在的工具名或参数 | 工具白名单校验、参数 JSON Schema 强校验 |
| 成本失控 | 一个任务跑了 50 轮烧掉几美元 | token 预算上限、按步骤计费告警 |
| 危险操作 | 误删数据、误发邮件 | 写操作需人工确认（Human-in-the-loop）、工具分级权限 |
| Prompt 注入 | 工具返回的网页内容里藏恶意指令 | 工具输出标记为不可信、敏感操作二次确认 |

**工程共识**：生产级 Agent 必须有「刹车」——迭代上限、预算上限、人工审批点，三者至少具备两个。

## 常见问题

**Q：Agent 和工作流（Workflow）有什么区别？**
A：工作流的步骤是**写代码时固定**的（A→B→C），Agent 的步骤是**运行时由模型动态决定**的。Anthropic 的定义很直接：Workflow 是「LLM 被编排」，Agent 是「LLM 自主指挥自己的流程」。能用 Workflow 解决就别上 Agent——更便宜、更可控。

**Q：RAG 会被 Agent 取代吗？**
A：不会。Agent 式检索（Agentic RAG）只是把「一次性检索」升级成「多轮动态检索」，向量库、Embedding 这些基础设施照旧。RAG 是 Agent 的一个工具。

**Q：小模型（7B/14B）能跑 Agent 吗？**
A：能跑但体验差。Agent 对模型的指令遵循、JSON 输出稳定性、多步推理能力要求很高，小模型容易在中途「忘记目标」或输出非法格式。生产建议起步 32B+，或用 GPT-4o/Claude 级 API。
