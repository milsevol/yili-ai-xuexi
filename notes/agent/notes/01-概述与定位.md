# 01 概述与定位

## 一句话

**Agent（智能体）= LLM + 规划 + 记忆 + 工具使用**，它能自主地把一个模糊目标拆成步骤、调用工具、观察结果、再决策下一步，直到任务完成。LLM 应用经历了 Prompt → RAG → Agent → 多 Agent 四次演进，Agent 是「让模型动手干活」的范式跃迁，但它有能力边界：幻觉、死循环、成本失控，工程上必须用框架和护栏兜住。

## 什么是 Agent

学术定义：能**感知环境**（Perception）、**自主决策**（Decision）、**执行动作**（Action）以达成目标的实体。放到 LLM 语境里：

```
Agent = LLM（大脑）
      + Planning（把目标拆成步骤）
      + Memory（记住做过什么、学到什么）
      + Tools（手脚：搜索、查库、调 API、执行代码）
```

与普通「调一次 LLM API」的本质区别：

| 维度 | 单次 LLM 调用 | Agent |
| --- | --- | --- |
| 交互轮数 | 1 轮（问→答） | 多轮循环（想→做→看→再想） |
| 状态 | 无状态 | 有状态（记忆、中间结果） |
| 外部世界 | 只靠训练语料 | 可调用工具获取实时信息 |
| 目标 | 回答一个问题 | 完成一个任务 |
| 错误处理 | 错就错了 | 可自我纠错、重试、换路径 |

一句话判断：**如果你的系统里 LLM 的输出会决定下一步调什么工具、并且这个循环会跑多轮，那你做的就是 Agent。**

## 一个生活化类比：从「顾问」到「实习生」

把 LLM 想成一个刚毕业的聪明实习生：书读得多、表达好、反应快，但**被关在一间没有窗户的房间里**，只有一张嘴，没有手、没有电脑、没有公司账号。

| Agent 部件 | 生活类比 | 在系统里对应 |
| --- | --- | --- |
| LLM | 实习生的大脑与嘴 | 推理、理解、生成 |
| Tools | 手脚、门禁卡、系统账号 | 搜索、查库、发邮件、跑代码 |
| Memory | 随身笔记本 | 对话历史、中间结果、长期偏好 |
| Planning | 工作方法 | 拆任务、列 TODO、遇阻重规划 |

按「给了实习生什么」可以分出三代产品：

```
聊天机器人：隔着玻璃问他问题           → 只能凭记忆回答
RAG：      再塞给他一摞资料             → 回答前会翻资料，但仍然只说不做
Agent：    给工位、电脑、账号、笔记本   → 告诉他目标，他自己干活并交付
```

但别忘了管理实习生的常识：**目标要清晰、权限要有边界、交付要有验收标准、过程要有日报**。对应到工程上就是任务描述、工具白名单、评估与人工审批、trace 日志。所以更准确的说法是：

> Agent 不是「更会聊天的模型」，而是「被授权干活的模型 + 一套工作系统」。

## Agent 的一天：一次竞品调研

先不谈原理，看一个真实任务长什么样。用户只说了一句：

> 调研三家国产挂耳咖啡品牌的定价，做一张对比表，并给出我们的定价建议。

一个 Agent 的实际执行轨迹（简化）：

```
[09:00] 思考  目标可拆为：找品牌 → 抓价格 → 对齐规格 → 算单价 → 汇总 → 自检
[09:01] 动作  search("国产挂耳咖啡 品牌 销量 2025")
[09:01] 观察  返回 12 条结果，锁定 A/B/C 三个品牌
[09:02] 动作  fetch_page("https://brand-a.com/products")
[09:02] 观察  拿到 5 个 SKU 的价格与克数
[09:03] 动作  fetch_page("https://brand-b.com/shop")
[09:03] 观察  页面是 JS 渲染，正文为空 → 失败
[09:04] 思考  直接抓取失败，改用搜索引擎缓存 + 电商平台页面
[09:04] 动作  search("brand-b 挂耳咖啡 价格 10g×10")
[09:05] 观察  拿到 B 品牌 3 个 SKU 价格
[09:06] 动作  get_internal_price_table()   # 内部 ERP 查我方成本价
[09:06] 观察  返回我方 4 个 SKU 成本
[09:07] 动作  calculator("89 / 10 / 10")   # 统一换算成元/克
[09:07] 观察  0.89
[09:08] 思考  C 品牌缺少规格信息，需要补一次
[09:08] 动作  fetch_page("https://brand-c.com/faq")
[09:09] 观察  确认规格为 12g×8
[09:10] 动作  write_file("report.md", 对比表 + 建议)
[09:11] 思考  自检：三家都有单价、都有规格、结论有数据支撑 → 交付
```

这次任务大约 **9 次 LLM 调用、8 次工具调用、45 秒、1.8 万 token**。注意三个细节：

1. **没有一行 if/else 是写死的**：抓 B 品牌失败后改走搜索，是模型看到 Observation 后自己换的路径。
2. **第 09:08 步会「回头」**：发现 C 品牌缺规格，主动补一次抓取，而不是硬着头皮输出。
3. **每一步都留下痕迹**：动作、参数、结果都能落盘，出问题可复盘（详见第 09 章可观测性）。

这就是 Agent 与流水线的分水岭：**流水线只能走你预先想到的路，Agent 能在运行时找路——代价是它也可能走错路。**

## 什么时候该用 Agent

Agent 更贵、更慢、更不可控，所以第一原则是：**能用 Workflow 就别用 Agent，能用一次 RAG 就别上循环。**

```
任务来了
│
├─ Q1 步骤在写代码时能穷举吗？
│    ├─ 能 ─────────────→ Workflow / Pipeline（别上 Agent）
│    └─ 不能 ↓
├─ Q2 需要访问外部系统、实时数据或执行动作吗？
│    ├─ 不需要 ─────────→ 单次 LLM 或 RAG 就够了
│    └─ 需要 ↓
├─ Q3 失败代价可控吗（可回滚 / 有人复核）？
│    ├─ 不可控 ─────────→ Workflow + 人工确认点，或先做 Copilot
│    └─ 可控 ↓
└─ Q4 有客观反馈信号、可评估吗？
     ├─ 没有 ────────────→ 先做 Copilot（人机协作），别全自动
     └─ 有 ──────────────→ Agent + 迭代上限 + 预算 + trace
```

展开成判断表：

| 判断项 | 倾向 Workflow | 倾向 Agent |
| --- | --- | --- |
| 步骤是否固定 | 固定、可枚举、可画成流程图 | 运行时才知道下一步 |
| 是否需要外部动作 | 无动作，或只有一次固定调用 | 多工具、多轮、路径依赖结果 |
| 失败代价 | 高（资金、生产变更、对外发送） | 中低，可回滚、可重跑 |
| 能否人工兜底 | 可插入审批节点 | 可人工接管，或失败可丢弃 |
| 反馈信号 | 无客观对错 | 有明确成功判据（测试通过、数据对齐） |

三种常见落地形态，按自主性从低到高：

| 形态 | 谁决定流程 | 适用 |
| --- | --- | --- |
| Prompt / RAG | 代码固定 | 问答、知识库客服 |
| Workflow（可含 LLM 节点） | 代码固定，LLM 只做节点内决策 | 审核流、报表生成、内容加工 |
| Agent | LLM 动态决定下一步 | 深度研究、排障、多步操作 |

生产里最常见的是**混合体**：外层用 Workflow 保证确定性，把「需要探索」的那一个节点做成 Agent。例如报销系统：提交、校验、审批是固定流程，只有「发票与行程对不上时怎么查」交给 Agent。

## LLM 应用的四次演进

### 第一代：Prompt Engineering（提示词工程）

- 形态：一个 System Prompt + 用户输入 → 直接出答案
- 能力上限：模型训练数据里有什么就会什么，知识截止后的事不知道，不能联网、不能查库
- 典型问题：问「今天茅台股价多少」→ 模型只能瞎编或拒答

### 第二代：RAG（检索增强生成）

- 形态：用户问题 → 向量检索相关文档 → 拼进 Prompt → LLM 生成
- 解决了什么：知识时效性、私有知识接入、幻觉降低
- 局限：**检索是一次性的**，检索不到就答错；不能多步推理（「先查 A 公司财报，再和行业均值对比」这种链条做不了）；不能执行动作

```python
import os
from openai import OpenAI

client = OpenAI(
    api_key=os.getenv("DEEPSEEK_API_KEY"),
    base_url="https://api.deepseek.com",
)

# RAG 的典型链路：固定 pipeline，LLM 只在最后出现一次
# 伪代码：假定 vector_db 是已封装的向量库客户端
def rag(question: str) -> str:
    docs = vector_db.search(question, top_k=5)      # 一次性检索
    context = "\n\n".join(d.page_content for d in docs)
    resp = client.chat.completions.create(
        model="deepseek-chat",
        messages=[
            {"role": "system", "content": "只根据给定资料回答，资料没有就说不知道。"},
            {"role": "user", "content": f"资料：\n{context}\n\n问题：{question}"},
        ],
        temperature=0,
    )
    return resp.choices[0].message.content
```

### 第三代：Agent（单智能体）

- 形态：LLM 在循环里，每轮自己决定「继续想 / 调工具 / 输出最终答案」
- 解决了什么：多步推理、动态检索（查不到就换关键词再查）、执行动作（发邮件、写库、跑代码）
- 代价：延迟高（多轮串行调用）、token 成本高、可能死循环

### 第四代：Multi-Agent（多智能体）

- 形态：多个有角色分工的 Agent 协作（研究员 + 写手 + 审稿人），通过消息或共享状态通信
- 解决了什么：复杂任务分工、上下文隔离（每个 Agent 只看自己需要的上下文）、并行加速
- 代价：协调成本、状态一致性、token 成本翻倍

| 代际 | 关键词 | LLM 调用次数 | 代表技术 |
| --- | --- | --- | --- |
| Prompt | 提示词模板 | 1 | Prompt Template、Few-shot |
| RAG | 检索增强 | 1（检索是外挂） | Embedding、向量库、重排序 |
| Agent | 工具使用 + 循环 | N（动态） | ReAct、Function Calling、LangGraph |
| Multi-Agent | 分工协作 | N × M | AutoGen、CrewAI、Swarm |

**注意**：演进不是替代关系。90% 的生产系统仍是「RAG + 少量工具调用」的混合体，纯自主 Agent 只在明确需要多步决策的场景才值得引入。

## Agent 的典型应用场景

| 场景 | 为什么需要 Agent | 例子 |
| --- | --- | --- |
| 深度研究 | 需要多轮检索、交叉验证、综合 | Deep Research、投研报告生成 |
| 编程助手 | 需要读代码→改代码→跑测试→看报错→再改 | Claude Code、Cursor Agent |
| 数据分析 | 需要写 SQL→执行→看结果→修正 | ChatBI、Text2SQL Agent |
| 客服/工单 | 需要查订单→判断政策→执行退款 | 电商售后 Agent |
| 运维巡检 | 需要查监控→定位异常→执行预案 | AIOps Agent |

判断标准：**任务步骤在写代码时无法穷举、必须运行时动态决定**，才需要 Agent。步骤固定的任务用普通 pipeline 更稳更快。

## Agent 的能力边界

Agent 不是万能的，清楚边界才能不上当：

**能做好的**：
- 目标明确、工具接口清晰的多步任务（「查 A 股今天涨幅前 10 的股票并生成表格」）
- 有明确反馈信号的迭代任务（代码报错→修复→再跑）
- 基于工具的实时信息整合

**做不好的**：
- 开放式创意（「帮我写个爆款文案」——没有客观反馈，循环再多轮也不一定更好）
- 高精度计算与事实（模型会算错数、记错事实，必须靠计算器/检索工具兜底）
- 超长程任务（100+ 步的任务，错误会累积，需要人为分段）

## 常见误解

| 误解 | 实际情况 |
| --- | --- |
| Agent = 更长的 Prompt | Prompt 再长也不能联网、不能执行动作。Agent 的核心是「循环 + 工具 + 状态」，不是字数。 |
| Agent = 工作流 | 工作流步骤写死，Agent 运行时决策。二者常组合：外层 Workflow，内层 Agent。 |
| 一定要多 Agent | 单 Agent + 多工具通常更简单、更稳。多 Agent 是分工与上下文隔离的手段，不是目标（详见第 08 章）。 |
| 自主 = 不用管 | 自主性越高越需要护栏：迭代上限、预算、审批、trace，一个都不能少（详见第 09 章）。 |
| Agent 会取代 RAG | RAG 只是 Agent 可调用的一个检索工具；Agentic RAG 是把一次性检索升级成多轮检索（详见第 05 章）。 |
| 工具越多越强 | 工具过多会让模型选错。10 个以内、描述清晰、职责互斥，比堆 50 个工具更有效（详见第 05 章）。 |
| 上了 Agent 效果一定更好 | 没有评估就是玄学。先用固定测试集比「Workflow 基线 vs Agent」，再决定是否上线（详见第 09 章）。 |

## 风险与工程护栏

| 风险 | 表现 | 护栏 |
| --- | --- | --- |
| 死循环 | Agent 反复调同一个工具不收敛 | max_iterations 硬上限、循环检测（相同 Action 出现 3 次即终止） |
| 幻觉工具调用 | 编造不存在的工具名或参数 | 工具白名单校验、参数 JSON Schema 强校验 |
| 成本失控 | 一个任务跑了 50 轮烧掉几美元 | token 预算上限、按步骤计费告警 |
| 危险操作 | 误删数据、误发邮件 | 写操作需人工确认（Human-in-the-loop）、工具分级权限 |
| Prompt 注入 | 工具返回的网页内容里藏恶意指令 | 工具输出标记为不可信、敏感操作二次确认 |

**工程共识**：生产级 Agent 必须有「刹车」——迭代上限、预算上限、人工审批点，三者至少具备两个。

## 常见问题

**Q：Agent 和工作流（Workflow）有什么区别？**
A：工作流的步骤是**写代码时固定**的（A→B→C），Agent 的步骤是**运行时由模型动态决定**的。Anthropic 的定义很直接：Workflow 是「LLM 被编排」，Agent 是「LLM 自主指挥自己的流程」。能用 Workflow 解决就别上 Agent——更便宜、更可控。

**Q：RAG 会被 Agent 取代吗？**
A：不会。Agent 式检索（Agentic RAG）只是把「一次性检索」升级成「多轮动态检索」，向量库、Embedding 这些基础设施照旧。RAG 是 Agent 的一个工具。

**Q：小模型（7B/14B）能跑 Agent 吗？**
A：能跑但体验差。Agent 对模型的指令遵循、JSON 输出稳定性、多步推理能力要求很高，小模型容易在中途「忘记目标」或输出非法格式。生产建议起步 32B+，或用 GPT-4o/Claude 级 API。

**Q：Agent 的「自主」到底自主在哪？**
A：自主在「下一步做什么」由模型判断，而不是完全无人监管。工具白名单、预算上限、审批节点都是人划定的边界。自主 ≠ 放飞，边界外的动作一律拒绝。

**Q：一个 Agent 任务大概花多少钱？**
A：取决于轮数与上下文长度。以 DeepSeek 级价格，5 轮以内的简单任务通常几分钱到几毛钱；30+ 轮的研究型任务可能到几元。重点是设「单任务轮数上限 + token 预算 + 告警」，而不是事后看账单。
