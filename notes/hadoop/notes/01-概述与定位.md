# 01 概述与定位

## 一句话

**Apache Hadoop**：用一堆普通服务器，把「海量数据可靠地存下来」「把计算分散到数据所在的机器上并行跑」「把整个集群的 CPU/内存统一调度」这三件事做成一套开源软件，核心是 **HDFS + YARN + MapReduce** 三件套。

## 它解决什么问题

2000 年代中期，Google 面对的是「单机存不下、买高端存储太贵、机器又总会坏」。GFS（2003）和 MapReduce（2004）两篇论文给出的答案是：**用大量廉价机器 + 软件容错**。Hadoop 是这套答案的开源实现。

| 现实问题 | 传统思路 | Hadoop 的思路 |
| --- | --- | --- |
| 数据到 TB/PB，单机磁盘不够 | 买更大更强的存储阵列，纵向扩容 | 普通 x86 服务器加本地盘，横向加机器 |
| 机器一定会坏 | 靠硬件冗余（RAID、双机） | 把故障当常态：副本、校验和、重试、自动重建 |
| 数据搬来搬去太慢 | 把数据拉到计算程序所在机器 | 把计算任务调度到数据所在机器（移动计算） |
| 每套业务独占一批机器 | 烟囱式建设，利用率低 | YARN 池化资源，多队列多租户共享 |
| 单机算不动 | 多线程/多进程，受单机上限约束 | 一个作业切成很多 task，几千台机器并行 |

## 三件套的职责

| 组件 | 一句话职责 | 核心实体 | 明确不做什么 |
| --- | --- | --- | --- |
| **HDFS** | 分布式文件系统：文件切块、多副本、跨机存放 | NameNode、DataNode、Block | 不做计算；不支持任意位置改写，只支持追加 |
| **YARN** | 集群资源管理器：把 CPU/内存切成 Container 分配 | ResourceManager、NodeManager、ApplicationMaster | 不碰数据；不关心业务逻辑 |
| **MapReduce** | 分布式批处理编程模型 + 运行时 | Mapper、Reducer、Job | 不做存储；不擅长迭代、交互式、实时 |

三者关系：**HDFS 提供数据，YARN 提供资源，MapReduce 是跑在 YARN 上的一种计算框架**。Spark、Flink、Tez 也跑在 YARN 上，读的同样是 HDFS。

YARN 的几个默认值最好记住：`yarn.nodemanager.resource.memory-mb` = 8192（MB）、`yarn.nodemanager.resource.cpu-vcores` = 8；单个 Container 默认最大 8192MB、最小 1024MB；调度器默认 **CapacityScheduler**。伪分布式和测试集群里「资源申请不到」「作业一直 pending」，经常就是这几个默认值太小。

## 1.x 与 2.x/3.x：一次架构大手术

```
Hadoop 1.x
  Client → JobTracker（调度 + 监控 + 资源管理，单点）
              ├─ TaskTracker(节点1) [map slot | reduce slot]
              ├─ TaskTracker(节点2) [map slot | reduce slot]
              └─ ...
  问题：JobTracker 单点瓶颈（约数千节点量级）、slot 固定划分导致利用率低、只能跑 MapReduce
```

```
Hadoop 2.x / 3.x（YARN）
  Client → ResourceManager（只负责资源）
              ├─ NodeManager(节点1) → Container(AM) / Container(task)
              ├─ NodeManager(节点2) → Container(task)
              └─ ...
  每个作业自带一个 ApplicationMaster：申请资源、调度 task、汇报进度
```

| 维度 | 1.x | 2.x / 3.x |
| --- | --- | --- |
| 资源管理 | JobTracker 兼任 | 独立 YARN（RM + NM） |
| 计算框架 | 只能 MapReduce | MR / Spark / Flink / Tez 都能跑 |
| 单点瓶颈 | JobTracker 是单点 | RM 可做 HA（ZK + 状态存储） |
| 资源粒度 | 固定 map/reduce slot | 按内存/CPU 的 Container |
| 集群规模 | 数千节点 | 上万节点（受限于调度与运维） |

3.x 相对 2.x 的主要变化：**纠删码、多个 Standby NameNode、Router-Based Federation、默认端口调整、Java 11 支持、YARN Timeline Service v2**。本系列以 3.3/3.4 为准：这两个版本支持 JDK 8/11。3.5.0 已于 2026 年 4 月发布，但**服务端要求 Java 17**，存量企业仍以 3.3/3.4 为主。

## 发展简史

- **2002** Doug Cutting 和 Mike Cafarella 做 Nutch（爬虫 + 搜索引擎），遇到「海量网页怎么存怎么算」。
- **2003/2004** Google 发表 GFS 和 MapReduce 论文，Nutch 按论文实现了自己的版本。
- **2006** Hadoop 从 Nutch 独立，成为 Apache Lucene 的子项目；名字来自 Doug 儿子玩具大象。
- **2008** 成为 Apache 顶级项目；同年有团队用约 900 台机器跑出 TB 级排序纪录。
- **2011** Hadoop 1.0 发布（HDFS + MapReduce）。
- **2013** Hadoop 2.x 成熟，**YARN 成为通用资源管理器**，Spark 开始借 YARN 起飞。
- **2017/2018** Hadoop 3.0 发布：纠删码、多 NameNode、Router。
- **2023** 3.3.6；**2024** 3.4.0；之后 3.4.x 持续出小版本修复。

## 与 Spark、Flink 的关系

最常见的误解是「Hadoop = MapReduce」。准确的关系是：

| 角色 | 产品 |
| --- | --- |
| 存储底座 | HDFS、Ozone、对象存储（S3/OSS） |
| 资源底座 | YARN（也可是 K8s / Standalone） |
| 计算引擎 | MapReduce（老）、Spark（批/SQL/ML）、Flink（流）、Tez（DAG）、Hive（SQL 翻译） |

- **Spark on YARN**：Spark 负责算，YARN 负责分资源，HDFS 负责存。三者是协作，不是替代。
- **Flink on YARN / K8s**：同理，Flink 是流引擎，Hadoop 提供存与资源。
- **Hive on MapReduce / Tez**：Hive 只是把 SQL 翻译成作业，底层引擎可换。
- 所以「上 Spark 就不用 Hadoop」只在「你已经有对象存储 + K8s」时成立。

## 生态组件

| 组件 | 定位 | 和 Hadoop 的关系 |
| --- | --- | --- |
| **Hive** | SQL 数仓，把 SQL 翻译成 MR/Tez/Spark 作业 | 元数据在 MySQL 等，数据在 HDFS |
| **HBase** | 分布式 KV 数据库，支持随机读写 | 数据存 HDFS，强依赖 ZooKeeper，不走 YARN |
| **ZooKeeper** | 分布式协调（选主、锁、配置） | HDFS HA、HBase、Kafka 都用它 |
| **Tez** | DAG 执行引擎，Hive 常用 | 跑在 YARN 上 |
| **Sqoop** | 关系库 ↔ HDFS 批量导入导出 | 已进 Apache Attic（退休），新项目多用 DataX/Flink CDC |
| **DataX** | 阿里开源的离线数据同步 | 常替代 Sqoop |
| **Flume** | 日志采集到 HDFS/HBase/Kafka | 采集层，逐行/批量 |
| **Kafka** | 分布式消息队列 | 不是 Hadoop 组件，但常作为实时链路入口 |
| **Oozie / DolphinScheduler** | 工作流调度 | Oozie 老旧，DolphinScheduler 更常用 |
| **Ozone** | Hadoop 的对象存储（桶/键） | 3.x 之后的新存储选项，缓解小文件压力 |

## 今天还要不要学 Hadoop

**要学，如果**：

- 你在维护**存量集群**：HDFS 上的历史数据、Hive 数仓、HBase 业务库不会一夜迁走。
- 你要做**冷数据低成本存储**：HDFS + 纠删码在自建机房里仍然便宜。
- 你用 **HBase / Hive / YARN 多租户**：这些组件的调优和排障绕不开 HDFS/YARN。
- 你要理解 Spark/Flink 的**数据本地性、shuffle、资源模型**：根都在 Hadoop。

**可以少花精力，如果**：

- 纯云上新项目：对象存储 + Spark/Flink on K8s，HDFS 只是历史包袱。
- 只写 SQL：Hive/Spark SQL 的语法与优化器比 HDFS 内部更重要。

## Hadoop 不是什么

1. **不是数据库**：没有事务、没有二级索引、不支持按行随机更新；点查请用 HBase/OLAP 引擎。
2. **不是实时引擎**：MapReduce 是批处理，延迟分钟级起；实时请用 Flink。
3. **不是单一产品**：它是一组项目（Common/HDFS/YARN/MR）+ 生态，不是装一个服务就完事。
4. **不等于 MapReduce**：MapReduce 只是它自带的一个计算框架。
5. **不是「数据湖」本身**：数据湖还需要表格式（Iceberg/Hudi/Delta）和元数据治理。

## 动手体验：伪分布式最小闭环

前置：Linux/macOS、**JDK 8 或 11**（3.3/3.4 都支持，更高版本要看生态组件）、免密 `ssh localhost`、下载 Hadoop 二进制包并配好 `JAVA_HOME`。

```bash
# 1) 四个配置文件（$HADOOP_HOME/etc/hadoop/）
# core-site.xml   : fs.defaultFS = hdfs://localhost:9000
# hdfs-site.xml   : dfs.replication = 1
# mapred-site.xml : mapreduce.framework.name = yarn
# yarn-site.xml   : yarn.nodemanager.aux-services = mapreduce_shuffle

# 2) 格式化：一台机器只做一次！重复格式化会生成新 clusterID，DataNode 会起不来
hdfs namenode -format

# 3) 启动并确认进程
start-dfs.sh && start-yarn.sh
jps    # 期望看到 NameNode、DataNode、SecondaryNameNode、ResourceManager、NodeManager

# 4) 最小 HDFS 操作
hdfs dfs -mkdir -p /tmp/demo
printf 'hello hadoop\n' > /tmp/hello.txt
hdfs dfs -put /tmp/hello.txt /tmp/demo/
hdfs dfs -cat /tmp/demo/hello.txt
hdfs dfs -ls /tmp/demo
hdfs dfsadmin -report | head -20
```

验证入口：NameNode UI `http://localhost:9870`，YARN UI `http://localhost:8088`。
