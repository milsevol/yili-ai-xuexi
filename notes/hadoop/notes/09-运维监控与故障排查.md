# 09 运维监控与故障排查

## 一句话

**Hadoop 运维的核心是「元数据、磁盘、网络、资源队列」四件事**——90% 的线上故障，都能从这四类信号里找到影子。

## 监控体系

| 层次 | 工具 | 作用 | 现状 |
| --- | --- | --- | --- |
| JVM 层 | JMX（jmx_exporter / jconsole） | 堆、GC、线程、连接数 | 自建主流 |
| 组件层 | Hadoop metrics2 | 组件内置指标框架，可输出到文件/Graphite | 需要配 sink |
| 指标存储 | Prometheus + Grafana | 采集、告警、看板 | 自建最主流 |
| 平台层 | Cloudera Manager | 部署 + 监控 + 告警一体化 | CDP 商业版 |
| 平台层 | Ambari | HDP 时代的管理平台 | 随 HDP 停更，基本退役 |
| 主机层 | Zabbix / Node Exporter | CPU、内存、磁盘、网络 | 与大数据监控互补 |
| 历史方案 | Ganglia | 集群趋势图 | 已基本被替代 |

Hadoop 各组件的 JMX 要显式开，例如 NameNode 的 `HADOOP_NAMENODE_OPTS` 里加：

```bash
-Dcom.sun.management.jmxremote
-Dcom.sun.management.jmxremote.port=8004
-Dcom.sun.management.jmxremote.authenticate=false
-Dcom.sun.management.jmxremote.ssl=false
```

metrics2 的常见做法是配 sink：

```xml
<property>
  <name>hadoop.metrics2.sink</name>
  <value>org.apache.hadoop.metrics2.sink.GraphiteSink</value>
</property>
```

Prometheus 生态里更多用社区的 JMX exporter 或 metrics2 sink，官方只内置 FileSink/GraphiteSink 一类。

## 关键指标

| 组件 | 指标 | 看什么 |
| --- | --- | --- |
| **NameNode** | `HeapUsed` / `HeapMax`、GC 时间、`NumObjects`、`NumBlocks` | 堆是否逼近上限，对象数增长是否异常 |
| NameNode | `RpcQueueTimeAvgTime`、`NumOpenConnections`、`CallQueueLength` | 请求排队，通常是 GC 或元数据操作卡住 |
| NameNode | `SafeMode`、`MissingBlocks`、`CorruptBlocks` | 安全模式、丢块、坏块 |
| **DataNode** | `Capacity` / `Remaining`、`VolumeFailures`、`DataNodeVolumeFailures` | 磁盘水位、坏盘 |
| DataNode | `BlockReportAvgTime`、`xceiverCount`、`BlocksRead/Write` | 块汇报慢、读写线程打满 |
| **HDFS** | `UnderReplicatedBlocks`、`PendingDeletionBlocks`、`MissingBlocks` | 副本不足、删除积压、丢块 |
| **ResourceManager** | 队列 `used` / `available`、`AppsRunning` / `AppsPending`、`AM failures` | 队列是否打满、作业是否排队 |
| **NodeManager** | 运行容器数、`ContainerLaunchDuration`、磁盘健康 | 容器起不来、节点异常 |
| JVM | Full GC 次数与耗时、老年代使用率 | 停顿是否影响心跳/超时 |
| 系统 | load、`iostat %util`、网络丢包、swap 使用 | 慢盘、网络瓶颈、内存换页 |

经验阈值：磁盘使用率 **> 85%** 开始告警；Full GC 单次 **> 5 秒** 视为异常；DN 心跳延迟超过 30 秒要查网络；NN RPC 队列持续 > 0 说明处理不过来。

## 巡检清单

| 周期 | 检查项 |
| --- | --- |
| **每日** | 告警汇总；NN 是否安全模式；Missing/Corrupt Blocks；DN 掉线与容量；队列积压与失败作业；磁盘 > 85%；AM 失败率；JN/ZK 是否正常 |
| **每周** | 慢盘（`%util` 持续 > 90）；小文件增长；副本不足趋势；NN/DN GC 趋势；日志聚合是否正常；作业平均耗时变化 |
| **每月** | 容量增长与预测；NN 堆增长；跑一次 balancer；快照/元数据备份验证；keytab 与证书有效期；CVE 与版本评估；扩容/退役计划 |

巡检不要只看 UI，至少跑一遍命令：

```bash
hdfs dfsadmin -report
hdfs fsck / -files -blocks | tail -n 20
yarn node -list
yarn application -list -appStates RUNNING,FAILED
hdfs dfsadmin -safemode get
```

## 排查方法论

**先时间线，再日志，最后指标**，顺序不要反：

1. **时间线**：客户端几点提交 → RM 几点收到 → AM 几点启动 → 容器几点分配 → 任务几点失败。`yarn applicationattempts` 能看到每个 attempt 的起止时间和诊断信息。
2. **日志定位**：按「客户端 → RM → AM → NM → container → DN」逐层看，哪一层第一次出现 ERROR，问题就在那一层或它的下游。
3. **指标佐证**：日志说 OOM，就去 Grafana 看堆曲线；日志说超时，就看网络和 `%util`。
4. **复现与验证**：用小数据集复现，改一个变量验证假设，把结论写进故障库。

| 日志位置 | 内容 |
| --- | --- |
| `$HADOOP_LOG_DIR/hadoop-hdfs-namenode-*.log` | NN 启动、块操作、安全模式 |
| `.../hadoop-hdfs-datanode-*.log` | 磁盘、块读写、pipeline、坏盘 |
| `.../hadoop-yarn-resourcemanager-*.log` | 应用提交、容器分配、NM 失联 |
| `.../hadoop-yarn-nodemanager-*.log` | 容器启动、本地化失败、健康检查 |
| `log-dirs/userlogs/<appid>/<containerid>/` | AM 与 task 的 `syslog`、`stderr`、`stdout` |
| `yarn logs -applicationId <id>` | 聚合后的全量容器日志 |

## 典型故障案例

| 症状 | 可能原因 | 处理 |
| --- | --- | --- |
| NN 启动后一直安全模式 | DN 没起来、块汇报未完成、副本率低于阈值（`dfs.namenode.safemode.threshold-pct=0.9999`） | 先查 DN 与网络，等块汇报；确认数据安全后再 `hdfs dfsadmin -safemode leave` |
| NN 频繁 Full GC / OOM | 小文件过多、块数暴涨、堆太小 | 调大 NN 堆，合并小文件，必要时上 HDFS 联邦 |
| DN 磁盘写满 | 数据增长、回收站、副本堆积、日志占盘 | 设 `dfs.datanode.du.reserved`，清理，扩容，检查 `fs.trash.interval` |
| DN 卷变只读 / VolumeFailures | 坏盘、文件系统错误、挂载掉线 | 换盘、`dmesg` 查 IO 错误、重启 DN 让其重新识别卷 |
| 块损坏 CorruptBlocks | 磁盘静默损坏、内存错误、写入中断 | `hdfs fsck /path -blocks` 定位，`-delete` 删损坏文件，从上游重造 |
| DN 掉线 | 心跳超时、网络、进程被杀、机器宕机 | `hdfs dfsadmin -report`、`yarn node -list`，恢复后等块汇报 |
| 写 pipeline 超时 | 慢盘、网络抖动、DN 负载高 | DN 日志看 `Slow WritePipeline`，`iostat` 找慢盘，调整 `dfs.client-write-packet-size` |
| `LeaseExpiredException` | 客户端写完没 close 就退出 | 等租约恢复；`hdfs debug recoverLease -path /path/file` 手动恢复 |
| YARN 队列卡住 | 队列满、AM 百分比到顶、user limit、调度器异常 | `yarn queue -status root.prod`，看 RM 日志，必要时 kill 应用释放 |
| 容器超内存被杀 | `beyond physical memory limits`、exit 137 | 调容器内存、修代码泄漏，别直接关 pmem-check |
| Shuffle fetch 失败 | `Too many fetch failures`，网络/NM 磁盘/map 输出丢失 | 看 reduce 日志与 NM 磁盘，调 `mapreduce.reduce.shuffle.retry-delay` |
| hostname / DNS 不一致 | DN 用 IP 注册、客户端解析不到 | 统一 DNS，必要时 `dfs.datanode.use.datanode.hostname=true` |
| 时钟漂移 | Kerberos 认证失败、日志时间错乱 | chrony 同步，检查虚拟化时钟 |
| Kerberos 认证失败 | keytab 权限、principal 不匹配、票据过期 | `klist`、`kinit -kt` 复测，检查 KDC 时间 |
| 小文件过多 | NN 内存高、任务数爆炸 | HAR / 合并 / 改 ORC/Parquet / 对象存储 |

## 容量规划、扩容与退役

**容量公式**：

```
可用容量 = 裸容量 × (1 / 副本因子) × 安全水位（建议 75%–80%）
例：10 台 × 12 盘 × 4TB = 480TB 裸容量
    → 3 副本 = 160TB
    → 80% 水位 = 128TB 可用
```

- **扩容**：新机器装好 → 加入 workers 列表 → 启动 DN/NM → 确认 `dfsadmin -report` → 跑 balancer。
- **退役**：把节点写入 `dfs.hosts.exclude` → `hdfs dfsadmin -refreshNodes` → 等 Decommissioning 完成；YARN 侧配 `yarn.resourcemanager.nodes.exclude-path` 后 `yarn rmadmin -refreshNodes`。
- **Balancer**：

```bash
hdfs balancer -threshold 10
hdfs balancer -threshold 10 -Ddfs.datanode.balance.bandwidthPerSec=20971520
```

`-threshold` 是「节点使用率与集群平均值的偏差百分比」，默认 10。balancer 会占网络和磁盘，避开业务高峰；它只搬块，不会改变目录结构。

- **副本因子**：`hdfs dfs -setrep -w 3 /path`；冷数据可降到 2，但先确认容量与容灾要求；大规模冷数据更推荐 **纠删码（EC）**，例如 RS-6-3 的存储开销约 1.5 倍，远低于三副本的 3 倍，代价是读取和修复更耗 CPU。
- **配额**：`hdfs dfsadmin -setSpaceQuota 10t /path`、`hdfs dfsadmin -setQuota 100000 /path`（限制文件/目录数，防小文件）。

## 备份与恢复

| 对象 | 做法 |
| --- | --- |
| NN 元数据 | `dfs.namenode.name.dir` 配置多个目录（不同盘），`fsimage` + `edits` 定期备份 |
| 元数据快照 | `hdfs dfsadmin -fetchImage /backup/nn` 拉最新 fsimage 到异地 |
| EditLog | HA 下由 JournalNode 保存；非 HA 由 SecondaryNameNode/CheckpointNode 合并 |
| 可读性验证 | `hdfs oiv -i fsimage_xxx -o /tmp/fs.xml -p XML`，定期验证备份能解析 |
| 目录快照 | `hdfs dfsadmin -allowSnapshot /data` + `hdfs dfs -createSnapshot /data snap1`，误删可恢复 |
| 回收站 | `fs.trash.interval=1440`（分钟），`fs.trash.checkpoint.interval` 配合，默认 0 表示关闭 |
| 异地容灾 | `hadoop distcp -update -delete hdfs://src hdfs://dst` 或同步到对象存储 |

快照是**写时复制**，不复制数据，创建很快；但它不是备份，NN 元数据丢了快照也没了，异地备份仍要做。

## 升级与回滚

1. 读 release notes，确认兼容性（Hadoop 2 → 3 不兼容项很多）。
2. 备份 NN 元数据、配置文件、关键作业。
3. **先升 Standby NN**：停 standby → 换二进制 → 启动 → 等它追上 edits → 手动 failover → 再升原 active。
4. 滚动升级 DataNode、JournalNode；每个节点升级后确认注册正常再动下一个。
5. YARN/MR 的 RM、NM、HistoryServer 通常需要重启，会中断运行中应用，安排在窗口期。
6. HDFS 支持 `hdfs dfsadmin -rollingUpgrade prepare/query/finalize`，可在限定版本内回滚；**跨大版本不要指望降级**。
7. 升级后验证：`fsck`、读写测试、作业回归、监控指标正常。

## 安全与审计

- **认证**：Kerberos，服务用 keytab，用户用 `kinit` 或 delegation token。
- **授权**：HDFS ACL（`dfs.namenode.acls.enabled=true`）、YARN 队列 ACL（`yarn.scheduler.capacity.root.<queue>.acl_submit_applications`）、Hive 库表权限。
- **集中策略**：Ranger 插件覆盖 HDFS/Hive/HBase/YARN，支持列脱敏、行过滤、审计。
- **审计日志**：HDFS 的 `hdfs-audit.log` 记录谁在什么时候访问了哪个路径；Ranger 有自己的审计库。
- **加密**：传输层 `dfs.http.policy=HTTPS_ONLY`，静态加密用 HDFS Transparent Encryption + KMS。
- 原则：**不要用 hdfs 超级用户跑业务**，每个服务独立 principal 和 keytab，权限最小化。
