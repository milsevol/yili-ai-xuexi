# 03 技术架构与核心链路

## 一句话

**平台的技术架构要保证三件事：Agent 运行时可控（不跑飞）、工具调用可管（不越权）、整条链路可观测（可复盘）。** 三者缺一，平台就退化成"给每个部门发了一个 API Key"。

## 总体架构

```
 浏览器 / 企微 / OpenAPI
          │
          ▼
 ┌──────────────────────────────────────────────┐
 │ API 层（FastAPI）                             │
 │ 认证 · 租户上下文 · RBAC · 限流 · 幂等         │
 └───────┬──────────────┬───────────────┬────────┘
         │              │               │
         ▼              ▼               ▼
   Agent 服务      MCP 网关         管理服务
   （运行时）      （工具出口）      （租户/审批/审计）
         │              │               │
         ├──────► 模型网关 ──► 大模型供应商
         │              │
         │              ├── 行情 MCP（http）
         │              ├── 研报 MCP（sse）
         │              ├── 财报 MCP（http）
         │              └── 计算器（stdio 沙箱）
         │
         ▼
  PostgreSQL（元数据/运行记录/审计）
  Redis（会话/缓存/限流） · 对象存储（长结果）
  向量库（租户 namespace） · 消息队列（长任务）
  OTel：trace / metrics / logs
```

分层职责：

| 层 | 负责 | 不负责 |
| --- | --- | --- |
| API 层 | 身份、租户、限流、参数校验 | 业务编排 |
| Agent 服务 | 规划、工具循环、上下文预算、结果组装 | 工具实现、数据权限 |
| MCP 网关 | 工具发现、鉴权、schema 校验、超时熔断、审计 | 业务逻辑 |
| 模型网关 | 路由、配额、计费、降级、内容安全 | 会话状态 |
| 管理服务 | 租户、Agent/MCP 生命周期、审批 | 运行时执行 |

## 技术选型

| 组件 | 选择 | 理由 | 备选 |
| --- | --- | --- | --- |
| Web 框架 | FastAPI | 异步、Pydantic 校验、OpenAPI 自动生成 | Django + DRF（重） |
| 数据库 | PostgreSQL | JSONB、行级安全、事务 | MySQL（无 RLS） |
| 缓存 | Redis | 会话、限流、分布式锁 | — |
| 向量库 | pgvector 起步，Milvus 扩展 | 少一个组件；规模上来再拆 | Milvus / Qdrant |
| 消息队列 | Kafka / RabbitMQ | 长任务、索引、事件 | Redis Stream（轻量） |
| 前端 | Vue 3 + Vite | 团队熟悉，组件生态好 | React |
| 可观测 | OpenTelemetry + Prometheus + Loki | 标准协议，供应商无关 | 商业 APM |

## 同步调用链路

```
用户提问
  → API 层：认证、租户注入、限流
  → 加载 Agent 配置（已上线版本）
  → 运行时：规划工具
  → 逐工具：权限校验 → MCP 网关 → 参数校验 → 调用 → 结果压缩
  → 组装答案（结论 / 事实 / 引用）
  → 落库 runs + audit
  → 返回（或 SSE 流式返回）
```

每一步都要能回答：耗时多少、失败在哪、谁调用的、用了哪个版本、花了多少 token。

## Agent 运行时

### 循环骨架

```python
@dataclass
class RunContext:
    tenant_id: str
    user: User
    agent: Agent
    budget_tokens: int = 12_000
    max_steps: int = 6
    deadline_ms: int = 20_000

async def run(ctx: RunContext, question: str) -> RunResult:
    steps, used = [], 0
    plan = await planner(question, ctx.agent.tools)      # 1. 规划
    for tool in plan[: ctx.max_steps]:
        if time_left(ctx) <= 0:
            return degraded(steps, "超时，返回已完成部分")
        if not allowed(ctx.user, scope_of(tool)):        # 2. 鉴权
            audit(ctx, "run.denied", tool)
            return denied(steps, tool)
        args = await fill_args(tool, question)           # 3. 填参 + 校验
        result = await gateway.call(tool, args, ctx)     # 4. 调用（带超时/熔断）
        used += estimate(result)
        if used > ctx.budget_tokens:                     # 5. 预算控制
            result = compress(result)
        steps.append(step(tool, args, result))           # 6. 记录
    answer = await compose(question, steps)              # 7. 组装
    return RunResult(answer, steps, used)
```

### 四条硬约束

| 约束 | 做法 | 不做会怎样 |
| --- | --- | --- |
| 最大步数 | 默认 6 步，按 Agent 配置可调 | 死循环烧钱 |
| 截止时间 | 整条链路 20s，单工具 8s | 一个慢工具拖垮全部请求 |
| token 预算 | 规划前预留，工具结果超限压缩 | 上下文爆掉，答案被截断 |
| 重复动作检测 | 相同工具 + 相同参数第二次直接跳过 | 反复查同一个接口 |

### 失败处理

| 情况 | 策略 |
| --- | --- |
| 工具超时 | 重试 1 次（仅幂等工具），仍失败则降级为"数据不可用" |
| 工具 5xx | 连续 5 次失败熔断 30s，期间快速失败 |
| 参数校验失败 | 让模型重新填参，最多 1 次，仍失败则放弃该工具 |
| 全部工具失败 | 返回明确说明，不编造事实 |

> 降级不是隐藏失败：答案里必须写清楚"哪部分数据缺失"，这是金融场景的底线。

## MCP 网关

MCP 网关是平台唯一允许访问外部工具的出入口。它做六件事：

| 能力 | 实现要点 |
| --- | --- |
| 工具发现 | 启动时拉取 tool list 并缓存，定时刷新；失败保留上一版 |
| 鉴权 | 校验调用人 scope + Agent 是否被授权该工具，双条件 |
| 参数校验 | 按 `inputSchema` 用 Pydantic 动态校验，拒绝未知字段 |
| 超时与熔断 | 单工具超时、租户级并发隔离、失败熔断 |
| 结果治理 | 截断、脱敏、大结果转对象存储只回摘要 |
| 审计 | 记录 tool、参数摘要、耗时、状态、调用人、trace_id |

传输方式的选择：

| 传输 | 适用 | 注意 |
| --- | --- | --- |
| `http` | 大多数内部服务 | 简单、易扩缩容；注意超时与重试 |
| `sse` | 流式返回、长连接 | 需要连接池与断线重连 |
| `stdio` | 本地进程、沙箱计算 | 进程隔离、资源限制、禁止外网 |

工具注册后必须**默认未启用**：开发者能提交，管理员评估权限后启用。这条规则能挡掉大部分"顺手接了个生产库"的事故。

## 模型网关

模型网关把"用哪个模型"从 Agent 配置里抽出来：

```python
ROUTES = {
    "default": ["qwen-max", "deepseek-chat"],       # 主备
    "cheap": ["qwen-turbo"],
    "long_context": ["qwen-long"],
}

async def chat(tenant_id: str, messages, need: str = "default"):
    enforce_quota(tenant_id)                        # 租户 QPS / 日 token
    for model in ROUTES[need]:
        try:
            resp = await client.chat(model, messages)
            bill(tenant_id, resp.usage)             # 计量归集
            return resp
        except RateLimit:
            continue
    raise ServiceUnavailable("所有模型均不可用")
```

要点：

- **配额归集到租户与 Agent**，成本看板才有意义。
- 主备切换要控制"重试放大量"，避免故障时把备用模型也打挂。
- 提示词前缀稳定时开启缓存，长系统提示可显著降本。
- 内容安全在网关统一做一次，避免每个 Agent 各写一套。

## 会话与异步

| 场景 | 方案 |
| --- | --- |
| 短问答（≤ 15s） | 同步请求，SSE 流式输出 |
| 长任务（研报初稿、批量对比） | 提交任务返回 `task_id`，队列消费，前端轮询或 SSE 订阅 |
| 定时任务（晨报） | 调度器触发，写队列，走同一套运行时 |
| 人工审批中断 | 运行时持久化状态，审批后从断点续跑 |

会话状态别放内存：多实例部署后，下一次请求可能落到另一台机器。会话与运行步骤统一落 PostgreSQL，Redis 只做缓存。

## 可观测

一条 trace 至少包含：

```json
{
  "trace_id": "tr-8f2c",
  "tenant_id": "t-sec",
  "agent_id": "ag-sec-1",
  "agent_version": 3,
  "user_id": "u-sec-dev",
  "question_hash": "…",
  "plan": ["market_quote", "report_search"],
  "tool_calls": [{"name": "market_quote", "ms": 320, "status": 200}],
  "tokens": {"in": 820, "out": 460},
  "cost": 0.021,
  "status": "success"
}
```

核心指标：

| 指标 | 用途 | 告警建议 |
| --- | --- | --- |
| 运行成功率 | 整体健康度 | 5 分钟低于 95% 告警 |
| P95 延迟 | 体验 | 超过 15s 告警 |
| 工具错误率 | 上游依赖 | 单工具连续 5 次失败 |
| 权限拦截数 | 安全 | 突增即排查 |
| 单租户 token 消耗 | 成本 | 超过日预算 80% 提醒 |
| 跨租户拒绝数 | 风控 | 任意一次都告警 |

## 安全设计

| 风险 | 手段 |
| --- | --- |
| 提示词注入 | 工具结果与用户输入都视为不可信；系统提示固定优先级；输出前过滤 |
| 工具越权 | 创建时校验 + 运行时校验 + 网关二次校验 |
| 凭据泄漏 | 凭据只存在网关，Agent 与模型都拿不到 |
| 数据外带 | 出网白名单；工具结果脱敏；禁止任意 URL 抓取 |
| 沙箱逃逸 | stdio 工具跑在独立容器，限制 CPU/内存/网络 |
| 审计缺失 | 治理动作与拒绝事件强制写审计，写入失败则拒绝执行 |

## 性能与成本

| 手段 | 收益 | 代价 |
| --- | --- | --- |
| 工具结果压缩 | 上下文降 30%~60% | 细节丢失，需要保留原文链接 |
| 并行调用无依赖工具 | 延迟降 30%+ | 失败处理更复杂 |
| 提示词前缀缓存 | 输入 token 成本下降 | 提示词结构受限 |
| 小模型做意图分类 | 便宜、快 | 复杂意图需回退大模型 |
| 结果缓存（按参数哈希） | 重复查询几乎零成本 | 需要 TTL 与失效策略 |

成本必须能按租户、Agent、用户三个维度归集，否则月底没人认账。

## 本章对应演示

```bash
cd notes/agent-platform
./start.sh
```

对照代码看链路：

- API 层与租户注入 → `current_user()`、`tenant_agent()`
- 在线运行时（真实模型 + Function Calling）→ `execute_run_online()`、`llm_chat()`、`tool_schemas()`
- 工具执行分流 → `execute_tool()`：内置工具走 `BUILTIN_EXECUTORS`，自定义 MCP 走 `call_mcp_http()`
- 离线降级 → `execute_run_offline()`，步骤里会明确标注「离线模式」
- 工具目录（MCP 注册表）→ `tenant_tools()`、`toggle_mcp()`
- 运行记录 → `runs` 表（含 model 字段）与调试台的步骤时间线

**Demo 不是只做审计**：`execute_run_online()` 会把 Agent 的系统提示词、用户问题和工具 schema 一起发给 DeepSeek，模型自主决定调用哪个工具，平台的 `execute_tool()` 真实执行后再回灌结果，直到模型给出最终答复；自定义 MCP 按 JSON-RPC（`initialize` + `tools/call`）真实请求注册的端点。未配置 `DEEPSEEK_API_KEY` 或模型调用失败时，才降级为离线模拟，并在步骤里写明原因。

鉴权、状态机、审计、租户隔离始终是真实执行的，与模型在线与否无关。
