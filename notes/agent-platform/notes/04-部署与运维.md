# 04 部署与运维

## 一句话

**平台部署的难点不是把容器跑起来，而是把"有状态的部分"管住：数据库、对象存储、向量库、密钥，以及每一次 Agent 与 MCP 的版本变更。** 无状态服务可以随便重启，有状态组件和版本变更才是事故来源。

## 环境规划

| 环境 | 用途 | 数据 | 模型 |
| --- | --- | --- | --- |
| 开发（dev） | 联调、写 Agent | 造数，可随时重置 | 小模型 / mock |
| 预发（staging） | 上线前验收、压测 | 脱敏样本 | 与生产同版本 |
| 生产（prod） | 业务使用 | 真实数据 | 生产配额 |

三套环境的关键差异只有配置与配额，**镜像必须是同一个**。禁止"预发跑得好、生产是另一个包"。

## 组件清单

| 组件 | 作用 | 最低配置（示例） | 备注 |
| --- | --- | --- | --- |
| `platform-api` | FastAPI 应用，含 Agent 运行时 | 2C4G × 2 | 无状态，可水平扩展 |
| `platform-worker` | 长任务、索引、定时任务 | 2C4G × 2 | 与 API 同镜像不同入口 |
| PostgreSQL 15 | 元数据、运行记录、审计 | 4C8G，主备 | 必须开启备份与 RLS |
| Redis 7 | 会话、限流、锁 | 2C4G | 不做持久化依赖 |
| 对象存储 | 原文、大结果、导出文件 | 按量 | S3 兼容，如 MinIO |
| 向量库 | 知识检索 | 2C8G 起 | 小规模用 pgvector |
| 消息队列 | 长任务与事件 | 2C4G | Kafka 或 RabbitMQ |
| 模型网关 | 统一模型出口 | 2C4G × 2 | 可与平台同集群 |
| 可观测栈 | trace / metrics / logs | 托管优先 | OTel Collector |

## 部署拓扑

```
                    ┌──────────────┐
   用户 / 企微 ────► │  Ingress/WAF │
                    └──────┬───────┘
                           ▼
                 ┌───────────────────┐
                 │  platform-api × N │  HPA 3~10
                 └───┬───────┬───────┘
                     │       │
        ┌────────────▼─┐  ┌──▼─────────────┐
        │ PostgreSQL   │  │ Redis           │
        │ 主备 + 只读  │  │ 三主三从（可选）│
        └──────────────┘  └────────────────┘
                     │
        ┌────────────▼────────────┐
        │ 对象存储 / 向量库 / MQ   │
        └─────────────────────────┘
                     │
              ┌──────▼───────┐
              │ 模型 / MCP    │  ← 出网白名单
              └──────────────┘
```

网络策略：

- 平台服务只允许出网到**模型网关白名单**和**MCP 网关**，禁止任意外网访问。
- MCP 服务与业务数据源放在同一安全域，平台不直连业务库。
- 管理端（审批、审计）与用户端建议分域名，管理端加 IP 白名单或零信任接入。

## 本地一键启动

Demo 用 SQLite + 本地 mock，单进程即可：

```bash
cd notes/agent-platform
python3 -m pip install -r demos/requirements.txt
./start.sh --reset
```

生产形态的 `docker-compose` 片段（用于本地模拟依赖）：

```yaml
services:
  api:
    build: .
    environment:
      DATABASE_URL: postgresql://platform:****@pg:5432/platform
      REDIS_URL: redis://redis:6379/0
      MODEL_GATEWAY: http://model-gateway:8080
      MCP_GATEWAY: http://mcp-gateway:8090
    ports: ["8787:8787"]
    depends_on:
      pg: { condition: service_healthy }
      redis: { condition: service_started }
  pg:
    image: postgres:15
    environment:
      POSTGRES_DB: platform
      POSTGRES_USER: platform
      POSTGRES_PASSWORD: ****
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U platform"]
      interval: 5s
  redis:
    image: redis:7
  minio:
    image: minio/minio
    command: server /data --console-address ":9001"
```

## 配置项

| 变量 | 说明 | 示例 |
| --- | --- | --- |
| `DATABASE_URL` | PostgreSQL 连接串 | `postgresql://...` |
| `REDIS_URL` | 缓存与限流 | `redis://redis:6379/0` |
| `MODEL_GATEWAY` | 模型网关地址 | `http://model-gateway:8080` |
| `MCP_GATEWAY` | MCP 网关地址 | `http://mcp-gateway:8090` |
| `DEFAULT_TENANT_QPS` | 租户默认 QPS | `20` |
| `RUN_TIMEOUT_MS` | 单次运行超时 | `20000` |
| `MAX_STEPS` | Agent 最大步数 | `6` |
| `AUDIT_RETENTION_DAYS` | 审计保留天数 | `365` |
| `OTEL_EXPORTER_OTLP_ENDPOINT` | 观测后端 | `http://otel:4317` |

密钥统一放密钥管理服务（Vault / KMS），**不进 ConfigMap、不进镜像、不进代码仓库**。

## 启动顺序与健康检查

```
PostgreSQL → Redis → 对象存储/向量库 → 平台 API → Worker → Ingress
```

| 检查 | 路径 | 通过标准 |
| --- | --- | --- |
| 存活 | `/healthz` | 进程可响应 |
| 就绪 | `/readyz` | 数据库、Redis 可用，模型网关连通 |
| 业务自检 | `/api/overview` | 能读到种子租户数据 |

就绪探针不要检查模型供应商：对方抖动会导致平台整体被摘流量，应该降级而不是全下线。

## Kubernetes 关键配置

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: platform-api
spec:
  replicas: 3
  template:
    spec:
      containers:
        - name: api
          image: registry/platform-api:1.4.0
          resources:
            requests: { cpu: "500m", memory: "1Gi" }
            limits:   { cpu: "2",    memory: "2Gi" }
          readinessProbe:
            httpGet: { path: /readyz, port: 8787 }
            initialDelaySeconds: 10
          livenessProbe:
            httpGet: { path: /healthz, port: 8787 }
---
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: platform-api
spec:
  scaleTargetRef: { kind: Deployment, name: platform-api }
  minReplicas: 3
  maxReplicas: 10
  metrics:
    - type: Resource
      resource: { name: cpu, target: { type: Utilization, averageUtilization: 65 } }
```

扩缩容以 CPU + 队列积压为主；**不要只看 QPS**，Agent 调用的耗时差异很大。

## 监控与告警

| 指标 | 建议阈值 | 处理 |
| --- | --- | --- |
| 运行成功率（5 分钟） | < 95% | 查模型网关与工具错误 |
| P95 端到端延迟 | > 15s | 查慢工具与模型排队 |
| 工具错误率 | 单工具连续 5 次失败 | 熔断并通知 MCP 负责人 |
| 队列积压 | > 1000 且持续 5 分钟 | 扩容 worker |
| 数据库连接池使用率 | > 85% | 扩连接或查慢查询 |
| 单租户日 token | > 预算 80% | 通知租户管理员 |
| 审计写入失败 | 任意一次 | 立即告警，阻断相关写操作 |

## 备份与容灾

| 对象 | 策略 | RPO | RTO |
| --- | --- | --- | --- |
| PostgreSQL | 每日全量 + WAL 归档 | ≤ 5 分钟 | ≤ 1 小时 |
| 对象存储 | 跨区复制 / 版本化 | ≤ 15 分钟 | ≤ 2 小时 |
| 向量库 | 可从原文重建 | — | 视重建耗时 |
| 配置与密钥 | 版本化 + 定期演练恢复 | 0 | ≤ 30 分钟 |

每季度做一次恢复演练：**没演练过的备份等于没有备份**。

## 升级与回滚

| 变更类型 | 做法 | 回滚 |
| --- | --- | --- |
| 平台代码 | 滚动更新，先 1 个实例观察 10 分钟 | 回滚上一镜像 |
| 数据库迁移 | 只做向后兼容变更（先加列，后删列） | 保留上一版本兼容 |
| Agent 配置 | 平台内版本 +1，可切回上一版本 | 一键回滚 |
| MCP 工具 | 双跑新旧工具名，观察后再下线旧工具 | 切回旧工具名 |
| 提示词 | 灰度 10% 流量，看采纳率与拦截率 | 切回上一版本 |

**禁止**在发布窗口内同时改代码与改数据库结构；出问题时无法判断是谁导致的。

## 容量估算

以一个租户 300 人、日活 40% 为例：

```
日调用量   = 300 × 40% × 15 次/人 ≈ 1800 次/日
峰值 QPS   = 1800 × 20%（集中在 4 小时）÷ 14400s ≈ 0.03 → 按 1 QPS 预留
单次调用   = 输入 1500 tokens + 输出 600 tokens ≈ 2100 tokens
日 token   = 1800 × 2100 ≈ 378 万 tokens
实例数     = 按峰值 1 QPS × 每次 2s 占用 ≈ 2 个并发槽 → 2 个副本足够
```

容量规划要留三倍余量给突发与重试；真正的瓶颈通常在**模型供应商配额**，不在应用实例数。

## 本章对应演示

```bash
cd notes/agent-platform
./start.sh --reset           # 本地单进程形态
./start.sh --port 9000       # 换端口
```

Demo 把"有状态组件"简化成了 SQLite，但保留了生产部署时要关注的三个点：配置与数据分离（`.data/`）、可重置的初始化（`--reset`）、健康可观测（`/api/overview` 即业务自检）。上生产时按本章清单替换即可。
