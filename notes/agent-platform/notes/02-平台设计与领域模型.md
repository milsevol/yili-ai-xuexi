# 02 平台设计与领域模型

## 一句话

**平台设计只回答四个问题：对象有哪些（领域模型）、对象怎么变（生命周期）、谁能动谁（权限模型）、怎么被调用（接口契约）。** 这四件事定清楚，后面写代码只是填充；定不清楚，就会在实现阶段反复推翻。

## 领域模型

```
tenants 1 ──── n users
   │ 1
   ├──── n mcp_servers ──── 1..n tools（工具是 MCP 暴露的能力）
   ├──── n agents ───────── n tools（多对多：Agent 授权哪些工具）
   ├──── n runs（一次调用）
   └──── n audit（治理与安全事件）

agents  n ──── 1 users（created_by）
runs    n ──── 1 agents
runs    n ──── 1 users（调用人）
```

关键建模选择：

| 选择 | 说明 | 为什么这样设计 |
| --- | --- | --- |
| 工具挂在 MCP 下 | `mcp_servers.tool_name` 唯一标识工具 | 工具生命周期跟随服务，启停一次生效 |
| Agent 存工具名列表 | `agents.tools` 是 JSON 数组 | 运行时可逐个校验权限与可用性 |
| 运行记录与 Agent 解耦 | `runs` 冗余 `agent_name` 与答案 | Agent 下线或改名后历史仍可追溯 |
| 审计单独成表 | 不做软删除，不存业务正文 | 审计要求不可篡改、可长期保存 |

## 核心实体

### 租户与用户

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `tenants.id` | text | 租户 ID，如 `t-sec` |
| `tenants.name` | text | 展示名，如「华东证券 · 研究所」 |
| `tenants.industry` | text | 证券 / 资管 / 银行，用于策略与合规模板 |
| `users.tenant_id` | text | 归属租户，登录后注入上下文 |
| `users.role` | enum | `admin` / `developer` / `viewer` |

### MCP 服务

| 字段 | 说明 |
| --- | --- |
| `name` | 服务名，如「行情数据服务」 |
| `transport` | `http` / `sse` / `stdio` |
| `endpoint` | 网关地址或本地命令标识 |
| `scope` | 调用该工具需要的权限，如 `finance:read` |
| `tool_name` | 工具名，Agent 引用它 |
| `enabled` | 是否启用；停用后引用它的 Agent 运行会降级 |

### Agent

| 字段 | 说明 |
| --- | --- |
| `name` / `description` | 上架信息 |
| `system_prompt` | 人设与输出约束 |
| `tools` | 授权工具名数组 |
| `status` | 生命周期状态 |
| `version` | 每次发布 +1 |
| `created_by` / `reviewed_by` / `review_note` | 责任链 |

## 生命周期

Agent 的状态机（MCP 是简化的启用/停用两态）：

```
            submit                publish
  draft ──────────► pending ──────────────► published
    ▲                  │                       │
    │                  │ reject                │ offline
    │                  ▼                       ▼
    └──── rejected ◄───┘                    offline
    │                                          │
    └────────────── submit（重新提交）◄────────┘
```

| 状态 | 可执行动作 | 谁能执行 |
| --- | --- | --- |
| `draft` | 编辑、提交审核 | 创建人 / 管理员 |
| `pending` | 通过、驳回 | 租户管理员 |
| `published` | 调用、下线 | 业务用户 / 管理员 |
| `rejected` | 修改后重新提交 | 创建人 |
| `offline` | 重新提交 | 创建人 |

**状态机必须服务端校验**：不能靠前端隐藏按钮。示例：

```python
ALLOWED = {
    "draft": {"submit"},
    "pending": {"publish", "reject"},
    "published": {"offline"},
    "rejected": {"submit"},
    "offline": {"submit"},
}

def transition(agent, action, actor):
    if action not in ALLOWED[agent.status]:
        raise Conflict(f"{agent.status} 不允许 {action}")
    if action in {"publish", "reject"} and actor.role != "admin":
        raise Forbidden("只有租户管理员可以审批")
    if action == "submit" and actor.id != agent.created_by and actor.role != "admin":
        raise Forbidden("只有创建人可以提交")
```

## 多租户隔离

`tenant_id` 从 SSO token 解析，之后**由平台注入**，模型与前端都无法修改。四层落地：

| 层 | 手段 | 关键约束 |
| --- | --- | --- |
| 请求上下文 | 中间件解析身份，写入 request context | 业务代码禁止从请求体读 `tenant_id` |
| 存储 | 每表带 `tenant_id`；PostgreSQL 启用 RLS | 应用使用受限数据库角色 |
| 检索 | 向量库按租户 namespace 或强制 filter | 检索入口统一封装，禁止裸查 |
| 日志 / Trace | 所有事件带 `tenant_id` | 跨租户查询需二次授权并审计 |

```sql
-- PostgreSQL：即使应用层漏了 where，数据库兜底
ALTER TABLE agents ENABLE ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON agents
  USING (tenant_id = current_setting('app.tenant_id'));
```

跨租户访问应当**先拒绝、再审计、后告警**：

```
请求 → 解析身份 → 校验资源 tenant_id
                      ├─ 一致 → 继续
                      └─ 不一致 → 403 + audit(security.cross_tenant_denied)
```

## 权限模型

RBAC 决定"能不能用这个工具"，ABAC 决定"能看哪部分数据"。平台层只做前者，数据权限由工具背后的业务系统执行。

| 角色 | 可用 scope | 说明 |
| --- | --- | --- |
| `admin` | `*` | 租户管理员，审批与启停 MCP |
| `developer` | `market:read`、`finance:read`、`report:read`、`calc:run` | 创建 Agent，不能审批 |
| `viewer` | `market:read`、`report:read` | 只能调用已上线 Agent |

两条硬规则：

1. **创建时**：Agent 勾选的工具必须是本租户已启用、且创建人有权限的工具（防止借 Agent 提权）。
2. **运行时**：逐工具再校验一次调用人的 scope（防止 Agent 被转授给无权限用户）。

## 上架流程

```
开发者                平台                     租户管理员
  │  创建 Agent         │                          │
  ├────────────────────►│ 状态 draft               │
  │  提交审核           │                          │
  ├────────────────────►│ 状态 pending ───────────►│ 审批
  │                     │                          ├─ 通过 → published (version+1)
  │◄────────────────────┤ 通知结果 ◄───────────────┤─ 驳回 → rejected (附意见)
```

审核要看的四件事：工具权限是否最小、系统提示词是否有合规约束、是否声明数据来源、是否配置评测集。缺一项就驳回。

## 接口设计

| 方法 | 路径 | 作用 | 鉴权 |
| --- | --- | --- | --- |
| GET | `/api/bootstrap` | 身份、租户、角色、scope | 登录 |
| GET | `/api/overview` | 本租户 Agent / MCP / 运行 / 审计 | 登录 |
| POST | `/api/agents` | 创建 Agent（草稿） | developer/admin |
| POST | `/api/agents/{id}/submit` | 提交审核 | 创建人/admin |
| POST | `/api/agents/{id}/review` | 通过 / 驳回 | admin |
| POST | `/api/agents/{id}/offline` | 下线 | 创建人/admin |
| POST | `/api/mcp` | 注册 MCP | developer/admin |
| POST | `/api/mcp/{id}/toggle` | 启用 / 停用 | admin |
| POST | `/api/runs` | 调用 Agent | 登录 + scope |

约定：

- 身份放请求头或 Cookie，**不放 body**；生产用 `Authorization: Bearer <token>`。
- 错误统一 `{"detail": "..."}`，4xx 区分 401（未登录）/ 403（越权）/ 404（不存在）/ 409（状态冲突）。
- 所有写操作幂等键可选，重试不产生重复 Agent。

## 表结构

教学 Demo 用 SQLite，生产换 PostgreSQL，字段保持一致：

```sql
CREATE TABLE agents (
  id           TEXT PRIMARY KEY,
  tenant_id    TEXT NOT NULL,
  name         TEXT NOT NULL,
  description  TEXT NOT NULL DEFAULT '',
  system_prompt TEXT NOT NULL DEFAULT '',
  tools        TEXT NOT NULL DEFAULT '[]',   -- JSON 数组；PG 用 jsonb
  status       TEXT NOT NULL DEFAULT 'draft',
  version      INTEGER NOT NULL DEFAULT 1,
  created_by   TEXT NOT NULL,
  reviewed_by  TEXT,
  review_note  TEXT,
  created_at   TEXT NOT NULL,
  updated_at   TEXT NOT NULL
);
CREATE INDEX idx_agents_tenant ON agents (tenant_id, status);

CREATE TABLE mcp_servers (
  id         TEXT PRIMARY KEY,
  tenant_id  TEXT NOT NULL,
  name       TEXT NOT NULL,
  transport  TEXT NOT NULL,
  endpoint   TEXT NOT NULL,
  scope      TEXT NOT NULL,
  tool_name  TEXT NOT NULL,
  tool_label TEXT NOT NULL,
  enabled    INTEGER NOT NULL DEFAULT 1,
  created_at TEXT NOT NULL,
  UNIQUE (tenant_id, tool_name)
);
```

`runs` 保存问题、答案、步骤 JSON、状态、tokens 与耗时；`audit` 保存操作人、动作、对象与详情。

## 工具契约

MCP 注册的核心不是"填个地址"，而是声明一个可被校验的契约：

```json
{
  "name": "financial_report",
  "description": "查询上市公司财报核心指标，返回营收、毛利率、现金流",
  "inputSchema": {
    "type": "object",
    "properties": {
      "symbol": { "type": "string", "pattern": "^[0-9]{6}$" },
      "years": { "type": "integer", "minimum": 1, "maximum": 5 }
    },
    "required": ["symbol"]
  },
  "scope": "finance:read",
  "timeout_ms": 8000,
  "idempotent": true
}
```

| 字段 | 作用 |
| --- | --- |
| `description` | 模型选工具的唯一依据，写清楚"什么时候用" |
| `inputSchema` | 网关做参数校验，模型不能传任意结构 |
| `scope` | 运行时鉴权 |
| `timeout_ms` | 防止单个工具拖垮整条链路 |
| `idempotent` | 决定失败能否自动重试 |

## 版本与兼容

- Agent 版本：每次发布 `version + 1`，运行记录绑定版本号，可回滚。
- MCP 版本：工具名不变、schema 只做向后兼容的扩展；破坏性变更必须换新工具名并双跑一段时间。
- 提示词即配置：提示词变更与代码发布解耦，但同样要留版本与审计。

## 关键取舍

| 问题 | 选择 | 代价 |
| --- | --- | --- |
| 一个 Agent 一个系统提示词 vs 多套模板 | 单提示词 + 变量 | 灵活度低，但审核简单 |
| 工具名全局唯一 vs 租户内唯一 | 租户内唯一 | 跨租户合并数据时要加前缀 |
| 审批放在平台 vs 业务系统 | 平台内审批 | 平台要承担流程责任 |
| 运行记录存全量 vs 只存摘要 | 全量步骤（脱敏后） | 存储成本上升，但可复盘 |
